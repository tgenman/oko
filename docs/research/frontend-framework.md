# Выбор UI-фреймворка для Око

Дата исследования: 2026-10-14. Статус: исследовательская рекомендация, не утверждённое архитектурное решение и не спецификация реализации. TypeScript согласован пользователем; фреймворк обсуждается. Код приложения, зависимости и проверки этим исследованием не менялись. Источники: текущий checkout и официальная документация, прочитанная через Context7 и web. Прототипы, сборки и тесты не запускались; сравнительных измерений нет.

## Вывод

**React + TypeScript + Vite подходит Око наравне с Vue 3. Причин исключать React нет.** Предыдущая рекомендация Vue была слишком определённой: постепенное внедрение, работа с FastAPI и сохранение существующих HTTP-проверок доступны всем трём основным кандидатам.

Если опыт и предпочтения команды одинаковы, у Vue есть небольшое преимущество для нынешнего кода: локальные изменяемые значения, формы и обработчики событий ближе к `ref`/`reactive`, Composition API и `v-model`. Это оценка стоимости переноса, а не установленный факт. Если пользователю удобнее TSX, явное обновление состояния и React, этого достаточно для выбора React: выявленного продуктового требования, которое делало бы такой выбор хуже, нет. Svelte 5 также подходит, но пока не обнаружена задача Око, ради которой стоило бы предпочесть его собственные правила реактивности двум финалистам.

Рекомендуемый следующий шаг после выбора — небольшой сквозной перенос UI с проверкой поведения и сборки. Необходимость такого пилота не означает необходимость написать три приложения или откладывать выбор на большой сравнительный проект.

## Что именно требуется Око

Фронтенд уже выделен в `frontend/`, сервер — в `oko/`; граница проходит через HTTP читателя. Архитектура отдельно закрепляет владельцев DOM, фокуса, черновиков и допуска ответов. Runtime исполняет работу, Store сохраняет её. Пользовательский запуск сейчас не требует Node или сборки. Это важная существующая характеристика: новая сборка должна стать шагом разработки/подготовки артефакта, а способ доставки готовых файлов необходимо определить явно. [Архитектура frontend/backend](../architecture/frontend-backend.md).

Основной видимый долг — ручное согласование состояния и DOM. Редактор хранит черновики, перестраивает дерево/поля, запоминает фокус и восстанавливает его; панель статуса вручную создаёт карточки, обновляет поля, перемещает DOM и сохраняет раскрытие. Это основание рассмотреть компоненты, но не доказательство того, что вся существующая логика лишняя. [Редактор](../../frontend/settings-editor.js), [панель](../../frontend/status-panel.js).

Правила, которые должен сохранить любой вариант:

- Черновики принадлежат объекту настроек и переживают закрытие формы. Успешное сохранение очищает только отправленное значение, если пользователь не успел его изменить.
- Поздний ответ старой страницы не меняет новую страницу. Повторное открытие того же меню создаёт новый контекст.
- Успешная серверная мутация согласуется с локальными данными даже после закрытия формы; потеря права показывать сообщение не отменяет состоявшуюся запись.
- Открытие другого материала сразу очищает старый; поздние текст, версия и медиа не возвращаются. При прекращении показа освобождаются blob URL и останавливается воспроизведение.
- Опрос статуса не должен произвольно менять порядок карточек и сбрасывать раскрытые детали. Завершившаяся раскрытая карточка удерживается в текущей группе до закрытия деталей.

Эти требования подтверждены [UI-состоянием](../architecture/ui-settings.md), [открытым материалом](../architecture/opened-material.md), [ui-operations.js](../../frontend/ui-operations.js) и [status-panel.js](../../frontend/status-panel.js). Они относятся к поведению Око и не исчезают при смене фреймворка.

### React: полноценный кандидат

React официально поддерживает внедрение в часть существующей страницы. Для этого достаточно инструментов сборки и `createRoot` в выбранном контейнере; документация прямо предлагает Vite и интеграцию с существующим бэкендом. Next.js, SSR и сервер на Node не являются условием использования React. [Добавление React](https://react.dev/learn/add-react-to-an-existing-project), [приложение со своей сборкой](https://react.dev/learn/build-a-react-app-from-scratch).

TSX даёт единый синтаксис TypeScript для компонентов и логики. Сложные переходы можно описать типизированными событиями и reducer, а правила черновиков вынести в обычные TS-функции. Это хороший вариант, если именно такая форма кода удобна сопровождающему. Он не требует Redux, router или библиотеки форм с первого дня. [Типы props, hooks и reducer](https://react.dev/learn/typescript).

Цена переноса: существующие изменяемые переменные нельзя механически заменить на `useState`. Значение state внутри обработчика относится к render, в котором обработчик создан. Для правила «сохраняем A, во время запроса вводим B, ответ не стирает B» нужно явно сравнить отправленное значение с актуальным состоянием через корректный переход или владельца. [State as a Snapshot](https://react.dev/learn/state-as-a-snapshot).

Другой риск — перенести все действия в `useEffect`. Сохранение по клику остаётся обработчиком события; производные значения обычно вычисляются при render; effects нужны для синхронизации с внешними системами. Сама документация React предостерегает от лишних effects. [You Might Not Need an Effect](https://react.dev/learn/you-might-not-need-an-effect).

Нельзя обосновывать отказ от React словами «он всегда перерисовывает весь DOM» или «обязательно вручную расставлять memo». Render компонента и замена DOM — разные операции; актуальная документация также описывает React Compiler, автоматически добавляющий мемоизацию. Его включение — отдельный выбор сборки, а не обязательная часть первого переноса. [React Compiler](https://react.dev/learn/react-compiler), [сохранение состояния](https://react.dev/learn/preserving-and-resetting-state).

**Сильное возражение к React для Око:** снимки render и hooks требуют более заметного преобразования нынешних mutable closures. Если TSX не даёт команде практического преимущества, эта дополнительная смена модели может не окупиться.

### Vue 3: немного ближе к текущим формам

Composition API позволяет собрать реактивные значения, обработчики и lifecycle одного сценария рядом. `v-model` сокращает связку поля и черновика; шаблон явно отделяет структуру DOM от операций. Это основание ожидать меньшего механического объёма переноса форм. Ожидание требует проверки на коде Око. [Composition API FAQ](https://vuejs.org/guide/extras/composition-api-faq.html), [привязка форм](https://vuejs.org/guide/essentials/forms.html).

Vue не избавляет от дисциплины состояния. `ref`/`reactive`, прокси, разворачивание refs и границы отслеживания имеют свои правила; неаккуратное извлечение значения из реактивного объекта может разорвать связь. Политика черновиков также не появляется от `v-model`: нельзя связать поле прямо с очередным серверным снимком и ожидать сохранения несохранённого ввода. [Reactivity Fundamentals](https://vuejs.org/guide/essentials/reactivity-fundamentals.html).

SFC требуют специализированной поддержки шаблонов и `vue-tsc`; обычный успешный `vite build` ещё не означает проверку типов. Это нормальная часть инструментов Vue, но реальная дополнительная зависимость по сравнению с TSX и `tsc`. [Vue TypeScript](https://vuejs.org/guide/typescript/overview.html).

**Сильное возражение к Vue:** преимущество близости к текущему стилю невелико и может сохранять неудачную модель mutable state. Если сопровождающему удобнее React и TSX, выбирать Vue ради нескольких коротких привязок формы нерационально. Постепенное внедрение не является уникальным преимуществом Vue. [Варианты использования Vue](https://vuejs.org/guide/extras/ways-of-using-vue.html), [частичный React](https://react.dev/learn/add-react-to-an-existing-project).

### Svelte 5: подходит, но не очевидно выигрывает

Svelte компилирует компоненты; `$state` создаёт реактивное состояние, `$derived` описывает вычисляемое, `bind:value` связывает ввод. Есть TS внутри компонентов и `svelte-check`. Не следует оценивать современный Svelte по старой модели Svelte 3/4 с одними `$:` statements. [Overview](https://svelte.dev/docs/svelte/overview), [state](https://svelte.dev/docs/svelte/$state), [TypeScript](https://svelte.dev/docs/svelte/typescript).

Для Око привлекательны краткие формы и компонент, владеющий своим UI. Встраивание возможно через `mount`/`unmount`; SvelteKit не обязателен. [Imperative component API](https://svelte.dev/docs/svelte/imperative-component-api).

Цена — дополнительные правила компилятора и реактивности. Runes не являются обычными импортированными функциями, а реактивный код вне компонентов использует специальные `.svelte.js`/`.svelte.ts`. В `$effect` чтение после `await` не становится автоматически отслеживаемой зависимостью. Cleanup остаётся необходимым. [Runes и модули](https://svelte.dev/docs/svelte/overview), [effect](https://svelte.dev/docs/svelte/$effect).

**Сильное возражение к Svelte:** пока нет измеренной проблемы или предпочтения команды, ради которых переход на этот набор правил лучше React/Vue. Обещания меньшего bundle или лучшей отзывчивости без сборки одинакового среза Око не являются результатом исследования.

## Lifecycle не заменяет правила актуальности

Все кандидаты дают точки очистки. React показывает `ignore` guard в cleanup effect; Vue предоставляет очистку watcher, причём `onWatcherCleanup` регистрируют синхронно, до `await`; Svelte вызывает teardown effect перед следующим исполнением и при уничтожении и предоставляет `getAbortSignal` для текущего effect/derived. [React useEffect](https://react.dev/reference/react/useEffect), [Vue watchers](https://vuejs.org/guide/essentials/watchers.html), [Svelte effect](https://svelte.dev/docs/svelte/$effect), [Svelte getAbortSignal](https://svelte.dev/docs/svelte/svelte#getAbortSignal).

Для Око этого недостаточно: меню может закрыться без уничтожения долговечного владельца; разные назначения запросов независимы; мутация может завершиться после закрытия формы. Поэтому `createOperations` или эквивалентная типизированная модель сохраняются. Abort экономит работу, а guard определяет право применить ответ. Браузерные сценарии намеренно используют транспорт, игнорирующий AbortSignal. [Текущий механизм](../../frontend/ui-operations.js), [browser README](../../tests/browser/README.md).

Черновики должны жить у владельца, который переживает нужные переходы. Переносить их в локальный state компонента, размонтируемого при закрытии поля, нельзя без явного сохранения на более долгом уровне. Аналогично cleanup DOM не является достаточным основанием забыть результат серверного сохранения. Это вывод из требований Око, общий для всех кандидатов.

## DOM, фокус и медиа

Стабильные ключи помогают сохранять соответствие данных и DOM. React учитывает тип и положение компонента, Vue использует `:key` для переиспользования и перестановки, Svelte — keyed each. Ключ сам по себе не гарантирует сохранение DOM при переносе между разными родителями, условном удалении или смене типа. [React identity](https://react.dev/learn/preserving-and-resetting-state), [Vue list keys](https://vuejs.org/guide/essentials/list.html#maintaining-state-with-key), [Svelte each](https://svelte.dev/docs/svelte/each).

Для Око это означает: не использовать номер строки, случайный ключ или время опроса; не пересоздавать media subtree из-за обновления соседнего статуса; хранить раскрытие карточки и её текущую группу как состояние представления. При закрытии материала явно останавливать playback и освобождать blob URL. Эти выводы следуют из продуктовых требований, а не из обещания какого-либо фреймворка.

Фокус по событию, возврат к opener и управление медиа остаются допустимыми императивными операциями через ссылки на DOM. React refs, Vue template refs и Svelte `bind:this` предназначены для такого доступа. Однако сторонний код не должен параллельно перестраивать принадлежащее компоненту дерево. [React DOM refs](https://react.dev/learn/manipulating-the-dom-with-refs), [Vue template refs](https://vuejs.org/guide/essentials/template-refs.html), [Svelte bindings](https://svelte.dev/docs/svelte/bind).

### Один сценарий, по которому стоит оценивать решение

Пользователь отправил значение A, затем ввёл B, закрыл поле и снова его открыл. После этого сервер подтвердил сохранение A. Правильный результат: сохранённое значение — A, текущий черновик — B; ответ первого открытия не меняет навигацию второго. Сравнение отправленного значения с текущим черновиком уже есть в `settings-editor.js`; соответствующее поведение проверяет `test_ui_lifecycle.cjs`. [Редактор](../../frontend/settings-editor.js), [сценарии lifecycle](../../tests/browser/test_ui_lifecycle.cjs).

Во всех трёх вариантах нужно различать сохранённое значение, черновик объекта, отправленное значение и контекст показа. React выражает обновление через state/reducer или долговечного владельца; Vue и Svelte — через реактивное состояние и обработчики. Привязка поля делает отображение проще, но не выбирает за приложение, какое из этих значений можно перезаписать. Отдельный универсальный механизм хранения для этого сравнения не требуется.

У React есть дополнительная деталь при выборе API формы: успешная функция в `<form action={...}>` сбрасывает uncontrolled-поля. Для независимого сохранения полей Око это поведение нужно учитывать; обычный `onSubmit` остаётся доступен. Это свойство конкретного API, а не препятствие использованию React. [React form](https://react.dev/reference/react-dom/components/form).

## Библиотеки поверх фреймворка

Выбор React не требует одновременно выбирать библиотеку компонентов, query cache и глобальное хранилище. Для доступных диалогов и меню есть готовые primitives во всех трёх экосистемах: [Radix для React](https://www.radix-ui.com/primitives/docs/overview/accessibility), [Reka UI для Vue](https://www.reka-ui.com/docs/overview/introduction), [Bits UI для Svelte](https://www.bits-ui.com/docs). Наличие таких библиотек проверено по их документации; соответствие конкретных компонентов дизайну, CSP и поведению фокуса Око не проверялось. Их использование — отдельный выбор для конкретного виджета.

Query cache тоже не стоит вводить автоматически. Например, TanStack Query по умолчанию считает данные устаревшими, повторно запрашивает их при некоторых событиях и повторяет неудачные queries. В Око уже есть согласованный polling, правила удаления и отбрасывания старых ответов; подключение библиотеки требует явной настройки этих политик. При этом mutations по умолчанию не повторяются — переносить на них утверждение о retries queries неправильно. [Query defaults](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults), [mutations](https://tanstack.com/query/latest/docs/framework/react/guides/mutations).

## Другие варианты

| Вариант | Что предлагает | Почему не первый выбор по текущим данным |
| --- | --- | --- |
| Solid | JSX и мелкая реактивность signals; функция компонента не повторяется как React render | Подходит технически, но визуальное сходство JSX не делает модель React-совместимой. Нет выявленной задачи Око, требующей этого отличия |
| Angular | Структурированный набор средств, reactive forms; компоненты можно экспортировать как custom elements | Для текущего локального читателя пока не обоснован перенос на более широкий набор соглашений Angular. Не следует отвергать его как «невозможный для постепенного внедрения» |
| Preact | React-подобный API и `preact/compat` | Если нужны React-библиотеки, совместимость надо проверять; документация перечисляет различия. Измеренной необходимости оптимизировать размер framework runtime пока нет |
| Lit | Web Components, реактивные свойства и декларативные шаблоны | Разумный кандидат для переиспользуемых web components. В Око такой потребности пока нет; Shadow DOM по умолчанию меняет доступ глобального CSS и DOM-поиска, что увеличивает объём миграции существующей связности |
| htmx | Сервер возвращает HTML-фрагменты для обновления страницы | Основной подход требует пересмотреть текущую границу JSON HTTP и серверное владение представлением. Владение черновиками, медиа и поздними ответами всё равно нужно спроектировать |
| TypeScript без framework | Типизированные контракты и владельцы без замены DOM-механики | Полезный минимальный шаг, но ручные создание/согласование/перестановка DOM сохраняются |

Источники: [Solid reactivity](https://docs.solidjs.com/concepts/intro-to-reactivity), [Solid components](https://docs.solidjs.com/concepts/components/basics), [Angular forms](https://angular.dev/guide/forms), [Angular custom elements](https://angular.dev/guide/elements), [Preact integration](https://preactjs.com/guide/v10/getting-started/), [Preact differences](https://preactjs.com/guide/v10/differences-to-react/). Последняя колонка — оценка применительно к Око, не сравнительный benchmark.

Дополнительно: [Lit Shadow DOM](https://lit.dev/docs/components/shadow-dom/), [Lit reactive properties](https://lit.dev/docs/components/properties/), [htmx documentation](https://htmx.org/docs/). Lit допускает настройку render root, поэтому Shadow DOM — цена стандартного подхода, а не непреодолимое ограничение. Слабое место htmx здесь — стоимость смены архитектуры существующего приложения, а не невозможность построить на нём интерактивный интерфейс.

## Сборка, сервер и типизированный HTTP

Vite поддерживает интеграцию с собственным бэкендом: сборка выдаёт статические assets и при необходимости manifest, сервер подставляет их ссылки. Это позволяет сохранить Python-процесс пользовательского запуска. Нужны явные правила доставки `dist`, выбора HTML/assets, MIME, cache invalidation и поведения при отсутствующей сборке. Dev-server и production build проверяются отдельно. [Vite backend integration](https://vite.dev/guide/backend-integration).

Существующий CSP использует `script-src 'self'` и `style-src 'self'`. Следует использовать предварительно скомпилированные компоненты и внешние CSS/JS; HMR, injected styles и дополнительные dev origins нужно проверять отдельно, без автоматического ослабления production CSP. Это ограничение интеграции любого выбранного стека. [Заголовки читателя](../../oko/reader/app.py).

Сборка TypeScript не равна проверке типов. Добавляются отдельные `tsc --noEmit`, `vue-tsc` или `svelte-check` по выбранному стеку. Существующие обнаружение JS, синтаксические проверки, ESLint, staged-проверки и проверку графа ES imports нужно научить новым расширениям и реальной сборке: сборщик меняет имена и устройство выходных modules. Нужно также исключить ситуацию, когда `python -m oko` незаметно выдаёт устаревший `dist` после изменения исходников. [Vite TypeScript](https://vite.dev/guide/features#typescript), [browser README](../../tests/browser/README.md).

Dev proxy требует отдельного согласования: сервер сравнивает Origin с собственным Host; простая смена Host прокси не гарантирует прохождение этой проверки. Это повод спроектировать локальный режим разработки, а не отключать существующую проверку origin. [Middleware читателя](../../oko/reader/app.py).

Сервер уже экспортирует JSON Schema из wire types для карточек, навигации, материала, версий и статуса. Это база для получения TS-типов, но **не полный контракт всех форм и команд**. Нельзя объявлять весь transport типобезопасным, добавив типы только этих пяти ответов. Выбор генератора и расширение схем требуют отдельного решения; `as SomeResponse` на результате `fetch` само по себе не проверяет ответ. [Действующий HTTP-контракт](../architecture/frontend-backend.md).

В текущих сценариях не установлена необходимость SSR, full-stack framework, нового router, глобального store или отдельного репозитория. Они могут появиться при конкретных продуктовых требованиях; их не нужно включать в цену перехода на React/Vue/Svelte заранее.

Независимыми от framework разумно оставить transport и небольшие правила операций/черновиков, когда у них есть ясный самостоятельный контракт. Обычное состояние UI следует вести идиоматически в выбранном framework. Создание собственного универсального store ради гипотетической будущей замены framework способно воспроизвести тот долг, который переход должен уменьшить.

## Практичный первый срез

Сначала определить исключительное владение небольшим контейнером — например, списком/карточками проблем внутри стабильной оболочки панели статуса. Вся панель не полностью изолирована: она переносит `debug-panel`, взаимодействует с чужим диалогом и меняет `inert` у reader shell. Поэтому нельзя считать полную замену `status-panel.js` автоматически маленькой задачей. [Код панели](../../frontend/status-panel.js).

Такой срез проверит пользу декларативного представления на создании и обновлении карточек. Следующий отдельный срез — одно поле настроек с существующим владельцем черновиков. Он проверит более сложные правила «сохранить → новый ввод → закрыть → поздний ответ → снова открыть». Перенос всего редактора первым шагом имеет более широкий риск из-за связей с menus, navigation, подписками и reconnect. [UI-владельцы](../architecture/ui-settings.md).

Критерии будущего пилота:

1. Настоящий сервер выдаёт production build с текущими авторизацией и CSP; неизвестный API route не превращается в HTML.
2. Сохраняются клавиатура, фокус, раскрытие и порядок при polling; новый framework и старый код не пишут в один DOM-контейнер.
3. Сохранение поля не стирает более новый ввод, а устаревшие ответы не меняют текущую страницу даже при игнорировании abort.
4. Существующие HTTP и браузерные сценарии проверяют поведение; скриншоты wide/mobile просмотрены. Потребность менять locators оценивается по сохранению пользовательского поведения, а не внутреннего устройства компонента.
5. Заменённая ручная отрисовка удалена; количество владельцев состояния не выросло; описано, как добавить следующее поле/карточку и сколько частей для этого нужно менять.

Playwright остаётся подходящей проверкой при любом кандидате: рекомендации проверять видимое поведение и изолировать внешние зависимости не зависят от framework. Не требуется заменять существующий HTTP/browser путь component-only тестами. [Playwright best practices](https://playwright.dev/docs/best-practices), [текущие проверки Око](../../tests/browser/README.md).

## Что исследование не установило

- Нет сравнительных измерений размера сборки, времени render, памяти, времени разработки или частоты ошибок на одинаковом срезе Око.
- Не установлен опыт пользователя с React/Vue/Svelte. Он может перевесить небольшую разницу в близости к текущему коду.
- Не оценены конкретные будущие UI-библиотеки и их совместимость с дизайном/доступностью Око. Наличие компонентов диалога не является уникальным свойством одного кандидата.
- Не проверены production build, dev HMR, CSP и доставка assets: это будущая проверка интеграции, а не уже подтверждённый результат.
- Нет основания утверждать, что один framework надёжнее генерируется агентами или автоматически предотвращает ошибки асинхронности.

Итоговая рекомендация: выбрать между React и Vue по удобству сопровождения; при равных вводных — небольшой перевес Vue для нынешних форм. React остаётся столь же допустимым инженерным выбором, а его исключение по сложности подключения или требованию Node-сервера было бы ошибкой.
