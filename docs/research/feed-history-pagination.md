# История RSS/Atom и YouTube

2026-10-13. Исследование; реализация не изменена.

Исторический срез до реализации истории YouTube. Последующая реализация и её проверки: [итог разбора](../verification/uncommitted-completion.md).

## Что происходит сейчас

Для [фида Kurzgesagt](https://www.youtube.com/feeds/videos.xml?channel_id=UCsXVk37bltHxD1rDPwtNM8Q) проверка публичного XML исполнителем основной задачи дала 15 записей. В корне есть только ссылки `self` и `alternate`, без `next` и архивных ссылок. Даты: от `2026-08-20T14:00:18+00:00` до `2026-10-08T14:07:00+00:00`. Добавление `&max-results=60&start-index=16` вернуло те же 15 ID в том же порядке. Это результат конкретной проверки, а не документированная гарантия лимита 15 или доказательство поведения всех возможных параметров.

Официальная [инструкция YouTube по уведомлениям](https://developers.google.com/youtube/v3/guides/push_notifications) описывает Atom как поток новых видео и изменений названия/описания. В изученной документации не найдено поддерживаемого способа листать историю `feeds/videos.xml`. Поэтому текущий ответ нельзя считать «первой страницей», за которой обязательно есть вторая.

В Око `RSSSource.read_entries()` загружает один URL, а `discover()` выбирает N из полученных записей: [код](../../oko/collection/rss.py). YouTube использует тот же механизм начальной истории: [адаптер](../../oko/collection/youtube/source.py). [Согласованная спецификация](../../.scratch/initial-history/spec.md) прямо ограничивала RSS/YouTube доступным окном без отдельного архива. Ограничение соответствует прежней спецификации, но не новой потребности получить 60.

## Как получить 60 видео YouTube

Официальный путь: `channels.list(part=contentDetails,id=CHANNEL_ID)` → `contentDetails.relatedPlaylists.uploads` → `playlistItems.list(part=snippet,contentDetails,playlistId=...,maxResults=50)` → следующая страница через `nextPageToken`. Это документированная пагинация списка загрузок канала: [uploads](https://developers.google.com/youtube/v3/docs/channels#contentDetails.relatedPlaylists.uploads), [playlistItems.list](https://developers.google.com/youtube/v3/docs/playlistItems/list).

Если первые две страницы содержат достаточно доступных записей, для 60 достаточно поиска канала и двух запросов списка; второй результат обрезаем до нужного количества. Оба метода стоят по 1 единице квоты, итого 3; исключённые/недоступные записи могут потребовать дополнительных страниц. Это расчёт по контракту, не выполненный запрос API. [channels.list](https://developers.google.com/youtube/v3/docs/channels/list), [playlistItems.list](https://developers.google.com/youtube/v3/docs/playlistItems/list).

Нужны проект Google Cloud, включённый API и API key для публичных данных; подключение личного аккаунта через OAuth для этого сценария не требуется. [Настройка API](https://developers.google.com/youtube/v3/getting-started), [credentials](https://developers.google.com/youtube/registering_an_application).

Для границы по дате нужен `contentDetails.videoPublishedAt`: `snippet.publishedAt` — дата добавления в плейлист. Название, описание и превью доступны в `snippet`. Нельзя принимать первые N записей плейлиста за доказанно последние N по дате без проверки порядка. [Контракт playlistItem](https://developers.google.com/youtube/v3/docs/playlistItems).

Остановка обхода на первой записи старше границы допустима только при подтверждённом порядке по дате; иначе нужно продолжать просмотр страниц и фильтровать найденные записи.

Альтернатива без собственного API key — yt-dlp, например получение метаданных канала с `--flat-playlist --playlist-items 1:60 --dump-single-json --ignore-config`. Видео при таком выводе не скачивается; `flat-playlist` пропускает извлечение отдельных видео. Но часть метаданных отсутствует, а даты в таком режиме могут быть приблизительными. URL канала включает загрузки разных типов; `/videos` ограничивает выбор конкретной вкладкой. [README yt-dlp](https://github.com/yt-dlp/yt-dlp#readme).

yt-dlp листает продолжения веб-интерфейса YouTube через continuation tokens, а не Atom: [исходник `_tab.py`, метод `_entries`](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/extractor/youtube/_tab.py). Из этого следует зависимость от устройства сайта. Вариант проще для пользователя по настройке ключа, но менее предсказуем для долговечной интеграции; точная дата и полное описание могут потребовать дополнительных запросов.

## Обычный RSS/Atom

[RFC 5005](https://www.rfc-editor.org/rfc/rfc5005.html) допускает страницы со ссылками `first`, `last`, `previous`, `next`; для архивов — `prev-archive`, `next-archive`, `current`. Приложение B показывает те же расширения в RSS 2.0 через `atom:link`. Это возможность издателя, а не обязательная пагинация каждого фида.

Следовательно, универсальный сборщик может следовать объявленным ссылкам, объединять уникальные ID/GUID, останавливаться при достижении N/даты или отсутствии продолжения. Нужно учитывать повторы и петли. Если ссылок нет, выдумывать `page=2` или `limit=60` нельзя: необходим документированный API/архив конкретного сайта либо накопление новых выпусков со временем. Отсутствие следующей ссылки не доказывает отсутствие старых публикаций на сайте.

## Предложение для Око

1. Для YouTube оставить Atom для текущих обновлений. Для истории технически подходит отдельная возможность существующего адаптера через uploads API, но выбор интеграции ещё не принят: проверенные позднее [правила API](https://developers.google.com/youtube/terms/developer-policies) требуют обновления/удаления публичных API-данных через 30 дней и ограничивают скрейпинг и производные данные. Это существенно для архива и тезисов Око. Публичный список и субтитры — разные операции; загрузка истории не должна повторно запрашивать сохранённые субтитры.
2. Для RSS/Atom добавить обход реально объявленных ссылок пагинации/архива. Без них честно показывать ограничение окна.
3. Различать в UI «загрузка остановилась на доступном окне» и «запрошенная история загружена». «Доступно 15» означает найденные записи текущего XML, а не всего канала; «начальная история завершена» сейчас слишком легко читается как исполнение запроса 60.
4. У существующего фида набор начальной истории уже фиксируется через `history_ids` и `history.freeze`: [Store](../../oko/storage/store.py). Продолжение должно явно расширять этот набор, сохраняя подписку и дедупликацию по стабильному ID видео. Удаление и повторное добавление не заменяют такую операцию. Цель — найти 60 различных публикаций; для перечисления не нужны 60 запросов субтитров.

Рекомендации требуют новой спецификации. Фактическая сетевая проверка основного исполнителя: два GET публичного Atom (исходный URL и вариант с `max-results/start-index`). API/yt-dlp не запускались, ключи не создавались, субтитры и пользовательское хранилище не запрашивались. Проверка документа: `git diff --check` прошла.

## Повторная проверка и примеры реализации

2026-10-13, по просьбе пользователя. Ещё четыре GET публичного XML для того же канала:

| Запрос | Результат |
| --- | --- |
| Исходный `channel_id=UCsXVk37bltHxD1rDPwtNM8Q` | 15 записей |
| Канал + `max-results=60` | Те же 15 ID в том же порядке |
| Канал + `start-index=16` | Те же 15 ID в том же порядке |
| `playlist_id=UUsXVk37bltHxD1rDPwtNM8Q` — плейлист загрузок | Те же 15 ID в том же порядке |

Ни один ответ не содержит ссылки продолжения. Параметры присутствуют в возвращаемом `self`, но не меняют выборку; отражение параметра в URL не доказывает его поддержку.

Примеры из интернета:

- [yt-feed-cli, README автора](https://github.com/NataliaBondarenko/yt-feed-cli#readme): утилита читает официальные channel/playlist XML; `--number` ограничивает вывод, а сам фид содержит до 15 записей.
- [RSS-Bridge, YoutubeBridge.php](https://github.com/RSS-Bridge/rss-bridge/blob/master/bridges/YoutubeBridge.php): обычный канал читает XML. Для плейлиста код сначала читает HTML и `ytInitialData`; при количестве больше 15 использует JSON страницы. В коде отмечено ограничение первой сотней элементов и отсутствие обхода continuation. Это пример получения расширенного списка другим источником, а не скрытой пагинации XML.
- [Первоначальное сообщение RSS-Bridge #891](https://github.com/RSS-Bridge/rss-bridge/issues/891): пользователь описал, что увеличение внутреннего лимита не позволило получить весь канал. Это историческое наблюдение, не самостоятельное доказательство текущего контракта.
- [Вопрос и воспроизведение на Stack Overflow, 2017](https://stackoverflow.com/questions/42258132/fetching-videos-list-from-a-youtube-playlist-through-rss-doesnt-return-more-tha): отсутствие `rel=next`, ограничение 15 и неработающие `max-results/start-index`. Совет использовать эти параметры относится к старому API v2; текущая проверка выше подтверждает, что они не расширяют этот XML.

[Документация Google](https://developers.google.com/youtube/v3/guides/push_notifications) подтверждает официальный адрес Atom, но в изученных документах не найдено обещания полного архива или пагинации этого URL. Вывод ограничен проверенными ответами и реализациями: рабочего способа получить 60 через официальный XML не найдено. Возможность получения 60 через другие интерфейсы YouTube сохраняется.

Счётчик больше 15 в RSS-клиенте сам по себе не доказывает загрузку архива: клиент может накапливать записи при регулярном обновлении. Конкретный механизм накопления истории в пользовательском News Explorer здесь не проверялся.
