# Telegram web: частота запросов и риск ограничения доступа

Дата: 2026-10-21. Исследован checkout `61571822b59120debb7a89132de416f9f5b20e7d`.
Статус: исследование и предложение; поведение приложения не изменено.

## Вывод

Общий ограничитель Telegram web нужен: сейчас последовательное выполнение заданий
не задаёт частоту HTTP-запросов, а реакция на 429 не закрывает допуск остальным
заданиям. Гарантировать отсутствие блокировок нельзя: документированного безопасного
RPS для HTML `t.me/s/…` в проверенных официальных материалах не найдено.

Веб-доступ Око не использует Telegram-аккаунт: он получает публичный HTML отдельным
HTTP-клиентом без переданной авторизации и аккаунтной сессии. Поэтому непосредственный
риск — ограничение HTTP-доступа сборщика, предположительно по исходящему IP или другим
сетевым признакам. Это технический вывод по коду, а не гарантия Telegram о механизме
блокировок. Вероятность, длительность и пороги блокировки неизвестны; фактическую
блокировку рабочего экземпляра исследование не установило.

## Что подтверждают первичные источники

- [Telegram Channels](https://telegram.org/tour/channels#links-to-posts): публичные
  публикации можно открывать в браузере через ссылки `t.me`. Наличие предпросмотра
  само по себе не обещает неограниченный автоматический сбор.
- [MTProto errors](https://core.telegram.org/api/errors#420-flood): `FLOOD_WAIT_X`
  требует ждать X секунд после превышения допустимой частоты вызовов API.
  Это другой интерфейс, не HTTP 429 публичного HTML.
- [Bots FAQ](https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this):
  опубликованные ограничения отправки сообщений ботами не определяют частоту
  скачивания `t.me/s`.
- [Obtaining API ID](https://core.telegram.org/api/obtaining_api_id#using-the-api-id):
  Telegram предупреждает о контроле неофициальных API-клиентов и банах за
  flood/spam. Этот аккаунтный риск нельзя автоматически приписывать анонимному HTML.
- [RFC 9110, Retry-After](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3):
  заголовок допускает секунды и HTTP-date. Обе формы нужны для корректной паузы.

Отдельный риск условий использования: актуальные [Telegram ToS](https://telegram.org/tos)
отсылают к запрету scraping. [Content Licensing](https://telegram.org/tos/content-licensing)
ограничивает доступ предполагаемым использованием платформы и работой легитимных
клиентов; отдельно ограничивает сбор и использование данных для AI, включая deployment,
с исключениями по явному согласию соответствующих пользователей. Применимость этих
положений к персональному чтению и ИИ-обработке Око требует отдельного разбора;
это не заключение о доказанном нарушении. Рейтлимитер регулирует нагрузку и не решает
вопрос разрешённости использования данных.

## Что делает текущий код

| Место | Наблюдение | Значение |
| --- | --- | --- |
| `oko/collection/telegram/web.py:load` | Отдельный AsyncClient; до пяти переходов, без паузы между запросами | Нет общего ограничения RPS, каждый переход тоже запрос |
| `WebTelegram.page/history_page` | Запрос HTML на каждую страницу истории | История и догоняющий сбор создают серии запросов |
| `WebTelegram.fetch` | Повторный HTML-запрос для отдельной публикации | Стоимость сбора больше одного запроса на фид |
| `oko/storage/store.py:discovered` | Для Telegram envelope заново ставит fetch завершённых без ошибки непросмотренных материалов с members, кроме source_deleted | Проверяются и старые материалы, даже когда новых публикаций нет |
| `oko/collection/telegram/media.py:Downloader` | Скачивает вложения; collect повторно вызывает download и для ранее полученных ресурсов | Дополнительные запросы/байты к CDN; ограничение пула соединений не ограничивает RPS |
| `oko/reader/runtime.py` | Web-фиды входят в один common lane; одно collection-задание одновременно | Защита от параллельных фоновых заданий, но не от частых последовательных запросов |
| `Runtime.connect_telegram_binding` | Проверка подключения вызывает preview отдельно от common lane | Ограничитель только планировщика не охватит все обращения |
| `web.load`, `Downloader.open` | При 429 читают целые секунды Retry-After, иначе 60 с; максимум 86400 с | HTTP-date не поддерживается; длительная серверная пауза сокращается |
| `Runtime._account_wait` | Общая сохранённая пауза только для клиентского FloodWaitError | HTTP 429 не закрывает допуск другим Telegram web-заданиям |
| `Store.retry` | Откладывает конкретное задание | Следующее задание может обращаться к тому же сервису сразу |
| `Store.refresh_feed`, инициализация Store | Ручное обновление сбрасывает next, кроме специальных FloodWait/YouTube; запуск сбрасывает next pending-заданий | Web Retry-After не защищён от ручного обновления и перезапуска |
| `oko/subscriptions/subscriptions.py` | Общий интервал по умолчанию 15 минут | Это период постановки обновлений, не интервал отдельных HTTP-запросов |

При одном проходе без пагинации приблизительная стоимость HTML — F + U запросов,
где F — число web-фидов, U — число повторно загружаемых непросмотренных публикаций.
Например, 20 фидов и 400 таких материалов дают около 420 HTML-запросов за проход,
без учёта медиа, подключений, редиректов и повторов. Это расчёт по коду, не замер
пользовательской установки. История добавляет запросы страниц. Увеличение интервала
до 30–60 минут уменьшит число проходов, но сохранит серии запросов внутри прохода.

## Предложение минимальной защиты

1. Один общий допуск на HTTP-запросы Telegram web для всех фидов данного Runtime:
   подключение, discovery, история, fetch и каждый переход. Объединить `t.me` и
   `telegram.me` в одну группу. При нескольких экземплярах за одним IP их локальные
   лимиты складываются; один Runtime не обеспечивает общий бюджет всего IP.
2. Стартовая внутренняя настройка: не более одного HTML-запроса каждые 2 секунды,
   без накопления разрешений на всплеск; необязательная добавочная задержка 0–0,5 с.
   Это осторожная инженерная гипотеза, не опубликованный безопасный лимит Telegram.
   При 420 запросах минимальное время только HTML составит около 14 минут.
3. При 429 немедленно закрывать общий допуск Telegram web. Уважать Retry-After
   в обеих формах, не сокращать серверную паузу. Без пригодного заголовка —
   увеличивать паузу при повторных ограничениях, например 1, 2, 4… до 60 минут.
   Ручное обновление и перезапуск не должны обходить сохранённый deadline.
4. Для медиа — отдельный ограниченный бюджет по origin, охватывающий аватары,
   вложения и переходы; 429 одного CDN origin закрывает его общий допуск.
   Не считать произвольную внешнюю ссылку частью Telegram и не останавливать RSS
   из-за паузы Telegram. После 429 прекращать дальнейшие скачивания этой группы
   внутри уже выполняющегося collect, а не только откладывать повтор всего задания.
5. Ожидание принадлежит Runtime, сохранённый deadline — Store. Не держать action
   lock во время ожидания и не занимать common lane долгим sleep: другие источники,
   удаление, выключение и чтение должны продолжать работать. Отмена до допуска
   не должна отправлять запрос. HTTP-слой должен проверять допуск каждого запроса,
   включая подключение вне фонового lane.
6. Учитывать HTTP-код, группу, число запросов/байты, 429, срок паузы и причину
   ожидания без содержимого публикаций и секретов. Повторные 403/страницу ограничения
   не трактовать как удаление материала; прекращать частые повторы. 403 сам по себе
   не доказывает блокировку IP.

Сокращение повторных загрузок — следующий отдельный шаг: повторно использовать
уже полученную страницу и локальные ресурсы там, где это сохраняет свежесть.
Полностью убирать проверку непросмотренных материалов без решения о своевременности
обнаружения правок и удалений нельзя. Переход на Telethon не является автоматическим
решением: появляются аккаунтные ограничения и отдельный FloodWait.

## Фактическая проверка и ограничения

- Прочитаны актуальные исходники, глоссарий, правила разработки и архитектура
  выполнения. Рабочий Docker-выпуск и его настройки не проверялись.
- Выполнен локальный скрипт через `.venv/bin/python` с `httpx.MockTransport` и
  синтетическим HTML из `tests.support.telegram_web.page`: 429 с Retry-After=120
  возвращает delay=120 и code=source_unavailable без remote_type; следующий
  непосредственный вызов load сразу делает второй запрос и успешно возвращает пост.
  Это проверка адаптера; отсутствие общего HTTP cooldown в Runtime установлено
  чтением кода, не полноценным HTTP-тестом планировщика.
- Тот же скрипт подтвердил: Retry-After в форме HTTP-date превращается в 60 с,
  значение 172800 сокращается до 86400 с.
- Внешние источники прочитаны через веб-поиск. Личные подписки и Telegram-профили
  не использовались, лимиты Telegram нагрузкой не испытывались. Статистика рабочего
  трафика, фактические 429, пороги антиабьюза и вероятность бана не измерены.
- Изменён только этот исследовательский документ; тестовые наборы приложения
  не запускались. Для будущей реализации нужны проверки через HTTP interface с
  синтетическим transport и управляемым временем: общий бюджет разных фидов и
  подключений, редиректы, общий 429, обе формы Retry-After, перезапуск и ручной refresh,
  отмена ожидания, изоляция RSS/Telethon/CDN, остановка collect после ограничения.
