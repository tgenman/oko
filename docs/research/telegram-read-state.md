# Telegram: прочитанное при чтении не по порядку

Проверено 2026-10-08 по официальным исходникам и документации Telethon. Реальные сообщения не читались, Telegram API не вызывался, credentials не использовались. Это проверка документированной семантики, не эксперимент на аккаунте.

## Подтверждённое ограничение

Через обычную отметку истории нельзя пометить сообщение 120 прочитанным, оставив 119 непрочитанным в том же диалоге. `send_read_acknowledge` документирует накопительную отметку всех сообщений с ID ≤ `max_id`. Передача списка сообщений также не даёт раздельных отметок: реализация берёт максимальный ID. Без сообщения и границы используется `max_id=0`, который этот helper документирует как прочтение всей истории; Око не должно использовать такой вызов для ограниченного набора материалов. [Официальный исходник Telethon: send_read_acknowledge](https://github.com/LonamiWebs/Telethon/blob/v1/telethon/client/messages.py)

| Тип источника | Вызов истории |
| --- | --- |
| Обычная группа, тип Chat | messages.readHistory |
| Приватный или публичный broadcast-канал, тип Channel | channels.readHistory |
| Supergroup / megagroup, тип Channel | channels.readHistory |

Диспетчеризация по типу сущности видна в `send_read_acknowledge`; supergroup определяется как Channel с флагом megagroup в официальной документации. Наличие публичного username в этой диспетчеризации не участвует. [Исходник метода](https://github.com/LonamiWebs/Telethon/blob/v1/telethon/client/messages.py), [официальная документация Chats vs Channels](https://github.com/LonamiWebs/Telethon/blob/v1/readthedocs/concepts/chats-vs-channels.rst).

Канонические страницы Telegram: [messages.readHistory](https://core.telegram.org/method/messages.readHistory), [channels.readHistory](https://core.telegram.org/method/channels.readHistory). Их прямое получение в этой проверке закончилось таймаутом; web-инструмент также вернул ошибку доступа. Фактическое подтверждение выше получено из живых файлов официального репозитория Telethon, доступных через raw.githubusercontent.com. Ветка v1 изменяема, commit SHA не фиксировался.

## Предлагаемое продуктовое решение

Это рекомендация для обсуждения, ещё не согласованное поведение и не реализованный код.

1. Око немедленно отмечает выбранную карточку локально просмотренной и удаляет её контент согласно принятому правилу. Служебная запись об обработке и ожидающей синхронизации сохраняется.
2. Telegram получает отметку только до последней безопасной границы: все более ранние релевантные непрочитанные сообщения этого диалога уже подтверждены пользователем. Просмотр 120 при непросмотренном 119 ставит 120 в локальную очередь; граница не перескакивает через 119. После просмотра 119 можно продвинуть её до 120.
3. Для сводки очередь пополняется ID всего обработанного набора, включая не вошедшее в текст из-за фильтрации, как уже согласовано. Отдельное скрытие фильтром само по себе не означает пользовательского просмотра.
4. В режиме автопрочитывания условие продвижения границы — полное сохранение материала, включая требуемые медиа. Нельзя подтверждать более поздний пост через более ранний ещё не сохранённый материал и считать это выполнением гарантии полноты.

Такой алгоритм следует из накопительной семантики источника. Он сохраняет свободу сортировки и локального чтения, но Telegram может временно показывать непрочитанное, уже просмотренное в Око.

## Ограничения и следующие проверки

- «Непрерывность» означает отсутствие непрочитанных сообщений в истории соответствующего диалога, а не наличие каждого целого ID: алгоритм должен учитывать существующие сообщения, известные удаления, исходную границу и полноту получения истории. Нельзя просто проверять числовую последовательность 118, 119, 120.
- Первоначальная загрузка только последних суток создаёт отдельное решение: что делать со старой непрочитанной историей вне импорта. Продвинуть серверную границу поверх неё, сохранив её непрочитанной, нельзя в описанной модели. Нужно явно согласовать исходную границу или разрешение очистить старый долг.
- Другие Telegram-клиенты могут менять прочитанность независимо от Око. Политика обратной синхронизации не определена; внешнюю отметку нельзя автоматически приравнивать к локальной команде удаления без отдельного решения.
- Forum topics и обсуждения требуют отдельной проверки методов и границ. Это исследование подтверждает обычную историю групп и каналов, но не обещает корректную синхронизацию тем форума через один общий max_id.
- При ошибке отправки ack служебная очередь должна сохраняться после удаления контента и переживать перезапуск. Доступность аккаунта, ограничения частоты и фактический readback здесь не проверялись.
