# Устойчивое получение субтитров YouTube

Дата исследования: 2026-10-13. Статус: исследование и рекомендации, без реализации и проверки личных подписок.

## Вывод

Замена одной библиотеки другой не решает блокировку исходящего IP. Для Око разумный порядок: сохранить уже добавленное переиспользование субтитров, различать причины ошибок, при блокировке выдерживать общую паузу для YouTube; затем сравнить явно настроенный proxy и управляемый API. `yt-dlp` полезен против несовместимости клиента и требований PO Token, но на том же IP не является независимым запасным каналом. Публичные Invidious/Piped стоит рассматривать как эксперимент, а не основной backend. Основания — ограничения [youtube-transcript-api](https://github.com/jdepoix/youtube-transcript-api#working-around-ip-bans-requestblocked-or-ipblocked-exception), [PO Token provider](https://github.com/Brainicism/bgutil-ytdlp-pot-provider#verification) и [публичных Invidious instances](https://docs.invidious.io/instances/).

## Что есть в текущем checkout

- Зависимость закреплена на `youtube-transcript-api==1.2.4` в [pyproject.toml](../../pyproject.toml). [Worker](../../oko/collection/youtube/worker.py) создаёт новую `Session` для каждого видео, делает `list()` и `fetch()` выбранной дорожки: ru, en, остальные языки; внутри языка ручные субтитры раньше автоматических. `trust_env=False` означает, что настройка `HTTPS_PROXY` сама по себе здесь не включит proxy.
- [LocalCaptions](../../oko/collection/youtube/source.py) ограничивает дочерний процесс 60 секундами и 2 МБ JSON. `TranscriptsDisabled`/`NoTranscriptFound` превращаются в отсутствие текста; в параллельно изменяемом checkout к завершению исследования также появился пропуск ещё не начавшегося live event через `VideoUnplayable`/`SourceSkipped`. Остальные исключения становятся ошибкой. `YouTubeSource.fetch()` сохраняет ошибку субтитров внутри материала; это не исключение, автоматически останавливающее сбор следующих видео.
- В текущих незакоммиченных изменениях уже есть reuse текста с `captions=available`, в том числе при повторной загрузке. Это не отсутствующий кэш, который требуется написать заново; см. [отчёт проверки](https://github.com/tgenman/oko/blob/365e2b38f86d6e2bedccbb40b14c615b6f069455/docs/verification/youtube-caption-reuse.md). Состояние запущенного пользовательского экземпляра этим не доказано.
- [Runtime](../../oko/reader/runtime.py) уже допускает одну активную задачу сбора. Проблема не доказывает параллельный шторм: в просмотренном пути нет отдельного интервала между запросами субтитров и общей паузы после блокировки YouTube. Одной сериализации недостаточно для ограничения частоты последовательных запросов.

## Причины и варианты

| Вариант | Что даёт | Ограничения и решение для Око |
|---|---|---|
| Текущий `youtube-transcript-api` + spacing/cooldown | Убирает лишние повторные запросы и ограничивает нагрузку | Не снимает уже существующую блокировку IP; первый шаг независимо от backend |
| Та же библиотека + явно заданный proxy | Другой исходящий IP без замены формата субтитров | Расходы и эксплуатация proxy; результат надо измерить |
| `yt-dlp` + PO Token provider | Альтернативная реализация клиента, поддержка attestation | Не независим от IP; больше компонентов и обновлений |
| Supadata / youtube-transcript.io | Поставщик обслуживает получение субтитров | API key, лимиты, стоимость; видео-ID передаётся третьей стороне |
| Invidious/Piped | Готовые альтернативные API | Публичные серверы сами зависят от YouTube и могут ограничивать автоматизацию |
| Аудио + локальный ASR | Текст, когда дорожки субтитров нет | Сначала нужно получить аудио; новый вид результата и существенно более тяжёлая обработка |

Таблица — инженерная оценка по первоисточникам ниже, не результат сравнительного прогона.

### 1. Библиотека и proxy

Авторы `youtube-transcript-api` описывают `RequestBlocked`/`IpBlocked` как типичный результат блокировки облачных IP либо чрезмерных запросов с собственного адреса. Есть `WebshareProxyConfig` для rotating residential proxies и `GenericProxyConfig` для собственного HTTP/HTTPS/SOCKS proxy. Сам README предупреждает, что proxy тоже может быть заблокирован. Рекомендация конкретного поставщика — опыт автора с referral-ссылкой, а не независимый benchmark. Cookie authentication помечена как временно неработающая. [README](https://github.com/jdepoix/youtube-transcript-api#working-around-ip-bans-requestblocked-or-ipblocked-exception), [cookies](https://github.com/jdepoix/youtube-transcript-api#cookie-authentication).

Рекомендация: сохранить `trust_env=False`, а при выборе proxy передавать конфигурацию явно только адаптеру субтитров. Это даёт проверяемый маршрут вместо случайного влияния окружения. Не включать бесконечную ротацию и повторы: число попыток и затраты должны быть ограничены. Бесплатный VPN или один статический proxy нельзя считать гарантированным исправлением.

### 2. yt-dlp и PO Token

`yt-dlp` умеет получать обычные и автоматические субтитры без скачивания видео: соответствующие опции — `--write-subs`, `--write-auto-subs`, `--skip-download`, `--sub-langs`. [README](https://github.com/yt-dlp/yt-dlp#subtitle-options).

Документация различает PO Token для `gvs` (медиа), `player` и `subs` (субтитры). Поддержка токена для медиа сама по себе не доказывает доступность субтитров. Для web/mweb токен Player/Subs привязан к конкретному видео. Требования клиентов меняются; старые рецепты с постоянным токеном или фиксированным client нельзя считать устойчивым контрактом. [PO Token Guide](https://github.com/yt-dlp/yt-dlp/wiki/PO-Token-Guide).

Готовый [bgutil-ytdlp-pot-provider](https://github.com/Brainicism/bgutil-ytdlp-pot-provider) состоит из plugin и генератора токенов: HTTP-сервера либо запускаемого скрипта, с Node.js/Deno или Docker. Автор прямо пишет, что токен не гарантирует устранение 403/bot checks и не снимает IP-based login restrictions. Поэтому пробовать этот путь стоит после разделения ошибок IP и token/client, а не после каждой неудачи на том же адресе. Использование аккаунта через cookies имеет риск блокировки аккаунта по предупреждению [yt-dlp](https://github.com/yt-dlp/yt-dlp/wiki/Extractors#exporting-youtube-cookies); личный аккаунт не нужен для первого эксперимента.

### 3. «Зеркала»: Invidious и Piped

[Invidious API](https://docs.invidious.io/api/#get-apiv1captionsid) предоставляет `/api/v1/captions/:id`: список дорожек, выбор по языку/label, WebVTT. [Piped API](https://docs.piped.video/docs/api-documentation/) возвращает в `/streams/:videoId` массив `subtitles`, язык, `autoGenerated` и URL дорожки. Это альтернативные интерфейсы получения данных, не доказанное независимое долговременное хранилище субтитров.

В официальном [списке Invidious](https://docs.invidious.io/instances/) отмечены проблемы YouTube и сокращение публичных instances. Правила требуют от публичных серверов одновременно ограничивать автоматизированный трафик и ротировать IP для запросов к YouTube. Следствие для Око: доступность страницы просмотра не доказывает доступность captions API для программы. Список живых mirrors нельзя зашить как гарантированный failover. Самостоятельный instance переносит обслуживание extractor/proxy на нас, а не устраняет зависимость от YouTube. Работоспособность конкретных серверов в этом исследовании не измерялась.

### 4. Управляемые API

**Supadata.** Есть [официальный Python SDK](https://github.com/supadata-ai/py). [Transcript API](https://docs.supadata.ai/get-transcript) принимает `mode=native`, `auto` или `generate`: по умолчанию `auto` может перейти к AI-транскрибации. Возможны HTTP 200 либо 202 с job ID; завершённый job нужно забрать в течение часа. Для текущей семантики Око выбирать `native` явно: ASR не должен незаметно становиться «исходными субтитрами». Поставщик ограничивает доступ публичными видео и не поддерживает незавершённые live streams. Документированы 1 credit за native transcript, 2 credits за минуту генерации; даже ответ 206 «transcript unavailable» стоит credit. Генерация может длиться около 100 секунд до синхронного ответа: текущий лимит Око 60 секунд нельзя переносить на этот сценарий без проектирования фонового ожидания.

На дату чтения [тарифа Supadata](https://supadata.ai/pricing): бесплатные 100 credits/месяц; Basic — 300 credits/месяц, $60/год; Pro — 3000 credits, $17/месяц. Налоги не включены; auto-recharge следует оставлять выключенным в эксперименте. Это заявленные условия поставщика, не подтверждение доступности оплаты из конкретной страны.

**youtube-transcript.io.** [API](https://www.youtube-transcript.io/api) принимает до 50 ID за запрос, требует API token, ограничивает частоту 5 запросами за 10 секунд и при 429 возвращает `Retry-After`. [Plus](https://www.youtube-transcript.io/pricing) заявляет 1000 transcripts за $9.99/месяц. Он подходит вторым кандидатом для сравнения; реклама «для любого публичного видео» не является измеренной гарантией. Точное сохранение выбора языка/ручной дорожки надо проверить отдельно для обоих API.

Вывод: управляемый API избавляет нас от обслуживания собственного пула IP, но заменяет его зависимостью от поставщика. Сначала измерить native captions на небольшом наборе, проверить причины отказов и списание credits; обещания процентной доступности здесь не делаются.

### 5. Официальный YouTube API и ASR

Официальный [`captions.download`](https://developers.google.com/youtube/v3/docs/captions/download) требует авторизации и права редактирования видео. Это вариант для собственных/управляемых каналов, не общий способ получать субтитры чужих подписок.

Для локального распознавания готов [whisper.cpp](https://github.com/ggml-org/whisper.cpp), включая Apple Silicon/Metal/Core ML. Но ASR потребляет аудиофайл: если YouTube блокирует и его получение, распознавание не исправляет сетевую часть. Оно полезно для доступного аудио при отсутствии captions. Для Око это отдельная возможность: лимиты длительности/размера, удаление временного аудио, отмена, provenance `local_asr` с версией модели и сохранение отличия от YouTube manual/auto captions. Это предложение, сейчас аудио/ASR отсутствуют в [описании интеграции](youtube-captions.md).

## Предлагаемый следующий шаг

1. Разделить `blocked/rate_limited`, временную сетевую ошибку, отсутствие дорожки, недоступное видео и несовместимость extractor. Фиксировать стадию, класс исключения, HTTP status/`Retry-After`, время, backend и число попыток; не сохранять cookies, credentials и подписанные URLs.
2. Добавить интервал между новыми caption fetch и общий cooldown по исходящему маршруту после блокировки. Сохранение `captions=error` не должно стирать сигнал об общей паузе. Runtime управляет ожиданием, Store сохраняет срок и попытки, адаптер сообщает причину. Другие источники должны продолжать работу. Конкретный интервал — параметр эксперимента, публичного гарантированного лимита YouTube в изученных источниках нет.
3. Оставить reuse успешного текста. Для временных ошибок проектировать ограниченные отложенные повторы с jitter и бюджетом, а не быстрый повтор каждого видео. Внутренние retries библиотеки/proxy и внешние retries планировщика должны расходовать общий бюджет, а не перемножаться; предел процесса 60 секунд также учитывать. Изменение нынешнего правила «ошибка требует явного повтора» сначала отразить в спецификации.
4. Для проверки выбрать один новый путь: explicit proxy с текущей библиотекой либо Supadata `native`. Начать с малого независимого набора публичных video ID; сравнить ru/en, ручные/авто дорожки, отсутствие дорожки, длительность и возраст публикации. Не повторять массово уже заблокированные запросы.
5. Сравнить долю успешных native captions, ошибки по классам, p50/p95 времени, запросы/credits на успех, соответствие выбранному языку и содержимому. Успех в одном запросе не доказывает устойчивость: нужна ограниченная повторная проверка через время. Отдельно проверить синтетически cooldown, отмену и перезапуск через HTTP interface читателя.

Пункты выше — план возможной реализации и проверки, не уже выполненная работа. Выбор proxy/платного API/ASR меняет прежние ограничения [исследования от 2026-10-09](youtube-captions.md); старый отчёт не переписывался.

## Фактически проверено

Прочитаны текущие локальные worker/source/runtime и документация; найдены и прочитаны первичные источники библиотек, API и тарифов по указанным ссылкам. Все ссылки на ветки `master`/`main`, wiki и тарифы изменяемые: выводы относятся к дате чтения. Личные подписки и аккаунты не использовались; библиотеки, proxy и новые платные API не подключались; получение реальных субтитров и сравнительный benchmark не запускались. Поэтому причина конкретных обрывов Око и эффективность вариантов на его исходящем IP пока не установлены.
