# Проверка точного коммита чтения

Проверено дерево `0fef6a0bcd32370896506860331858adce0d0a33` коммита
`d81eb5e96664c8fa4d001ea5ac1898697f330fcf`: чистая изолированная копия,
временная PostgreSQL и синтетические источники. План шардов
`7cc2d847dcecab3b403a587242e1c72d0d97207d413b930547ff757b5bc2986f`
охватывает **250 файлов**. Python, браузер и инструментальные наборы
запускались последовательно; внутри Python-шардов — до четырёх работников,
в браузерных — два. SHA и чистота копии проверялись между наборами.

Первый Python-шард при двух параллельных запусках завершился с разными
падениями: ожидание готовности читателя за 3 секунды и ожидание материала
Telegram за 4 секунды. Каждый из этих сценариев затем прошёл отдельно без
изменения кода и тайм-аутов. Все 90 файлов первого шарда были повторно
запущены одним процессом: **439 passed, 4 skipped**; набор файлов в JUnit
совпал с планом. Два исходных неуспешных отчёта сохранены и не заменены.

Остальные наборы:

- Python 2: **464 passed**; PostgreSQL: **181 passed, 2 skipped**.
- Браузер 1 и 2: **90 и 95 passed**; отдельный latency-набор: **4 passed**.
  Снимок мобильных настроек истории просмотрен.
- Инструменты: **155 passed**; Node: **38 passed**; контракт, сборка, линтер,
  типы, diff и **5 HTTP-тестов** прошли.

Отдельная локальная сверка проверила план, хеши тестовых файлов, пять успешных
отчётов шардов и JUnit последовательного повтора: **1273 passed, 6 skipped**
по 250 файлам. Это составное свидетельство, а не успешный штатный CI-аудит:
`ci_shards.py verify` правильно завершился ошибкой из-за неуспешного отчёта
первого шарда. JUnit сам по себе не подписывает ревизию; связь с коммитом и
списком файлов дополнительно зафиксирована скриптом запуска и журналом.

Два пропуска требуют Linux с bubblewrap, ещё четыре относятся к отложенным
сценариям автоматического обновления публикаций (#216). Локальная проверка не
заменяет Linux CI и не подтверждает развёртывание. В четырёх latency-сценариях
наибольший p95 составил **179 мс** при пороге теста 300 мс; это единичное
локальное измерение, не оценка production.

Внутренние записи приложения сериализуются общим graph lock. Независимое ревью
отметило предел: произвольная параллельная правка другого участника истории
напрямую через SQL не участвует в этом lock и не проверялась как изолированная
операция; заявлять такую гарантию нельзя.
