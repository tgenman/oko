## Что сохранено и почему

| Область | Оценка необходимости |
| --- | --- |
| Смерть процесса после atomic move/commit; физическое удаление | Нужны. HTTP-вызов в одном процессе не проверяет фактическую смерть и восстановление с диска. Filter/theses/viewed затрагивают разные пути фиксации. |
| Реальные SDK/worker, proxy, авторизация и подтверждение Telegram | Нужны. Проверяют границы внешних библиотек и дочерних процессов; маленький fake вместо SDK потерял бы эти ошибки. |
| 300 диагностических событий и повторная доставка | Сохранены: сценарий намеренно проверяет повтор после большой серии событий другого отправителя, включая перезапуск. Последний full: 1,46 с; сейчас это не основной ограничитель. |
| API schema, generated drift, strict wire/static contracts | Нужны. Проверка готовых DTO не доказывает, что команда генерации продолжает выдавать корректные DTO. Сокращена повторная подготовка, а не отрицательные примеры. |
| Git index, task_changes, сохранение staged/unstaged и конкурентный git add | Нужны для существующих инструментов. Проверки рабочего файла не заменяют проверку staged blob, а обычный успешный commit не проверяет восстановление пользовательского индекса. |
| Runner | CLI smoke, ошибки runtimes, выбор профилей, дедупликация, параллельность, SIGINT/descendant cleanup и отдельные отчёты сохранены. Следующий крупный кандидат — проверять построение плана команд без нового CLI-процесса для каждого варианта, оставив сквозные тесты запуска и очистки. Это потребует отдельного изменения структуры runner. |
| Frontend builder/cache/watch | Сохранены обе границы: ошибка одноразового CLI должна завершиться неуспехом и сохранить старое поколение; watch должен публиковать новые поколения и сохранять assets открытой вкладки. Начальная успешная сборка в обоих сценариях похожа, но её простое удаление оставит другую гарантию непроверенной. |
| GitHub Issues и process logs tools | Маленькие проверки существующих отдельных инструментов. Они не являются дубликатами продуктовых сценариев читателя. |
