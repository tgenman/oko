# Ускорение проверок через выбор уровня тестирования

Дата: 21 октября 2026. База: `f213a76fa689432b6ed2d7b1e47ac131a4c15968`.
Работа: отдельный worktree `test-runtime-speed/oko`.
Задание: ускорить полный прогон, переписав дорогие проверки по пирамиде тестирования.

## Что переписано и что сохранено

| Проверка | Новый уровень и сохранённая гарантия |
| --- | --- |
| Два обхода 1000 RSS-страниц | Настоящий RSSSource с MockTransport: ровно 1000 запросов, запрет 1001-го, пустые страницы, redirect в посещённую ветку, отложенный архив. Без тысячи пауз scheduler по 20ms. |
| RSS и Atom, 200 публикаций | Adapter: все 200 идентичностей и порядок, overlap, redirect, пустая страница, относительные ссылки и xml:base. HTTP: шесть публикаций проходят те же виды страниц до loaded/cards. |
| HTTP у page_limit | Курсор получен настоящим adapter после 999 запросов, сохранён через Store до запуска приложения. Runtime продолжает с диска, HTTP показывает requests=1000/page_limit/loaded=0. Повторный запуск не запрашивает страницу 1001. |
| Три SDK/fetch контракта | Node с настоящими Request/Response и импортом production transport: binary bytes/headers, авторизация, JSON/media/keepalive, шесть исходных ошибок и отсутствие retry. Все исходные assertions сохранены. |
| Браузерная задержка чтения | Прежние четыре библиотеки, 40 первых + 40 повторных кликов в каждой, настоящий click/DOM observer, активная обработка, p95 <200ms. Ожидание записи observer через animation frame вместо 100ms polling; часы не подменены. |
| Распределение исполнения | Python использует четыре workers и в полном прогоне. Browser выбирает восемь файлов при >=12 logical CPU, четыре при меньшем/неизвестном числе CPU; существующий override 2/4/8. Отдельная performance-команда сохранена. |

Pagehide/pageshow, отображение malformed response и повтор diagnostics той же occurrence
остаются браузерными. Реальные смерть/отмена процессов, поздние ответы, сохранение,
восстановление и очистка не заменены mocks. Production-код и defaults не менялись.
Результаты тестов не кэшируются; новые skips не добавлены.

## Сопоставление полных запусков

Один компьютер (12 logical CPU), одни зависимости, временные данные и синтетические
adapters. Все запуски — из автоматических изолированных снимков, с полным tools.
Каждый запуск прошёл целиком. Это последовательные одиночные замеры, не статистический
benchmark; общая нагрузка ОС не фиксировалась.

| Группа | Исходный all tools | Перенос RSS + Python4 + browser4 | Browser8 |
| --- | ---: | ---: | ---: |
| Python | 266,40s | 165,74s | 169,00s |
| TypeScript/browser, включая performance | 203,85s | 192,55s | 163,23s |
| Tools | 117,43s | 113,58s | 135,18s |
| Полное wall-clock | **288,03s (4:48)** | **213,00s (3:33)** | **189,94s (3:10)** |

Группы перекрываются: их время нельзя складывать. Итог примерно на 34% быстрее.
Browser8 замедляет tools, но ускоряет полный запуск; поэтому выбран только для больших
машин с сохранением ручного ограничения. Критический путь теперь примерно поровну
делят Python и браузер. До 90 секунд этот результат не дошёл.

RSS-файлы в полных запусках: 77,88s исходный HTTP-файл против 17,49s суммарно для
двух новых файлов при browser8. Это сумма case durations, а не отдельный wall-clock.
Отдельный исходный 1000-page HTTP case занял 23,09s call; новый HTTP resume999 —
0,61s call в целевом прогоне. Все 1000 шагов остаются в adapter-проверках.

Исторические 91,25s найдены в `test-cycle-pr-20261015.md`: тогда было 346 Python,
117 TypeScript и 111 tools, использовались готовые assets и кэш типов. Теперь набор
существенно больше; историческая цифра не является сравнением одинакового состава.

## Фактическая проверка и ограничения

- Исходный полный: 708 Python + 9 HTTP, 206 TypeScript + 4 performance,
  145 tools; два прежних skipped. Всё PASS.
- Полный browser8: 711 Python + 9 HTTP, 206 TypeScript + 4 performance,
  145 tools; те же два skipped. Всё PASS, checkout guard PASS.
- До исправления бюджета Python regression ожидает четыре workers и получает два
  (RED); после исправления проходят полный runner и реальные interruption/cleanup cases.
- Целевые RSS + runner: 73 PASS, 2 interruption cases отдельно прошли в следующем запуске.
- После полного замера добавлены автоматический CPU-выбор и перенос трёх transport
  cases в Node. Финальные 55 runner tests PASS (19,77s), включая выбор CPU/override,
  охват файлов, failure/report и реальную отмену. Прямой Node: 3 PASS (0,58s).
- Финальный build + browser двух transport-файлов: PASS (16,49s суммарно,
  browser 3,74s), tooling/browser types PASS. Полный набор после этих узких правок
  повторно не запускался; замер browser8 использовал тот же эффективный лимит явно.
- Независимое ревью первоначального изменения и узкий повтор новых правок:
  actionable замечаний нет. Скриншот 400 материалов при активной обработке просмотрен.
