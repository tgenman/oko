# Сценарный разбор проекта хранения

29 октября 2026. Разбор выполнен ведущим исполнителем по документам и текущим
владельцам кода. **Это не независимое ревью и не запуск поведенческих тестов.**
Код приложения, миграции и рабочая база не изменялись.

Объём — общий [проект](../architecture/storage-redesign.md), пять физических схем,
согласованные Publication/Job/медиа и требования пользователя: три крона, отсутствие
прикладных триггеров, сохранение готового фильтра при выключении, завершение начатого
вызова и выбор первого начавшего фида. Входной снимок правок сохранён инструментом
task_changes отдельно от checkout. База кода — `54cf7217`; проверка зависимости
HTTP-работы ограничена read-only снимком её статуса и worktree HEAD `3c84042e`.

## Что уточнено после разбора

### 1. Потребность в работе и Job должны фиксироваться вместе

В первоначальном варианте следующий крон сам находил ожидающую публикацию без Job.
Контрпример: много pending_filtering публикаций имеют failed Job, а новой работы нет.
Один индекс status публикации не исключает весь такой набор; поиск отсутствующих
Job способен повторять большой обход. Это вывод о возможном плане, не измерение.

Проект изменён: владелец операции атомарно сохраняет статус и нужную Job. Крон
читает indexed pending Job и проверяет объект. Blocked сохраняет приостановленную
работу вне очереди запуска; событие изменения условия пересматривает её. Пропавшая
Job исправляется миграционной/startup сверкой, не постоянным polling всей библиотеки.

### 2. Выключение и crash — разные события

Разрешение закончить уже running попытку не разрешает бесконечно восстанавливать
новые внешние вызовы под старым enabled=true в snapshot. После crash допуск проверяется
по текущей настройке: при выключенном этапе восстановленная работа blocked.
Готовый результат сохраняется. Это уточнение не вводит отмену обычного running
вызова только из-за переключателя.

### 3. Отмена истории не является успешной загрузкой

Текущий `JobRepository.cancel_history` ставит fetch Job в done. Это конфликтовало
с проектным правилом, по которому ожидающий объект с done без результата выглядит
повреждённым и может быть восстановлен. В новом описании pause даёт blocked,
cancel — cancelled; миграция классифицирует прежний done по подтверждённому run.
Отмена одного run не отменяет независимую потребность другого владельца.

### 4. Владелец допуска YouTube определён однозначно

Ранее проект оставлял выбор между условными updates и сериализацией исходов.
Выбрано использование существующего единственного caption-слота: он освобождается
после фиксации результата допуска, чтобы старый успех не снимал более новое
ограничение. Это уточнение проекта, а не утверждение о доказанной ошибке текущего
runtime. Вызов сети остаётся вне SQL-транзакции.

### 5. Неизвестная длительность не равна нулю

В первоначальном DDL elapsed_seconds был NOT NULL DEFAULT 0. При crash это могло
выдать неизвестную длительность за измеренный ноль. Поле сделано nullable:
новый захват очищает его, измеренная длительность сохраняется отдельно от NULL.
Число таблиц и колонок не изменилось.

## Сквозные сценарии

Таблица фиксирует результат проверки логики описания, не PASS runtime-теста.

| ID | Сценарий | Правило проекта после разбора |
| --- | --- | --- |
| S01 | Два захвата одной Job | Объект и Job блокируются в одном порядке; второй проверяет уже изменившиеся generation/status |
| S02 | Ошибка между результатом и finish | Обе записи откатываются; ноль строк условного finish не считается успехом |
| S03 | Вход A → B → A | Каждый значимый переход закрывает generation; совпавшая подпись не возвращает старый допуск |
| S04 | Меняется только prompt_theses | Фильтр сохраняется; сравнивается подпись этапа, не весь pass JSON целиком |
| S05 | Выключен фильтр с готовым результатом | Результат, hidden и его применение сохраняются, новых запусков нет |
| S06 | Выключение во время running | Тот же актуальный вызов может завершиться; текущие права/вход всё ещё проверяются |
| S07 | Выключение, затем crash | Восстановленный новый вызов blocked до действующего допуска |
| S08 | Общая публикация и разные первые этапы фидов | Pending кандидаты не выбирают владельца; первый commit захвата сохраняет один контекст и согласует остальные Job |
| S09 | Много постоянных ошибок, новых данных нет | Failed/unavailable/blocked не попадают в pending индекс и не переоткрываются самим тиком |
| S10 | Просмотр общей статьи, нужной посту | Карточка исчезает, исходник/медиа остаются зависимостью; собственная AI-работа без фида закрывается |
| S11 | Цикл ссылок без корня чтения | Недостижимый компонент очищается; входящий счётчик сам по себе не удерживает цикл |
| S12 | Move файла, crash до/после commit | Нет ложного ready; активный путь защищён, после restart orphan отличим от сохранённого ключа |
| S13 | Telegram принял отметку, локальный commit потерян | Повтор сначала сверяет внешнюю границу того же account/peer, не предполагает отсутствие эффекта |
| S14 | Новый needs_sync во время старого RPC | Старое завершение не снимает новый true |
| S15 | Поздняя страница старого run | Не меняет cursor/состав нового run; принятие актуальной загрузки общего объекта рассматривается отдельно |
| S16 | Отмена истории с незагруженными карточками | Cancelled не становится done/новым pending только из-за незавершённого статуса Publication |
| S17 | Source wait, restart или поздний caption-успех | Срок не сокращается новым входом/повтором; старый результат не сбрасывает чужой допуск |
| S18 | GET, stop, restore и другой storage ID | GET read-only; storage identity сохраняет защиту; сведения закрытого Store не принимаются как новые |

Для каждого сценария в [плане реализации](../architecture/storage-implementation-plan.md)
указан этап и реальная граница проверки. Во время разбора не обнаружено необходимости
добавлять таблицу: кандидат остаётся из 20 таблиц. Исполнимость этих правил должна
подтвердить реализация; этот вывод не доказывает отсутствие иных ошибок.

## Выполненная структурная сверка после уточнений

Скрипт Python повторно проверяет декларации CREATE TABLE/INDEX, колонки, цели
REFERENCES, карту 44 исходных таблиц, локальные ссылки, fences и пробельные ошибки.
Проверка не использует PostgreSQL-парсер и не подключается к БД.

- 20 таблиц и 150 колонок; имена внутри областей не повторяются.
- 23 явно объявленных индекса после добавления jobs_blocked.
- 15 ссылок REFERENCES указывают на описанные таблицы/колонки.
- 14 прежних структур убираются, 10 объединяются, 20 остаются с items → publications.
- В целевых SQL-блоках нет CREATE TRIGGER/FUNCTION.

Предыдущий [структурный отчёт](storage-schema-design-20261029.md) сохраняет исходные
22 индекса до этой проверки. В нём не переименован старый результат в новый PASS.

## Ограничения и дальнейшая работа

Не выполнялись SQL, миграции, concurrency/fault/HTTP/browser-проверки и нагрузочные
замеры. Не проверялись конкретные данные рабочей библиотеки. Ни один предложенный
DDL или переход не объявляется готовым к production только по этому разбору.

Независимое ревью реализации остаётся обязательным этапом. Параллельная HTTP-работа
ещё имела незавершённый CI в момент чтения; её итоговый main нужно зафиксировать
перед кодовыми изменениями. Реализация и рабочее переключение не начаты.
