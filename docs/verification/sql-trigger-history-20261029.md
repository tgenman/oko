## Вывод

В проверенном коде нет цепочки «SQLite не имел SELECT FOR UPDATE → понадобились триггеры для безопасного захвата заданий». Захват заданий по статусу существовал с 8 октября, до всех триггеров; конкурентный доступ рабочего процесса был сериализован Python-lock. Первые триггеры 20 октября добавили сохранённые признаки изменения входов, необходимые для сокращения повторного согласования. В том же коммите отдельно добавили индекс по pending-заданиям: это два разных участка работы. При переходе на PostgreSQL 25 октября перенесли существующие триггеры и сохранили модель одного Store, принудительно закрепив её advisory lock. Захват по FOR UPDATE / SKIP LOCKED не был введён.

Исходные чаты подтверждают, что триггеры вводились агентом при выполнении задач оптимизации. В просмотренных сообщениях пользователя и спецификациях #53–56 нет требования реализовать инвалидацию именно триггерами. Обоснование реализации говорит об актуальности, атомарности и сокращении повторных обходов; сравнения с явными Python-записями или причинной ссылки на отсутствие SELECT FOR UPDATE не найдено. Это ограниченный вывод по доступным первичным источникам, а не утверждение о внутренних мотивах исполнителя.

## 1. Очередь по статусу уже существовала до триггеров

Первый найденный `next_job` — коммит `86357ef7a7a0b01e7e920c27e2a570453448c424`, 8 октября 13:05 МСК. В `oko/store.py:80–97` уже есть:

```sql
SELECT * FROM jobs WHERE status='pending' AND next<=?
ORDER BY ... LIMIT 1;
UPDATE jobs SET status='running',attempt=attempt+1,generation=generation+1
WHERE id=?;
```

Завершение ограничено `id`, `generation` и `status='running'`; при запуске незавершённые running переводятся обратно в pending с новым generation. Это очередь с состояниями и защитой от поздних результатов, задолго до dirty-триггеров. [Источник](https://github.com/tgenman/oko/blob/86357ef7a7a0b01e7e920c27e2a570453448c424/oko/store.py#L80-L97).

Непосредственная база перед первыми триггерами — `938018e044a98eda3a3c594f415a25404c20a270`. В `oko/storage/store.py:328–363` тот же выбор pending и переход в running; `SELECT` стоит перед `with self.db`, а `UPDATE` сам по себе не содержит `AND status='pending'`. Это НЕ алгоритм конкурентного захвата несколькими независимыми процессами. Код рассчитывал на владельца выполнения. [Источник](https://github.com/tgenman/oko/blob/938018e044a98eda3a3c594f415a25404c20a270/oko/storage/store.py#L328-L363).

Сериализация видна непосредственно у вызывающей стороны: `Runtime._actions = asyncio.Lock()`; в `run()` весь цикл допуска, reconciliation и выбора jobs находится под `async with self._actions`. Обработка запускается `asyncio.create_task`, а внешние ожидания происходят вне action lock; принятие результатов вновь использует его. Это обеспечивает параллельные внешние запросы без параллельных переходов состояния. [Источник](https://github.com/tgenman/oko/blob/938018e044a98eda3a3c594f415a25404c20a270/oko/reader/runtime.py#L1129-L1174).

Следовательно, отсутствие `SELECT FOR UPDATE` не было незакрытой проблемой, которую 20 октября решали триггерами. Это свойство старой модели одного владельца.

## 2. Что на самом деле было дорого

Перед `4850baa5` `Filters.sync()` выбирал **все** `items WHERE viewed=0`, для каждой публикации вычислял signature по версии содержимого, настройкам и конфигурации обработчика, читал сохранённую signature и статус job; затем решал, требуется ли отменить/создать pending-задание. `PublicationTheses.sync()` делал аналогичный полный обход, дополнительно читая актуальный результат фильтра и правила YouTube. [Фильтрация](https://github.com/tgenman/oko/blob/938018e044a98eda3a3c594f415a25404c20a270/oko/reviews/filtering.py#L23-L56), [тезисы](https://github.com/tgenman/oko/blob/938018e044a98eda3a3c594f415a25404c20a270/oko/reviews/theses.py#L24-L75).

Runtime вызывал эти проверки каждые примерно 0,5 секунды, ещё до `next_job`. Поэтому ускорить `SELECT jobs WHERE status='pending'` было недостаточно **для данной реализации**: статусы создавались и актуализировались дорогим предшествующим проходом. Полный пересчёт можно было заменить явными переходами из Python, но это требовало изменить именно слой инвалидации, а не только запрос выбора jobs.

Ключевое различие:

- `processing_dirty`: входы этой публикации могли измениться; нужно проверить, что следует делать.
- `jobs.status='pending'`: задание уже сформировано и ожидает исполнения/срока/допуска.

Dirty-публикация после проверки могла оставить готовый результат неизменным, отменить неподходящее задание, сделать новое pending или разблокировать тезисы. Триггеры НЕ выполняли LLM-работу и НЕ захватывали job.

## 3. 20 октября: одновременно dirty-триггеры и индекс pending

Коммит `4850baa579269ad9b3a625567614188980ac10e9`, 20 октября 13:49:37 МСК, впервые добавил SQL-триггеры. Полный `git log --all --reverse -i -G 'create[[:space:]]+trigger'` не обнаружил более раннего изменения с CREATE TRIGGER. Репозиторий не shallow.

В `oko/reviews/coordination.py:69–83,104–145`:

- изменения `items`, версий контента и результата фильтра добавляют ID в `processing_dirty`;
- `sync()` читает только эту таблицу, запускает Python `filters.sync([item])`, затем `theses.sync([item])`, затем удаляет отметку;
- комментарий подчёркивает `No suspension`, то есть отсутствие interleaving в середине обработки, а не использование row locking;
- `invalidate()` для изменения настроек заполняет ту же dirty-таблицу **прямо из Python**;
- обнаруженная при чтении потеря файла передаётся через `_repairs` и затем Python вставляет отметку.

[Источник](https://github.com/tgenman/oko/blob/4850baa579269ad9b3a625567614188980ac10e9/oko/reviews/coordination.py#L64-L145).

Это важный контрпример к гипотезе «триггер был единственным способом атомарно выставлять отметки в SQLite»: сам тот же модуль уже использовал прямые записи Python для части событий.

Точная граница: `Store.settings_changed()` вызывает `processing.invalidate(scope, owner)` внутри `with self.db` ([код](https://github.com/tgenman/oko/blob/4850baa579269ad9b3a625567614188980ac10e9/oko/storage/store.py#L680-L692)); `Filters.read()` и чтение тезисов вызывают `processing.repair(item)`, если ожидаемый готовый файл отсутствует/не подходит ([тезисы](https://github.com/tgenman/oko/blob/4850baa579269ad9b3a625567614188980ac10e9/oko/reviews/theses.py#L176-L179)). А `Filters.restore()` не ставит dirty напрямую: Python записывает `filter_restores`, на эту запись реагирует `processing_filter_restored`/`processing_restore_changed`, после чего Python вызывает sync ([restore/retry](https://github.com/tgenman/oko/blob/4850baa579269ad9b3a625567614188980ac10e9/oko/reviews/filtering.py#L126-L141)). Не следует ошибочно перечислять restore как прямую Python-запись dirty.

А в `oko/storage/store.py:119` **тем же коммитом** добавлен ровно предлагаемый пользователем механизм ускорения выбора:

```sql
CREATE INDEX IF NOT EXISTS jobs_pending_next
ON jobs(next,kind,item) WHERE status='pending';
```

[Источник](https://github.com/tgenman/oko/blob/4850baa579269ad9b3a625567614188980ac10e9/oko/storage/store.py#L118-L119).

Исторический отчёт разделяет результаты:

- неизменившийся reconciliation: 4 578 / 17 602 SQL на 104 / 400 публикациях → 1 / 1;
- выбор AI-job среди 20 000 завершённых: 60 239 → 301 VM-инструкция благодаря partial index;
- дополнительная стоимость записи из-за индекса и dirty-отметок измерена отдельно.

[Отчёт после слияния PR #59](https://github.com/tgenman/oko/blob/3ea37e2e/docs/verification/sql-background-54.md).

В первом коммите были ещё две группы триггеров: `telegram_read_dirty` и `source_configuration_*` (счётчик `sources-version`), чтобы ReadSync и обновление конфигурации источников не пересчитывали всё без изменений. Их функции — инвалидация/согласование; захват jobs они не реализуют. [Telegram](https://github.com/tgenman/oko/blob/4850baa579269ad9b3a625567614188980ac10e9/oko/collection/telegram/read_sync.py), [конфигурация](https://github.com/tgenman/oko/blob/4850baa579269ad9b3a625567614188980ac10e9/oko/subscriptions/subscriptions.py).

### Реально найденное влияние ограничений SQLite

Тот же отчёт фиксирует: первый прототип триггеров упал с `UNIQUE constraint failed` из-за наследования SQLite conflict policy внешнего UPSERT; понадобился собственный `ON CONFLICT DO NOTHING`. Это конкретная связь SQLite и сложности триггеров, но ограничение вызвало необходимость чинить выбранный подход, а не было причиной его выбора. [Отчёт](https://github.com/tgenman/oko/blob/3ea37e2e/docs/verification/sql-background-54.md).

### Особенно показательная последующая правка

Всего через 12 минут `5a1a4c5b9525c48cc01dfdb45aeea8c01308035d`, 16:05:18, **перенёс пересчёт списков из триггеров в Python**:

## 5. PostgreSQL: перенос существующей модели, а не конкурентная очередь

`3434cd088e82c2581b91d68d612805c9a7cd357e`, 25 октября 00:17:38, ввёл PostgreSQL. `003-projections.sql` начинается комментарием: "Native reader, processing, collection and source revision triggers. Each projection changes in the same transaction as its authoritative inputs." В отчёте указаны 145 нативных projection triggers. [Миграция](https://github.com/tgenman/oko/blob/3434cd088e82c2581b91d68d612805c9a7cd357e/oko/storage/postgres/003-projections.sql), [отчёт](https://github.com/tgenman/oko/blob/3434cd088e82c2581b91d68d612805c9a7cd357e/docs/verification/postgresql-2026-10-25/README.md).

Подсчёт `CREATE TRIGGER` в `003-projections.sql` коммита `3434cd08` даёт:

| Группа имён | Число | Назначение |
| --- | ---: | --- |
| `reader_v_*` | 107 | Версии ресурсов читателя, счётчики и производные состояния |
| `source_*` | 16 | Ревизия конфигурации источников |
| `journal_*` | 9 | Связи записей журнала и очистка прежних результатов |

Большинство перенесённых триггеров обслуживало протокол выборочного обновления читателя. Переустройство очереди само по себе не устраняет эти 107 триггеров: потребуются явные правила обновления версий/счётчиков или изменение способа их получения. Подсчёт имён не измеряет объём или стоимость выполняемой ими логики.

При этом `JobRepository.next_job()` сохранил обычный SELECT pending, чтение глобального `job-dispatch-generation`, UPDATE running; FOR UPDATE / SKIP LOCKED отсутствуют. [Источник](https://github.com/tgenman/oko/blob/3434cd088e82c2581b91d68d612805c9a7cd357e/oko/storage/job_repository.py#L176-L241).

`ProcessingWorker.tick()` по-прежнему работает под `execution._actions`; claim и снимок входов коммитятся вместе, затем запускается внешняя обработка, затем под action lock проверяются Store, допуск, generation и актуальность входа. [Источник](https://github.com/tgenman/oko/blob/3434cd088e82c2581b91d68d612805c9a7cd357e/oko/workers/processing.py#L32-L136).

Более того, PostgresConnection.claim_store() **явно запрещает второй Store на одной схеме**:

```python
# Data roots can differ while pointing to one PostgreSQL schema. Only
# one Store may recover and dispatch its persisted work at a time.
```

Берутся shared schema advisory lock против миграций и отдельный exclusive instance advisory lock. Второй читатель получает `Another Oko reader owns this database schema`. [Источник](https://github.com/tgenman/oko/blob/3434cd088e82c2581b91d68d612805c9a7cd357e/oko/storage/postgres_connection.py#L47-L60).

Это не только комментарий: `test_one_store_owns_recovery_even_with_a_different_data_root` проверяет отказ второго экземпляра и возможность преемника после закрытия первого. [Тест](https://github.com/tgenman/oko/blob/3434cd088e82c2581b91d68d612805c9a7cd357e/tests/reader/test_postgres_transactions.py#L256-L266).

Причина такой защиты видна в Store startup: все running jobs глобально переводятся в pending с увеличением generation. Допуск двух Store сделал бы обычный запуск второго вмешательством в активную работу первого. [Источник](https://github.com/tgenman/oko/blob/3434cd088e82c2581b91d68d612805c9a7cd357e/oko/storage/store.py#L122-L135).

Текущий поиск `rg 'FOR UPDATE|SKIP LOCKED' oko` результатов не дал. История добавлений этих конструкций в `oko` также не обнаружена. PostgreSQL row locks не были исторической заменой триггерам и не стали основой claim в проверенной реализации.

## 6. Что это означает для гипотезы пользователя

Гипотеза содержит разумное направление перепроектирования: PostgreSQL способен дать независимым воркерам row-level claim по индексированному status. Однако исторически:

1. Статусы и выбор pending существовали с 8 октября.
2. Индекс pending появился вместе с первыми триггерами, а не был ими заменён.
3. Синхронизацию job claim обеспечивал Python-владелец, триггеры её не обеспечивали.
4. Dirty-триггеры отвечали за то, какие входы нужно пересогласовать до выбора pending.
5. Большинство позднейших триггеров обслуживали UI-версии/счётчики/журнал, не распределение работы.
6. Переход PostgreSQL сознательно сохранил одну работающую копию Store и усилил её защиту; возможностей PG для многопроцессной очереди не использовал.

Поэтому причина не сводится к SQLite. Выбранный подход развивался как поддержание производных данных при записи поверх прежнего приложения. Возможность сделать это явно в Python видна прямо в истории. Исходные обсуждения устанавливают контекст выбора: локальная архитектура → оптимизация повторных обходов → выборочные UI-обновления → перенос действующих механизмов на PostgreSQL. Они не содержат отдельного обоснования, что SQLite не позволял реализовать это в Python.

## Граница между происхождением и возможным перепроектированием

У SQLite действительно одна одновременно пишущая транзакция, а у PostgreSQL есть row locks и `FOR UPDATE SKIP LOCKED` для нескольких потребителей очереди. Но это разные механизмы с разными ролями:

- Статус и индекс находят уже подготовленную работу.
- Захват строки предотвращает одновременное присвоение задания разными транзакциями.
- Инвалидация определяет, какие результаты/задания стали неактуальны после изменения входов.
- Версии и счётчики сообщают браузеру об изменившемся представлении.

Конкурентный допуск в этой реализации обеспечивали единственный владелец и Python-блокировка; row-level claim не использовался. Сами триггеры не снимают ограничение SQLite на число пишущих транзакций.

Технически Python мог атомарно выполнять основные и производные записи и на SQLite — это доказано `invalidate()` первого dirty-коммита и переносом digest перед commit в #56. Для PostgreSQL вариант с Python-записями, индексированными статусами и коротким row-level claim возможен, но заменить только SELECT недостаточно для нескольких независимых экземпляров: потребуется пересмотреть глобальное startup-восстановление running jobs, владение попытками/lease, допуск и отмену, приём поздних результатов и актуализацию входов. Это перечень затронутых обязанностей из исследованного кода, а не готовый план реализации и не утверждение, что проекту необходимы несколько процессов.

Текущую архитектуру одного экземпляра можно упрощать переносом trigger-логики в явные Python-транзакции и без внедрения многопроцессных воркеров. Польза/стоимость такого изменения здесь не измерялась; исторические before/after сравнивали полный обход с поддержанием отметок, а не два варианта их записи — SQL-trigger и Python.

Первичные справочные источники: [SQLite transactions](https://www.sqlite.org/lang_transaction.html), [SQLite triggers](https://www.sqlite.org/lang_createtrigger.html), [PostgreSQL SELECT locking clause](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE).

## Дополнение: откуда взялась модель единственного процесса

Она появилась раньше и очереди обработки AI, и триггеров, как исходный продуктовый выбор локального приложения:

- В `.scratch/oko-product/architecture-proposal.md` уже до первого рабочего выпуска описаны один локальный Python-процесс (UI/API/планировщик/исполнители), SQLite как состояние и очередь одной базы, повторный запуск открывает существующее Око. [Исторический документ](https://github.com/tgenman/oko/blob/86357ef7a7a0b01e7e920c27e2a570453448c424/.scratch/oko-product/architecture-proposal.md).
