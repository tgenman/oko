## Что реализовано

- HTTP получает ReaderApplication. Сценарии настроек, подписок, папок, истории,
  подключений, просмотра, завершения чтения и исходов команд вынесены из Runtime.
- Доменное сохранение выполняют SubscriptionService, ReadingService,
  ConnectionService и CommandJournal. Чтение идёт через ReadingQueries/ReaderFacts,
  сохраняя пакетные SQL и request-local cache. SQL подписок выделен в
  SubscriptionRepository; модели и контракт импорта сохранены.
- Execution владеет допуском, Store/epoch и внешними ожиданиями; JobControl —
  текущими задачами, отменой, повтором и очисткой. Их собирает create_app до
  запуска Runtime. Планировщик остаётся прежним до следующего этапа.
- Один ReadingConnection и общий короткий SQL access_lock используются
  транзакциями и синхронными проекциями. Настройки, доменная инвалидация и
  изменение Job сохраняются одним commit. Вложенный repository commit не
  фиксирует часть действия; пойманный rollback прерывает весь внешний scope.
- Пересчёт ReaderVersions перед commit сохранён. Послеcommit fault hooks
  отложены до фактической фиксации. Финальная проекция остановки имеет отдельный
  retained_store до закрытия соединения, без открытия допуска новым командам.
- Медиа передаётся порциями с fd, открытого под SQL lock. Удаление файла после
  подготовки ответа не ломает отправку; fd закрывается в ASGI finally.

HTTP/OpenAPI, схема пользовательской базы и версии зависимостей не менялись.
Рабочая установка, её настройки, аккаунты и данные в #113 не использовались.
Исходная dirty-ветка пользовательского checkout не переносилась в worktree.

## Уточнение блокировок по результатам проверки

Длительная очистка клиента уже координировалась через action mutex. Использовать
его для новых GET оказалось неверно: чтение блокировалось до окончания close,
хотя SQL-транзакция давно завершилась. Существующий HTTP-сценарий требует
доступности чтения во время такой очистки.

Поэтому разделены две ответственности: Execution._actions сохраняет порядок
действий/cleanup; единственная SQL-блокировка ReadingConnection.access_lock
охватывает только синхронные участки и освобождается до внешних ожиданий.
Вторая блокировка SQL и второе соединение не добавлялись. RLock не различает
asyncio Task, поэтому внутри защищённых участков запрещены await/AsyncWith/AsyncFor.
Отдельная AST-проверка закрепляет это условие для transaction и защищённых проекций.
Действующее устройство описано в [архитектуре слоёв](../architecture/application-layers.md).
