Первый полный интеграционный прогон FAIL за 320,93 с: HTTP и десятки Python-сценариев ждали материалы до timeout. Короткий Demo HTTP probe обнаружил фактический `KeyError: 'full'` в Store.save. Pending-публикация имеет complete=False и не содержит full; недавно добавленная защита старой полной копии обращалась к этому ключу при первой загрузке.

Независимое ревью не нашло ослабления защиты старого содержимого. Рабочие данные для диагностики не использовались.

## Почему локальные ускорения почти не меняли полный результат

Примерно 26 с вне параллельных наборов + максимум из Python 198 с, browser 193 с и tools 157 с дают около 224 с. Эти три времени не складываются. Если ускорить только Python до 178 с, browser 193 с ограничит выигрыш примерно пятью секундами. Ускорение одного browser до 175 с оставит Python 198 с на критическом пути.

Старый разрыв tools-процессов в 49 с относится к предыдущему дереву. На свежем успешном прогоне tools заканчивают за 148,87 и 156,58 с; это уже не главный хвост. Python-процессы: 197,63 / 161,77 / 161,84 / 185,95 с. Идеальная перебалансировка Python сама по себе всё равно упрётся в почти равное browser-время.

Наиболее дорогие Python-файлы в успешном прогоне: actions_cost 31,90 с, reading_cost 28,82 с, collection/test_telegram 27,30 с, docker_release 24,55 с, codex_bridge 23,77 с. Tools hooks 49,04 с, governance 41,66 с и frontend_builder 39,54 с дорогие, но весь tools-набор заканчивается раньше двух главных наборов.

## Фазы двух тяжёлых Python-файлов

Временный pytest-plugin оборачивает только существующие функции подготовки и TestClient, записывает wall/process CPU. Он не меняет ответы, Store, критерии и исходники тестов. Изолированный совместный запуск material_read_cost + actions_cost: **26 PASS за 17,08 с**. В полном прогоне их worker-wall времена 18,53 и 31,90 с; сумма 50,43 с — не elapsed полного набора, файлы могли идти параллельно.

| Фаза | Вызовы | Wall | CPU процесса |
|---|---:|---:|---:|
| Подготовка library | 26 | 4,01 с | 2,63 с |
| prepared, включая часть library | 4 | 3,78 с | 2,66 с |

prepared и library пересекаются, поэтому складывать все строки нельзя. Только непересекающиеся library + startup уже занимают 7,8 с. HTTP — около 10% общего времени этого запуска; сборка app — около 22 мс на приложение. Следующий резерв Python следует искать в повторной подготовке/старте и устройстве матриц, а не предполагать, что большая часть времени уходит на HTTP-валидацию.

## Накладные расходы кликов

В отдельном временном harness из существующего performance-теста: 400 материалов, idle, 80 настоящих кликов на вариант, тот же MutationObserver подтверждает выбранный материал и 40+40 samples. Первая часть с обычным locator.click, вторая с force=true. Измеряется только click-фаза, без подготовки/старта/снимков:

| Вариант | 80 кликов | p95 first/repeat |
|---|---:|---:|
| Обычный | 4,819 с | 26,6 / 28,0 мс |
| force=true | 2,746 с | 26,4 / 27,0 мс |

Это показывает заметную стоимость actionability-ожиданий Playwright сверх времени приложения. Общую длительность этих двух тестов сравнивать нельзя: второй использует уже подготовленный immutable template. Режим force не перенесён в основной набор: он требует отдельной проверки всех active/idle профилей и сохранения пользовательских гарантий. Даже устранение этих двух секунд на 80 кликах само по себе не уберёт Python с критического пути.
