# №05: независимая синхронизация прочитанного Telegram

2026-10-10. База: `2d386f0`.

## Поведение

Собственный Telethon-клиент Око читает серверную границу и проверяет существующие ID истории перед накопительным подтверждением. Автопрочитывание даёт право после полного сохранения текста/медиа; выключенный режим — после явного «Просмотрено». Подтверждение не удаляет непросмотренный оригинал. Просмотр позднего поста немедленно удаляет его локальный контент, но Telegram ждёт ранние сообщения. Полностью сохранённый ранний пост получает приоритет подтверждения перед загрузкой позднего.

Начало импорта фиксируется в курсоре. Верхняя граница старой истории фиксируется при первой проверке и не расширяется при последующих запусках. Отдельное разрешение read_history по умолчанию выключено; без него старое непрочитанное задерживает продвижение. Изменение режима/транспорта, закрытие последней вкладки и остановка отменяют собственный запрос и запрещают публикацию устаревшего результата. Уже отправленный Telegram-запрос нельзя отозвать: при неизвестном исходе очередь сохраняется и следующий запуск сверяет серверную границу.

Проверяется фактическая история страницами по 100 ID. Числовые пропуски не объявляются отсутствующими сообщениями без завершённой проверки соответствующего диапазона. Известные допустимые ID, отсутствующие в проверенном диапазоне, получают служебную отметку missing и не создают вечное ожидание; они не используются как ложная серверная граница. Повторная фактическая выдача такого ID возвращает его в проверку. Forum topics по-прежнему отвергаются до отправки ack.

Обычный положительный результат helper принимается; BoolFalse проверяется серверным readback, поскольку повтор уже прочитанной границы может вернуть False. max_id=0 не отправляется. Дополнительные mentions/reactions не очищаются. Семантика накопительного max_id сверена с [Telethon 1.45.0](https://docs.telethon.dev/en/stable/modules/client.html?highlight=GetHistoryRequest); граница берётся через [messages.getPeerDialogs](https://core.telegram.org/method/messages.getPeerDialogs).

## Владение состоянием

`collection/telegram/read_sync.py` скрывает права, план безопасного продвижения, проверенные отсутствующие ID и состояние очереди. SQLite содержит feed/message ID, основание saved/viewed, since, initial, confirmed, status/signature/error и задания повторов. Тексты в эту очередь не попадают. Права явного просмотра записываются вместе с tombstone до физического удаления; старые tombstones также импортируются без восстановления контента.

Store сохраняет и удаляет материалы, Runtime владеет допуском/отменой/внешними вызовами, worker использует Telethon и отдаёт только служебные поля read state. Read-задания отдельны от сбора и готовности источников. API status содержит telegram_reads; UI показывает причину ожидания/ошибку и действующие режимы фида.

## API и процессные проверки

Согласованная граница — HTTP API с настоящими временными SQLite/файлами и подменённым внешним Telegram. Проверены:

- просмотр позднего ID, немедленное удаление и сохранение очереди после перезапуска;
- полноценные и прерванные медиа при автопрочитывании, отсутствие локального удаления;
- старая история без разрешения и с разрешением, внешняя отметка без удаления оригинала;
- неизвестный результат ack, ошибка/повтор и восстановление без текста;
- подтверждение всего состава папки через общий viewed_set;
- поздний ответ проверки истории после stop/close/смены транспорта;
- старое хранилище без таблиц очереди, удалённый источником пост, страницы истории и приоритет раннего полного поста;
- настоящий дочерний worker с подменой только Telethon SDK: BoolFalse с подтверждённым readback и с отказом. Исходные Telegram-тесты сохранены.

Первая проверка позднего просмотра воспроизвела отсутствие очереди до реализации. Последующие проверки воспроизвели отсутствие обновления внешней границы, потерю прав старых tombstones и вечное ожидание удалённого ID; после исправлений проходят. Сбои неправильных маршрутов диагностического теста и неполной имитации окна SDK исправлены в тестовом наборе, не выдаются за дефекты продукта.

## Браузер A

На синтетическом временном источнике проверены подписи настройки auto_read/read_history и выключенное разрешение старой истории. После просмотра позднего поста UI показывал «Ожидание синхронизации Telegram · источники 1/1 · Ожидает более раннее сообщение Telegram». После просмотра раннего через API — «Готово · источники 1/1», ноль карточек. Эта проверка не использовала личный контент.

## Ограниченная настоящая проверка

Через собственный LocalTelegram выбраны существующие приватный broadcast-канал и обычная группа Chat. Проверены реальные read_state, read_window и положительный max_id через acknowledge с readback. В канале окно вернуло пять ID, в группе три. Подтверждалась **только уже прочитанная серверная граница**, её readback остался прежним; новые непрочитанные сообщения и старый долг не отмечались. Это подтверждает реальные методы и их идемпотентный путь, но не является экспериментом перехода unread→read на личной истории. Такой переход и порядок проверены управляемым API-набором.

Новая авторизация не создавалась, секреты/сессии не копировались, MCP не вызывался. Содержимое и приватные ID/названия не включены в fixtures/отчёт; временный spool и диагностические скрипты удалены. Настоящая проверка не отправляла сообщения и не запускала AI.

## Исправления ревью

Standards обнаружил P2: Runtime вручную завершал транзакции неактуального read-задания. Завершение перенесено в ReadSync.suspend; Runtime больше не обращается к db/commit в новом сценарии.

Spec обнаружил P2: уже приобретённые saved-права оставались активными после выключения auto_read. В текущем выключенном режиме запрос теперь допускает только viewed-права; auto_read входит в проверяемую подпись. API-регрессия сначала воспроизвела ack29 при просмотре только11, затем подтвердила ack11 и ожидание явного просмотра29 после перезапуска. Ранее подтверждённая серверная граница не откатывается.
