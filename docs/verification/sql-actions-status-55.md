В каждой библиотеке четыре равных фида; выбранная папка содержит 26/100
публикаций. Отдельная HTTP-проверка оставляет в выбранной папке 26 публикаций
и увеличивает остальные с 26 до 100: стоимость подготовки не растёт, менее
400 SQL. Состав подтверждения по-прежнему включает скрытые, незагруженные и
нечитаемые публикации; чужие карточки не строятся.

Статус и просмотр имеют HTTP-бюджеты соответственно менее 100 и 150 SQL.
Просмотр возвращает 200, материал становится 404, остальные карточки сохраняются.
SQL HTTP измеряется по ContextVar запроса отдельно от фона. На неизменившемся
статусе первый запрос читает 104 заголовка, второй — ни одного; тело проблемы
не переписывается. Изменение файла перечитывает один заголовок и корректно
завершает ту же проблему. updated_at сохраняет значение времени чтения.

Диагностический кеш хранит только title/full/captions/reason. Его ключ включает
путь версии, inode, mtime_ns и размер. Выпавшие элементы удаляются при снимке,
просмотр сразу освобождает запись; описание и текст не дублируются в памяти.
Чтение статуса отделено от записи reconciliation; повторно используются настройки,
привязки, ограничения YouTube и ReadSync. Принадлежность материалов читается
только для объектов проблем, а не для всей библиотеки.

## История и журнал

На 20000 служебных записях проверены настоящее HTTP-действие просмотра и
повторная установка индексов при открытии базы. Работа просмотра ограничена
5000 VM-инструкциями. Промежуточная проверка выявила 400500 инструкций:
ReadSync собирал историю не относящегося к Telegram фида. Ограничение фидов
по transport до сборки конфигурации устранило лишний обход.

Статус на 20000 успешно завершённых заданиях первоначально стоил 540200
инструкций. Частичный индекс активных заданий и ограничение внутренней сводки
снизили его до 100100; оставшееся чтение архива было планом INNER JOIN ошибок
истории. Поиск от записей самой истории по уникальному ключу задания устранил
его; регрессия требует менее 10000 инструкций на весь HTTP-статус. Ошибочные
завершённые задания сохраняются в текущем состоянии, успешный архив не участвует.

Отдельные SQL-измерения с шагом progress_handler=100:

| Операция | Без индекса | С индексом |
| --- | ---: | ---: |
| История по item, 20000 записей | ~60000 | <100 |
| Отмена задания по item, 20000 записей | ~60100 | <100 |
| Последний исход по identity, 3000 команд | ~18102000 | ~102000 |

HTTP-проверка создаёт 3000 идентичностей с двумя исходами у каждой, включая
последние succeeded/failed/unknown/pending. Видны 2999 актуальных проблем,
старые исходы не возвращаются, два неизвестных исхода сохраняются после
перезапуска. Весь запрос ограничен 1,5 млн VM-инструкций; повторный статус
не переписывает те же проблемы. Существующие проверки сохраняют очистку
по сроку и идентичность завершённых записей.
