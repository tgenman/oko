## Изменения и покрытие

Telegram reload-сценарии вместо фиксированных пауз ждут завершения collection через существующий HTTP interface. `ReaderClock` переводит только часы синтетического сценария, оборачивает существующий `reader_advance`, вызывает оригинал и ждёт два реальных прохода Runtime. Таймаут 2 с остаётся ограничением отказа; исходный callback восстанавливается в finally. Для отрицательных retry-сценариев сначала подтверждается terminal fetch error, затем переводятся часы и наблюдаются реальные проходы планировщика. В одном случае дополнительно проверяется, что HTTP operations остались terminal error. Работа Runtime/Store, asyncio.sleep и ответы приложения не подменяются.

Синтетические functional web fixtures явно используют существующий `configure_fast_web` (10 rps) вместо продуктовых 2 rps: это временное тестовое хранилище. Бюджеты ограничителя и рабочие настройки не меняются. Ожидания реальных задач сохранены; сокращены фиксированные паузы и ненужные интервалы синтетической сети.

Новая Node-матрица вызывает настоящий MenusOwner и generated SDK через управляемый Fetch adapter: 102 комбинации полей, scope, save/reset, unchanged/new/ABA; 4 поздних успеха/отказа после смены контекста; 3 failed save/discard сценария. Итого 109. Модели данных типизированы, новых production interfaces нет, приватные счётчики владельца не читаются. Для позднего контекста проверяется сохранение его текущего сообщения; select сам по себе не обещает пустое сообщение.

Удалены три повторных browser-сценария: delayed interval save, failed interval discard и late Telegram reset ABA. Реальные HTTP представители сохранены в Telegram limit-файле (delayed navigation и failed command discard), обычный reset обоих числовых полей остаётся в браузере. Полная матрица save/reset проверяется в Node. Семь целевых Playwright-сценариев сохраняют настройки, наследование, reopen/reset, валидацию HTML, responsive layout, соседние черновики и HTTP-очистку ошибок. Другие сценарии focus/close/navigation/late replies не менялись.
