# Сокращение чтений при открытии материала

Дата: 2026-10-20. База до изменений: `ad56948e228056adb9df66b3d9665bd1ee1cd01b`.
Изменения находятся в рабочем дереве; коммит, публикация и обновление рабочего
Docker-выпуска не выполнялись. Личная база и настоящие источники не использовались.

## Что изменено

- Открытие не вызывает обслуживание таймеров, очистку истории и обновление
  runtime-метаданных. Переходы публикует существующий Runtime, включая режим
  выключенного сбора. Очистка выполняется ограниченными порциями.
- Для изменённых частей HTTP получает общий ограниченный набор входов:
  выбранные публикации, версии, задания, нужные фиды, настройки и параметры
  проверки результатов. Снимок живёт только в одном синхронном чтении.
- Текст собирается прямо из текста и метаданных. Полный материал с фильтром,
  тезисами и медиа больше не собирается ради удаления этих полей из ответа.
  История подключения фида для открытия не читается.
- Версии разных видов получаются одной выборкой; актуальность сигнатур,
  допуск ранее принятых результатов и retained digest сохранены.
- Вне HTTP-снимка прежние точечные запросы сохранены. Это существенно для
  стоимости записи и обхода исторических версий.
- UI и публичная схема API не менялись. Паритет проверен для pending/available,
  demo, RSS, YouTube, Telegram web/client/legacy, а также фильтра, тезисов,
  медиа и предыдущей версии.

## Стенд и воспроизведение

До: локальный clone `ad56948` в `/tmp/oko-read-short-before`.
После: изолированное дерево задачи в `/tmp/oko-read-short-final-check`.
Оба используют одинаковые Python/Node/Chrome и одни и те же seeder, измеритель,
данные и фронтенд из базы. Прежние пользовательские UI-правки исключены из обеих
проверочных копий. Новый код проверялся отдельно от грязного исходного checkout.

Основные воспроизводимые команды из соответствующего checkout:

```sh
.venv/bin/python -m pytest -q -s tests/reader/test_material_read_cost.py
./scripts/check browser --in-place --compact --files tests/browser/test_reading_performance_http.ts
```

Новый cost-тест копируется в baseline без изменения его продуктового кода.
Он ожидаемо падает на прежних бюджетах, сохраняя измерения до assert.
После изменений проверяется тот же настоящий HTTP interface через TestClient.
Trace/файлы относятся к конкретному запросу, не к работе Runtime.

Для браузера — 104/400 материалов, по 40 первых открытий и 40 повторных на каждом
размере, отдельно idle и активная синтетическая обработка с задержкой 150 мс.
Итого 320 открытий на версию кода. Измеряется capture click → появление текста
выбранной публикации; ожидание actionability и прокрутка Playwright в метрику
не входят. Это не холодный дисковый кэш. Текст около 2,1 KB, без медиа.

Дополнительные измерители сохранены рядом с raw JSON:

```sh
OKO_CONCURRENCY_OUTPUT=/tmp/oko-tabs node --require tsx/cjs --require ./scripts/register-browser-typescript.cts --test --test-concurrency=1 docs/verification/material-read-shortening-data/concurrency.cjs
PYTHONPATH=. .venv/bin/python docs/verification/material-read-shortening-data/contention.py /tmp/contention.json
PYTHONPATH=. .venv/bin/python docs/verification/material-read-shortening-data/write-cost.py /tmp/write.json
```

Перед запуском concurrency нужно создать каталог вывода. Тот же измеритель
копируется в baseline. Реальные вкладки — 1/5/20, 104 материала, по 20 разных
открытий на вкладку; синтетическая обработка с задержкой 1 с остаётся активной
до и после серии. Это отдельный профиль нагрузки от основного benchmark.
ASGI contention probe отдельно от браузера измеряет HTTP-задержки, ожидание
`_actions` и lag event loop; он не включает TCP или рендеринг.

## SQL и файлы: один и тот же действующий endpoint

Сравнивается `/api/v3/reading/materials/{item}`. Числа старого совместимого
`/api/v3/materials/{item}` не смешиваются с новым открытием.

| Материал, на библиотеке 104 и 400 | До | После |
| --- | ---: | ---: |
| Обычный: SELECT | 31 | 7 |
| С фильтром, тезисами, медиа и прежней версией: SELECT | 39 | 7 |
| Все события SQL trace: обычный / с обработкой | 40 / 48 | 7 / 7 |
| DML-события trace при открытии | 7 | 0 |
| Повторные открытия одного файла | 2 | 1 |
| Открытия файлов: обычный / с обработкой | 2 / 4 | 1 / 3 |

DML trace до изменений включает попытки служебных записей и повторные callback
триггеров. Это не семь сетевых обращений и не доказательство семи физических
изменений страниц БД. В итоговом чтении DML отсутствует.

Семь SELECT итогового открытия: версии четырёх ресурсов; публикация с её
текущими метаданными; задания публикации; её исторические версии; её фид и
привязка; настройки трёх уровней одной выборкой; параметры проверки результатов.
Исторические версии и задания — отдельные коллекции, их не объединяют JOIN,
который размножает строки. Чужие материалы и история подключения не читаются.

Бюджет <=8 SELECT подтверждён и для обработанного материала. Тело каждого
ресурса сверяется с соответствующими полями прежнего ответа, а не только со
схемой. История из 1000 версий вне HTTP проверяется отдельно: <=2 запросов
на выдачу предыдущих версий, без SELECT текущего номера на каждый элемент.

Неизменившийся пакет со списком и четырьмя частями открытого материала:

| Библиотека | SQL до → после | Файлы после | Размер ответа до/после |
| --- | ---: | ---: | ---: |
| 104 | 17 → 2 | 0 | 10 408 B |
| 400 | 17 → 2 | 0 | 37 049 B |

Сокращение числа обращений не делает пакет константным: его метаданные по-прежнему
растут с выбранным списком. VM на 400 в одиночном замере: примерно 18 300 →
18 800, то есть заметного сокращения работы SQLite здесь не показано. Содержимое
не пересобирается, но сравнение большого набора ID/версий остаётся работой.

## Время открытия

Финальный изолированный прогон: `20261020T161957Z-df849150`, 4 latency-сценария,
320 открытий; перед ними отдельно прошли два функциональных сценария версий.
До — `20261020T155120Z-88514d01`. Значения p95, первое / повторное открытие:

| Материалов / фон | До, мс | После, мс |
| --- | ---: | ---: |
| 104 / idle | 17,9 / 18,0 | 18,1 / 17,7 |
| 104 / обработка | 17,8 / 18,0 | 18,2 / 18,3 |
| 400 / idle | 34,0 / 33,4 | 30,8 / 29,7 |
| 400 / обработка | 34,4 / 32,1 | 34,0 / 29,9 |

Все восемь p95 ниже 200 мс. Большого ускорения одиночного открытия не показано:
серверная работа уменьшилась, но в этом стенде заметную долю занимает браузер.
Небольшие различия не считаются статистически доказанным выигрышем.

Дополнительный стресс с реальными одновременными вкладками, 104 материала:

| Вкладки / открытия | До p95, мс | После p95, мс |
| --- | ---: | ---: |
| 1 / 20 | 17,3 | 16,7 |
| 5 / 100 | 85,1 | 44,8 |
| 20 / 400 | 285,6 | 496,3 |

20 активных вкладок — нестабильный режим на этой машине. Промежуточный вариант
дал 247,4 мс, итоговая серия — 496,3 мс; отдельные повторы baseline и итогового кода остановились
по существующему 5-секундному таймауту click. Порог не повышался. Стабильное
ускорение или p95 <200 мс на 20 вкладках **не подтверждены**. Эти данные не
подменяются более удачным промежуточным прогоном.

Серверная ASGI-проба выполняется отдельно; её raw результаты находятся в
`before-contention.json` / `after-contention.json`. Она позволяет отличить
ожидание `_actions` от задержки планирования event loop, но не заменяет TCP
и браузерный benchmark. Короткие серии и p95 малого числа lag-сэмплов не
используются для доказательства устранения всех блокировок.

[Просмотренный скриншот итогового стенда](material-read-shortening-data/after-400-active.png).
Один удачный короткий замер SQL не используется как доказательство ускорения UI.

## Цена записи

Изменение `originals` одного фида вместе с согласованием его настроек:

| Материалов / выбранный фид | SQL до → после | VM до → после | Wall time, один замер до → после |
| --- | ---: | ---: | ---: |
| 104 / 26 | 1316 → 926 | 19 400 → 14 900 | 19,8 → 24,8 мс |
| 400 / 100 | 4942 → 3442 | 73 000 → 56 100 | 80,8 → 77,2 мс |

Wall time одиночных запусков шумный; уменьшение каждого времени не заявляется.
Промежуточный вариант увеличивал VM из-за широких JOIN вне HTTP-снимка; это
исправлено возвращением точечных fallback. Промежуточные измерения сохранены
в `exploratory-after-write.json`, итоговые — в `after-write.json`.
Само обслуживание Runtime вынесено из чтения, а не объявлено бесплатным.

## Проверки, ревью и ограничения

- Исходный browser benchmark: `20261020T155120Z-88514d01`, 4 passed / 320 открытий.
- Первые cost-тесты на baseline воспроизвели превышение новых бюджетов: 40/48
  trace вместо 7; rich fixture сначала выбирала чужой filter-job, затем была
  исправлена явным выбором принадлежащего материалу задания.
- Первый широкий pytest из sandbox: 428 passed / 24 failed. 22 падения были
  связаны с запрещёнными сокетами/дочерними серверами; два — с устаревшим
  ожиданием конкретных отдельных запросов jobs. Прогоны с разрешёнными
  loopback/Chrome выполнены в изолированном checkout.
- Первый isolated all `20261020T160142Z-3e0533d9`: contracts/types/build/HTTP,
  browser, tools и остальные наборы PASS; Python 607 passed / 2 failed из-за
  слишком широкого подсчёта запросов jobs в проверке legacy endpoint. Счётчик
  исправлен с учётом отдельной истории/fetch. Повтор
  `20261020T160627Z-e757b74e` — целевые Python PASS.
- Второй isolated all `20261020T161419Z-f056f99e`: Python, contracts, types,
  build, HTTP, tools и остальные наборы PASS; browser имел одно падение
  предположения о немедленной тишине после готовности карточки. Runtime мог
  ещё публиковать финальный статус запуска. Проверка теперь требует две
  фактически неизменившиеся проверки в прежнем временном бюджете.
- После второго all исправлены найденные независимым reviewer повторные
  SELECT текущего номера внутри обхода истории. Добавлена регрессия 1000
  версий. Целевой повтор `20261020T161857Z-97a700a8`: contracts, types,
  Python и browser PASS. Отдельный pytest окончательного кода: 37 passed.
- Окончательная проверка нового ожидания тишины и серии latency:
  `20261020T161957Z-df849150`, browser/types PASS. Две функциональные проверки
  и четыре performance-сценария выполнялись последовательно.
- Mypy: 81 source files PASS. Независимый reviewer подтвердил сохранение
  source/access, signatures, retained digest, версий и владения. Найденный
  N+1 устранён и повторно проверен без новых замечаний.

Полный all без падений на самой последней редакции не заявляется: после
локальных исправлений повторялись затронутые наборы. Исторические неудачные
и параллельные latency-серии сохранены; они не подменяют финальный benchmark.
