# Управление работой Око

ReaderApplication выполняет действия читателя через сервисы и узкий JobControl.
Execution хранит общий допуск и внешние ожидания. Три независимых воркера владеют
фоновыми попытками, Store — SQLite, файлами и восстановлением. Host отвечает за
время жизни процесса. [Полная схема и транзакции](application-layers.md).

Это разделение #114 заменяет Runtime над пайплайном из #89. Публичный HTTP,
правила присутствия вкладок и смысл «выключить»/«остановить» сохраняются.
Рабочее переключение всех трёх воркеров выполняется вместе в #115; подготовка
целевого кода не обновляет рабочую установку.

## Действия и остановка

ReaderApplication скрывает полный сценарий «Просмотрено», завершения папки,
переключения доступа и удаления фида. Контроллер проверяет форму/сессию и переводит
исход в HTTP; он не согласует поколения, отмену и очистку вручную.

Доменная запись и изменения Job выполняются одной короткой транзакцией. Для
просмотра сервис удаляет принадлежности, инвалидирует содержимое и недостижимые
зависимости; JobControl в том же контексте отменяет работу и ставит очистку.
После commit выполняются ожидание отмены и файловая очистка. Сбой отмены заданий
откатывает всю команду. Общая статья сохраняется, пока нужна другому корню;
цикл ссылок не удерживает себя после удаления последнего читаемого корня.

Остановочный intent сразу закрывает новый допуск. JobControl инвалидирует
поколения до ожидания отмены. Даже адаптер, подавляющий CancelledError, не может
восстановить удалённый материал или принять результат старого Store.
Затем Host останавливает кроны, завершает читательскую проекцию и закрывает Store.
Финальный снимок использует retained_store и не открывает доступ новым командам.

Execution._actions сохраняет порядок действий/lifecycle; SQL access_lock —
отдельная короткая блокировка одного соединения. Во время длительного
Telegram.close SQL свободен: материалы и настройки остаются доступны GET.
Исчезновение последней вкладки не продлевает grace повторным закрытием.
Выключение Око останавливает сбор/обработку, сохраняя HTTP и содержимое:
[питание](work-power.md).

## Внешние проверки

`oko/execution.py::_ExternalCheck` регистрирует ожидание, снимает регистрацию
при завершении и повторно проверяет Store/допуск/epoch при приёме. Сеть выполняется
вне action mutex и SQL-транзакции. Сценарий владеет валидацией, таймаутом,
проверкой личности и последовательностью шагов подключения.

Подключение Telegram сохраняет исходный Store; финальный допуск использует
поколение последнего запроса сведений. Неуспешная проверка профиля может записать
недоступность только в исходном актуальном контексте. Прерванное подключение
требует нового действия, поздний ответ не создаёт фид.

Сохранение параметров Codex после каталога проверяет Store и допуск, сохраняя
прежнюю политику epoch. Готовое и уже начатое выполнение защищено ADR-0001.
RSS и клиентский Telegram передают настоящую отмену запроса; проверки llama.cpp
и Codex переводят её в существующую ошибку действия; web preview передаёт отмену.
Рефакторинг не унифицирует эти разные пользовательские исходы.

## Сбор и ограничения

CollectionWorker владеет common/personal/collection lanes, отдельными media/captions
слотами и заданиями read sync каналов. У Telegram-профилей изолированы user ID,
lock, generation и spool. Проверка подключения использует клиент без сбора.
FloodWait сохраняется для аккаунта, освобождая остальные lanes; подтверждённая
граница прочитанного сохраняется при частичном успехе и перезапуске. Группы/темы
не поддерживаются, каналы web/client и альбомы сохранены.

TelegramHTTP общий для фоновых и пользовательских проверок: сохранены глобальный
бюджет HTML и отдельные бюджеты серверов медиа, включая переходы. Настройка
Telegram Request Limit применяется без отмены активного запроса. Deadline 429
сохраняется, ручное обновление его не сокращает; Retry-After принимает секунды и
HTTP-date. MTProto FloodWait остаётся отдельным ограничением.

Обычный сбор догружает неполное; полная копия не переполучается автоматически
только для обнаружения правок. Явная перезагрузка получает новое описание и затем
медиа, соблюдая допуск. Текст сохраняется при ошибке одного вложения; временная
ошибка отдельной Job повторяется с сохраняемым backoff, постоянная требует
явного основания. Подтверждённый тип channel сохраняется при обновлении web config.
Подробные продуктовые правила: [последнее состояние](latest-publication.md).

## Чтение и проверка

ReadingQueries/ReaderFacts собирают синхронный снимок. Совпадающее тело проблемы
не переписывается; принадлежности читаются пакетно только для нужных объектов.
Архив успешных Job не участвует в текущем статусе. Подтверждение завершения
сравнивает точный состав, включая скрытое и ещё не загруженное.

Основная приёмка — существующий HTTP с временной SQLite, синтетическими
источниками и моделями; UI — Playwright. Проверяются остановка, поздние ответы,
совместные зависимости, чтение во время очистки, поколения и восстановление.
[Фактические результаты #114](../verification/pipeline-workers-114.md).

История решений и проверок прежнего Runtime сохранена в
[документе до #114](https://github.com/tgenman/oko/blob/2c8c9a0e19c7e4870411f31b6d02d07f14511a1e/docs/architecture/reader-work.md)
и связанных с ним отчётах; прежние имена модулей и групповые сценарии не являются
границами целевого кода.
