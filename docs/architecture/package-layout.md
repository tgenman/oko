# Пакеты Око и организация тестов

## Код

- `oko/reader` содержит HTTP-контракт, DTO и wire-проекции; `oko/application` —
  пользовательские сценарии ReaderApplication.
- `oko/services` содержит доменные операции и запросы; `oko/domain` — общие ошибки,
  подготовленный вход обработки и последствия сбора без Job.
- `oko/workers` содержит три независимых крона: CollectionWorker, FilterWorker,
  SummaryWorker. JobControl хранит активные попытки, отмену и общую ёмкость модели.
- `oko/collection` содержит контракты источников, RSS, Telegram и YouTube adapters,
  их HTTP/процессные клиенты. Процессный клиент платформы не является четвёртым
  воркером пайплайна. Общие типы и ошибки — в collection/contracts.py.
- `oko/processing` содержит контракт AI, атрибуцию, инструкции, ошибки и адаптеры
  Codex/llama.cpp. Контракт не импортирует адаптеры.
- `oko/storage` содержит PostgreSQL, файлы, репозитории сущностей, JobRepository и
  recovery; общая граница БД — `database.py`, нативная схема PostgreSQL — версионируемые SQL-миграции. FilterResults/SummaryResults/ProcessingState заменяют старый reviews.
  ReadSync хранит границы чтения каналов, JobRepository владеет его заданиями.
- `storage/feed_facts.py` выбирает и нормализует общие читательские поля фида;
  каталог отдельно дополняет их историей и аватаром, открытый материал — привязкой Telegram.
- `oko/subscriptions` содержит модели подписок и наследование правил.
- `oko/host.py` собирает технический lifecycle; `oko/execution.py` — общий допуск.
  `oko/__main__.py` запускает процесс под instance lock. Runtime над этапами удалён.
  Пустые __init__.py не создают интерфейсы реэкспорта.

[Слои и транзакции](application-layers.md), [действия читателя](reader-work.md)
и [актуальность обработки](processing-coordination.md) задают границы переноса.
Единственное хранилище сохраняется; воркеры используют сервисы сущностей и
JobRepository, сервисы не владеют Job или адаптерами. Контроль импортов дополняет
HTTP/PostgreSQL-проверки поведения.

Фронтенд в `frontend/` использует React, TypeScript и Vite; точки входа, владение состоянием и поставка описаны в [архитектуре фронтенда](frontend-backend.md). Канонический HTTP-контракт и генерация Python/TypeScript-библиотек описаны в [OpenAPI-контракте](../../api/README.md).

## Тесты

Сценарии сгруппированы по ответственности в `tests/reader`, `tests/collection`, `tests/processing`, `tests/reviews` и `tests/lifecycle`; браузерные проверки — в `tests/browser`, чистые TypeScript/Node-контракты — в `tests/node`. Общие помощники находятся в `tests/support`: HTTP-клиент и ожидания, синтетические модели и источники, Telegram-подключения, запуск и очистка тестовых процессов. `tests.process_server` остаётся точкой процессных проверок.

Поддержка не импортирует `test_*`; сценарии не импортируют другие сценарные наборы. Помощник одного сценария остаётся рядом с ним. `conftest.py` нужен только для реальных pytest fixtures. Не дробить тесты по assertions и не разделять между тестами изменяемый client. Сценарии восстановления и остановки могут быть отдельны от основных сценариев тезисов.

Основная граница проверки — существующий HTTP interface читателя с временными PostgreSQL/файлами и синтетическими внешними adapters; UI проверяется настоящим браузером. Сохранить проверки workers через запуск, а не только импорт, отмены, поздних ответов, удаления и восстановления. Личные источники и настоящий обработчик не запускаются без соответствующего задания. Команды и объём проверок определяет [порядок разработки](../agents/development.md).

## Полные результаты Source

`collection/contracts.py` задаёт внутренние `DiscoveryResult` и `FetchResult`.
Результат фиксирует публикации/материал, сведения об источнике и частичные ошибки
одной попытки. CollectionWorker не читает изменяемые поля adapter после discover/fetch.

`collection/sources.py` выбирает и настраивает существующие RSS, Telegram web/client
и YouTube adapters. Стабильная настройка сохраняет кеш; изменившаяся настройка
не меняет экземпляр выполняющейся попытки. Модуль не обращается к Store, сети
или workers при настройке. История и формат курсоров остаются прежними.

Воркеры создают ресурсы под action lock, выполняет внешнее ожидание вне lock
и принимает результат после повторного допуска. CaptionAttempt, FloodWait,
ReadSync и владение workers сохраняются; Store отвечает за staging и фиксацию.

## Переход к PublicationAdapter (#90)

`collection/adapters.py` задаёт внешний контракт `PublicationAdapter` / `FeedAdapter`,
ключ `(platform, external_id)`, общий `PublicationContent`, поток одиночного медиа
и типизированные ошибки. Здесь нет ID хранилища, расписания и соединения PostgreSQL.

`collection/telegram/adapter.py` реализует Telegram Web: определяет внешний ключ,
считает публикации с учётом альбомов, фиксирует верхнюю границу окна и возвращает
публикации от старых к новым. Курсор — непрозрачная строка; завершённое окно
открывает следующее при следующем проходе. Файлом и его фиксацией владеет вызывающий.

Небольшие Source-проекции связывают внешний API адаптеров с CollectionWorker. Все
источники сохраняют последнее состояние Publication в PostgreSQL. Ссылки на медиа
превращаются в MediaFile, скачиваемые независимыми jobs. Старые файловые
сборщики и тесты прежних форматов удалены. Текущий выпуск не содержит мигратор
старых хранилищ. Детали: [единый пайплайн](latest-publication.md).
