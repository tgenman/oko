# Пакеты Око и организация тестов

## Код

- `oko/application` содержит прикладные сценарии читателя и JobControl;
  `oko/services` — операции сущностей и запросы; `oko/domain` — общие предметные
  ошибки. `oko/execution.py` хранит общий допуск. Текущее разделение, транзакции
  и временная роль Runtime описаны в [слоях приложения](application-layers.md).

- `oko/collection` содержит контракты источников, синтетический Demo, RSS и Telegram/YouTube adapters с их клиентами и workers. Общие типы и ошибки находятся в `collection/contracts.py`, независимо от конкретного источника.
- `oko/processing` содержит общий контракт AI, атрибуцию, инструкции и ошибки, а также adapters Codex и llama.cpp. Контракт не импортирует adapters; настройка подключения и проверка адреса llama.cpp принадлежат его adapter.
- `oko/reviews` содержит фильтрацию, тезисы отдельных публикаций и согласование актуальности обработки.
- `oko/reader` управляет чтением, составом карточек и выполнением работы; `oko/storage` — SQLite, файлами, атомарной записью и восстановлением; `oko/subscriptions` — подписками и наследованием настроек.
- `oko/__main__.py` собирает запуск `python -m oko`. Пустые `__init__.py` обозначают пакеты, не создавая interfaces для реэкспорта.

Runtime владеет работой Око; Store — фиксацией и восстановлением. См. [управление работой](reader-work.md) и [согласование обработки](processing-coordination.md). Перенос файлов не должен вводить второй storage adapter или универсальный framework обработки.

Фронтенд в `frontend/` использует React, TypeScript и Vite; точки входа, владение состоянием и поставка описаны в [архитектуре фронтенда](frontend-backend.md). Канонический HTTP-контракт и генерация Python/TypeScript-библиотек описаны в [OpenAPI-контракте](../../api/README.md).

## Тесты

Сценарии сгруппированы по ответственности в `tests/reader`, `tests/collection`, `tests/processing`, `tests/reviews` и `tests/lifecycle`; браузерные проверки — в `tests/browser`, чистые TypeScript/Node-контракты — в `tests/node`. Общие помощники находятся в `tests/support`: HTTP-клиент и ожидания, синтетические модели и источники, Telegram-подключения, запуск и очистка тестовых процессов. `tests.process_server` остаётся точкой процессных проверок.

Поддержка не импортирует `test_*`; сценарии не импортируют другие сценарные наборы. Помощник одного сценария остаётся рядом с ним. `conftest.py` нужен только для реальных pytest fixtures. Не дробить тесты по assertions и не разделять между тестами изменяемый client. Сценарии восстановления и остановки могут быть отдельны от основных сценариев тезисов.

Основная граница проверки — существующий HTTP interface читателя с временными SQLite/файлами и синтетическими внешними adapters; UI проверяется настоящим браузером. Сохранить проверки workers через запуск, а не только импорт, отмены, поздних ответов, удаления и восстановления. Личные источники и настоящий обработчик не запускаются без соответствующего задания. Команды и объём проверок определяет [порядок разработки](../agents/development.md).

## Полные результаты Source

`collection/contracts.py` задаёт внутренние `DiscoveryResult` и `FetchResult`.
Результат фиксирует публикации/материал, сведения об источнике и частичные ошибки
одной попытки. Runtime не читает изменяемые поля adapter после discover/fetch.

`collection/sources.py` выбирает и настраивает существующие RSS, Telegram web/client
и YouTube adapters. Стабильная настройка сохраняет кеш; изменившаяся настройка
не меняет экземпляр выполняющейся попытки. Модуль не обращается к Store, сети
или workers при настройке. История и формат курсоров остаются прежними.

Runtime создаёт ресурсы под action lock, выполняет внешнее ожидание вне lock
и принимает результат после повторного допуска. CaptionAttempt, FloodWait,
ReadSync и владение workers сохраняются; Store отвечает за staging и фиксацию.

## Переход к PublicationAdapter (#90)

`collection/adapters.py` задаёт внешний контракт `PublicationAdapter` / `FeedAdapter`,
ключ `(platform, external_id)`, общий `PublicationContent`, поток одиночного медиа
и типизированные ошибки. Здесь нет ID хранилища, расписания и соединения SQLite.

`collection/telegram/adapter.py` реализует Telegram Web: определяет внешний ключ,
считает публикации с учётом альбомов, фиксирует верхнюю границу окна и возвращает
публикации от старых к новым. Курсор — непрозрачная строка; завершённое окно
открывает следующее при следующем проходе. Файлом и его фиксацией владеет вызывающий.

Небольшие Source-проекции связывают внешний API адаптеров с Runtime. Все
источники сохраняют последнее состояние Publication в SQLite. Ссылки на медиа
превращаются в MediaFile, скачиваемые независимыми jobs. Старые файловые
сборщики, миграторы и тесты прежних форматов удалены. Детали:
[единый пайплайн](latest-publication.md).
