# Последнее состояние Publication: переходный путь #91

На хранилище, созданном командой переноса, Telegram Web сохраняется в новой модели.
Остальные источники продолжают прежний путь до своих шагов миграции. Запуск новой
версии приложения сам по себе не переключает существующее хранилище.

`storage/publications.py` владеет сохранением Publication в SQLite. Существующая
таблица `items` расширена полями Publication: platform/external_id, title,
published_at, discovered_at, content, media_ids, filtered_content,
summarized_content, processing_metadata, status. Пустые JSON — `{}`, media_ids —
`[]`, title — пустая строка; неизвестная дата публикации — NULL. Время хранится
как UTC Unix timestamp. Готовность задаётся статусом. Старые поля items остаются
проекцией для действующего читателя и удаляются при завершении перехода.

Feed хранится в `feeds` с platform/external_id, URL, описанием, временем создания,
enabled, adapter/config, cursor, interval_seconds и настройками этапов.
Текущие папки, важность, настройки и разрешения остаются в прежних полях/таблицах.
Новая модель использует уникальность `(platform, external_id)` и таблицы
`feed_publications`, `publication_links`, `media_files`. Отдельной сущности обхода нет.
Новые Feed/Publication/MediaFile получают UUID. Существующие ID при переносе сохраняются
и явно перечисляются в отчёте. Преобразование старых Telegram URL принадлежит
адаптеру; Store не конструирует внешний ключ.

Файлы медиа находятся в `media/<publication_id>/<media_id>`. MediaFile хранит ключ
ресурса, locator, имя, MIME, размер, storage_key, статус и причину. Неизвестные MIME,
размер и storage_key — NULL. В content блок media ссылается на media_id; media_ids
фиксируется в той же транзакции. В этом шаге загрузка файлов ещё синхронна со сбором;
независимые задания вводятся в #92.

`content/<id>/<number>/original.md` и производные файлы — временная однонаправленная
проекция JSON для старого HTTP/обработчика. Подготовка файлов выполняется до короткой
принимающей транзакции. В ней проверяется допуск задания, сохраняются JSON и указатель
проекции. Предыдущие каталоги/индексы удаляются; читатель не получает историю.
При запуске проекция восстанавливается из SQLite и канонических файлов медиа.
Завершение чтения отменяет работу и удаляет данные обычным заданием удаления.

Пока обработчик не переведён на blocks в #93, extra._reader и
processing_metadata._legacy содержат данные восстановления его файлов. Это
переходный формат, не второй источник истины. Переносятся только результаты,
прошедшие текущие проверки подписи/принятия. Их фактическое происхождение сохраняется.
Изменение входа очищает результаты, неизменный вход сохраняет их. Согласование
проверяет актуальность и при изменении правил. Параметры модели для будущих запусков
сами по себе не обесценивают результат, согласно ADR 0001.

## Перенос на отдельную копию

Остановить владельца исходного хранилища, включая встроенные процессы записи.
Команда не останавливает приложение и не переключает рабочую установку:

```sh
.venv/bin/python -m oko.storage.migration /absolute/source /absolute/new-directory
```

Новый каталог должен отсутствовать и находиться вне исходного. Команда проверяет
существующую instance.lock и отказывает при занятом хранилище или SQLite journal/WAL.
Она копирует базу и файлы, проверяет integrity_check и SHA-256 каждого файла.
Манифест исходника сверяется после копирования и перед публикацией результата.

Результат: `backup/` с неизменёнными исходными данными и всей историей,
`storage/` с новым хранилищем и `report.json` с манифестом backup, соответствием
ключей/ID, принятыми результатами, конфликтами и непереносимыми элементами.
У новой копии отдельный storage_id для допуска браузерных ответов. При конфликте
success=false, каталог storage отсутствует; backup и отчёт остаются для разбора.
Нечитаемое последнее содержимое назначается к повторному сбору.

Рабочий каталог не меняется, автоматического запуска нового хранилища нет.
Переключение выпуска и политика возврата входят в отдельный согласованный выпуск
после завершения миграции. Фактические проверки записываются в docs/verification.
