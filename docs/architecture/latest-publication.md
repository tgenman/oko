# Единый пайплайн последнего состояния Publication

Один процесс Python выполняет независимые периодические проходы сбора, загрузки
файлов, фильтра и тезисов. Runtime владеет выполнением и отменой; Store — короткими
транзакциями, SQLite и локальными файлами. Сеть и модель работают вне транзакции.
Этапы согласуются через сохранённые статусы и существующую jobs, без общего workflow.

## Данные

`items` хранит Publication: id, platform, external_id, url, title, published_at,
discovered_at, content, media_ids, filtered_content, summarized_content,
processing_metadata, status. JSON по умолчанию `{}`, список медиа `[]`, заголовок
без названия `''`; неизвестная published_at — NULL. Время — UTC Unix timestamp.
Новые ID — UUID; старые сохраняются и перечисляются в отчёте переноса.
Уникальность публикации — `(platform, external_id)`. Ключи конструирует адаптер.

`feeds` хранит Feed и существующие настройки читателя. Целевые поля: platform,
external_id, url, description, created_at, enabled, adapter, config, cursor,
interval_seconds, filter_config, summary_config. Один активный адаптер на фид.
`feed_publications` связывает фиды и публикации многие ко многим;
`publication_links` — направленные связи публикаций. Обе таблицы имеют составной PK.
Папки, важность, разрешения, Telegram-профили и настройки остаются в прежних таблицах.
Служебные поля items для чтения/групп сохраняются; они не являются второй копией
содержимого целевой Publication. Telegram-группы продолжают прежний путь.

Platform: telegram, youtube, telegraph, instagram, twitter, other_web, rss.
Последние два социальных адаптера пока не реализованы. RSS-запись и статья —
разные Publication; две RSS-ленты могут ссылаться на одну общую статью.
Telegram-альбом — одна Publication. Известные участники позволяют сопоставлять
частичные страницы альбома. Неизвестная идентичность даёт диагностику, не догадку.

## Адаптеры и сбор

[Контракт](../../oko/collection/adapters.py): PublicationAdapter имеет fetch и
потоковый download_media одного ресурса; FeedAdapter добавляет resolve_feed,
cursor_before и discover. Вход и выход содержат только внешние ключи, ссылки,
метаданные, блоки и описания ресурсов. Внутренние ID, БД и расписание им неизвестны.

Действуют telegram_web_adapter, telegram_client_adapter для каналов, rss_adapter,
web_adapter и youtube_adapter. Небольшие Source-проекции передают результат общему
сборщику; старые файловые преобразователи вызываются только офлайн при переносе.
Готовый discover-content сохраняется без повторного fetch. Курсор фиксируется
вместе с принятой порцией. Он непрозрачен для Store и хранится у Feed.

Начальная история и догрузка выбираются по количеству. Адаптер определяет позицию
N−1 от последней, фиксирует верхнюю границу окна и выдаёт от старых к новым,
включая начальную позицию. Недобор и повреждённые записи диагностируются отдельно.
Просмотр не продвигает курсор через несобранные публикации. После удаления явный
повтор истории вправе вернуть публикацию; постоянных tombstone на новом пути нет.

## Содержимое, медиа и обработка

`content.blocks` содержит text/quote/media/external_media; специфичные данные
источника находятся в extra. Внешние `$media` заменяются внутренними media_id
при сохранении. `media_ids` и связи сохраняются в той же транзакции.
`media_files` хранит владельца, resource_key, source_locator, name, mime_type,
size_bytes, storage_key, status и reason. Неизвестные MIME/размер/путь — NULL.
Файл хранится в `media/<publication_id>/<media_id>`. Фото и вложения скачиваются;
YouTube-видео остаётся внешним, обложка и субтитры — отдельные MediaFile.

Поток → временный файл → fsync → move → короткий commit ready. Поколение и
владелец проверяются при принятии. Смена locator того же ресурса сохраняет ID;
замена ресурса получает новый ID. Старые байты не выдаются под новым содержимым.
Текст доступен до завершения медиа. Очистка защищает активные временные/конечные пути.

PublicationStatus: pending_collection → pending_filtering → pending_summary → ready;
фильтр может завершить в filter_out. Выключенные этапы пропускаются; filter_out
не суммаризируется. Причина ошибки и допуск Job отделены от этапа Publication.
Временные ошибки повторяются бесконечно с удвоением от 60 до 3600 секунд;
настройки глобальные. failed требует ручного повтора; source-wait сохраняет срок.

Фильтр и тезисы читаются непосредственно из JSON, без постоянной Markdown-проекции.
processing_metadata хранит фактические input/settings hash, signature, время и
происхождение результата; _pass фиксирует один выбранный фид на проход.
[Правила обработки](publication-processing.md) сохраняют ADR 0001 о параметрах Codex.
Изменившийся вход убирает прежний результат; при неизменном входе результат остаётся.
Текст связанной статьи пересчитывает корень. Рекурсии нет: RSS → статья,
Telegram → Telegraph. Общая публикация использует один согласованный результат.

## Запуск и перенос

CLI под instance.lock активирует пайплайн в новом/пустом хранилище. Заполненная
старая база требует офлайн-переноса; отказ запуска её не изменяет. Встроенный
create_app не переключает существующие данные автоматически.

Офлайн-команда создаёт backup, новую storage и report.json в новом каталоге,
проверяет integrity_check и SHA-256 всех исходных файлов. При конфликте storage
не публикуется. Отчёт содержит соответствие ключей, результаты, старые границы
истории, прерванные работы и непереносимые элементы. Старые версии остаются
только в backup. Неподтверждённые результаты удаляются из новой копии для пересчёта.
Неизвестная незавершённая Job блокирует перенос. Отключённые фиды сохраняются
отключёнными. Рабочая установка сама не переключается.
