## Основа уже реализована

Действующий механизм описан в [выборочных обновлениях](selective-reading.md).
Он заменяет прежнее предложение протокола в этом документе; второй протокол
или повторная реализация #53–#56 не нужны.

| Согласованное требование | Фактическое состояние кода |
| --- | --- |
| Собственная сохранённая версия сущности, обновляемая вместе с записью | `reader_entities`, SQLite triggers в транзакции изменения; запись прежних значений защищена от лишнего увеличения |
| Нет общего номера базы и журнала событий | Хранятся текущие версии сущностей и составов, а не история доставки |
| Пакетная проверка известных версий примерно раз в секунду | `POST /api/v3/reading/check`, один цикл ReaderSession |
| При совпадении версии данные не собирать и не передавать | Ответ `unchanged` без тела сущности; метаданные ID/версий передаются |
| Добавления, удаления, изменение порядка | Собственная версия состава списка и актуальные упорядоченные ID; карточки в том же пакете |
| Открытие сразу, независимо от опроса | Отдельный `GET /api/v3/reading/materials/{item}` |
| Отдельные текст, фильтр, тезисы и медиа | Четыре версионированных ресурса, проверка общей исходной ревизии при показе |
| Перезапуск и пропуски | Сохранённые версии и `storage_id`; обычный restart их не сбрасывает; restore меняет линию данных |
| Совместимость | Новые операции добавлены к API v3; прежние ответы сохранены |

Проверенные точки кода: `oko/storage/reader_versions.py`,
`oko/reader/versions_v3.py`, `frontend/src/reading/resources.ts`,
`frontend/src/reading/coordination.ts`, `frontend/src/reading/opened.tsx`

### Отличия от предварительного списка сущностей

В реализации у `card` и `material` отдельные версии. Предварительное предложение
использовать один счётчик не было обязательным свойством пользовательского
протокола. Разделение уже обслуживает компактную карточку и тело независимо;
предлагается сохранить его, а не объединять ради прежнего наброска.

Версии папок включены в навигационный ресурс; у фидов есть самостоятельные
ресурсы. Настройки не добавлены как самостоятельный ресурс фонового пакета;
действующие операции настроек сохраняются, изменения отражаются на зависимых
ресурсах. Самостоятельная версия ответа настроек из предварительной таблицы
остаётся возможным отдельным расширением, не выполненной частью #56.

Для списка при записи вычисляется digest упорядоченных ID, и только изменившийся
состав получает новую версию. Это уже реализованный способ обслуживания
производной сущности, не новый журнал. Стоимость записей и метаданных учтена
в отчётах; не заявляется постоянная стоимость на любом размере списка.

## Что подтверждает существующая приёмка

Источник: [отчёт #57](../verification/sql-acceptance-57.md), синтетический стенд.
Новые замеры при этой сверке не проводились.

| Сценарий | До | После |
| --- | ---: | ---: |
| Один материал через прежний HTTP GET | 92 SQL | 21 SQL |
| Весь список, 400 материалов, прежний HTTP GET | 25 639 SQL | 4 039 SQL |
| Неизменившийся пакет нового протокола, 104/400 материалов | Другая операция, прямое сравнение не используется | 17 SQL, без чтения файлов содержимого |
| Открытие 400 материалов с активной обработкой, p95 first/repeat | 167,5 / 179,7 мс, база уже с #53–#55 | 36,3 / 29,7 мс после #56 |

Финальная серия отчёта содержит 320 открытий. Цель p95 <200 мс выполнена на
этом стенде: временные данные, синтетическая модель, текст около 2,1 KB без
медиа, внешняя сеть сбора отключена. Это не измерение личной базы или рабочего
Docker-экземпляра. Неизменившийся пакет на 400 материалах всё ещё передаёт
около 37 KB метаданных; наличие 17 SQL не означает нулевой стоимости.

Исторические неуспешные прогоны, ограничения полного all и конкуренция браузерных
тестов сохранены в отчёте #57. Эта сверка не заменяет их новым заявлением
о полном успешном прогоне.

## Уточнение после трассировки открытия материала

Повторный замер на временной синтетической библиотеке из 104 материалов:
старый `/api/v3/materials/{item}` — 21 SELECT; действующий
`/api/v3/reading/materials/{item}` — 40 событий SQLite trace. Второе число
включает BEGIN/COMMIT, попытки служебных записей и повторные callback при
триггерах; это не 40 независимых SELECT и не сетевые обращения к БД.

Показатель 21 относился к совместимому старому маршруту и не описывает
полную работу текущего открытия. Предыдущий вывод, что следующим шагом
остаётся только UI, был неполным. Низкий p95 синтетической приёмки не
доказывает отсутствие лишней работы или запаса при конкурентной нагрузке.

В действующем пути подтверждены:

- `VersionedReading.read` вызывает `advance` до чтения. Открытие обслуживает
  наступившие сроки, очистку проблем/исходов команд и runtime-метаданные.
- Текстовая часть получается из полного материала, после чего фильтр,
  тезисы, медиа и другие поля отбрасываются. Отдельные части читаются снова.
- Получение настроек тянет полное описание фида с историей загрузки и её
  агрегатами. Строка публикации и некоторые состояния перечитываются.
- Версии четырёх частей одного материала читаются отдельными SELECT по виду.

## Предлагаемый план сокращения пути чтения

Это локальное продолжение #53–#56 с сохранением действующего протокола,
а не его замена. План ниже сохранён как основание реализации; фактические
результаты, неудачные прогоны и ограничения находятся в отдельном отчёте.

### 1. Зафиксировать наблюдаемую стоимость текущего маршрута

Один стенд и один текущий endpoint до/после. Отделять SELECT, служебные
записи, callback триггеров, время ожидания блокировки, работу SQLite,
чтение файлов и сериализацию. Использовать данные и сценарии #57;
изолированный SQL и браузер с активным фоном — разные измерения.

### 2. Убрать обслуживание приложения из запроса открытия

Наступление сроков и изменение состояния публикует существующий Runtime,
очистку истории он выполняет вне HTTP-чтения ограниченными порциями.
Не вводить новый scheduler. Обеспечить переходы и при отсутствии вкладок,
включая режим выключенной работы: чтение и истечение видимых ожиданий имеют
свои правила. Согласованные 1–2 секунды проверять через управляемые часы.

Запрос открытия не вызывает `advance`, очистку истории, согласование задач
или запись статуса. При холодном запуске необходимые служебные данные
готовятся до приёма запросов. Цель горячего пути — ноль DML-записей.

### 3. Получать один ограниченный снимок данных материала

Общий для четырёх частей снимок содержит только выбранную публикацию,
её версии ресурсов/содержимого, нужные настройки, состояния работ и ссылки
на сохранённые результаты. Получать связанные данные наборами, без вызовов
полного каталога фидов и истории подключения. Чтение версии и соответствующих
данных согласовано; чужие публикации не обходятся.

Внутри одного запроса строка публикации, настройки и метаданные читаются
однократно. Версии четырёх частей выбранного ID получаются одним SELECT.
Избегать одного огромного JOIN, размножающего строки из нескольких коллекций:
несколько ограниченных индексных выборок лучше такого объединения.
Текстовые и производные файлы читаются не более одного раза при необходимости.

Проектный бюджет открытия — до 8 SELECT и ноль DML на выбранных сценариях.
Это ограничение будущей приёмки, а не измеренный результат. Бюджет проверяется
на материалах с тезисами, фильтром, медиа и предыдущими версиями, а не только
на пустом синтетическом примере. Объём строк/файлов и VM также ограничиваются
запрошенным материалом: уменьшение числа SELECT не оправдывает полный обход.

### 4. Собирать ответ прямо из нужных данных

Текстовая часть собирается прямо из текста и его метаданных. Тезисы, фильтр
и медиа читают только собственные необходимые данные, используя общий снимок.
Не собирать полный ReadableMaterial с последующим удалением полей.
Первое открытие остаётся одним HTTP-запросом с четырьмя частями; фронт не
делает четыре последовательных сетевых обращения.

Чтение не пересчитывает обработку. Принятие результата и его актуальность
по-прежнему принадлежат #54: необходимые признаки готовности/инвалидации
должны сохраняться при изменении входов и принятии результата. Нельзя просто
удалить проверки сигнатур: сначала обеспечить эквивалентный допуск результата,
включая настройки, просмотр, отмену и перезапуск. Готовый файл сам по себе
не доказывает принятие результата.

### 5. Оставить проверку версий дешёвой

Пакетная проверка читает только версии и доступность запрошенных сущностей.
Без изменений — без файлов, полной сборки, глобального статуса и обслуживания
архива. Проектный бюджет установившегося неизменившегося пакета — до 2 SELECT
плюс неизбежная обработка присланных ID, ноль DML. Новая область/первое чтение
измеряются отдельно. Разбиение слишком большого пакета должно быть явно
учтено в бюджете, а не маскироваться правилом «один запрос».

Существующие metadata-only ответы и размер O(N) не меняются автоматически.
Их сокращение оправдано отдельными измерениями; Redis, внешний кэш,
журнал событий и замена SQLite в этот объём не входят.

### 6. Проверить конкурентный сценарий и корректность

Сохранить тесты #57 и добавить контролируемые 1/5/20 вкладок с опросом и
активной синтетической обработкой. Замерять p50/p95/p99, ожидание блокировок,
время блокировки event loop и цену записи после переноса работы. Нельзя
объявить перенос затрат с чтения на запись бесплатным.

Для прежнего стенда сохраняется цель p95 <200 мс; для более высокой
конкуренции сначала получить базу и зафиксировать результат/ограничения.
Не повышать пороги ради прохождения. Не выносить общий SQLite connection
в произвольные потоки. Если после сокращения работы остаётся измеримая
блокировка чтениями файлов или сборкой, отдельно спроектировать исполнение
чтений с корректным владением соединениями и снимками.

Регрессии: одинаковый ответ текущего API, поздние версии, изменение настроек
во время обработки, удаление, восстановление, таймеры и режим выключенной
работы. Только после этой проверки переходить к отдельному поведению UI ниже.

Полные требования: [изменения поведения открытого материала](opened-material-updates-design.md).

| До реализации | Согласованное изменение, реализованное в `4c13bff` |
| --- | --- |
| `clear()` при просмотре, недоступности и исчезновении карточки | Сохранить уже полученный материал в текущей вкладке, явно показывать недоступность догрузки |

| Нет сохранения смыслового места при замене текста | Удерживать видимый абзац; ближайшее место/относительная позиция как fallback |
| Смена состава медиа очищает ресурсы и повторяет загрузку | Сохранять неизменившиеся медиа и воспроизведение, догружать только новые |

Предлагаемый порядок отдельной задачи:

1. Разделить в сессии открытия показанные данные и новые полученные данные.
   Опрос и сравнение версий переиспользуют существующий механизм #56.
2. Сохранить показ при исчезновении карточки/просмотре/временной потере связи.
   Серверное удаление не откладывать; после перезагрузки копию не восстанавливать.
3. Добавить кнопку новой версии и сохранение абзаца. Применять только
   согласованные по исходной ревизии текст, фильтр, тезисы и медиа.
4. Сделать обновление медиа сохраняющим уже загруженные ресурсы. Освобождать их
   при завершении показа, не при каждом обновлении списка вложений.
5. Проверить эти сценарии в Playwright и HTTP; повторить целевой benchmark,
   чтобы новые правила показа не ухудшили подтверждённую базовую скорость.

Изначально это было предложение выполнения. Разрешение на реализацию UI
получено следующим сообщением пользователя; серверные сокращения чтений
сохранены.

## Вопросы исходного проектирования

- Новая фильтрация может изменить показанный текст без авторской правки:
  определить способ показа такого результата.
- Если показана старая ревизия, текущий API отдаёт части актуальной ревизии.
  Он не гарантирует догрузку исторических тезисов. Разделить удержание уже
  полученного и чтение сохранённых исторических частей; новую генерацию
  старых результатов не вводить автоматически.
- Уточнить незавершённое открытие, поздние ответы после просмотра, явную смену
  папки и остановку приложения. Не смешивать их с исчезновением карточки.

Вопросы выше сохранены как история проектирования. Принятые решения описаны
в [проекте открытого материала](opened-material-updates-design.md),
а действующие правила — в [архитектуре открытого материала](opened-material.md).
