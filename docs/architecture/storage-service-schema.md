# Служебное состояние, проблемы и миграции

29 октября 2026. **Проект, без реализации.** Последние пять таблиц
[целевой схемы из 20 таблиц](storage-redesign.md). SQL ниже не запускался.
Физическое описание прикладного ядра находится в соседних schema-документах.

## state — 2 колонки

```sql
CREATE TABLE state (
    key   text PRIMARY KEY CHECK (key <> ''),
    value jsonb NOT NULL CHECK (value <> 'null'::jsonb)
);
```

Это небольшой каталог долговечных значений с фиксированными владельцами Python,
не универсальное место для новых UI-кэшей. Тип/схема значения задаются именем или
разрешённым семейством ключей. Настройки с наследованием остаются в settings.

| Ключ/семейство | Решение |
| --- | --- |
| `work-enabled` | Сохранить boolean — намерение включённости Око после restart |
| `storage-id` | Перенести UUID из reader_identity; обычный restart сохраняет, restore меняет по существующему правилу |
| `processor:codex`, `processor:llamacpp` | Сохранить проверенную конфигурацию обработчика; не копировать учётные данные/сессии |
| `telegram-retry:<user_id>` | Сохранить абсолютный deadline ограничения аккаунта для всех его фидов |
| `source-http:<scope>` | Сохранить абсолютное ограничение HTTP-источника |
| `telegram-http:<group>` | Сохранить состояние ограничений группы запросов, включая необходимый backoff |
| `feed-status:<feed_id>` | Перенести содержательные gap/changes/ошибки к последнему итогу фида, не держать вторую копию в state |
| `sources-version` | Удалить после замены потребителей явной актуализацией конфигурации |
| `settings-sequence`, `settings-version`, `settings-version:<feed>` | Удалить после перехода на фактические снимки/signature и явную инвалидацию Job |
| `job-dispatch-generation` | Удалить после введения непереиспользуемой пары Job ID + generation |
| `publication-pipeline`, `journal-index-version` | Удалить как маркеры прежнего устройства; совместимость задаёт журнал миграций |

Каждый существующий ключ перечисляется в отчёте переноса; неизвестный ключ не
выбрасывается молча. Исторические числа/JSON-строки преобразуются в типизированный
JSONB без двойного кодирования. Сроки сохраняют UTC-смысл, а не время процесса.
Ограничение на общий аккаунт нельзя удалить из-за удаления одного из его фидов.

В текущем `ProcessingRequest` есть обязательный settings_version. Удаление ключей
его генератора требует изменить этот внутренний контракт и обоих потребителей
Codex/llama.cpp вместе. Не допускается оставить фиктивный постоянный 0 и заявить,
что защита актуальности сохранена. В новом варианте её обеспечивают снимок запроса,
signature и Job generation; модель не назначает себе допуск присланным полем.

`storage-id` остаётся обязательным для принятого HTTP-контракта. Удаление таблицы
reader_identity не означает удаления заголовка X-Oko-Storage-Id или проверок
позднего ответа от другой библиотеки.

## youtube_access — 4 колонки

```sql
CREATE TABLE youtube_access (
    id            smallint PRIMARY KEY CHECK (id = 1),
    next_at       timestamptz,
    blocked_until timestamptz,
    strikes       integer NOT NULL DEFAULT 0 CHECK (strikes >= 0)
);
```

Одна строка описывает существующую общую политику получения субтитров. NULL deadline
означает отсутствие соответствующего ограничения; при переносе прежний 0
нормализуется по этому смыслу. Это не новая конфигурация лимитов по каждому видео.

Next_at ограничивает очередной допуск, blocked_until — подтверждённую паузу
источника, strikes — необходимый счётчик последовательных ограничений. Эти факты
переживают restart. `paused` вычисляется по времени и не хранится ещё раз в
reader_youtube_time. Общая политика backoff не заменяется новой в рамках схемы.

Проверка и резервирование очередного допуска выполняются под блокировкой этой
строки до внешнего запроса. Неуспешный запрос не освобождает срок задним числом.
Предлагается сохранить один активный запрос субтитров в этой области, используя
существующий collection-owned слот. Слот удерживается до фиксации исхода допуска
в youtube_access, а не только до возврата байтов: старый успех тогда не снимает
ограничение следующего запроса. Изменение связывается с текущим Store и владельцем
слота. Во время внешнего вызова SQL-транзакция не удерживается; другие операции
сбора и модели продолжаются. Это конкретизация прежнего варианта «условный update
либо сериализация», требующая теста позднего ответа после stop/restart.

Proxy-конфигурация и секреты остаются в прежнем защищённом хранилище; таблица
не становится местом хранения proxy-пароля. Подключение новой системы лимитов
не является целью проекта.

## reader_action_results — 7 колонок

```sql
CREATE TABLE reader_action_results (
    sequence     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    id           text NOT NULL UNIQUE CHECK (id <> ''),
    identity     text NOT NULL CHECK (identity <> ''),
    body         jsonb NOT NULL CHECK (jsonb_typeof(body) = 'object'),
    started_at   timestamptz NOT NULL,
    completed_at timestamptz,
    result       text NOT NULL CHECK (result IN (
                     'pending', 'unknown', 'succeeded', 'failed', 'abandoned'
                 ))
);

CREATE INDEX reader_action_latest
    ON reader_action_results (identity, sequence DESC);

CREATE INDEX reader_action_cleanup
    ON reader_action_results (completed_at, sequence)
    WHERE completed_at IS NOT NULL;

CREATE INDEX reader_action_objects
    ON reader_action_results USING gin ((body -> 'objects') jsonb_path_ops);
```

ID — идентичность команды для HTTP и повторного обращения. Identity — её
предметный контекст для сопоставления последних исходов; sequence задаёт их
однозначный порядок. Они имеют разные назначения и не заменяются одним случайным UUID.

Body хранит типизированный контекст команды, служебные ссылки на объекты и
структурированную ошибку. Он не архивирует текст публикаций и их названия.
Строковый command_error с JSON внутри преобразуется в объект при сохранении,
с совместной адаптацией его потребителей; некорректный старый JSON даёт отчёт.

Повтор того же ID с другим контекстом отклоняется до эффектов. Неизвестный исход
не считается неуспехом и не повторяется автоматически: после сбоя сервер сверяет
фактическое состояние в пределах правил команды. Таблица сама по себе не даёт
гарантии exactly-once для внешнего действия. Начало, подтверждённый исход и
возможность явного повтора сохраняют текущий контракт команд.

### Удаление двух производных таблиц

Reader_material_links не нужна: объекты выбираются из исходного body.objects
через native JSONB containment, с проверкой плана GIN. Копия массива в другой
таблице не создаётся. Индекс не означает, что любой произвольный JSON-запрос
автоматически станет быстрым; форма запросов и стоимость порций проверяются.

Reader_action_superseded заменяется запросом «есть более поздняя sequence той
же identity». Очистка выбирает ограниченную порцию завершённых старых строк,
проверяет это условие и удаляет их явно. Последний исход и незавершённая команда
не удаляются только из-за возраста. Используется нынешний срок порядка суток
для прежних завершённых исходов; новую общую политику хранения здесь не вводим.

Очистка идёт по индексу `(completed_at, sequence)` порциями с курсором; проверка
наличия более поздней sequence выполняется по индексу `(identity, sequence)`.
Курсор принадлежит работающему Store и откатывается вместе с транзакцией. После
рестарта обход начинается снова; при большой доле последних квитанций удаление
может потребовать нескольких порций, но один проход не обходит весь архив.

Точный отказ от команды (`abandoned`) отличается от failed и unknown. Просмотр
объекта очищает его ссылки/действия, но не превращает уже подтверждённый успешный
исход команды в неуспешный. Служебное подтверждение и содержимое удаляемого
объекта имеют разный срок жизни.

## reader_problems — 7 колонок

```sql
CREATE TABLE reader_problems (
    id          text PRIMARY KEY CHECK (id <> ''),
    identity    text NOT NULL CHECK (identity <> ''),
    origin      text NOT NULL CHECK (origin IN ('action', 'background')),
    body        jsonb NOT NULL CHECK (jsonb_typeof(body) = 'object'),
    created_at  timestamptz NOT NULL,
    finished_at timestamptz,
    outcome     text CHECK (outcome IN ('resolved', 'irrelevant')),
    CHECK ((finished_at IS NULL) = (outcome IS NULL))
);

CREATE UNIQUE INDEX reader_problem_current
    ON reader_problems (identity) WHERE finished_at IS NULL;

CREATE INDEX reader_problem_cleanup
    ON reader_problems (finished_at, id) WHERE finished_at IS NOT NULL;

CREATE INDEX reader_problem_objects
    ON reader_problems USING gin ((body -> 'objects') jsonb_path_ops);
```

Identity связывает текущую проблему с её причиной. ID обозначает конкретный
случай: после завершения новая проблема получает новый ID, а старый случай не
возвращается в current при restart. Partial UNIQUE защищает один активный случай.
Вместо отдельного rowid для bounded cleanup достаточно пары finished_at/id.

Ошибка Job и проблема не одно и то же: одна проблема может объединять несколько
заданий с общей причиной. Нормальное ожидание срока не является новой проблемой.
Содержимое body — причина, последствия, допустимые действия и ссылки; не копия
публикации. Код хранит только изменившийся body, без записи на каждый GET.

### Явное обновление проблем

Владелец изменяющей операции вызывает Python-операцию проблем в той же транзакции:
при ошибке/успехе Job, изменении конфигурации/доступа, завершении команды или
удалении объекта. Пересматриваются затронутые identity, а не все задания библиотеки.

Закрытие одной Job не закрывает общую проблему, если её причина остаётся у других
Job. Изменение конфигурации, устраняющее причину, завершает соответствующие случаи;
повторный старт не создаёт копию уже завершённого случая. Начальное восстановление
может проверить состояние ограниченными порциями перед запуском внешней работы.

GET /status и /status/details только читают готовые факты и живые метаданные
Execution/Host. Старый вызов Problems.reconcile, выполняющий записи при сборке
ответа, должен исчезнуть из GET. Иначе проект «чтение без скрытых записей» не выполнен,
даже если SQL-триггеров уже нет.

Недавние завершённые проблемы сохраняют нынешний ограниченный период порядка
суток. Локальную порционную очистку выполняет служебная часть существующего
крона сбора; выключенный сетевой сбор не требует включать источники или модель
ради локальной очистки. Нового четвёртого крона и таблицы истечения сроков нет.

## oko_schema_migrations — 4 колонки

```sql
CREATE TABLE oko_schema_migrations (
    version    integer PRIMARY KEY CHECK (version > 0),
    name       text NOT NULL CHECK (name <> ''),
    checksum   text NOT NULL,
    applied_at timestamptz NOT NULL DEFAULT clock_timestamp()
);
```

Сохраняются версии, имена и SHA-256 существующих миграций. Их содержимое и checksum
не переписываются ради более красивой начальной схемы. Новый переход добавляется
после реально установленной истории; номер уточняется на актуальном main.

Миграционная роль владеет DDL и ledger. Приложение проверяет совместимость и не
устанавливает таблицы/триггеры при обычном запуске. Все изменения одного выпуска
и запись ledger коммитятся вместе либо откатываются. Один мигратор исключает
другого и действующий Store через прежний механизм lease.

Полная история на пустой базе может создать старые триггеры, а новая миграция
удалит их. Проверяется конечный каталог: 20 прикладных/служебных таблиц из проекта,
ноль пользовательских триггеров и прикладных функций. Встроенные механизмы FK и
identity не считаются возвращением прикладных триггеров. Старые compatibility views
items_read/items_by_feed/unviewed_items_by_feed/reading_memberships не нужны после
перевода их потребителей на новые таблицы; их нельзя оставить скрытой зависимостью.

Новая библиотека получает work-enabled=false, новый storage-id и строку
youtube_access с id=1, без действующих deadlines. Аккаунты Telegram и история
появляются только при соответствующем подключении/запросе. При переносе заполненной
библиотеки эти defaults не перезаписывают существующую включённость, идентичность
или ограничения источников.

## Проверка будущего перехода

- Все state keys классифицированы; дедлайны аккаунтов/источников переживают restart,
  неизвестные ключи не исчезают без отчёта.
- Старый settings_version не остался обязательным неподдерживаемым входом adapter.
- Два допуска YouTube не обходят next_at; старый успех не снимает новое ограничение.
- Повтор ID команды с иным контекстом отклонён; unknown не приводит к автоматическому
  повтору внешнего действия; подтверждённый результат после restart доступен.
- Конкурентные события одной проблемы не создают два current; закрытие одной Job
  не завершает проблему других Job той же причины.
- JSONB-запросы находят ровно нужные ссылки, очистка не зависит от удалённого
  reader_material_links, последний исход команды сохраняется.
- GET статуса не пишет в БД и не читает удалённые версии; независимые ETag/details
  сохраняют контракт параллельного HTTP-проекта.
- Миграция на пустой и заполненной копии даёт весь целевой каталог; ошибка на
  любом шаге не оставляет частично обновлённые данные/ledger.

## Фактическая проверка проектирования

Прочитаны текущие Problems, state writers, YouTubeAccess, ProcessingRequest и
механизм миграций. DDL и обязанности проверяются статически. SQL, внешние источники,
рабочая база и продуктовые тесты в рамках этого документа не запускались.
