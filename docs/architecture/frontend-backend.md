# Фронтенд и бэкенд Око

## Действующая архитектура

React + strict TypeScript находятся в frontend/src; Vite собирает готовые assets. frontend/src/main.tsx связывает модуль согласования чтения с владельцами настроек и состояния; shell.tsx задаёт структуру, renderer.tsx держит один React root и его именованные portals. Владельцы хранят локальное состояние и управляют своими ресурсами; универсальный application store/router не вводился. reader-session.ts единолично владеет heartbeat/polling/BroadcastChannel/page events; cleanup не отправляет stop/close.

Редактируемый HTTP-контракт — [OpenAPI](../../api/openapi.yaml). Generated Python DTO используются в входных и выходных handlers; доменная валидация выполняется в ReaderApplication и доменных сервисах; Store сохраняет данные. Generated TypeScript SDK задаёт операции. APIreader настраивает отдельный Fetch client и учитывает исходы команд; общие errors/transport сохраняют diagnostic headers, unknown network outcomes и bearer только своего origin. Binary operations выводятся из canonical metadata и читаются как Blob, а media links используют авторизованный raw fetch.

[API-first policy](../../api/README.md) задаёт валидацию схемы и проверку актуальности generated-библиотек. Browser snapshots получают schema2020-12 из canonical bundle и используют Ajv8; ручных wire-схем нет. Standalone Swagger не запускает читатель. Встроенные docs поставляются локально, требуют явного Authorize для Try и не создают reader lease.

Python static delivery проверяет content hashes, ревизию контракта и freshness checkout до запуска читателя. Assets находятся в immutable generations с atomic pointer; старые chunks остаются доступны открытым вкладкам при watch rebuild. Локальный запуск описан [для checkout](../development/package.md); облачный выпуск поставляется как [приватный runtime package](../development/cloud-deploy.md).

## Владение

Фронтенд владеет DOM, фокусом, навигацией, черновиками, локальными предпочтениями и допуском позднего ответа к текущему показу. ReaderApplication владеет действиями читателя, Execution — общим допуском и внешними ожиданиями, три воркера — выполнением попыток, JobControl — отменой, Store — фиксацией и восстановлением, Host — временем жизни процесса. Сервер формирует состав чтения и эффективные настройки. Браузер не вычисляет membership и не повторяет правила актуальности обработки.

Действуют решения [UI-состояния](ui-settings.md), [открытого материала](opened-material.md), [управления работой](reader-work.md), [состава чтения](reading-composition.md) и [согласования обработки](processing-coordination.md).

## HTTP interface

Seam между фронтендом и бэкендом — HTTP interface читателя. Существующие URL, локальная сессия, проверка host/origin и защитные заголовки сохраняются. Успешная серверная запись остаётся состоявшейся после закрытия формы; отмена браузерного ожидания не откатывает её. Несколько читающих запросов не обещают один транзакционный снимок.

Запущенный из checkout читатель выдаёт интерфейс и API на одном origin; Node нужен для подготовки frontend, но не для работы сервера. Неизвестные маршруты данных не превращаются в HTML; обход пути, скрытые файлы и symlink за пределы каталога assets отклоняются. Правила единственного API v3: [api/README.md](../../api/README.md).

При сборке HTTP-приложения полные схемы ответов Pydantic подготавливаются один раз на тип в процессе через `SchemaRoute` и публичные hooks Pydantic. Ограниченный кэш хранит только схемы; первая подготовка синхронизирована. Каждый ответ проходит валидацию и сериализацию с параметрами своего маршрута. Host, Execution, Store, handlers и зависимости принадлежат отдельному приложению. Кэш не хранит ответы и не удерживает приложения. Новая версия схем загружается новым процессом; дешёвые обёртки FastAPI и параметры запросов остаются отдельными для приложения.

2026-10-16: consumers читателя и настроек полностью используют v3 SDK; старые handlers и v2 библиотеки сняты. Middleware возвращает прежним запросам типизированный 410 после security checks. Доменный Store выдаёт внутренние снимки с историческими фактами; отдельные проекции строят generated v3 DTO. Контролируемые browser fixtures могут описывать исторические данные сценария, но доставленные wire responses проверяются только по canonical v3; реальная HTTP-приёмка идёт без такого преобразования.

## Согласование чтения

`frontend/src/reading/coordination.ts` собирает существующих владельцев списка,
дерева, открытого материала и действий читателя. Модуль скрывает полный цикл
загрузки состояния, навигации и карточек, допуск поздних ответов и согласование
последствий действий. `main.tsx` не хранит поколения запросов, выбранные ID области
или копию каталога. Сессия браузера продолжает единолично владеть опросом,
heartbeat, BroadcastChannel и событиями страницы.

Согласованные границы и проверяемое поведение:
[согласование чтения](reading-coordination.md).

## Доступ к постоянному читателю

До авторизации сервер выдаёт отдельную HTML-форму и CSS; React-читатель и его
ресурсы требуют сессию. `browser-auth.ts` сохраняет общий fetch-владелец JSON
и медиа. `access.ts` отслеживает отказ авторизации, периодически проверяет
сессию, проверяет возврат к вкладке и распространяет выход через BroadcastChannel.
При блокировке он сначала завершает владельцев читателя через `stopAccess`,
размонтирует React-root с очисткой эффектов и layout observers, затем прерывает
запросы и чтения их тел, очищает DOM и открывает форму входа.
Контроллер сохраняется до EOF/cancel; ответ, пришедший после потери доступа,
не допускается к отображению. Сервер проверяет доступ перед выдачей ответа
и между фрагментами защищённых потоков. Это не меняет общие настройки и
семантику «Просмотрено».
