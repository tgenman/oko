# Согласование актуальности обработки

2026-10-11. Кандидат 1 архитектурного обзора от 2026-10-10. Пользователь согласовал объём, сохранение поведения, подготовленную работу для Runtime и восстановление без миграции. Исходная база: `a86ec7a6f0386361ee1f219805bc75ccc557165e`.

## Решение

Сосредоточить в одном deep module согласование актуальности фильтра, тезисов публикации, карточек событий и обзоров за период. Module скрывает порядок пересборки зависимых результатов, выбор обработки для задания, связывание запроса с проверкой актуальности и принятие ответа.

Разместить implementation в пакете `oko/reviews`. Точные имена файла, класса и методов выбрать при реализации в соответствии с этим interface. Алгоритмы Filters, Events и Digests остаются самостоятельными; общая обработка не превращает их в одинаковые этапы. Согласование тезисов, сейчас находящееся в Store, становится внутренней ответственностью module обработки.

Сохранить решения [управления работой](reader-work.md), [прогресса обзора](digest-progress.md), [структуры пакетов](package-layout.md) и [состава чтения](reading-composition.md). Не менять продуктовую спецификацию, UI, маршруты читателя, SQLite/Markdown, правила повторных попыток и порядок приоритизации заданий.

## Текущее трение

- `Store.sync_theses` согласует четыре вида результатов в порядке Filters → Digests → Events → тезисы; название скрывает реальный объём действия.
- Принятие версии, недоступность источника, настройки, завершение чтения, принятие фильтра, восстановление скрытого материала и периодический проход Runtime вызывают разные части согласования.
- `Runtime._execute_ai` строит таблицу операций с отдельными request, проверкой актуальности, текстом этапа и save; дополнительно знает пустой этап и освобождение плана Digests.
- Filters, Events и Digests владеют своими алгоритмами и состоянием. Простой перенос таблицы операций или переименование sync не убирает знание об их совместном использовании у callers.

## Interface и seam

Interface выражает три связанных сценария: согласование результатов с текущим состоянием, подготовка работы выбранного задания, проверка и принятие ответа этой работы. Подготовленная работа связывает точный запрос с теми правилами актуальности и принятия, которые действовали при подготовке; Runtime не собирает отдельные callbacks по kind задания.

В подготовленной работе доступны сведения, необходимые Runtime для выбора обработчика, проверки разрешения публичного AI и отображения этапа. Она также скрывает обработку этапа без внешнего запроса и освобождение принадлежащего ей временного плана при завершении, отмене или ошибке. Точные типы выбрать при реализации; не возвращать наружу набор несвязанных функций, порядок вызова которых должен знать Runtime.

Seam проходит между управлением выполнением в Runtime и domain implementation обработки. Вызовы согласования из Store и обзоров используют один module; caller не выбирает вручную последовательность четырёх видов результатов. Чтение результатов сохраняет независимую проверку актуальности, чтобы задержка фонового прохода не показывала устаревшее как готовое.

Готовый module должен иметь depth: при удалении его implementation знание о порядке зависимостей и связывании обработки снова распределится между Store, Runtime и обзорами. Делегирование прежним функциям допустимо внутри implementation, но сохранение прежнего протокола у callers не проходит deletion test.

## Владение и выполнение

- Runtime владеет блокировкой действий, живыми вкладками, допуском, отменой и принадлежащими ему внешними ожиданиями. Проверки processor adapter и запрос к модели остаются вне блокировки.
- Подготовка и принятие выполняются под существующей блокировкой. После проверки обработчика Runtime снова проверяет допуск; перед принятием ответа — актуальность работы и принадлежность текущему Store.
- Store владеет транзакциями, заданиями, атомарной записью, файлами, физическим удалением и восстановлением. Module обработки использует существующее хранение; не создаёт независимую очередь или соединение SQLite.
- Filters, Events и Digests сохраняют domain-правила результата. Прогресс, разбиение и переходы обзора остаются внутри Digests.
- Согласование не вызывает само себя рекурсивно через save/restore/sync. После изменения результата следующий необходимый пересчёт имеет одного владельца внутри module; способ организации внутренних вызовов выбрать при реализации.
- Codex и llama.cpp остаются существующими adapters на seam обработчика. Новый framework, registry плагинов, универсальный граф обработки и второй storage adapter не нужны.

## Сохраняемое поведение

1. Правка оригинала делает прежние зависимые результаты неактуальными; прежний ответ не может опубликоваться для новой версии.
2. Загрузка известных оригиналов не уничтожает замороженный набор ID обзора. После принятия версии обзор пересобирается в том же наборе; новые поступления автоматически в него не добавляются.
3. Изменение промпта, обработчика или разрешений учитывается при подготовке, после проверки обработчика и при принятии. Нельзя передать запрещённый исходник публичному AI или использовать прежний результат вместо разрешённой обработки.
4. «Просмотрено» сохраняет нынешний охват оригиналов и удаление всего контента. Поздний ответ не восстанавливает оригиналы, версии или результаты; остальные оригиналы остаются доступны.
5. Недоступность публикации в источнике сохраняет локальную копию. Сетевой сбой повторной загрузки не становится правкой содержимого.
6. Неполные исходники, недоступные субтитры, фильтрация, ручное восстановление скрытого материала и пустые допустимые наборы сохраняют прежние правила.
7. Перезапуск продолжает корректный сохранённый прогресс обзора. Повреждённый прогресс пересобирается по прежним правилам; сиротский файл не становится готовым результатом.

## Проверки реализации

Основная test surface — существующий interface читателя с настоящими временными SQLite/файлами и заменяемыми внешними source/AI adapters. Не переносить основные проверки на внутренние helpers ради нового module.

Сохранить существующие сценарии в `tests/collection/test_source_revisions.py`, `tests/reviews/test_filters.py`, `test_events.py`, `test_digests.py`, `test_digest_recovery.py`, `tests/processing/test_theses_recovery.py`, `tests/lifecycle/test_runtime_actions.py` и `tests/reader/test_folder_completion.py`.

Дополнять только отсутствующие проверки:

- Правка оригинала во время задержанного ответа: старый ответ отбрасывается, новые результаты соответствуют новой версии; набор ID обзора сохранён.
- Изменение разрешений во время проверки обработчика и во время генерации: новый запрещённый запрос не уходит, старый ответ не принимается как актуальный.
- Изменение фильтра или ручное восстановление: зависимые тезисы, события и обзоры согласуются без рекурсивного вызова и повторной постановки неизменившихся заданий.
- Завершение чтения во время обработки одиночного материала, события или обзора: удалённое не возвращается; несвязанные материалы доступны.
- Перезапуск посреди обзора: принятые этапы не отправляются повторно; корректный файл прежней версии продукта читается без миграции.
- Неизменившееся состояние при повторных проходах: готовые результаты сохраняются, поколения и число внешних запросов не растут.

Запустить затронутые проверки, полный pytest и строгий mypy. Если внешние adapters не меняются, реальные интеграционные проверки не представлять как повторно выполненные: отдельно указать, что проверено через подменяемые adapters. Проверку и ревью реализации записать в отдельный отчёт.

Locality: порядок согласования и связывание работы находятся в одном module. Leverage: одинаковое действие согласования обслуживает сохранение версии, настройки, завершение чтения и восстановление. Interface скрывает совместный протокол, сохраняя самостоятельную implementation каждого вида результата.
