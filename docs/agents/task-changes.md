# Изменения задачи в грязном checkout

`scripts/task_changes.py` сохраняет исходное состояние, строит diff задачи и готовит её коммит отдельно от прежних staged/unstaged правок. Он использует Git inventory, сохраняет байты symlink без чтения целей, а содержимое снимка проверяет по digest. Поддерживаются обычные файлы, symlink, бинарные данные, режим executable и удаления; submodules, конфликтный индекс, skip-worktree, assume-unchanged и intent-to-add отклоняются.

## Начало задачи

До изменения файлов создайте снимок вне checkout, в новом каталоге:

```sh
python3 scripts/task_changes.py snapshot /tmp/oko-task-start
```

Снимок содержит исходный HEAD, состав индекса и файлы из `git ls-files -co --exclude-standard`. Игнорируемые файлы туда не входят. Снимок сохраняет исходное состояние, а не выбирает объём коммита. Каталог не перезаписывается.

## Diff и подготовка

```sh
python3 scripts/task_changes.py diff /tmp/oko-task-start
python3 scripts/task_changes.py prepare /tmp/oko-task-start \
  --output /tmp/oko-task-ready \
  --files oko/example.py tests/example.py
```

`--files` задаёт явный объём. Подготовка отделяет изменения после снимка от прежних правок и создаёт временный индекс поверх исходного HEAD. При добавлении/переименовании указывайте новый путь, при удалении — прежний, при переименовании — оба. Файлы, уже изменённые до снимка и с тех пор неизменные, не становятся изменениями задачи.

Проверьте `tree/` (выбранные файлы), полный diff и необходимые тесты именно подготовленного индекса:

```sh
GIT_INDEX_FILE=/tmp/oko-task-ready/index git diff --cached
GIT_INDEX_FILE=/tmp/oko-task-ready/index ./scripts/check staged
```

Подготовка не меняет рабочие файлы или настоящий индекс. До полного прогона создайте проверочную копию подготовленного дерева:

```sh
python3 scripts/task_changes.py checkout /tmp/oko-task-ready --output /tmp/oko-task-check
```

Это независимый локальный Git checkout: HEAD остаётся исходной базой, индекс и рабочие файлы содержат дерево задачи. Сохраняются удаления, переименования, бинарные файлы, ссылки и режим executable. Прежние dirty/staged и игнорируемые данные не переносятся. У копии нет remote; исходный checkout и его индекс не меняются. Изменённая подготовка и существующий каталог назначения отклоняются.

Установленные в исходном checkout `.venv` и `node_modules` подключаются ссылками, как и при автоматическом снимке `check all`. Существующие пути в подготовленном дереве сохраняются. Зависимости не устанавливаются; данные приложения и собранные assets не подключаются. Запускайте нужные наборы runner из копии. После исправления повторяется затронутый набор; успешный полный прогон не дублируется в исходном checkout. Копия сохраняет реальную Git-базу: `git diff --cached --check` относится только к задаче.

Конфликт останавливает подготовку, оставляя файл с маркерами в `conflicts/`; конфликт symlink/бинарного файла или удаления сообщается отдельно. Исправьте соответствующее изменение задачи и повторите подготовку в новый каталог. Сам инструмент решение конфликта не выбирает. Изменение исходного HEAD/индекса требует нового снимка и проверки объёма работы.

## Явный коммит

```sh
python3 scripts/task_changes.py commit /tmp/oko-task-ready --message 'feat: example'
```

Команда проверяет HEAD, исходный индекс, выбранные рабочие файлы, временный индекс и показанное `tree/`. Перед коммитом также проверяется возможность переноса прежних staged правок поверх результата. Сначала вручную выполните `./scripts/check staged` над подготовленным индексом: автоматические hooks в проекте отсутствуют. Восстановление выполняется под эксклюзивным `index.lock`: конкурентная запись либо обнаруживается до замены, либо получает стандартную ошибку занятого индекса. После успеха настоящий индекс содержит прежние staged изменения поверх нового HEAD, а рабочие файлы сохраняются.

При ошибке до коммита HEAD и настоящий индекс остаются прежними. Если hook изменил дерево коммита или индекс изменился одновременно с коммитом, команда сообщает необходимость ручного согласования и сохраняет текущий индекс; новый HEAD уже может существовать. Push, merge, reset, clean и перезапуск приложения инструмент не выполняет.

## Интеграция с актуальным main

После разрешения на публикацию переносите только коммиты задачи на свежий `main`:

```sh
./scripts/prepare-integration --output /tmp/oko-integration \
  --branch codex/my-task --commits <SHA-коммита-задачи>
```

Команда получает `main` из origin, фиксирует его SHA и создаёт новую копию вне
checkout именно на этом SHA. Затем переносит явно перечисленные коммиты, сохраняя
исходную ветку, индекс и dirty-файлы. Локальный clone иначе может назвать
`origin/main` старую локальную ветку `main`, даже после fetch в исходном checkout.
В новой копии origin указывает на исходный remote, а не на локальный каталог.
Конфликт оставляется только в копии; команда завершается с ошибкой и печатает путь.

Результат перед публикацией проверяется в этой копии. Зависимости при необходимости
подключите из исходного checkout; команда не устанавливает их и не выполняет push.
