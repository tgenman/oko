# Порядок разработки

## Выбор процесса

Для ограниченной задачи с общим изменяемым состоянием работает один исполнитель в одном checkout. Не делить её на агентов только по файлам: разделение должно давать независимые результаты. При необходимости параллельной работы сначала определить независимые объёмы и владение изменениями. Явно вызванные пользователем скиллы и его ограничения определяют процесс этой задачи, включая worktree, делегирование и ревью.

Перед изменением выбрать проверяемый результат и существующую границу проверки. При уже согласованных границах и неизменном контракте повторное согласование не требуется. Новую публичную границу или изменение поведения явно обозначить. Когда пользователь делегировал технические решения, исполнитель сам выбирает границы и проверки, фиксирует их и продолжает работу; повторное разрешение на каждое решение не требуется.

Для локальной правки документации или представления достаточно проверки соответствующего результата и diff. Для изменения состояния, асинхронного поведения, хранения или внешнего взаимодействия нужны проверки этих сценариев и ревью. Независимый reviewer получает ссылку на спецификацию, точную базу diff и результат проверок; повторное ревью сосредоточено на исправленных замечаниях и затронутом поведении.

После успешной проверки повторять её при новых изменениях или нерешённых сомнениях. Итоговый отчёт содержит выполненные проверки и ограничения. Коммиты, слияния, публикация и перезапуск пользовательского экземпляра выполняются в объёме запроса пользователя или явно вызванного им процесса.

## Действующие команды

Команды выполняются из checkout; runner сам определяет его корень:

```sh
./scripts/check ui
./scripts/check all
./scripts/check python types
./scripts/check http
```

Состав режимов задаёт [runner](../../scripts/check): UI проверяет выдачу модулей настоящим HTTP-сервером и браузерный интерфейс, полный режим добавляет серверные проверки. Отдельные наборы выбираются аргументами runner; после исправления повторяется затронутый набор. Команда сообщает результат и время каждого набора; отсутствие зависимости и прерывание не считаются успехом. Она не устанавливает зависимости и не запускает личные источники. Подготовка окружения, Git hooks, CI и переменные путей описаны в [инструкции проверок](../../tests/browser/README.md).

При локальной доработке сначала допустим один затронутый сценарий: выбранный Python-набор через `python -m pytest` или браузерный файл через `node --test`. После успешного целевого запуска выбирается режим runner по риску изменения. Не повторять полный набор без новых изменений или нерешённых сомнений.

Для UI-рефакторинга основное доказательство — действия в настоящем браузере, включая задержанные ответы и переключение контекста; для изменения серверного поведения — HTTP interface с временной SQLite и файлами. Тест не должен зависеть от того, в каком внутреннем module находится реализация. Общие помощники размещаются по [правилам структуры тестов](../architecture/package-layout.md).
