# Порядок разработки

## Выбор процесса

Для ограниченной задачи с общим изменяемым состоянием работает один исполнитель в одном checkout. Не делить её на агентов только по файлам: разделение должно давать независимые результаты. При необходимости параллельной работы сначала определить независимые объёмы и владение изменениями. Явно вызванные пользователем скиллы и его ограничения определяют процесс этой задачи, включая worktree, делегирование и ревью.

Перед изменением выбрать проверяемый результат и существующую границу проверки. Для настройки поведения сначала проверить существующие параметры; новый параметр вводить, когда существующие не выражают запрос пользователя. При уже согласованных границах и неизменном контракте повторное согласование не требуется. Новую публичную границу или изменение поведения явно обозначить. Когда пользователь делегировал технические решения, исполнитель сам выбирает границы и проверки, фиксирует их и продолжает работу; повторное разрешение на каждое решение не требуется.

Для локальной правки документации или представления достаточно проверки соответствующего результата и diff. Для изменения состояния, асинхронного поведения, хранения или внешнего взаимодействия нужны проверки этих сценариев и ревью. Независимый reviewer проверяет соответствие запросу, включая необходимость новых параметров, и получает ссылку на спецификацию, точную базу diff и результат проверок; повторное ревью сосредоточено на исправленных замечаниях и затронутом поведении.

После успешной проверки повторять её при новых изменениях или нерешённых сомнениях. Итоговый отчёт перечисляет выполненные наборы, их объём и ограничения. После падения полного прогона и успешного ограниченного повтора указывать оба результата; успех повтора относится к выбранным сценариям. Коммиты, слияния, публикация и перезапуск пользовательского экземпляра выполняются в объёме запроса пользователя или явно вызванного им процесса.

## Действующие команды

При грязном checkout используйте [снимок и подготовку коммита задачи](task-changes.md): сохраняйте исходное состояние до правок, выбирайте файлы явно и до полного прогона создавайте проверочную копию командой `task_changes.py checkout`.

Команды выполняются из checkout; runner сам определяет его корень:

```sh
./scripts/check ui
./scripts/check lifecycle
./scripts/check lifecycle --match 'a completed field write'
./scripts/check all --compact
./scripts/check python types
./scripts/check http
./scripts/check browser --files tests/browser/test_material_list.ts tests/browser/test_reader_http.ts
./scripts/check python --files tests/development/test_check_runner.py
```

Локальный `all` автоматически проверяет зафиксированный снимок рабочего дерева.
Новый код сначала добавьте в индекс. Отчёт записывайте после завершения либо в
исходном checkout после появления `Snapshot:`. Обновление checkout с остановкой
при ошибке, состав снимка, `--in-place` и чтение компактных отчётов описаны в
[процессе проверок](../development/check-workflow.md).

Состав режимов задаёт [runner](../../scripts/check): UI проверяет выдачу модулей настоящим HTTP-сервером и браузерный интерфейс, полный режим добавляет серверные проверки. Отдельные наборы выбираются аргументами runner; после исправления повторяется затронутый набор. Команда сообщает результат и время каждого набора; отсутствие зависимости и прерывание не считаются успехом. Она не устанавливает зависимости и не запускает личные источники. Подготовка окружения, Git hooks, CI и переменные путей описаны в [инструкции проверок](../../tests/browser/README.md).

Для локальной правки представления выбрать затронутый браузерный файл через `--files` и проверить diff; полный `ui` нужен при изменении общего UI-поведения или нерешённых сомнениях. При локальной доработке сначала допустим один затронутый сценарий: выбранный Python-набор через `python -m pytest` или браузерный файл через `node --require tsx/cjs --require ./scripts/register-browser-typescript.cts --test`. После успешного целевого запуска выбирается режим runner по риску изменения. Не повторять полный набор без новых изменений или нерешённых сомнений.

Для UI-рефакторинга основное доказательство — действия в настоящем браузере, включая задержанные ответы и переключение контекста; для изменения серверного поведения — HTTP interface с временной SQLite и файлами. Тест не должен зависеть от того, в каком внутреннем module находится реализация. Общие помощники размещаются по [правилам структуры тестов](../architecture/package-layout.md).
