# Завершение проектирования пайплайна

Интервью завершено по поручению пользователя. Ниже исторический аудит и раунды.
Открытые пункты закрыты простыми решениями в [итоговой спецификации](https://github.com/tgenman/oko/issues/89)
или явно исключены из объёма. Новых ответов пользователя этот документ не требует.

Сверка обсуждения и документов от 2026-10-22. Это карта решений, а не разрешение
на реализацию. Код приложения в рамках разбора не меняем.

## Что уже принято

- Одна `Publication` для поста, альбома, RSS-записи, статьи и видео. RSS-запись
  и статья по её ссылке — разные публикации. Feed–Publication — многие ко многим.
- Адаптер формирует `(platform, external_id)`; Око использует ключ для поиска
  и создания записи. Внутренние ID назначает Око. Это относится и к ссылкам на статьи.
- Два интерфейса адаптеров, строковые курсоры, обход от старых к новым,
  включённая начальная позиция, фиксированная верхняя граница истории, выбор последних N.
- Один процесс, SQLite, локальные файлы, независимые кроны этапов.
- Job возвращена: короткие транзакции захвата и фиксации, внешняя работа между ними,
  поколение запуска, восстановление прерванных заданий. Временные ошибки повторяются
  бесконечно с задержкой от минуты до часа. Предел трёх попыток отменён.
- Только последнее состояние. История переносимых данных остаётся в резервной копии.
  Новый текст сохраняется сразу; медиа догружаются. Изменение входа очищает устаревшие
  результаты; неизменившийся вход сохраняет их. Поздний ответ не применяется.
- Общий content с blocks/extra; форматы filtered_content, summarized_content,
  processing_metadata описаны в content-format.md. Начальные JSON — {}, media_ids — [].
- Отдельная загрузка каждого медиа в поток; locator интерпретирует адаптер.
  YouTube-видео внешнее, обложка и субтитры локальные.
- Раскрываем RSS → основная статья и Telegram → Telegraph без рекурсии.
  Результаты обработки объединённого входа сохраняем у исходной RSS/TG-публикации.
- Первое внедрение — Telegram Web с новым API поверх текущего хранения.
  История по дате и Restore исключены из целевой модели, но текущий код пока не меняем.

## Последний раунд: 59–64

Приняты частичные страницы с диагностикой (59), первый успешный результат общей
публикации с отбрасыванием второго (60), содержимое прямо из discover (61),
ключ ресурса отдельно от locator (62), удаление старого файла без ссылок без
ожидания скачивания замены (64). Подробности — в migration.md.
Принят пункт 63: подтверждённое отсутствие входа завершает этап с пустым
результатом без вызова модели; причина в processing_metadata. Ошибка получения
входа не маскируется пустым текстом. Пункт 65: один фид задаёт настройки всего
прохода. Таблица ниже отражает оставшуюся детализацию.

## Раунд 66–68

Скачиваем видео и аудио, кроме внешнего YouTube-видео. Статья без собственного
фида после сбора готова, её текст обрабатывается в составе исходного поста/RSS.
Постоянная ошибка останавливает Job с причиной и ручным повтором после исправления;
она не превращается в бесконечный временный повтор. Подробности в тематических
документах и migration.md.

## Исправленные расхождения документов

- Убраны заявления, что захват работы, временные повторы и формат медиа-блоков
  совсем не определены. Добавлены ссылки на принятые правила.
- В migration.md явно обозначена хронология: поздние решения заменяют ранние.
  Судьба истории уже определена решением 26; повторно выбирать её не нужно.
- Уточнено, что внешний ключ связанных публикаций приходит из адаптера.
- Глоссарий и docs/architecture описывают также действующий продукт (версии, история
  по дате, группы). Их нельзя считать уже переведёнными на целевую модель; обновление
  этих частей должно сопровождать соответствующий шаг миграции.

## Дерево оставшихся решений

Каждая ветка сначала требует правила поведения, затем окончательных типов и схемы.
Ниже перечислены вопросы; рекомендации интервью не считаются принятыми решениями.

| Ветка | Открытое правило поведения | Что можно завершить после ответа |
|---|---|---|
| Общая публикация | Один фид задаёт настройки всего прохода; первый актуальный результат принимается, второй отбрасывается | Обработка без фида, сохранение выбранных настроек и пересчёт |
| Внешняя идентичность | Нормализация URL, переименование Telegram-канала, ключ альбома, RSS без guid/id, коллизии и редиректы | Единый контракт идентичности для разных адаптеров и уточнения ключей |
| Частичные страницы | Ошибка отдельной записи discover и продвижение курсора; повтор повреждённой записи | Тип диагностики, атомарное сохранение страницы и позиции |
| Готовое содержимое discover | Как передать уже полученный текст RSS без повторного запроса | Окончательные DiscoveryPage и PublicationContent |
| Медиа | Как отличить обновлённый locator от нового ресурса; контракт загрузки видео/аудио (скачиваем всё, кроме YouTube-видео) | Описание медиа, контекст повтора, download_media и исходы замены/исчезновения |
| Недостаточный вход | Подтверждённое отсутствие завершает этап с пустым результатом, появление входа вызывает пересчёт | Представление отсутствия в API и причины в processing_metadata |
| Ошибки и управление | Постоянная ошибка останавливает Job; остаются детали отмены и внешних ожиданий | Точные статусы Job, типы исключений, ограничения областей и настройки |
| Хранение и удаление | Где живут настройки/курсор/привязка адаптера и отметка просмотра; безопасная очистка | Полная UML/DDL, ограничения связей, атомарность БД и файлов |
| Миграция | Порядок шагов после Telegram Web, критерии приёмки и возврат на резервную копию | Исполнимый план переноса и проверок без молчаливой потери поведения |

## Дополнительные найденные расхождения

- Противоречие удержания старого файла разрешено пунктом 64: файл без ссылок
  можно удалить после сохранения нового содержимого, не ожидая загрузки замены.
- В текущем Store внешний ID дополняется фидом, а Telegram-альбомы сопоставляются
  по участникам (`oko/storage/store.py`). При переходе к ключам адаптера нужно
  явное сопоставление старых ключей и новых, иначе появятся дубли и потеряются
  отметки просмотра. Само правило целевой идентичности этим не пересматривается.
- Текущий RSS discover уже передаёт teaser (`oko/collection/rss.py`); новый контракт
  должен сохранить эту возможность. Нынешнее пропускание некорректных RSS-записей
  в реализации не считается автоматически принятым правилом целевого API.

## Долги эскиза API

На момент аудита Kotlin-эскиз не являлся завершённым контрактом
(теперь заменён [UML и описанием типов](adapters.md)):

- У download_media нет сигнатуры и типов результата.
- Нет типов исключений, срока и области обязательного ожидания.
- DiscoveryPage возвращает PublicationContent с needsFetch и готовым содержимым
  при наличии (решение 80); диагностику ещё предстоит добавить.
- Частичный результат и диагностика отдельных записей не представлены.
- Недобор истории оговорён, но способ передать его причину/величину не закреплён.
- Сопоставление media с JSON по key закреплено решением 79; остаётся точный
  контракт обновления locator того же ресурса.
- Правила повторного сбора сохранены на словах, но не выражены окончательным контрактом.
  Нужно также описать открытие нового окна после завершения курсора с фиксированной границей.

Строковый курсор и ExternalReference уже согласованы; новые обёртки ради их
переименования не нужны. Типы результатов дополняем только для недостающих данных.

## Условие завершения

После ответов сверяем одну согласованную версию API, полную схему хранения,
таблицу переходов и план миграции. Проверочные сценарии: повторная страница,
общая публикация, обновление статьи, смена адаптера, истёкший locator, падение
между записью файла и БД, поздний ответ, просмотр/удаление во время работы.
Отложенные функции перечисляем явно; они не должны оставлять необходимый путь
без определённого поведения. Начало реализации — отдельное указание пользователя.

## Раунд 69–71

Настройки сбора (`adapter`, `config`, `cursor`, `interval_seconds`) находятся
в Feed, отдельной FeedCollection нет. Статьи telegraph/other_web без фида
загружает web_adapter. Заголовок Publication может быть пустой строкой,
дата источника — null, время обнаружения обязательно. Схема entities.md обновлена.

## Раунд 72–73

Не храним память о просмотре ради исключения повторного сбора; viewed_at не добавляем.
Сбор определяется курсором. Решение 74 подтверждает: повторный обход истории
или окна обновления намеренно может вернуть просмотренное. Память о просмотре
ради предотвращения возврата не переносим в целевую модель.
Неизвестные size_bytes/mime_type/storage_key у MediaFile — null, имя без названия —
пустая строка; при ready файл и storage_key обязательны.

## Раунд 75–76

В Feed приняты filter_config и summary_config (JSON); настройки фиксируются
на начало прохода. Публикации страницы и новый курсор сохраняются одной короткой
транзакцией; повтор страницы после сбоя использует внешний ключ существующих записей.

## Раунд 77–78

Файл полностью сохраняется в постоянном хранилище перед фиксацией ready в БД;
транзакция проверяет актуальность задания. Неиспользуемые файлы и остатки
прерванных загрузок удаляются периодической очисткой, активные сохранения
защищены. Физическое удаление не удерживает транзакцию публикации.

## Раунд 79–80

Приняты MediaReference и единый PublicationContent для discover/fetch.
Kotlin-эскиз обновлён. В ответе адаптера `$media` содержит key ресурса, не locator;
перед сохранением ключ заменяется внутренним ID. needsFetch относится к содержимому,
а загрузка медиа независима.

## Замена экспериментального формата

По просьбе пользователя Kotlin-эскиз удалён; актуальный API описан в adapters.md
через UML и таблицы типов. OpenAPI для внутрипроцессных адаптеров не вводится.
