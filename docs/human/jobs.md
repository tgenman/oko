# Задания выполнения

## Согласованная граница

В целевой архитектуре используем отдельную служебную таблицу `Job`, опираясь
на текущую `jobs`. Это решение заменяет временный отказ от Job в пунктах 50–54.
Первый этап миграции остаётся API адаптеров; код очереди в рамках интервью не меняем.

Предыдущий этап сохраняет результат и переводит статус публикации. Следующий этап
выбирает подходящие публикации и организует их выполнение через Job.
`Publication.status` описывает этап обработки, `MediaFile.status` — готовность файла,
`Job.status` — состояние запуска. Новые статусы публикации ради захвата не требуются.

## Предлагаемые служебные поля

| Поле | Назначение |
|---|---|
| `operation` | Обнаружение, загрузка публикации, загрузка медиа, фильтрация или суммаризация |
| `target_id` | Внутренний ID обрабатываемого объекта |
| `status` | Ожидает, выполняется, завершено, отменено или остановлено с ошибкой |
| `next_run_at` | Срок следующего разрешённого запуска |
| `retry_delay` | Текущая задержка повтора |
| `generation` | Отличает текущий запуск от отменённого или заменённого |
| `error` | Последняя ошибка |

Названия и физическая схема уточняются при реализации контракта; новую параллельную
очередь рядом с текущей jobs не создаём.

Уникальность задания — `(operation, target_id)`. Для нового входа или ручного запуска
переиспользуется строка с увеличением `generation`. Повторный проход крона не создаёт
дубликат ожидающей или выполняющейся работы. История всех запусков не накапливается.
Очистку старых завершённых заданий планируем отдельно позже; сроки и правила удаления
пока не выбраны. Удаление и последующее создание строки не должны возвращать допуск
старому ответу: защиту поколения нужно сохранить и при очистке.

## Короткие транзакции

Принято: транзакция не держится во время внешнего вызова. SQLite допускает только
одну одновременную транзакцию записи, поэтому длительный сетевой вызов не должен
занимать её. [SQLite Transactions](https://www.sqlite.org/lang_transaction.html).

Согласованный порядок:

1. В короткой транзакции проверить допуск и срок, захватить ожидающий Job,
   перевести его в `running` и назначить новое поколение запуска.
2. Выполнить внешний вызов без открытой транзакции.
3. В короткой транзакции проверить поколение, актуальность входа и существование
   непросмотренного объекта; атомарно сохранить результат и завершить Job.
4. Ответ потерявшего актуальность запуска не публикуется.

```text
BEGIN
  Проверить допуск и перевести Job: pending → running
COMMIT

Скачивание / вызов модели — без транзакции

BEGIN
  Проверить актуальность запуска, сохранить результат
  Перевести Job: running → done
COMMIT
```

Сохранённое значение `running` не удерживает блокировку SQLite. Другие этапы
могут записывать свои результаты во время внешнего вызова. Исполнитель выбирает
только ожидающие задания, а проверка и перевод в `running` атомарны, поэтому
одну ожидающую работу не захватывают два исполнителя.

При следующем старте единственного процесса до запуска исполнителей прерванные
`running` возвращаются в ожидание с новым поколением и задержкой повтора. Внешний
вызов может повториться, если прошлый ответ не был зафиксирован. Уже сохранённый
актуальный результат остаётся доступен. Сроки повторов и ограничения источника
сохраняются. Старт восстановления допускается только после подтверждения,
что прежний экземпляр больше не владеет хранилищем.

## Повторы

Временные ошибки повторяются без ограничения числа попыток. Задержка удваивается
от 1 минуты до 1 часа; начальная и максимальная задержки настраиваются.
Подтверждённая недоступность выбранным способом доступа ждёт изменения доступности.
Ограничения источника действуют для затронутой области.
Возвращение Job не возвращает предел трёх попыток или настройку счётчика попыток.

Постоянная ошибка (например, нарушение контракта адаптера или неподдерживаемый
формат) останавливает Job. Причина показывается пользователю; после исправления
нужен ручной повтор. Статус публикации остаётся на незавершённом этапе, другие
задания продолжаются. Наличие такой Job не позволяет крону автоматически создать
повтор той же работы только потому, что статус публикации всё ещё ожидающий.
Это не прежний failed по исчерпанию попыток: предел попыток не возвращается.

Готовые актуальные тезисы могут оставаться доступными, пока отдельный Job выполняет
ручную регенерацию. Сведения о принятом результате не подменяются состоянием запуска.

Точные коды статусов и очистка старых заданий ещё требуют фиксации.
Во время интервью изменяется только документация.
