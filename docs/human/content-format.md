# Формат содержимого публикации

## Согласованный исходный content

После получения содержимого `content` использует общую структуру:

```json
{
  "blocks": [],
  "extra": {}
}
```

До получения содержимого поле равно `{}`. Готовность определяется статусом,
а не наличием блоков. Порядок `blocks` задаёт порядок содержимого.

| Тип блока | Поля и смысл |
|---|---|
| `text` | `role`: `body` или `description`; `text`: Markdown |
| `quote` | Цитируемый `text`, `author`, `source_url`; чужой текст отделён от собственного |
| `media` | `ref` с маркером `$media`; `role`: `image`, `cover`, `video`, `audio`, `attachment`, `subtitles`; возможны `caption`, `language` |
| `publication` | `publication_id`: внутренняя ссылка на связанную публикацию; её текст здесь не дублируется |
| `external_media` | `kind` и `url` внешнего медиа, например YouTube-видео без локального файла |

В ответе адаптера `$media` содержит ключ ресурса внутри публикации. Список
`media: List<MediaReference>` передаёт соответствующие key, locator, name, mimeType
и sizeBytes. Оркестратор сопоставляет ключи, назначает внутренние ID и подставляет
их перед сохранением. Locator непосредственно в `$media` больше не передаётся. Связанные публикации также получают внутренние
ID при сохранении; точный маркер внешней ссылки в ответе адаптера ещё определяется.

Специфичные поля размещаются в `extra`, например в `extra.telegram`.
Общие потребители могут игнорировать незнакомые расширения. Поля, необходимые
для корректного показа или обработки, должны входить в общий контракт.

## Пример сохранённого Telegram-поста

Здесь `M1` и `P1` — условные обозначения внутренних UUID.

```json
{
  "blocks": [
    {
      "type": "text",
      "role": "body",
      "text": "Текст поста с **форматированием** и ссылкой на статью."
    },
    {
      "type": "media",
      "role": "image",
      "ref": { "$media": "M1" },
      "caption": "Подпись к фотографии"
    },
    {
      "type": "publication",
      "publication_id": "P1"
    }
  ],
  "extra": {
    "telegram": { "is_album": false }
  }
}
```

## Пример YouTube

```json
{
  "blocks": [
    { "type": "text", "role": "description", "text": "Описание видео" },
    { "type": "external_media", "kind": "video", "url": "<URL видео>" },
    { "type": "media", "role": "cover", "ref": { "$media": "M1" } },
    {
      "type": "media",
      "role": "subtitles",
      "language": "ru",
      "ref": { "$media": "M2" }
    }
  ],
  "extra": {}
}
```

## filtered_content

Хранит готовые очищенные блоки, причину и точные удаления. Модель возвращает решение
и фрагменты для удаления, сервис проверяет их по исходнику и строит блоки сам.
Произвольное переписывание исходного текста фильтром не допускается.

```json
{
  "blocks": [
    {
      "type": "text",
      "role": "body",
      "source_publication_id": "P1",
      "text": "Полезный текст поста."
    },
    {
      "type": "text",
      "role": "body",
      "source_publication_id": "P2",
      "text": "Полезный текст связанной статьи."
    }
  ],
  "reason": "Удалён рекламный фрагмент статьи.",
  "removed": [
    {
      "publication_id": "P2",
      "block_index": 0,
      "text": "Точный удалённый фрагмент."
    }
  ],
  "extra": {}
}
```

- Типы блоков совпадают с исходным `content`.
- `source_publication_id` указывает происхождение блока в объединённом представлении.
- В `removed` индекс указывает блок исходной публикации, переданный в конкретный
  запрос обработки. Удаления проверяются по тому же входу; поздний результат для
  изменившегося входа не применяется.
- Обработка статьи в контексте поста не изменяет исходный `content` самой статьи.
- При отсутствии изменений `reason = ""`, `removed = []`.
- При исключении публикации `status = filter_out`, `blocks = []`, причина обязательна.
  Исходный `content` сохраняется.
- Цитаты остаются отдельными блоками с различением авторства.

## summarized_content

Хранит список тезисов с внутренними ID публикаций-источников.

```json
{
  "points": [
    { "text": "Первый тезис.", "source_publication_ids": ["P1"] },
    { "text": "Тезис по статье.", "source_publication_ids": ["P2"] },
    { "text": "Вывод из поста и статьи.", "source_publication_ids": ["P1", "P2"] }
  ],
  "extra": {}
}
```

Ссылки для открытия берутся из `Publication.url`. Все указанные ID должны входить
в фактический запрос к модели; неизвестный источник не принимается.

До выполнения этапов оба результата равны `{}`; готовность определяется статусом.
Метаданные обработчика и подписи хранятся отдельно от пользовательского содержимого,
в `Publication.processing_metadata`, атомарно с результатами.

## processing_metadata

Секции `filter` и `summary` содержат `input_hash`, `settings_hash`, `processor`,
`model`, `completed_at` и параметры фактического запуска. Проверки актуальности
не должны считать смену модели/параметров будущего запуска причиной автоматического
пересчёта готового результата. Метаданные и содержимое относятся к одному принятому
результату; поздний ответ для изменённого входа не публикуется.

Обычная суммаризация использует очищенное фильтром представление при включённой
фильтрации, иначе исходное. YouTube использует исходные субтитры. Публикация
в состоянии `filter_out` не суммаризируется.

## Подтверждённое отсутствие входа

Если источник подтвердил отсутствие текста для обработки, модель не вызывается.
Этап завершается с пустым результатом; для суммаризации это
`{"points": [], "extra": {}}`. Причина сохраняется в `processing_metadata` вместе
с результатом. Это не `{}` незавершённого этапа и не ошибка скачивания.
При появлении входа результат пересчитывается. Точный код причины и поля метаданных
пропущенного вызова ещё предстоит включить в окончательную схему.

Весь проход обработки общей публикации использует настройки одного фида;
происхождение принятого результата должно соответствовать именно этим настройкам.
