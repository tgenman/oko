# Обновление checkout и изолированные проверки

Результат ретроспективы 2026-10-19: остановка цепочки при ошибке обновления,
зафиксированный состав полной проверки, отдельный исход изменения checkout
и компактные отчёты. Изменения касаются инструментов разработки.

## Обновление

```sh
./scripts/update-checkout
```

Команда проверяет отсутствие tracked/staged правок, выполняет `git pull --ff-only`
для текущей tracking-ветки, затем сборку и `validate_frontend()`. Ошибка любого
шага останавливает последующие. Сообщение об успешном обновлении содержит HEAD
и появляется только после всех шагов. Конфликт, расхождение веток и локальные
правки остаются для явного разрешения; команда их не сбрасывает и не коммитит.
Личные данные не копируются, приложение не запускается. Используются уже
установленные npm-зависимости и Python из `OKO_PYTHON` / `.venv`.

## Полная локальная проверка

```sh
./scripts/check all --compact
```

Локальный `all` фиксирует рабочее содержимое файлов, известных Git index:
учитывает staged новые файлы, unstaged правки и удаления. Индекс и HEAD исходного
checkout сохраняются. Новый код в `frontend`, `oko`, `tests`, `scripts` и `api`
нужно сначала явно добавить в индекс: иначе команда остановится, а не пропустит
его молча. Остальные untracked-файлы, включая резервные копии, в снимок не входят.

Снимок создаётся во внешнем временном каталоге через материализацию дерева
`task_changes.py`; его Git index независим, remotes удалены. Данные приложения
и готовые assets не переносятся. Установленные `node_modules` и `.venv`
переиспользуются по ссылке, без установки зависимостей. Сборка создаётся в снимке.
Исходный checkout можно редактировать после сообщения `Snapshot:`.

Логи и report.json по умолчанию остаются в исходном `.scratch/check-runs`.
Метаданные отчёта содержат исходный checkout, проверяемый checkout, HEAD и tree.
Снимок сохраняется для разбора результата; его путь печатается при запуске.
После подготовки launcher заменяется runner через execve: отмена остаётся у
существующего владельца процессов, завершает его тесты и сохраняет report с кодом 130.
Для грязного checkout, где нужно отделить правки разных задач, сначала применяется
[подготовка выбранного дерева](../agents/task-changes.md): автоматический снимок
фиксирует видимые tracked-правки целиком и не выбирает объём задачи.

В CI, а также при явном `--in-place`, проверяется текущий checkout. Целевые наборы
сохраняют прежний запуск. Снимок не отменяет проверку неизменности файлов:
если тест меняет tracked/untracked файлы внутри проверяемого checkout, общий
запуск завершается с ошибкой. Прошедшие тестовые наборы сохраняют PASS,
а независимый `checkout.status` становится FAIL со списком `changed_files`.
Сообщение не приписывает изменение файлов тесту или человеку без доказательств.

## Компактный вывод

`--compact` показывает итог наборов, упавшие сценарии, отдельный checkout_changed,
время и путь отчёта. Полный вывод команд сохраняется в output.log.
Сохранённый отчёт можно прочитать без повторного запуска:

```sh
./scripts/check-report .scratch/check-runs/<run>/report.json
./scripts/check-report .scratch/check-runs/<run>/report.json --json
```

Сводка исключает длинные command inventories. Она сохраняет исходный exit_code,
статусы наборов, failures, изменения checkout, длительность и путь полного лога.
Исторические отчёты без отдельного checkout-исхода помечаются NOT RECORDED.
Некорректный/незавершённый отчёт возвращает код 2 без traceback.

## Проверка инструментов

CLI проверяются на временных Git-репозиториях и заменяемых build/Python
executables: отказ Git/build/validation, локальные правки, стабильность снимка
при редактировании исходника, мутация тестового checkout, новый staged код,
исключение untracked данных и компактный вывод с полным логом.
Эти сценарии входят в существующую группу tools и существующий CI.


## Длительности и выбор инструментальных проверок

Pytest-запуски сохраняют JUnit XML рядом с отчётом. `test_durations` и
`file_durations` в report.json содержат времена сценариев и файлов, а
`worker_durations` — длительности параллельных исполнителей. Elapsed группы
учитывает самого долгого исполнителя и при FAIL. `check-report` показывает
медленные файлы; JSON-сводка также сохраняет пять медленных сценариев.
Исторические отчёты без этих полей по-прежнему читаются.

Автоматический tools-набор в `all` и `tools --if-changed` использует карту
входов `TOOL_FAMILIES` в scripts/check. Объединяются все затронутые семейства;
неизвестный tooling-вход или недоступное сравнение выбирает полный набор.
`tools` без `--if-changed` по-прежнему запускает все инструментальные тесты;
явный `--files` сохраняет приоритет. Выбранные пути записываются в
`tool_selection.tests` отчёта.


## Распределение по измеренным длительностям

Runner сохраняет последние три успешных измерения каждого файла в
`.scratch/check-cache/test-timings/<test-groups>.json` и использует их медиану при распределении
Python/tools и браузерных файлов. Число исполнителей и состав групп прежние.
Сначала файлы назначаются по прогнозу времени, затем внутри группы выполняются
в прежнем порядке по размеру. Для новых файлов оценка по размеру масштабируется
из известных измерений; при отсутствии или повреждении истории действует прежняя
балансировка по размеру. Прогнозы — только подсказки: они не отбирают тесты и
не заменяют результат выполнения.

Полные и отдельные группы имеют разные файлы истории. Целевой `--files` не переобучает её.
История разделяется по платформе, архитектуре, числу CPU и browser-workers.
Неуспешные проверки, изменившийся checkout и выборки по кейсам (`--match`, `::`,
pytest selectors) её не обновляют. Запись выполняется атомарно под файловым lock.
Для frozen all используется история исходного checkout; снимок по-прежнему
проверяет зафиксированные байты. `timing_plan` и `timing_history` в report.json
показывают использованные подсказки и прогноз нагрузки. Браузерный дополнительный
Node reporter пишет реальные времена исходных файлов, сохраняя обычный TAP.

CI переносит только этот каталог advisory JSON через pinned actions/cache. Матрица,
параллельность, обязательные группы и Full checks остаются прежними. Попадание
в timing cache никогда не пропускает тесты. Проверка задержки чтения по-прежнему
выполняется после функциональных браузерных сценариев с теми же 320 кликами
и бюджетом p95 <200 мс.
