# Единое переключение трёх воркеров (#115)

Ниже сохранён план перехода #115 для прежнего выпуска. Его команды и состояние
готовности относятся к той версии и не являются текущей процедурой развёртывания.

## Что подготовлено и что ещё требуется

Исходный код проверяется целиком: HTTP → application → сервисы → репозитории;
CollectionWorker, FilterWorker и SummaryWorker имеют собственные кроны в одном
процессе. Runtime над пайплайном из #89 заменён этим решением пользователя.
Сетевые вызовы находятся вне общей короткой транзакции одного SQLite-соединения.
Доменный результат и условный done Job одного поколения сохраняются одним commit.

[Схема](../human/pipeline-workers.md), [архитектура](../architecture/application-layers.md),
[результаты подготовки](../verification/pipeline-acceptance-115.md).

Синтетическая приёмка не определяет формат установленной базы. После разрешения
на выпуск сначала установить фактические старый SHA и формат данных. Текущий
`python -m oko.storage.migration` переносит только Publication-формат с маркером
`publication-pipeline=complete`. При более старом формате — остановиться:
нужны отдельно проверенные преобразование и его совместимость по
[исторической процедуре](publication-migration.md). Нельзя запускать новый Store
над старым рабочим каталогом или считать исторический converter частью main.

## Порядок выпуска

Все значения путей и SHA ниже должны быть явно записаны в отчёт **до команд**.
Использовать инструменты проверенного выпуска из отдельного чистого checkout.
Ни одна команда не должна полагаться на default `--home`.

| Значение | Назначение |
| --- | --- |
| `REPO` | Чистый checkout проверенного нового кода |
| `NEW_SHA` | Полный SHA с успешным полным прогоном и CI |
| `OLD_HOME`, `OLD_SHA` | Фактическая прежняя установка и её выпуск |
| `NEW_HOME` | Новый отдельный каталог установки, отличный от OLD_HOME |
| `BACKUP` | Проверенная копия прежнего кода/SQLite/файлов |
| `CANDIDATE_DATA` | Новый отдельный каталог пробного переноса |

1. **Подготовить выпуск без запуска.** После разрешения записать фактический
   старый SHA, image/helper SHA, формат данных, пути, свободное место и доступный
   способ возврата. Подготовить один неизменяемый новый выпуск через
   `scripts/oko-release --repo "$REPO" --home "$NEW_HOME" prepare --ref "$NEW_SHA"`,
   затем `install --release "$NEW_SHA"` с теми же `--repo/--home`.
   `install` не запускает HTTP и воркеры. Старый полный путь пока работает.
2. **Остановить старый полный путь и все записи.**
   `scripts/oko-release --home "$OLD_HOME" stop` должен завершиться успешно.
   Записать отсутствие reader-контейнера, LaunchAgent/helper, активного владельца
   `data/instance.lock`, владельца `scratch/execution.lock` и `scratch/active.json`.
   Остановленный HTTP исключает новые команды. Отдельные ручные процессы,
   CLI и другие установки с доступом к этому каталогу тоже должны отсутствовать.
   Не удалять lock/active.json для обхода отказа. Одного свободного порта мало.
3. **Повторить проверку групп на остановленном исходнике.** Через Python нового
   выпуска открыть `OLD_HOME/data/state.sqlite` только `mode=ro`, под
   `oko.storage.migration.offline_owner(OLD_HOME/data)` вызвать `group_guard(db)`.
   Записать результат. Группа с материалами, пустое подключение группы,
   сообщения/темы, настройки, история, Job, файловые ссылки и неподтверждённый
   владелец/тип означают отказ; не удалять и не исключать строки ради переноса.
   Проверка выполняется до копирования; мигратор повторяет её под тем же
   владением непосредственно перед своей копией. Не возобновлять старые записи
   между этими проверками и переключением.
4. **Сохранить и проверить backup.**
   `scripts/oko-release --home "$OLD_HOME" backup` возвращает отдельный BACKUP.
   Инструмент сверяет SHA256 дерева источника и скопированного дерева до записи
   `backup.json`; сохранить manifest прежнего выпуска и доступные ему код/image.
   Проверить SQLite `quick_check` в копии только для чтения и наличие всех файлов,
   на которые ссылается ready-медиа. Повреждение, нехватка места или изменение
   источника означают отказ. Backup с отсутствующим `backup.json` не принят.
5. **Перенести в отдельную копию и принять отчёт.** Python именно нового выпуска:
   `python -m oko.storage.migration "$BACKUP/data" "$CANDIDATE_DATA"`.
   Мигратор не запускает воркеры и ничего не переключает. Проверить
   `migration-report.json`: verified/source_unchanged/settings.verified=true,
   switched=false, пустой conflicts; сопоставления ID, counts, настройки, результаты,
   пересчитываемые публикации и хэши файлов. Он проверяет quick_check,
   foreign_key_check, идентичность ID и сохранность устойчивых настроек.
   Проверенные Telegram-профили потребуют повторной проверки доступности после
   запуска; их account/user_id/generation/checked сохраняются.
   Сохранить отчёт и отдельно отметить непереносимые элементы и ограничения.
   Любой конфликт или отказ запрещает переключение; неизвестные данные не
   считаются пустыми. Исходник и backup остаются сохранены.
6. **Установить принятую копию без включения работы.**
   `scripts/oko-release --home "$NEW_HOME" migrate --source "$CANDIDATE_DATA"`.
   Каталог назначения должен быть пустым. Инструмент проверяет полное совпадение
   скопированных байтов до открытия Store и выключает общую работу; при ошибке
   новый частичный target удаляется, кандидат сохраняется. Не использовать
   `update` для преобразования схемы и не импортировать исходник в обход шага 5.
7. **Одно переключение кода и данных.** При остановленном OLD_HOME запустить
   только `scripts/oko-release --home "$NEW_HOME" start`. Один manifest выбирает
   совместимые reader image и helper. Новый процесс запускает HTTP и все три
   крона вместе; общая работа пока выключена. Не включать старые циклы, отдельные
   режимы фильтра/тезисов и двойную запись. Проверить `/api/v3/status`, подписки,
   карточки, материал и локальные медиа через существующий HTTP/браузер;
   подтвердить версии и отсутствие старого писателя. Токены в отчёт не сохранять.
8. **Включить работу и проверить восстановление в разрешённом объёме.** Включение
   разрешает все три воркера, а не поэтапные выпуски. Реальные источники и модели
   требуют соответствующего разрешения пользователя: если его нет, оставить
   работу выключенной и не считать рабочую приёмку завершённой. Проверить общий
   проход, готовые результаты, отсутствие зависших running Job, штатную остановку
   и повторный запуск. Сохранить фактические результаты и ограничения.

Запуск Store/HTTP уже может писать recovery и служебные версии **даже при
выключенной работе**. Поэтому граница «до новых записей» относится не к первому
вызову модели, а к любому изменению новой библиотеки, включая старт процесса.

## Возврат и отчёт выпуска

До новых записей и до запуска нового процесса возврат использует сохранённую
согласованную тройку прежний код + база + файлы. Не подставлять новый каталог
данных старому коду. Возобновление OLD_HOME входит в отдельно разрешённую операцию
выпуска, с подтверждением остановки NEW_HOME и освобождения портов/владения.

После любых новых записей **не выполнять автоматический rollback/restore**,
переключающий читателя на устаревшую библиотеку. Сначала остановить новый экземпляр,
сохранить оба состояния и новые файлы, описать различия; нужен согласованный
перенос новых данных либо отдельное явное разрешение на их потерю. Наличие
архива retired-data само по себе таким разрешением не является.

Отчёт рабочего выпуска должен содержать разрешение и его границы; OLD_SHA/NEW_SHA,
фактические image/helper и origin/main SHA; пути OLD_HOME/NEW_HOME/BACKUP/кандидата;
доказательства остановки всех писателей; оба результата guard; backup digest и
проверку SQLite/файлов; отчёт миграции и ограничения; время единого переключения,
HTTP/браузерную приёмку, проверку перезапуска и положение границы новых записей.
Старое хранилище и backup не удаляются. Только после этой приёмки можно завершить #115.

### Консервативный отказ на осиротевших данных

Guard проверяет владельца каждого известного вида Job и устойчивых ссылок
истории/Telegram/медиа. Неизвестный вид Job тоже даёт конфликт. Даже завершённая
Job удаления без сохранившейся Publication не доказывает, что её владелец был
каналом. Такая библиотека потребует отдельного разбора конфликта и согласованного
решения; инструмент не удаляет эту запись и не считает её безопасной автоматически.
Это ограничение подготовки переноса, а не предложение очищать рабочую базу.


## Сохраняющий перенос известных legacy-остатков

После явного поручения пользователя выполнить совместимый перенос допускается
`python -m oko.storage.migration SOURCE NEW_DIRECTORY --legacy`. Это не очистка:
все старые Job и history_members остаются в тех же таблицах, с теми же ID и
значениями. В новой базе добавляются проверяемые аудиторские копии завершённых
технических остатков; счётчики истории не теряют эти записи.

Для шага 3 исходник под offline_owner открывается mode=ro, создаётся только
SQLite-копия в памяти (ReadingConnection); на ней выполняются normalize и
строгий group_guard. Восстановление типа требует сохранённого public preview
claim и полного совпадения старого Web-binding, владельца, username, URL и
адаптера. Просто отсутствующий source_kind или kind=web не дают допуска.
Повторить эту проверку после остановки всех записей. Исходник не исправлять.

После проверки backup шаг 5 выполняется с --legacy. Проверить в отчёте
compatibility.restored_types и compatibility.retained; убедиться, что аудит
совпадает с исходными строками, source_counts и ID сохранены, исходник не изменён.
Прочие этапы процедуры остаются прежними. Неизвестные и активные осиротевшие Job, pending-история без владельца,
группы и недоказанные типы по-прежнему останавливают переключение. Этот режим не
преобразует формат до Publication. Архив — служебный аудит переноса, а не активная
история чтения; он сохраняется после дальнейшего штатного удаления текущих строк.
