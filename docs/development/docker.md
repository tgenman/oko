# Рабочий выпуск на Mac

Око запускается в Docker Desktop (`desktop-linux`), а Codex — пользовательским LaunchAgent на Apple Silicon Mac. Адрес читателя — `http://localhost:8765`, опубликован только `127.0.0.1:8765`. Это реализация [проекта](../architecture/docker-runtime.md); запуск выпуска и перенос личных данных выполняются отдельными действиями.

## Подготовка

Нужны работающий Docker Desktop со свободным портом 8765, Git и `uv 0.11.28`. `prepare` создаёт отдельное Python 3.13 окружение Mac и строит `linux/arm64` образ с Python 3.13.9 и Node 24.10.0 на этапе сборки. Python/npm зависимости берутся из lock-файлов. Builder проверяет generated API, типы и целостность frontend assets. Runtime содержит только Python-окружение и готовые assets; Node остаётся в builder.

Отслеживаемые файлы checkout должны быть чистыми; посторонние untracked файлы не входят в Git snapshot. Изменения текущей разработки сначала сохранить в отдельной ветке/checkout; `prepare` не сбрасывает и не коммитит их. Выпуск строится из явного Git ref через `git archive`, а не из изменяемого рабочего дерева:

```sh
./scripts/oko-release prepare --ref <проверенный-коммит>
./scripts/oko-release install --release <полный-SHA-коммита>
```

Команды не запускают приложение. Чужой listener на порту 8765 не завершается автоматически. В браузере используйте `http://localhost:8765`; настройка DNS и системных прав не требуется.

Выпуски и данные по умолчанию находятся в `~/Library/Application Support/Oko/`. Альтернативный путь задаётся глобальным `--home /абсолютный/путь` перед именем команды и должен быть вне checkout. Эта опция предназначена также для временных синтетических проверок. Другой каталог получает отдельные Compose project и LaunchAgent label; порты 8765/8767 по-прежнему общие.

## Запуск и остановка

```sh
./scripts/oko-release start
./scripts/oko-release status
./scripts/oko-release open
./scripts/oko-release stop
```

`start` проверяет порт 8765, подключает LaunchAgent, запускает Compose и проверяет HTTP status/Store, затем доступность `/v1/health` helper из контейнера с правильным секретом и версией выпуска, без inference. Повторный `start` проверяет уже работающий собственный контейнер, не перезапуская его. При неуспехе контейнер и helper останавливаются. В `~/Library/LaunchAgents/` создаётся ссылка на приватный plist; при следующем входе helper возобновится. Для тестовой установки есть глобальная опция `--launchagents /временный/каталог` у `install`. Docker восстанавливает контейнер по `unless-stopped`, когда запущен Docker Desktop. Сон Mac и остановка Docker прерывают доступность.

`stop` останавливает только Compose project выбранной установки, выгружает её LaunchAgent и удаляет принадлежащую ей ссылку автозапуска. После выгрузки до 30 секунд ожидает освобождение execution lock и проверяет отсутствие `scratch/active.json`. Оставшийся marker означает неподтверждённую очистку дочерних процессов; команда сохраняет его и блокирует backup, update, restore и migrate до отдельной проверенной очистки. Свободный lock при оставшемся marker не считается безопасной остановкой. `KeepAlive` не отменяет явную остановку; следующий `start` снова включает автозапуск. Чужой plist сохраняется, запуск сообщает конфликт. Настройки Docker Desktop и его автозапуска команда не меняет.

Первый запуск нового хранилища использует `--initially-disabled`: сбор и обработка выключены до отдельного включения в интерфейсе. При обычных restart сохраняется ранее выбранное состояние. Закрытие вкладок не завершает сервер. `open` получает свежий reader bearer из приватного `data/runtime.json` и открывает внешний URL с fragment, не печатая токен. Браузер создаёт отдельную от bearer сессию только явным запросом `X-Oko-Remember: 1`. Readiness/health probe такого заголовка не отправляет и не создаёт браузерных credentials. После очистки браузерной сессии снова выполните `open`.

## Изоляция

- `releases/<SHA>/source/` — Git snapshot и собственная `.venv` процесса Codex. Manifest фиксирует commit, digest образа, helper revision и protocol 1. Образ запускается по `sha256`, старые выпуски сохраняются.
- `data/` — долговечные данные читателя, включая браузерную авторизацию. В Compose монтируется только этот каталог и отдельный secret.
- `secrets/codex` и `codex.json` — файлы с правами `0600`. Секрет связи не является reader bearer. Авторизация Codex остаётся на Mac. Бинарник Codex проверяется helper по существующему allowlist SHA-256; внешний app update может заменить его. В таком случае обработка блокируется до отдельной проверки нового CLI; reader продолжает работать. Бинарник приложения Codex не копируется в выпуск.
- `scratch/` — приватные временные задания helper; `logs/` — его журналы. Helper слушает только `127.0.0.1:8767`; контейнер обращается через `host.docker.internal`.
- Контейнер использует UID/GID владельца Mac, read-only rootfs, временный `/tmp`, отключённые capabilities. Checkout, dev `.venv`, `node_modules`, личные данные и Telegram-сессии не входят в Docker context: `.dockerignore` содержит явный source allowlist и исключения секретов.

Health контейнера проверяет reader HTTP со свежим bearer и Store. Наличие Codex не является условием рестарта контейнера. Доступность helper отображается отдельно в интерфейсе. До переноса обязательна синтетическая проверка именно установленного Docker Desktop: достижимость loopback helper из контейнера, запрет LAN, неверный bearer/Origin, отмена и прекращение осиротевшего задания. HTTP adapter tests не доказывают сетевую достижимость Mac.

## Первый перенос

Перенос личных данных требует отдельного задания. Старое Око должно быть остановлено; PID из контейнера не используется для завершения процесса Mac.

```sh
./scripts/oko-release migrate --source /абсолютный/путь/к/старому/data
```

Команда требует пустой `data/`, проверяет lock старого процесса и копирует каталог, сохраняя оригинал. Символические ссылки требуют отдельного плана и отклоняются. Копия выключается через Store до первого запуска. Отдельно проверьте Telegram-профили и пути сессий, абсолютные пути старого Mac, llama.cpp адрес и прокси: localhost в контейнере указывает на контейнер. Telegram-окружение и авторизация не копируются из checkout автоматически. До проверки путей не включайте сбор; перенос внешних Telegram-сессий не следует подменять подключением checkout целиком.

## Обновление, резервная копия и возврат

Для обычного обновления до актуального `origin/main`:

```sh
./scripts/update-working-oko
```

Скрипт получает `main` из GitHub и фиксирует его SHA, создаёт временный чистый
clone и вызывает из него `prepare`, затем `update`. Текущий checkout не переключается;
незавершённые tracked и untracked правки в сборку не попадают. При ошибке подготовки
переключение рабочего выпуска не выполняется. Временный clone удаляется после команды.
Это команда обновления рабочего экземпляра с коротким перерывом, а не проверка:
после успешной сборки она делает резервную копию и переключает установленную пару.

Для выбора конкретного проверенного коммита из чистого checkout:

```sh
./scripts/oko-release prepare --ref <новый-проверенный-коммит>
./scripts/oko-release update --release <полный-новый-SHA>
```

Подготовка не меняет рабочий выпуск. `update` останавливает текущую пару, подтверждает освобождение execution lock Codex и отсутствие `scratch/active.json`, затем делает согласованную копию всех данных под lock, сохраняет предыдущий manifest и переключает helper + образ вместе. Две версии не открывают одну базу. Смена состояния сериализована отдельным lock установки. Если запуск не удался, выбранный выпуск остаётся доступным для диагностики, процессы остановлены; автоматического восстановления поверх изменённых данных нет.

Отдельная копия возможна только при остановленном контейнере и свободном lock:

```sh
./scripts/oko-release stop
./scripts/oko-release backup
./scripts/oko-release start
```

`backups/<время>/` содержит все данные и manifest с release и SHA-256 содержимого. `rollback --release <предыдущий-SHA>` допускается только к зафиксированному предыдущему выпуску и при побайтово неизменившихся данных. Это консервативное правило: даже миграция SQLite может потребовать явного restore. Неизвестная совместимость или новые записи блокируют возврат и оставляют процессы остановленными.

Для явного восстановления выбранной копии с потерей последующих изменений:

```sh
./scripts/oko-release restore --backup <ID-копии> --acknowledge-data-loss <тот-же-ID>
```

Проверяются целостность копии и наличие соответствующего выпуска. Текущее состояние предварительно сохраняется новой резервной копией и отдельным `retired-data-<время>/`; исходная копия не переписывается. После этого восстанавливаются данные и согласованная пара выпуска. Команда не удаляет более поздние данные, но они перестают быть активными. Перед восстановлением нужен осознанный выбор копии; автоматической отмены пользовательских записей нет.

## Фактические проверки

Проверки реализации фиксируются в итоговом отчёте задачи отдельно от инструкций выше. Командный тестовый seam — настоящий `scripts/oko-release` с временным Git-репозиторием и данными, подставными executable Docker/uv/launchctl для операций ОС. Он проверяет snapshot, приватность установки, остановку перед копированием, защиту исходных данных и явное согласие на потерю изменений. Такие тесты не заменяют сборку настоящего образа, проверку Docker Desktop/launchd, сеть, браузер и перенос Telegram.
