# Выпуск единого пайплайна и возврат

Это инструкция для отдельно разрешённого выпуска. Реализация #90–#98 сама
не мигрирует личные данные и не перезапускает установку. Все примеры используют
абсолютные пути, которые оператор выбирает перед выполнением.

## Подготовка при остановленных владельцах

1. Зафиксировать SHA старого установленного выпуска и проверенного нового коммита.
   Для Docker использовать `oko-release status` и current.json выбранной установки.
2. Штатно остановить старую пару `./scripts/oko-release --home OLD_HOME stop`.
   Подтвердить остановку контейнера, helper и всех встроенных писателей, отсутствие
   scratch/active.json и свободные instance/execution locks. Не удалять SQLite
   journal/WAL вручную: незавершённую транзакцию восстанавливает прежний выпуск.
3. Сделать согласованную копию `./scripts/oko-release --home OLD_HOME backup`.
   Сохранить её ID, release и digest. До завершения переноса старый выпуск не запускать.
4. В окружении нового проверенного checkout выполнить:

   ```sh
   .venv/bin/python -m oko.storage.migration /absolute/OLD_HOME/data /absolute/conversion
   ```

   conversion должен отсутствовать и находиться вне исходного каталога.
   Команда проверяет integrity_check, файловый манифест, неизменность источника и
   backup. Результат — backup/, storage/, report.json. success=false означает
   запрет переключения: storage не публикуется. Исправлять конфликты в прежнем
   выпуске либо разбирать отчёт; не включать частичную копию вручную.
5. Проверить report.json: success=true, conflicts=[], соответствие всех фидов,
   ключей и ID, файлы, результаты, history_boundaries, interrupted_jobs,
   removed_viewed и unportable. Непереносимый неподтверждённый результат означает
   новый проход обработки; отсутствие исходного текста не заменяется пустым успехом.
   Повторно сравнить SHA-256 backup/ с backup_manifest; исходник остаётся нетронутым.

## Проверка и переключение

Простой безопасный путь — отдельная установка NEW_HOME с новым выпуском и пустым
каталогом data. Она использует прежние штатные команды, без временного dual-write:

```sh
./scripts/oko-release --home NEW_HOME prepare --ref NEW_SHA
./scripts/oko-release --home NEW_HOME install --release NEW_SHA
./scripts/oko-release --home NEW_HOME migrate --source /absolute/conversion/storage
```

`migrate` здесь только копирует уже преобразованную storage и выключает общий
допуск работы. Старый OLD_HOME сохраняется. Перед первым запуском проверить
профили Telegram и пути сессий, адрес локальной модели, прокси и разрешения.
У двух установок общий порт; старая должна оставаться остановленной.

Запустить NEW_HOME явно, проверить авторизацию, status, список/открытие материалов,
связанные статьи, скачивание сохранённых файлов, папки и настройки. Сначала не
включать сбор или модели и не отмечать материалы просмотренными. Временная
копия и отдельный storage_id не дают старой вкладке принять ответы другой базы.
После проверки отдельно включить работу и проверить один разрешённый источник.
Зафиксировать фактические SHA, результат и ограничения проверки.

CLI отказывается запускать заполненную прежнюю базу без маркера завершённого
переноса. `oko-release update` сам по себе не преобразует её: прямое обновление
старой установки без этой процедуры остановится с инструкцией переноса.

## Возврат

До новых пользовательских/фоновых записей остановить NEW_HOME, сохранить её
диагностику и запустить прежнюю пару OLD_HOME с её неизменённой базой и файлами.
Возврат означает именно старую пару release + data; старый код не открывает
преобразованную SQLite. Backup и conversion не удалять после проверки.

После начала новых записей автоматический возврат на старую базу запрещён.
Сначала остановить владельцев и сохранить согласованную копию нового состояния.
Затем выбрать перенос новых изменений либо явное восстановление с осознанной
потерей этих изменений. Штатный restore требует backup ID и повторного
`--acknowledge-data-loss`; он предварительно сохраняет текущие данные.
Ни сбой запуска, ни неуспех проверки не разрешают молча восстановить старую копию.
