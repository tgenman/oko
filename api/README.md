# Контракт читателя

`openapi.yaml` — редактируемый источник всех операций `/api/` в OpenAPI 3.1. Первоначальный baseline взят из действующего HTTP и дополнен ответами, которые раньше возвращались как словари. FastAPI не перезаписывает этот файл. Обработка, допустимость действий и состояние вкладки остаются ответственностью приложения.

Команды из корня checkout:

```sh
python scripts/api.py validate
python scripts/api.py bundle --output /tmp/oko-openapi.json
python scripts/api.py docs
```

После установки закреплённых npm-зависимостей последняя команда открывает самостоятельный Swagger по `http://127.0.0.1:8766/docs`. Можно задать `--port` и `--assets`. Читатель, Runtime, Store и внешние источники не создаются. Все assets локальные; Try it out и Authorize отсутствуют. Просмотр не выполняет API-запросов. Встроенная в работающий читатель документация с явной авторизацией поставляется отдельно.

Bundle содержит те же локальные references, без внешних `$ref`. Его канонические UTF-8 байты: JSON с `ensure_ascii=False`, `sort_keys=True`, `separators=(',', ':')` и одним завершающим переводом строки. По этим байтам сборка считает SHA-256 для согласованности контракта, библиотек и документации.

Пустой JSON schema в `ValidationError.input` и значениях `ctx` намеренно допускает произвольные диагностические JSON-данные. Остальные ответы перечисляют DTO, обязательность и nullable-поля. Ограничения, зависящие от каталога моделей, часового пояса и текущего состояния, описаны в контракте и дополнительно проверяются сервером.

Проверки проходят через команду bundle и существующий HTTP interface: `tests/api/test_contract.py`. Они используют временные хранилища и синтетические adapters.

## Изменения контракта

`validate`, `bundle`, `npm run api:generate` и `npm run api:check` требуют непустые
буквальные `examples` у каждой именованной схемы и `example` либо именованные
`examples` с `value` у каждого небинарного ответа. Все примеры проверяются по JSON
Schema 2020-12, включая форматы. `null` и `false` считаются полноценными примерами;
для бинарных ответов пример не требуется. Отсутствующий или невалидный пример
останавливает команду до записи bundle или generated-библиотек. Ошибка указывает
схему либо метод, маршрут, статус и media type ответа.

Состав операций сверяется с реальными маршрутами приложения в
`tests/api/test_contract.py`; фиксированное число операций в тестах не задаётся.

После изменения схемы или генератора выполните `npm run api:generate` и закоммитьте полученные библиотеки вместе с исходниками. `npm run api:check` проверяет валидность схемы и актуальность библиотек без изменения checkout. Frontend build использует ту же проверку с кэшем по содержимому входов.

`./scripts/check staged` при изменении API, генераторов или их зависимостей проверяет точные байты Git index. Автоматический pre-commit удалён. Во временный каталог попадают только входы генерации и generated-библиотеки; незакоммиченные изменения рабочих файлов не влияют на результат. Одобрение baseline и отдельный candidate-режим не требуются. Для полного прогона используется `./scripts/check all`.

Все contract references должны быть существующими локальными JSON pointers. Внешние references не загружаются. Node, Python и генераторы нужны для разработки/сборки и отсутствуют в пути обычного запуска читателя.

## Единственный API v3

57 предметных операций обслуживается через `/api/v3`. Прежние unversioned `/api` и `/api/...` после Host/Origin/bearer проверок возвращают `410 api_version_removed`; команды не исполняются, перенаправлений и SPA fallback нет. Переходные SDK/DTO v2, их генерация и `baseline.json` удалены. Исторический semantic mapping сохранён в [дизайне перехода](../.scratch/independent-api/contract-design.md), а текущий контракт — единственный источник wire-моделей.

`oko/reader/snapshots.py` валидирует внутренние снимки Store/Runtime, включая исторические необязательные поля. Это не HTTP-контракт и не второй API. На границе используются только generated v3 models. Исторические receipts и проблемы читаются без разрушительной миграции; старые UI-действия не исполняются.

Независимый клиент проверяет поддерживаемый semantic major из status. Другой digest совместимого клиента не запрещает запросы; exact digest связывает только артефакты одной поставки. `--api-only` не требует assets/Node или presence. Самостоятельный клиент на стандартной библиотеке проверяется в `tests/fixtures/independent_v3_client.py` вместе с процессным сценарием.

### Восстановление работы v3

`RuntimeStatus` передаёт предметные коды проблем и закрытые рекомендации восстановления. Клиент владеет текстами и навигацией; сервер не передаёт page/field/menu. При неизвестном исходе записи клиент сверяет receipt и не повторяет команду автоматически. Исторические записи без подтверждённой роли Telegram не получают выдуманную роль.

`POST /api/v3/collect` принимает необязательный `CollectionTarget`: без тела собирает все источники, `feed` ограничивает обновление одним фидом, `folder` — всеми фидами папки. Ручная команда также продолжает незавершённые загрузки и повторяет упавшую фильтрацию и тезисы; успешные актуальные результаты сохраняются. Цель повторно допускается под блокировкой Runtime: отсутствующий фид возвращает 404, удаляемый — 409. Это исполняемая граница уже объявленного `retry_collection`.

`PATCH /api/v3/feeds/{identity}` принимает `new_folder`: непустое название до 200
символов, с обрезкой внешних пробелов. Создание новой папки и перенос фида выполняются
в одной транзакции; сочетание с `folder_id` и занятое название возвращают
`400 action_invalid` без изменений каталога. Уникальность регистрозависимая.
Команда учитывается как `feed_patch` с полем `new_folder`; повтор после неизвестного
исхода не выполняется автоматически.

### Включение работы

`PUT /api/v3/power` с `{"enabled": false}` выключает сбор и обработку, сохраняя
HTTP и локальное чтение; `true` возобновляет работу. Выбор сохраняется в хранилище.
`RuntimeStatus.runtime_state=disabled` и `work_allowed=false` отличают выключенное Око
от завершённого процесса. Команды внешней работы возвращают `409 runtime_disabled`.
Команда учитывается как `power` с desired `enabled`; при потерянном ответе сверяйте
status/receipt, не повторяйте неизвестный исход автоматически.
`POST /api/v3/stop` по-прежнему завершает процесс.

### Сведения фида

`PATCH /api/v3/feeds/{identity}` принимает `title`: локальное название длиной
1–200 символов после обрезки внешних пробелов. Совместное сохранение `title` и
`folder_id` атомарно; идентичность и адреса источника не меняются. Поле учитывается
в `feed_patch` receipts. Неизменные значения не обновляют Modified.

`GET /api/v3/settings/feed/{id}` и результат изменения собственных настроек включают
`activity`: nullable UTC даты `created`, `modified`, `updated`, `marked_read`,
число `unread` и nullable `description`. Старые неизвестные даты остаются null.
Unread включает все известные непросмотренные публикации, в том числе скрытые,
загружаемые и недоступные; оно может отличаться от видимого count дерева.
Description относится к внешнему источнику. Открытие настроек не обращается к источнику.

### Ошибки операций Codex

Все четыре операции Codex описывают `409 runtime_stopped` после остановки Runtime.
Получение каталога, сохранение настроек и проверка также сохраняют отдельный
`409 runtime_disabled` при выключенном Око; чтение сохранённого состояния доступно.
503 при сохранении настроек и проверке допускает как `processor_unavailable`,
так и `storage_unavailable`, используя существующий `CodexModels503Errors`.
Успешно выполненная диагностика с недоступным Codex остаётся ответом
`200 state: unavailable`. Уточнение схемы сохраняет фактические ответы сервера,
включая статусы, предметные коды и receipts команд.
