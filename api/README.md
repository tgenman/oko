# Контракт читателя

`openapi.yaml` — редактируемый источник всех операций `/api/` в OpenAPI 3.1. Первоначальный baseline взят из действующего HTTP и дополнен ответами, которые раньше возвращались как словари. FastAPI не перезаписывает этот файл. Обработка, допустимость действий и состояние вкладки остаются ответственностью приложения.

Команды из корня checkout:

```sh
python scripts/api.py validate
python scripts/api.py bundle --output /tmp/oko-openapi.json
python scripts/api.py docs
```

После установки закреплённых npm-зависимостей последняя команда открывает самостоятельный Swagger по `http://127.0.0.1:8766/docs`. Можно задать `--port` и `--assets`. Читатель, Runtime, Store и внешние источники не создаются. Все assets локальные; Try it out и Authorize отсутствуют. Просмотр не выполняет API-запросов. Встроенная в работающий читатель документация с явной авторизацией поставляется отдельно.

Bundle содержит те же локальные references, без внешних `$ref`. Его канонические UTF-8 байты: JSON с `ensure_ascii=False`, `sort_keys=True`, `separators=(',', ':')` и одним завершающим переводом строки. По этим байтам сборка считает SHA-256 для согласованности контракта, библиотек и документации.

Пустой JSON schema в `ValidationError.input` и значениях `ctx` намеренно допускает произвольные диагностические JSON-данные. Остальные ответы перечисляют DTO, обязательность и nullable-поля. Ограничения, зависящие от каталога моделей, часового пояса и текущего состояния, описаны в контракте и дополнительно проверяются сервером.

Проверки проходят через команду bundle, существующий HTTP interface и настоящий Swagger в Playwright: `tests/api/test_contract.py` и `tests/browser/test_api_docs.ts`. Они используют временные хранилища и синтетические adapters.

## Изменения контракта

`baseline.json` хранит полный проверенный контракт до следующего согласованного изменения. `npm run api:compat` сравнивает его с canonical OpenAPI. Изменения wire shape, обязательности/nullability, ограничений, путей, operationId, auth, headers, media types и HTTP-ответов останавливают проверку как **потенциально несовместимые**. Это консервативный сигнал для ревью: даже совместимое добавление требует разбора. Description/title/example/summary и корневые info/tags не считаются wire changes; реальные properties с такими именами сохраняются при сравнении.

Автоматический diff не доказывает семантическую совместимость. Изменения defaults, правил времени, принадлежности/состава, identity, PATCH/reset, побочных эффектов и ошибок отдельно проверяются человеком по спецификации, HTTP/browser-тестам и всем потребителям. Breaking change повышает major в `info.version`; совместимое дополнение — minor, исправление документации — patch. Генерация и сборка никогда не обновляют baseline автоматически.

После ревью зафиксируйте документ с прежней/новой версией, изменившимся поведением, совместимостью потребителей, порядком перехода и выполненными проверками. Затем явно выполните:

```sh
npm run api:baseline -- --review path/to/semantic-review.md
npm run api:generate
npm run api:check
```

Обновление требует изменённого `info.version` и непустого документа ревью. Команда записывает baseline и `baseline.review.json`: исходную/новую версии, SHA-256 обоих контрактов и полный текст ревью. Это сохранённое свидетельство решения; команда не проверяет качество текста и не заменяет независимого reviewer. Документ и evidence коммитятся вместе с контрактом и обеими generated-библиотеками.

`api:check` и frontend build проверяют совместимость и deterministic regeneration во временных каталогах без изменения checkout. Pre-commit при API/codegen/config изменениях дополнительно материализует соответствующие **байты Git index** во временный каталог и сравнивает обе generated-библиотеки с результатом генерации. Unstaged изменения не исправляют и не портят результат index checks; удалённые staged файлы также обнаруживаются. Изменение уже существующего baseline требует в index соответствующего evidence и новой версии. Первоначальный baseline в этой миграции совпадает с полным текущим контрактом.

Все contract references должны быть существующими локальными JSON pointers. `$ref`, `$dynamicRef` и `$recursiveRef` проверяются до OpenAPI validation; внешние references не загружаются. Node, Python и генераторы нужны для разработки/сборки и отсутствуют в пути обычного запуска читателя.

## Проверка кандидата до обновления baseline

Для breaking change сначала проверяется согласованный кандидат, затем reviewer принимает точные байты и только после этого обновляется baseline:

```sh
./scripts/check all --candidate /absolute/path/openapi.yaml
```

Runner копирует выбранное рабочее дерево (Git tracked и неигнорируемые untracked файлы с текущими правками) в отдельный каталог отчёта, заменяет `api/openapi.yaml` только в копии и передаёт вложенным командам один `OKO_CANDIDATE_CONTEXT`. Контекст проверяет корень копии, SHA-256 выбранных bytes контракта и неизменность reviewed baseline. Он наследуется генератором, frontend builder; сгенерированные библиотеки, assets и временные данные остаются в копии. Исходный checkout, его index и baseline не меняются. Закреплённые `.venv` и `node_modules` используются как зависимости. Личные источники и пользовательский экземпляр не запускаются.

Полный режим добавляет генерацию обоих SDK/DTO, повторную deterministic drift check к обычным `all` проверкам. Semantic diff хранит полный before/after wire contract, все изменённые pointers и digests в `compatibility.json`; отличие получает **PENDING_REVIEW**. Этот исход разрешает дальнейшие проверки, но не означает совместимость или разрешение выпуска. Ошибки validation, генерации, типов, сборки, HTTP, Playwright, process/lifecycle остаются **FAIL**. Отчёт отдельно указывает `candidate.full_check`; ограниченный запуск, например `check diff --candidate ...`, доказывает только выбранные проверки.

Копия помечена **UNREVIEWED**; её нельзя использовать как проверенную поставку. Сборка установочного пакета временно удалена. Команда обновления baseline в candidate-контексте запрещена. Без контекста обычные compatibility/build/staged gates сохраняют строгую проверку; случайный запуск из помеченной копии без её контекста завершается ошибкой. Synthetic fixture repositories и явно выбранные тестовые документы внутри временного каталога кандидата проходят обычную строгую проверку, а не получают candidate-исключение.

Reviewer получает `report.json`, полный `compatibility.json`, source/contract digests и фактические результаты наборов. После одобрения именно этих bytes применяется штатный `api:baseline -- --review ...` в рабочем checkout, затем обычные gates. Изменение кандидата требует нового evidence. Успешный candidate-прогон сам по себе не закрывает финальную приёмку и не публикует артефакты.

## Текущий переход к v3

Canonical описывает полный кандидат v3. Пока выполняются задачи 01–07, прежние consumers временно используют `legacy_generated` / `legacy-generated`, воспроизводимо сгенерированные из неизменённого reviewed baseline v2. Генерация и drift проверяют обе библиотеки. Это непубликуемый expand–contract этап; переходный путь удаляется в задаче 07. Обычный compatibility gate до semantic review намеренно отклоняет breaking change; для проверки используйте изолированный candidate-контекст.
