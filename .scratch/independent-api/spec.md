# Независимый API Око и строгие типы

Status: ready-for-agent
Label: ready-for-agent
Date: 2026-10-15
Type: specification

Пользователь поручил проектирование, спецификацию и задачи по результатам независимого ревью OpenAPI. **Реализация не разрешена этим документом и пока не начата.** Статус означает готовность описания для последующей реализации по отдельному указанию.

**Актуализация после ревью:** проект учитывает текущую базу OpenAPI 2.0.0 (49 операций, 72 схемы) и согласованную архитектуру Telegram-доступа. Групповые результаты, OPML и отдельные фиды тем не возвращаются. Telegram имеет веб-доступ по умолчанию и два клиентских профиля; доступ фиксируется при создании фида. API-работа интегрирует эти предметные решения, не проектирует второй Telegram backend.

## Problem Statement

Око должно предоставлять один понятный контракт приложения для веб-интерфейса, мобильного или другого клиента. Сейчас разработчик нового клиента должен знать структуру веб-меню, поддерживать протокол вкладок и поставлять веб-сборку даже для запуска API. Существенные последствия команд приходится выяснять из реализации: например, «Просмотрено» удаляет собранное содержимое, а не просто записывает факт открытия.

Генерация Python DTO и TypeScript SDK синхронизирована с OpenAPI, но схемы недостаточно точно выражают предметную область. В проверенном контракте они допускали сочетания события и обзора; эти варианты теперь исключаются отдельным продуктовым решением. Для сохраняемых функций остаются произвольные действия восстановления, неподдерживаемые null и неоднозначные состояния. На сервере ответы часто строятся как словари с Any, поэтому строгий статический анализ не проверяет их поля до выполнения запроса. Машинные состояния и ошибки смешаны с текстами интерфейса.

Нужен независимый, проверяемый контракт, который сохраняет возможности Око и переносит устройство экрана исключительно в клиент. Совместимость с независимым клиентом должна доказываться через HTTP, без браузера, веб-сборки и знания внутренних таблиц.

## Solution

Спроектировать и затем отдельной работой реализовать API v3: предметные операции, типизированные ресурсы, состояния и ошибки; явный жизненный цикл сервера; воспроизводимые Python/TypeScript-библиотеки. Существующий веб-интерфейс становится одним из потребителей этого контракта.

Самостоятельный запуск API работает до явной остановки без присутствия клиентов. Обычный локальный запуск читателя сохраняет прежнюю политику работы при наличии клиента и завершения после его ухода; эта политика принадлежит сборке процесса и нейтральному учёту клиентских сессий. Runtime не знает о вкладках, DOM или страницах настроек.

Состав чтения, эффективные настройки, актуальность обработки, допустимость действий, отмена и удаление остаются на сервере. Новому клиенту не требуется повторять эти правила. Подробные решения по операциям, типам и переходу находятся в приложении «Дизайн контракта».

## User Stories

1. Как разработчик клиента, я хочу работать по опубликованному OpenAPI, чтобы не читать Python и код веб-интерфейса для понимания операций.
2. Как разработчик мобильного клиента, я хочу получать предметные ресурсы и действия, чтобы выбирать собственную навигацию и компоновку.
3. Как разработчик клиента без браузера, я хочу запустить API без веб-сборки, чтобы использовать только возможности приложения.
4. Как владелец Око, я хочу явно запускать самостоятельный сервер, чтобы работа не прекращалась при отключении клиента.
5. Как пользователь локального читателя, я хочу сохранить прекращение работы после ухода последнего клиента, чтобы миграция не включила постоянную фоновую работу по умолчанию.
6. Как разработчик клиента, я хочу узнать политику выполнения и параметры сессии из API, чтобы не копировать таймеры веб-клиента.
7. Как пользователь двух клиентов, я хочу независимые сессии, чтобы закрытие одного не остановило работу другого.
8. Как пользователь, я хочу, чтобы явная остановка запрещала новую работу и отменяла принадлежащие Око ожидания, чтобы поздний ответ не восстановил остановленную работу.
9. Как разработчик клиента, я хочу различать состояния доступности публикации по обязательному признаку, чтобы обрабатывать только допустимые поля варианта и не поддерживать удалённые групповые карточки.
10. Как читатель, я хочу видеть готовые карточки и их источники, чтобы клиент не вычислял состав чтения самостоятельно.
11. Как читатель, я хочу различать полноту собранного материала и готовность тезисов, чтобы понимать, что именно доступно.
12. Как читатель, я хочу получать исходную публикацию, прежние версии и медиа, чтобы смена контракта не потеряла содержимое.
13. Как читатель, я хочу открывать материал без отметки «Просмотрено», чтобы открытие не удаляло данные.
14. Как разработчик клиента, я хочу явное описание последствий «Просмотрено», чтобы не привязать удаление к показу экрана.
15. Как читатель, я хочу завершать разбор папки после проверки состава, чтобы изменение состава требовало нового подтверждения.
16. Как читатель, я хочу учитывать скрытые и ещё не загруженные публикации при завершении папки, чтобы не оставлять незаметный остаток.
17. Как разработчик клиента, я хочу отличать отсутствие PATCH-поля от null и значения, чтобы корректно сохранять и сбрасывать настройки.
18. Как пользователь, я хочу сохранить наследование Око → тематическая папка → фид, чтобы миграция не меняла эффективные настройки.
19. Как разработчик клиента, я хочу знать допустимые области настроек и поля каждого запроса, чтобы ошибки обнаруживались до отправки.
20. Как пользователь, я хочу выбирать начальную историю по количеству или дате, чтобы эти способы не смешивались.
21. Как пользователь, я хочу передавать точное большое количество публикаций, чтобы разные языки клиентов не округляли выбор.
22. Как читатель, я хочу видеть загрузку, паузу, ожидание, завершение и отмену истории, чтобы состояние не зависело от комбинации противоречащих флагов.
23. Как пользователь, я хочу одиночное подключение RSS, YouTube и Telegram через веб или один из двух клиентских профилей, чтобы пользоваться согласованными способами доступа без OPML и отдельного подключения тем.
24. Как пользователь Telegram, я хочу сохранить безопасную границу прочитанного для клиентского доступа и отсутствие внешних отметок для веб-доступа, чтобы локальное «Просмотрено» не выполняло неподходящее действие от имени аккаунта.
25. Как пользователь, я хочу менять настройки подключения YouTube без возвращения секретов в ответах, чтобы состояние подключения оставалось доступным клиенту.
26. Как пользователь, я хочу выбирать обработчик и получать актуальный каталог моделей, чтобы схема не закрепляла устаревающий список моделей.
27. Как читатель, я хочу видеть происхождение результата отдельно от текущих настроек, чтобы понимать, чем он был получен.
28. Как разработчик клиента, я хочу машинные коды состояния и ошибок, чтобы не сравнивать русские сообщения.
29. Как пользователь, я хочу получать понятное объяснение проблемы и возможное восстановление, чтобы смена клиента не делала диагностику бесполезной.
30. Как разработчик клиента, я хочу получать типизированные цели восстановления, чтобы самостоятельно выбрать экран или выполнить допустимую команду.
31. Как пользователь, я хочу сохранять черновик после ошибки, чтобы повторный вход в настройки не терял ввод.
32. Как пользователь, я хочу отличать неизвестный сетевой исход от подтверждённой ошибки, чтобы приложение не повторяло потенциально выполненную команду.
33. Как разработчик клиента, я хочу сверять исход команды по её идентификатору, чтобы восстановить состояние после потери ответа.
34. Как разработчик клиента, я хочу отправлять диагностические события без сведений о DOM и обязательного понятия браузера, чтобы диагностика работала для любого клиента.
35. Как разработчик backend, я хочу строить конкретные типизированные ответы, чтобы неверное поле находил статический анализ, а не пользовательский запрос.
36. Как разработчик клиента, я хочу получать SDK с различимыми вариантами ответов, чтобы exhaustive-проверка обнаруживала пропущенный вариант.
37. Как разработчик, я хочу воспроизводимую генерацию и проверку несовместимости, чтобы ручные исправления generated-файлов не стали вторым контрактом.
38. Как разработчик, я хочу проверку настоящих HTTP-запросов и ответов против схемы, чтобы совпадение generated-файлов не подменяло корректность реализации.
39. Как пользователь веб-интерфейса, я хочу сохранить черновики, фокус, прокрутку, медиа и защиту от поздних ответов, чтобы изменение API не ухудшило чтение.
40. Как разработчик нового клиента, я хочу видеть несовместимую версию явно, чтобы старый запрос не был молча истолкован по новым правилам.
41. Как владелец данных, я хочу сохранить собранные материалы, настройки и идентичности при обновлении, чтобы миграция контракта не требовала повторного подключения источников.
42. Как reviewer, я хочу отдельные фактические результаты проверок, чтобы отличать готовый план от доказанной реализации.
43. Как пользователь Telegram, я хочу получать конфликт повторного подключения с данными существующих фидов, чтобы оно не меняло их доступ, папку или настройки.
44. Как пользователь, я хочу удалить фид и его локальные данные без отметки прочитанного в Telegram, чтобы осознанно добавить источник другим доступом.

## Implementation Decisions

1. **D01 — источник истины и версия.** Редактируемый OpenAPI 3.1 остаётся единственным транспортным контрактом. Целевой общий breaking release независимого API и согласованных Telegram-операций — 3.0.0 с префиксом `/api/v3`, поверх текущей 2.0.0. Перед реализацией подтвердить базу; не выпускать два несовместимых контракта с одним major. Если соседняя работа уже выпущена, выбрать следующий major после общего semantic review. В этой задаче действующий YAML, baseline и generated-библиотеки не изменяются.
2. **D02 — полнота перехода.** Исходные 50 операций и 77 схем ревью остаются реестром происхождения, включая снятые элементы. Непосредственная база — 49 операций и 72 схемы OpenAPI 2.0.0. Целевые операции определяются актуальными предметными сценариями: удалить OPML/topics, сохранить общие GET/PATCH настроек, добавить только сессии, чтение receipt, привязку профиля и удаление фида. Реестр содержит 50 целевых операций. Перед реализацией сверить изменения соседних задач; число операций не является самостоятельной целью.
3. **D03 — владение.** HTTP adapter принимает и выдаёт DTO. Runtime владеет исполнением, отменой, допуском результатов и последовательностью изменений; Store — фиксацией и восстановлением; состав чтения и обработка остаются серверными. Клиент владеет экранами, текстами навигационных кнопок, черновиками, фокусом и допуском позднего ответа к показу. Доменная implementation не импортирует generated wire DTO.
4. **D04 — сборка приложения.** API-приложение создаётся без проверки, импорта и загрузки веб-assets. Локальная сборка процесса дополнительно подключает готовый веб-интерфейс и проверяет его совместимость. Самостоятельный запуск `--api-only` не открывает браузер; `--no-browser` сохраняет прежний смысл «не открывать окно», а не превращается в постоянный сервер.
5. **D05 — политика выполнения.** Поддерживаются два фиксированных профиля запуска: `explicit` для API-only и `client_presence` для обычного читателя. Это свойства экземпляра, не настройки фида и не переключатель в UI. В первом работа не зависит от клиентов и заканчивается по явной остановке/завершению процесса. Во втором сохраняются существующие lease/grace и приостановка внешней работы без живых клиентов. Автозапуск службы ОС не вводится.
6. **D06 — клиентские сессии.** Нейтральный менеджер сессий принадлежит host-сборке, принимает создание/продление/завершение сессии и передаёт Runtime только разрешение работы или явное прерывание. Вкладки, страницы и visibility не входят в этот interface. При прежних defaults lease_seconds = 6, grace_seconds = 15, renew_after_seconds = 2; обязательно 0 < renew_after_seconds < lease_seconds. Web adapter отображает время жизни вкладки на этот протокол. В explicit сессии не обязательны для чтения, записи и обработки.
7. **D07 — сохраняемая отмена.** Исчезновение последней сессии в `client_presence` закрывает допуск внешних результатов и отменяет текущие ожидания как сегодня; возврат до конца grace разрешает восстановление работы. Повторное завершение одной сессии не продлевает grace. Явный stop необратим для экземпляра, действует в обоих профилях и завершает принадлежащие Око ресурсы. Сохранённая запись не откатывается из-за отмены HTTP-ожидания.
8. **D08 — безопасность и подключение.** Сохраняются один локальный пользователь, bearer, привязка к loopback, ограничения host/origin и безопасная выдача файлов. Client session не является авторизационной сессией и не заменяет bearer. Независимость контракта не означает готовую сетевую доступность с другого устройства; remote deployment, pairing и multi-user auth вне объёма.
9. **D09 — общие значения и разбор транспорта.** Идентичности, времена, даты, интервалы, точные целые, ссылки и счётчики имеют именованные типы и явные единицы. JSON body проверяется без coercion: строка не превращается в boolean/integer. Текстовые path/query/header разбираются по объявленной лексике параметра, затем проверяются тип и диапазон; это не исключение, разрешающее coercion JSON. Идентичность не выводится клиентом из префикса строки.
10. **D10 — варианты вместо optional-пакетов.** Варианты доступности содержимого публикации, выбор истории, происхождение результата, состояние проблемы, восстановление и ошибки моделируются как закрытые типы с обязательным признаком состояния. Карточка представляет одну публикацию; вариантов event/digest или задела для их возвращения нет. Ветки различаются `const`, объединяются `oneOf` и содержат обязательные поля своего варианта. Discriminator помогает генерации, но не заменяет ограничения схемы.
11. **D11 — чтение.** Карточки остаются готовой серверной проекцией состава чтения, с сортировкой, счётчиками, принадлежностью папке и источниками. Открытый материал содержит типизированное предметное содержимое, а не instructions для renderer. Полнота сбора, загрузка, фильтрация и обработка описываются отдельно. Состав папки состоит из исходных публикаций; групповых и рекурсивных материалов в публичном контракте нет.
12. **D12 — команды завершения.** «Просмотрено» и завершение папки — явные команды завершения разбора с документированным удалением собранного содержимого, всех версий, медиа и производных результатов. Открытие, получение данных и закрытие сессии не выполняют их. Preview/token папки, проверка актуального состава, охват скрытого и ещё не загруженного сохраняются. Ошибка после фиксации не означает откат; receipt отражает исход исполнения команды, а не обещание восстановления содержимого.
13. **D13 — обязательность и null.** Ответы не получают значения по умолчанию для маскировки отсутствующих обязательных данных. PATCH: отсутствует — не менять; null допускается только для явно определённого reset/отключения. Пять ошибочно nullable полей FeedPatch становятся optional non-null. Наследуемые Overrides сохраняют явный null-reset. Запросы и ответы не используют одну модель, если их обязательность различается.
14. **D14 — история.** Выбор истории — отдельные варианты `count` и `date`. Количество передаётся единственной точной положительной десятичной строкой; дублирующая пара count/count_text удаляется. Дата — календарная дата с IANA timezone; будущее проверяется сервером. Общая модель состояния истории отделяет выбранную границу от прогресса; выводимые из состояния flags не являются независимыми входами. Для нового AddFeed и Telegram web/client отсутствие initial_history задаёт mode=count, count="20"; null/неполный объект отвергаются. Старое отсутствие selection представлено HistoryState.absent без selection/счётчиков и с известной legacy_since либо null; not_started требует уже сохранённую selection. Миграция не назначает историю и не запускает сбор задним числом.
15. **D15 — настройки и подключения.** Настройки Око/папки/фида сохраняют общую пару GET/PATCH и общий строгий SettingsPatch из пяти действующих полей; scope — enum, owner проверяется по scope и Store. Сохраняются одиночные RSS/YouTube и согласованные Telegram web/client подключения, история и наследование. OPML/topics исключены. Telegram access/account/peer неизменяемы, каналы и группы уникальны независимо от доступа/папки, профили personal/collection проверяются по личности, веб не использует аккаунт или внешнее прочитанное. Удаление фида — отдельная локальная очистка без viewed/ack. Полный набор вариантов и конфликтов описан в приложении; доменная реализация принадлежит Telegram-спецификации. Response-only access legacy_client представляет старую неподтверждённую привязку с alias/source_locator и известным peer_id либо null, без выдуманных role/account_user_id. Он одинаков для каталога и duplicate_source; connect принимает только web/client.
16. **D16 — обработчики и результаты.** Каталог моделей и поддержанных усилий остаётся динамическим; нельзя заменить его зашитым enum моделей. Названия операций обработки, состояния и виды происхождения — закрытые типы. Неизвестное историческое происхождение остаётся явным вариантом; смена выбора для будущей работы не переписывает происхождение и не меняет правила актуальности.
17. **D17 — состояние работы.** В ответе состояния есть стабильные коды runtime/работы, прогресс и типизированные причины ожидания. Клиенты не ветвятся по локализованным строкам. Один ответ состояния не превращает остальные читающие операции в общий транзакционный снимок. Сохраняется восстановление сбора, фильтрации и тезисов; прогресс удаляемых обзоров в API не возвращается.
18. **D18 — проблемы и восстановление.** Проблема сохраняет идентичность, предметный код, затронутые ресурсы, время, состояние и последствие. Восстановление выражается конечным набором типизированных предметных намерений. `page`, имена меню и поля UI-черновика отсутствуют. Автоматическое ожидание, историческое исключение и текущая проблема не смешиваются. Недавно завершённые проблемы и их срок сохранения не теряются. Общий reconnect_feed исключён. Авторизация известного профиля восстанавливается существующим PUT; неподтверждённая привязка требует явного сопоставления роли. Смена источника/доступа — явные удаление с локальной очисткой и новое добавление, без скрытого upsert и нового endpoint.
19. **D19 — сообщения.** Стабильные коды и typed details достаточны для программной обработки. Сервер может возвращать диагностический текст и объяснение предметной проблемы; это не код состояния и не инструкция открыть определённый экран. Текст кнопок, локализация навигации и соответствие предметного намерения экрану принадлежат клиенту.
20. **D20 — исходы команд.** Сохраняются correlation ID и различие подтверждённого ответа, незавершённой команды и неизвестного сетевого исхода. Предметный context команды типизирован и не содержит HTTP route, UI page, секреты или отправленные значения настроек. Добавляется явное чтение receipt; сообщение клиента о потере ответа не доказывает неуспех серверной записи. Автоматический replay и обещание exactly-once не вводятся.
21. **D21 — ошибки.** Все документированные HTTP-ошибки имеют общий envelope со стабильным code и отдельные типизированные варианты details. Схема конкретной операции перечисляет её реальные ошибки; конфликт состава папки не включается в каждую ошибку всех маршрутов. Форматная ошибка запроса — 422; семантически недопустимое действие — 400; отсутствие — 404; конфликт состояния — 409; недоступность — 503; auth — прежний 403. Изменения относительно текущей v2 отмечаются явно; исходное ревью v1 остаётся историческим основанием.
22. **D22 — диагностика.** Событие клиента нейтрально к браузеру, сохраняет текущую дедупликацию, ограничение объёма, маскирование и привязку к материалу. Время события требует offset и нормализуется в UTC. Произвольный JSON допускается только в явно обозначенной ограниченной диагностической области; значения секретов в validation errors не возвращаются. Ошибка доставки диагностики не порождает её рекурсивную отправку.
23. **D23 — Python.** Каждый HTTP handler объявляет конкретный generated response DTO/union и формирует его через типизированное преобразование из предметного результата. Внешняя форма проверяется wire-моделью первой, затем выполняется доменная валидация. Словари Any, безусловный cast и повторная валидация словаря не считаются статической типизацией. Типизированные внутренние проекции вводятся только на реально затронутых seams; переписывание всего Store не требуется.
24. **D24 — генерация.** Генераторы и шаблоны должны сохранять strict primitives, required/null/omission, ограничения и сужение вариантов в Python и TypeScript. Это проверяется на новых типах до массового переноса handlers. Generated-файлы не редактируются вручную; исключения строгой проверки не расширяются. Код библиотек транспорта с техническими Any отделён от предметных DTO.
25. **D25 — клиентский SDK.** Операции и JSON-типы генерируются из одного контракта. Снаружи остаются bearer/origin, обработка транспортных ошибок и разрешение предметных действий в UI. Binary читается как binary, ошибки — как typed JSON. TS-типы сами по себе не валидируют JSON; проверка настоящих серверных ответов и управляемых browser snapshots сохраняется. Второй ручной реестр HTTP-маршрутов в UI не создаётся.
26. **D26 — миграция веб-клиента.** Веб-клиент переходит на v3 полностью, включая диагностику, receipts, настройки, историю, медиа и сессии. Прежние late-response guards, BFCache, работа нескольких вкладок, сохранение более нового черновика, reset/discard и очистка медиа сохраняются. Источники истины membership и processing freshness остаются на сервере.
27. **D27 — независимая совместимость и поставка.** Клиент допускается по поддерживаемому major и сохранённой семантической совместимости, не по равенству digest. Разные совместимые minor/patch и исправления документации не запрещают mutations. Digest проверяет только целостность/согласованность артефактов одной сборки. Новые варианты enum или обязательные/лишние response fields, ломающие старый strict decoder, не считаются совместимым minor. Старый unversioned API не переадресует mutations; после auth возвращает ошибку снятой версии. Старые вкладки требуется переоткрыть; перенос незавершённых клиентских черновиков между major не обещается.
28. **D28 — сохранённые данные.** Если сохранённые проблемы/receipts содержат UI-действия или прежние строки времени, нужен явный совместимый read-adapter либо атомарная миграция служебных записей с проверенным откатом. Внешние identity публикаций, файлы содержимого и настройки не меняются ради DTO. Неизвестные исторические значения получают ограниченный legacy-вариант с исходной диагностикой, а не произвольный kind во всех новых типах.
29. **D29 — проверяемый порядок.** Сначала контракт и инструментарий полноценного candidate-прогона, затем серверные сценарии, клиенты и поставка. Candidate запускается в изолированной проверочной копии с выбранным контрактом: генерация, build, HTTP/Playwright, package/install smoke проходят до semantic review. Schema/type/drift/integrity checks обязательны; отличие от released baseline фиксируется отдельно как PENDING_REVIEW и запрещает выпуск. Reviewer получает эти evidence и точный contract/source digest; после одобрения обновляется baseline штатным способом, затем выполняются обычные gates. Временная смесь старого/нового API не публикуется.
30. **D30 — измеримый результат.** Новый клиент выполняет чтение, настройку, предметную команду, сверку неизвестного исхода и остановку через публичный HTTP без веб-assets и heartbeat в explicit-профиле. В интерактивном профиле два разных клиента используют одинаковый протокол присутствия. Неверные варианты и nullable-поля отклоняются на границе; реальные ответы проходят schema validation с проверкой форматов, а типовые ошибки сборки DTO ловятся статически.

## Testing Decisions

1. **Основной test surface — существующий HTTP interface.** Настоящий сервер, временные SQLite/файлы, синтетические источники/модели и управляемые часы. Это уже заданная пользователем граница проверки; повторный выбор test seam не требуется. Новый способ запуска проверяется через тот же HTTP и существующие процессные тесты, не через private-методы.
2. Хорошая проверка подтверждает наблюдаемый результат и отсутствие нежелательного эффекта: верный состав, сохранённый черновик, отказ неверного запроса до изменения данных, отсутствие поздней фиксации. Имена классов, порядок внутренних вызовов и расположение модулей не являются приёмкой.
3. Независимый клиент — небольшой HTTP-сценарий без DOM, React, локального UI-state и доступа к Store. Это доказательство независимости, а не реализация мобильного приложения. Он использует только контракт, bearer и адрес сервера.
4. Проверить standalone API с удалёнными/недоступными веб-assets, без Node, из установленной поставки и другого рабочего каталога. Проверить обычный локальный запуск, повторное подключение к тому же экземпляру и запрет незаметной смены его профиля.
5. Проверить explicit: работа продолжается без сессий и после отключения клиента; stop прекращает её. Проверить client_presence: две сессии, expiry/close одной и последней, возврат в grace, повторный close, sleep/time jump и поздний ответ источника/модели. Сохранить ограничения времени очистки принадлежащих процессов.
6. Покрыть все варианты material/card/history/provenance/problem/recovery/errors положительными и отрицательными примерами. Любые поля удалённых event/digest, неверная ветка доступности содержания, неизвестный kind, отсутствие target, несовместимые mode/count/date, неверный scope и дополнительные поля должны отвергаться до эффекта.
7. Проверить PATCH omission/null/value для каждого семейства, пять non-null полей фида, пустую строку отдельно от reset, точное большое count и строгие JSON boolean/integer. Отдельно проверить корректные текстовые query/path, их неверную лексику, диапазоны, повторные параметры и неизвестные ключи. Проверить явно установленные request defaults и отсутствие response defaults.
8. Проверять известные formats (date, date-time, URI) явно, включая обязательную временную зону, а не только наличие format в YAML. Schema validation и domain validation проверяются отдельно там, где правило зависит от времени, существования объекта или каталога.
9. HTTP-ответы всех операций, включая binary и все реализованные ветви ошибок, сопоставляются с canonical OpenAPI. Неверный server DTO должен давать диагностируемый 500, не исправляться молча и не утекать в клиент как успешный ответ. Тесты не ограничиваются наличием method/path.
10. Статические отрицательные примеры проверяют реальную типовую гарантию: неверное поле DTO, отсутствующее обязательное поле варианта, неправильный return handler и неполный switch по union. Это проверки контрактного инструментария, не копии implementation бизнес-логики.
11. Сохранить HTTP-сценарии состава чтения, версий, удаления, завершения папки, фильтрации, индивидуальных тезисов, подключений и истории. Для Telegram проверить web без аккаунта, два профиля, уникальность источника, неизменяемость доступа, локальное удаление без ack, полноту/Telegraph и безопасное клиентское прочитанное по профильной спецификации. Сохранить unknown-outcome, delayed success, receipt persistence, duplicate observations и discard без отката записи.
12. Playwright проверяет существующий веб-интерфейс через v3: сессия, меню/формы, чтение и медиа, статус/восстановление, BFCache, несколько вкладок и поздние ответы. Просмотр сделанных им desktop/mobile screenshots обязателен для затронутых поверхностей. Computer Use и личные источники не используются.
13. Проверить детерминированную генерацию, stale output и staged/index checks. До baseline выполнить полноценный candidate-прогон, включая frontend build и installed-package smoke; он не должен блокироваться ожидаемым compatibility diff и не может выдавать release-ready результат. После semantic review — штатное обновление baseline и обычные gates. Отдельно доказать: изменение только описания меняет digest, но совместимый клиент продолжает работу; неподдерживаемый major отклоняется до mutation.
14. Prior art: существующие HTTP contract/governance, process/lifecycle/runtime actions, status problems, folder completion, settings/history и transport/browser suites. Развивать эти сценарии, не создавать параллельный test framework.
15. Фактические результаты реализации записываются отдельно: команды, число сценариев, успешные и неуспешные прогоны, ограничения, screenshots. Проверки предыдущего ревью и проверка этих документов не считаются доказательством работоспособности v3.

## Out of Scope

- Реализация API, изменение production-кода, OpenAPI/baseline, generated-файлов или тестов в ходе подготовки этой спецификации.
- Мобильное приложение, Electron, новый UI framework, редизайн и дополнительные функции чтения.
- События, обзоры за период, сжатие истории, OPML и пользовательские фиды отдельных тем Telegram. Не сохранять скрытые режимы, маршруты или DTO для их будущего возвращения.
- Доступ с другого устройства, публичный сервер, облачная поставка, multi-user auth, pairing и снятие существующих host/origin ограничений.
- Автозапуск ОС, daemon по умолчанию, новые таймеры/настройки в UI и универсальный framework исполнения задач.
- Изменение состава чтения, политики «Просмотрено», правил публичного AI и актуальности обработки сверх согласованного Telegram-плана. Не проектировать заново adapters/claims/lanes/ReadSync/Telegraph; API интегрирует их результаты, реализационное владение остаётся у профильной задачи.
- Переписывание всех внутренних словарей, SQLite и Source adapters ради единой системы типов; ORM или новая база данных.
- Автоматический replay команд, exactly-once, универсальный idempotency layer, pagination/streaming/WebSocket без отдельной необходимости.
- Поддержка прежних v1/v2 без срока удаления; одновременная постоянная поддержка двух веб-клиентов.
- Работа с личными источниками и настоящими моделями, перезапуск пользовательского экземпляра, коммит, merge или публикация реализации.
