**Реализация пока не поручена.** Пользователь согласовал только оформление семи задач.

**Что сделать:** Пользователь настраивает Око, папку, фид и обработчики через v3. Наследование, reset и черновики сохраняются; потеря ответа сверяется по receipt без повторного исполнения. Независимый клиент может отправить, прочитать и очистить диагностику.

## Критерии приёмки

- [ ] Настройка Codex и локального обработчика проходит полный путь через API и существующие формы: сохранение, проверка, динамический каталог моделей/effort, квоты, доступность и машинный код locality.
- [ ] Первая tracked mutation, её producer проблемы и минимальный показ неизвестного исхода работают здесь сквозным образом. Задача 06 позже объединяет панель всех сценариев; задача 02 не ждёт её реализации. Очистка/просмотр/доставка диагностики доступны в UI и по HTTP.

### Сохранённые критерии

Идентификатор C — прежний номер тикета и номер критерия; он сохраняет прослеживаемость после перенумерации. Составные пункты читаются с распределением ответственности в индексе задач.

- [ ] **C05.01** Сохранена одна пара GET/PATCH settings/{scope}/{owner} и общий SettingsPatch пяти полей. Scope имеет enum; oko допускает только global, folder/feed проверяются по ресурсу. Response tagged по scope, не размножены операции/одинаковые request types.
- [ ] **C05.02** Для каждого поля различаются omission, value и допустимый reset; пять non-null FeedPatch отклоняют null до изменения данных. Telegram access/account/peer/transport не переключаются PATCH, web не принимает auto_read/read_history; корректные ограничения возвращаются без частичной записи.
- [ ] **C05.03** Effective values имеют правильный тип value и origin; наследование и public_ai semantics сохранены.
- [ ] **C08.01** CommandContext закрыт по operation с обязательными ресурсами/полями; не содержит method/path/page, credentials и отправленных значений.
- [ ] **C08.02** Command observation и GET receipt различают pending/succeeded/failed/unknown/abandoned; неизвестный ID не доказывает отсутствие исполнения.
- [ ] **C08.03** Поздний подтверждённый результат не перезаписывается client observation; повтор observation безопасен; context mismatch типизирован.
- [ ] **C08.04** Correlation ID не объявлен idempotency key; network failure и abort не разрешают автоматический replay; discard не отменяет сохранённую запись.
- [ ] **C08.05** ClientDiagnosticEvent требует корректные timestamps с offset и нормализует UTC; сохраняет дедупликацию, masking, bounded persistence и забывание просмотренных материалов.
- [ ] **C08.06** Сохранённые v1/v2 receipts/diagnostics доступны после перехода; миграция служебных записей обратима и не изменяет содержимое публикаций.
- [ ] **C09.04** Мутация получает correlation ID до отправки; потерянный ответ сверяется через receipt без автоматического повторения.
- [ ] **C09.06** Binary parsing, JSON error parsing, no-store и diagnostic delivery не создают рекурсии или второго реестра маршрутов.
- [ ] **C11.01** Око/папка/фид используют одну generated пару GET/PATCH с typed scope/owner и общий SettingsPatch. Generic union значений поля не обходит связь ключа с типом; отдельных SDK wrappers для трёх уровней нет.
- [ ] **C11.02** Сохранение, reset и discard различаются; более новый ввод не стирается поздним успехом предыдущего сохранения.

## Проверка

HTTP и persistence-сценарии unknown outcome, delayed success/failure, повтор доставки, restart, discard, timestamp без timezone, redaction и недоступного журнала. Не использовать личные данные.

Дополнительно: проверить все критерии этого тикета через указанные выше HTTP/UI-сценарии. В задаче 01 проверки остальных семейств относятся к гарантиям инструментария; их полное поведение принимается в соответствующих задачах 02–06.

## Границы и проверка результата

Все требования родительской спецификации, дизайна контракта и исправления ревью обязательны. Здесь меняется разбиение работы, не продуктовый объём. Типы и ошибки сценария, серверный путь, generated consumer и существующий UI проверяются вместе. Поздние ответы, отмена, no-store, bearer своего origin и ограничения host/origin сохраняются. Новых клиентов, remote auth, личных подключений, редизайна, ORM, универсального scheduler или автоматического replay не добавлять.

Проверки используют настоящий HTTP, временные SQLite/файлы и синтетические источники/модели; браузер — Playwright. Для затронутого UI сделать и просмотреть desktop/mobile screenshots. Computer Use и личные аккаунты/модели не использовать. Проверять наблюдаемое поведение, не расположение внутренних модулей. Предметные DTO не обходить Any/cast, generated-файлы не править вручную.

Фактические команды, результаты, неудачные прогоны, ограничения и артефакты записать отдельно. Candidate допускает поведенческие проверки до baseline, но PENDING_REVIEW не является PASS совместимости или разрешением выпуска. Обычные gates сохраняют строгость. Исторические отчёты не переписывать; служебные миграции обратимы, материалы и настройки сохраняются. По умолчанию работает один исполнитель; зависимости не означают поручения параллельным агентам. Коммит, публикация и перезапуск пользовательского экземпляра не входят в задачу.
