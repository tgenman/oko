Parent: [Спецификация](../spec.md). [Дизайн контракта](../contract-design.md). [Порядок и покрытие](../tasks.md).

**Реализация пока не поручена.** Пользователь согласовал только оформление семи задач.

**Что сделать:** Пользователь настраивает два Telegram-профиля, подключает источник через web/client, читает полное или неполное содержимое и явно удаляет фид. Старые привязки и конфликты видны без выдуманной личности; клиентское прочитанное и локальная очистка отражают Telegram-план.

External dependency: [Telegram-план](../../telegram-access/spec.md), предметные модули и evidence их проверок. Отсутствие зависимости не подменяется stubs.

## Критерии приёмки

- [ ] Все Telegram-пути проверены через HTTP и веб-интерфейс с синтетическими adapters: настройка профилей, старые aliases, подключение, duplicate popup, история, media/Telegraph, прочитанное и удаление. Тема не является отдельным фидом; скрытый fallback отсутствует.
- [ ] Предметная зависимость из Telegram-плана реализована и проверена до закрытия тикета: binding/claims/profile generation, workers/lanes, history/cursors, media/Telegraph и ReadSync, возобновляемая очистка. API-тикет интегрирует эти модули и не поручает их повторную или неразрешённую реализацию. Отдельный предварительный Telegram API release не требуется.

### Сохранённые критерии

Идентификатор C — прежний номер тикета и номер критерия; он сохраняет прослеживаемость после перенумерации. Составные пункты читаются с распределением ответственности в индексе задач.

- [ ] **C05.06** Начальная история и догрузка различаются по default и допустимому сценарию; просмотренные публикации не возвращаются. Для Telegram пауза/ошибка архивной выборки не останавливает live, fetch выбранной count-истории ждёт завершения manifest; HTTP отражает общий History, не adapter cursor.
- [ ] **C05.08** Минимальные новые AddFeed и ConnectTelegram web/client, включая пропущенный access, получают count="20"; явные count/date сохраняются. Null, пустой объект и неполная selection дают 422 без записи.
- [ ] **C06.01** OPML preview/import/choices и публичные topics/topic_id отсутствуют в routes/DTO. Прежние импортированные фиды сохраняются, сценарии используют одиночное подключение.
- [ ] **C06.02** Telegram connect имеет closed web/client variants. Web — default, не требует аккаунта, не принимает profile/auto_read, не запускает worker или fallback. Client требует personal/collection; auto_read default false.
- [ ] **C06.03** GET profiles отдаёт два состояния и непрозрачные ссылки на существующие конфигурации без секретов. Один PUT role привязывает и проверяет аккаунт; тот же PUT восстанавливает прежний аккаунт, отдельного check endpoint нет.
- [ ] **C06.04** Смена личности занятого профиля и одинаковый user ID двух ролей отклоняются. Внешняя подмена session не приводит к чтению/ack другим аккаунтом; legacy aliases/данные не теряются до подтверждения.
- [ ] **C06.05** Access/account/peer неизменяемы. Подтверждённый duplicate_source возвращает непустой existing_feeds без upsert; старый конфликт перечисляет всех владельцев, не останавливает чтение и разрешает ручное удаление лишнего фида; конкурирующие подключения не обходят доменные claims. Ограничения распознавания веб-идентичности не скрыты.
- [ ] **C06.06** Группа собирается целиком без product-facing темы; сведения о темах остаются только там, где нужны ReadSync. Веб не подтверждает прочитанное. Нельзя вступать в группу или переключать доступ для восполнения материала.
- [ ] **C06.07** DELETE feed отражает возобновляемую локальную очистку deleting/deleted без viewed/ack/leave. Claims заняты до завершения, новое добавление имеет новый ID, поздний результат старого фида отвергается. Отдельного polling endpoint нет.
- [ ] **C06.08** Материал сохраняет Telegraph и доступные локальные медиа, явную неполноту и правильное различие дополнения/авторской версии; HTTP DTO не скрывает ограничения adapter.
- [ ] **C06.10** Ошибки связи, identity/profile/duplicate/deletion conflicts и отмена имеют типизированные code/details. Непроверенные доменные сценарии не подменены успешными stubs; до их evidence задача не закрывается.
- [ ] **C06.11** До подтверждения профилей каталог/настройки/чтение и duplicate_source сериализуют legacy_client с alias/source_locator/nullable peer_id без role/account_user_id. Проверены несколько старых владельцев и более двух aliases без выбора победителя, 500 и потери данных.
- [ ] **C06.12** После подтверждённого сопоставления роли тот же feed_id получает client access; не меняются контент/настройки. Connect отвергает legacy_client; web/client без initial_history сохраняют count="20".
- [ ] **C11.04** OPML и выбор темы удалены. Сохраняются RSS/YouTube/processor forms; Telegram показывает web/personal/collection, web выбран по умолчанию. Старые проверки доступа/catalog replies не меняют новый контекст.
- [ ] **C11.07** Форма профилей использует существующие конфигурации без мастера логина; повторная проверка — тот же PUT. Duplicate-source popup строится локально из typed данных; доступ существующего фида не переключается.
- [ ] **C11.08** Удаление фида требует явного действия с описанием локальной очистки и не означает Telegram-прочитанное; видны deleting/ошибки и возможность нового добавления после завершения.
- [ ] **C11.09** Absent истории не показывается как нулевой прогресс или выбранные 20 публикаций; not_started отображает сохранённый выбор. Новое Telegram-подключение согласовано с серверным default count="20".
- [ ] **C11.10** Старые неподтверждённые фиды и duplicate popup отображают alias без выдуманного профиля. Сопоставление использует GET/PUT profiles; отдельной формы/команды reconnect_feed нет. Удаление и новое добавление остаются явными действиями с предупреждением об очистке.

## Проверка

Настоящий HTTP с synthetic RSS/Telegram/web-HTML/Telegraph/YouTube/model adapters. Проверить web без аккаунта, personal/collection, конфликт ролей/источников, неизменяемость доступа, profile generation race, групповое прочитанное, удаление во время работы и повторное добавление. Подробные алгоритмы и worker evidence принадлежат Telegram-задаче; здесь проверяется публичный результат через тот же HTTP seam.

Playwright меню, independent operations, settings navigation, connections, history, Codex и YouTube; настоящие HTTP-сценарии и задержанные ответы. Просмотреть screenshots изменённых форм.

Дополнительно: проверить все критерии этого тикета через указанные выше HTTP/UI-сценарии. В задаче 01 проверки остальных семейств относятся к гарантиям инструментария; их полное поведение принимается в соответствующих задачах 02–06.

## Границы и проверка результата

Все требования родительской спецификации, дизайна контракта и исправления ревью обязательны. Здесь меняется разбиение работы, не продуктовый объём. Типы и ошибки сценария, серверный путь, generated consumer и существующий UI проверяются вместе. Поздние ответы, отмена, no-store, bearer своего origin и ограничения host/origin сохраняются. Новых клиентов, remote auth, личных подключений, редизайна, ORM, универсального scheduler или автоматического replay не добавлять.

Проверки используют настоящий HTTP, временные SQLite/файлы и синтетические источники/модели; браузер — Playwright. Для затронутого UI сделать и просмотреть desktop/mobile screenshots. Computer Use и личные аккаунты/модели не использовать. Проверять наблюдаемое поведение, не расположение внутренних модулей. Предметные DTO не обходить Any/cast, generated-файлы не править вручную.

Фактические команды, результаты, неудачные прогоны, ограничения и артефакты записать отдельно. Candidate допускает поведенческие проверки до baseline, но PENDING_REVIEW не является PASS совместимости или разрешением выпуска. Обычные gates сохраняют строгость. Исторические отчёты не переписывать; служебные миграции обратимы, материалы и настройки сохраняются. По умолчанию работает один исполнитель; зависимости не означают поручения параллельным агентам. Коммит, публикация и перезапуск пользовательского экземпляра не входят в задачу.
