# Ограничение запросов Telegram и повторный сбор

Статус: реализовано и проверено 2026-10-21; ожидает слияния PR #66.
GitHub: https://github.com/tgenman/oko/pull/66

## Согласовано

- Все HTML-запросы Telegram web одного экземпляра Око проходят общий ограничитель:
  не чаще 2 запросов в секунду (интервал между началами запросов не менее 500 мс),
  без накопления разрешений на всплеск. Это выбранный бюджет Око, а не гарантия
  безопасной частоты со стороны Telegram.
- HTTP 429 устанавливает общую паузу соответствующей группы запросов.
  Ручное обновление и перезапуск её не сбрасывают. Учитываются обе формы Retry-After:
  секунды и HTTP-date; серверная пауза не сокращается.
- Полностью загруженные в Око материалы больше не запрашиваются ради проверки
  правок и удалений, даже если пользователь ещё не нажал «Просмотрено».
  Правило действует для Telegram web и доступа через аккаунт. Неполные материалы
  продолжают догружаться.
- В контекстном меню поста появляется явная команда повторной загрузки,
  доступная и для полностью загруженного материала. Обычное обновление фида
  или папки не вызывает повторную загрузку полных материалов.
- Команда «Загрузить заново» для Telegram web и доступа через аккаунт повторно
  получает публикацию и все её вложения. Старая копия остаётся текущей до успешного
  получения полной замены. Частичный результат, в том числе изменившийся текст
  с недоступным новым вложением, не заменяет прежнюю полную копию. Старый файл
  вместо нескачавшегося нового не считается успешной полной перезагрузкой.
- Команда соблюдает общий допуск и сохранённые паузы. Неизменное содержимое
  не требует повторной ИИ-обработки; изменившееся проходит существующее
  согласование фильтрации и тезисов. Показ новой версии в открытом материале
  остаётся по существующим правилам.
- После временной ошибки явная перезагрузка автоматически повторяется после
  установленной паузы. Старая копия сохраняется. При окончательной недоступности
  публикации или вложения повторы прекращаются, читателю показывается причина.
  Существующие неполные материалы продолжают догружаться по обычным правилам;
  защита полной копии не превращает их в недоступные для чтения материалы.
- Аватары и вложения используют отдельный бюджет для каждого сервера медиа:
  2 запроса в секунду без всплесков. HTTP 429 закрывает общий допуск запросов
  к этому серверу, сохраняя работу остальных источников.
- Общий HTML-бюджет и бюджет медиа относятся к HTTP; частота аккаунтного MTProto
  не приравнивается к ним. Существующее ожидание FloodWait сохраняется.
- «Полностью загружен» обозначает полноту собранного материала, а «Просмотрено» —
  отдельное действие читателя с удалением локального содержимого. Эти понятия
  не объединяются.

Открытых продуктовых решений нет. Итог подтверждён пользователем вызовом
implement-spec; реализация выполнена в согласованном объёме.

## Ограничения выполнения

- Ожидания выполняются вне action lock. Пауза Telegram не занимает common lane
  долгим sleep и не препятствует RSS, чтению, удалению и выключению Око.
- Ограничитель проверяет каждый HTTP-запрос, включая проверку подключения,
  аватары и переходы. `t.me` и `telegram.me` используют общий HTML-бюджет.
- Без пригодного Retry-After повторные 429 увеличивают паузу: 1, 2, 4 минуты
  и далее до 60 минут. При наличии заголовка ожидание не короче указанного сервером.
- Все бюджеты действуют в пределах одного экземпляра Око; несколько экземпляров
  за одним IP не получают распределённый общий ограничитель в рамках этой задачи.
- Отдельные настройки пользователя для частоты не добавляются.

## Проверенные границы реализации

- `POST /api/v3/materials/{item}/retry` уже допускает повторную загрузку полного
  непросмотренного материала; новой HTTP-ручки ради меню не требуется.
- Контекстное меню находится в `frontend/src/reading/news-actions.tsx`;
  существующая кнопка повторной загрузки открытого материала показывается
  только для неполной копии.
- Сейчас защита от замены полной копии неполной в `oko/storage/versions.py`
  относится только к результату без изменения авторского содержимого.
  Для согласованной команды необходимо также защитить старую копию при
  изменившемся тексте и неуспешном получении новых вложений.

## Проверка

На этапе интервью менялось только описание решений. Фактические проверки
реализации: [отчёт](../../docs/verification/telegram-web-rate-limits.md).

План реализации: HTTP-сценарии с временным хранилищем и синтетическими источниками
проверяют общий лимит разных фидов и подключений, переходы, аватары и вложения,
обе формы Retry-After, сохранение паузы после ручного обновления и перезапуска,
отмену и доступность остальных источников. Для обоих способов доступа к Telegram
проверяются отсутствие повторного fetch полных материалов, догрузка неполных,
явная полная перезагрузка, сохранность старой копии при частичном результате,
временные и окончательные ошибки. Контекстное меню проверяется в Playwright
с просмотром скриншота. Изменения проходят независимое ревью по правилам разработки.
