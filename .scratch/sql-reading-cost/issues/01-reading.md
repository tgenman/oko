# 01: Чтение материалов, списков и счётчиков

Status: ready-for-agent
GitHub: https://github.com/tgenman/oko/issues/53
Blocked by: Нет

## What to build

Читатель открывает материал, фид, папку и общий список без повторного получения одинаковых настроек, версий и состояний обработки. Работа по выбранной области не строит материалы остальных областей. Подготовительный рефакторинг чтений выполнить внутри этой задачи до изменения сценариев; результат проверяется через существующие API и UI.

## Acceptance criteria

- [ ] Один материал получает только нужный фид; при росте числа посторонних фидов стоимость открытия не растёт линейно (исходно 92 SQL на 4 фидах и 172 на 20).
- [ ] Настройки фида/папки/Око, текущие и предыдущие версии, фильтр, принятые тезисы, происхождение и статус не перечитываются повторно в пределах одного чтения. Повторное использование ограничено актуальным снимком запроса.
- [ ] Компактная карточка не требует полной сборки открытого материала. Если нужен текст для превью, он читается один раз; одинаковая работа не переносится в файлы или Python.
- [ ] Выборка фида/папки ограничивается до построения карточек. При неизменной выбранной области добавление посторонних публикаций не даёт пропорционального роста SQL или чтений содержимого.
- [ ] Сохраняются состав, сортировка, превью, версии, медиа, скрытые/незагруженные материалы, счётчики и has_unviewed; browser-сценарии выбора и открытия остаются корректными.
- [ ] На четырёх фидах по 26 и по 100 материалов воспроизведены исходные замеры и зафиксированы сниженные бюджеты HTTP-навигации, списков и открытия; добавлены проверки роста стоимости.
- [ ] Индекс непросмотренных публикаций проверен на 20 000 материалах со 100 непросмотренными: обоснован выбранный план чтения/порядка, стоимость записи и безопасная повторная миграция.

## Проверка и ограничения

Проверять через существующий HTTP interface с временными SQLite/файлами, синтетическими источниками и обработчиком. Браузер — Playwright с проверкой запросов, видимого результата и просмотром скриншотов затронутых состояний. SQL trace конкретного запроса отделять от фоновой работы; планы и работу SQLite измерять отдельно от времени всего сценария. Фиксировать исходные и итоговые бюджеты, рост с размером выбранной области и посторонних данных. Проверять внешнее поведение, не расположение методов и не точную строку EXPLAIN.

Сохранить Runtime как владельца действий/отмены, Store как владельца транзакций/файлов/восстановления, единые правила состава чтения. Сохранить поколения заданий, актуальность результатов, версии, безопасную границу прочитанного Telegram и точный состав подтверждений. Смена параметров будущего выполнения Codex не инвалидирует готовые результаты. Индексы вводить по измерениям, с проверкой цены записи и повторного запуска миграции. Не ослаблять фиксацию, secure_delete или проверки поздних результатов.

Любое изменение HTTP-контракта проходит канонический OpenAPI, генерацию DTO/SDK и действующие проверки совместимости. Не добавлять тестовые endpoints, ORM, универсальный scheduler, глобальный кэш без инвалидации, пагинацию или редизайн. Личные источники, аккаунты, настоящий обработчик и пользовательский экземпляр не затрагивать. Каждая задача проходит свои необходимые проверки и остаётся работоспособной до итоговой приёмки. Результаты, неудачные прогоны и ограничения записать отдельно от требований. Метка ready-for-agent не запускает реализацию.

## Общая спецификация всех пяти задач

Полный контекст приведён здесь, чтобы задачи не зависели от неопубликованного локального файла. Критерии общей спецификации распределены между задачами; задача 01 отвечает только за свой раздел Acceptance criteria.

## Problem Statement

Чтение и обычные действия в Око многократно получают одни и те же настройки, версии и состояния обработки. Стоимость открытия списка, подготовки завершения папки и просмотра одной публикации растёт вместе с библиотекой, включая материалы других папок. Фоновая работа повторяет полные обходы даже при отсутствии изменений. Накопление просмотренных публикаций, завершённых заданий и результатов команд увеличивает стоимость отдельных запросов.

Аудит 2026-10-20 обнаружил 396 мест выполнения SQL в 18 модулях. На синтетических четырёх YouTube-фидах с 400 материалами без субтитров один HTTP-запрос списка всех карточек выполнил 25 639 SQL, навигация — 4 840, статус — 946. Полный цикл обновления этих трёх представлений составил 31 425 SQL. Браузер назначал следующий цикл через 500 мс после завершения предыдущего. Один проход согласования обработки выполнил 17 602 SQL, отметка одного материала просмотренным через Store — 17 599.

Это измерения синтетического стенда, не личной базы и не времени работы исключительно SQLite. Чтение файлов, JSON и вычисление актуальности входят в стоимость сценариев. Они показывают повторную работу, но не устанавливают производственный SLA.

## Solution

Сделать стоимость чтения и действий соразмерной запрошенной области и фактически изменившимся данным:

- Получать общие настройки и состояния пакетно, повторно использовать их в пределах одного согласованного чтения.
- Не строить полные материалы для данных, которым достаточно компактного представления.
- Ограничивать действия над фидом и папкой их составом; согласовывать обработку затронутых публикаций.
- Не пересобирать и не передавать неизменившиеся представления при фоновом обновлении.
- Индексировать подтверждённые дорогие обращения и проверять стоимость при накоплении истории.

Сокращение SQL и выборочное обновление браузера — самостоятельные части результата. Уменьшение частоты опроса не заменяет исправление серверных чтений, а уменьшение SQL не заменяет прекращение повторной передачи неизменившихся представлений.

Сохранить продуктовые правила чтения, обработки, завершения папок, версий, отмены и восстановления. Успешное действие текущей вкладки отражается после ответа сервера без ожидания фонового обновления. Для фоновых изменений используется требование существующего проекта: показ с задержкой не более 1–2 секунд в условиях доступного сервера и свободного тестового окружения.

## User Stories

1. Как читатель, я хочу открывать один материал без загрузки описаний всех фидов, чтобы размер подписок не определял стоимость этого действия.
2. Как читатель, я хочу открывать список фида без построения карточек других фидов, чтобы работа с небольшим фидом оставалась лёгкой в большой библиотеке.
3. Как читатель, я хочу открывать список папки без построения материалов других папок, чтобы выбор области ограничивал объём работы.
4. Как читатель, я хочу видеть прежний состав, сортировку и превью карточек, чтобы оптимизация не меняла смысл списка.
5. Как читатель, я хочу видеть корректные счётчики фидов и папок, чтобы скрытые, незагруженные и просмотренные публикации учитывались по существующим правилам.
6. Как читатель, я хочу готовить завершение папки без загрузки всех чужих карточек, чтобы подтверждение относилось к выбранной папке.
7. Как читатель, я хочу завершать папку с учётом скрытых и незагруженных публикаций, чтобы оптимизация не сужала охват «Всё просмотрено».
8. Как читатель, я хочу, чтобы подтверждение сохраняло точный состав публикаций, чтобы новые поступления не удалялись по старому токену.
9. Как читатель, я хочу отмечать одну публикацию просмотренной без пересогласования всей библиотеки, чтобы одиночное действие не зависело от числа чужих материалов.
10. Как читатель, я хочу сразу видеть результат успешного действия текущей вкладки, чтобы не ждать очередного фонового опроса.
11. Как читатель, я хочу получать фоновые изменения в пределах согласованной задержки, чтобы список и открытый материал оставались актуальными.
12. Как читатель, я хочу, чтобы неизменившаяся область не загружалась целиком повторно, чтобы открытый читатель не расходовал ресурсы без полезной работы.
13. Как читатель, я хочу сохранять фокус, прокрутку и выбранную карточку при обновлении, чтобы оптимизация не прерывала чтение.
14. Как читатель, я хочу, чтобы поздний ответ старой области не заменял текущий список или материал, чтобы быстрое переключение оставалось корректным.
15. Как читатель, я хочу видеть согласованные изменения из другой вкладки, чтобы просмотр и завершение фида не оставляли устаревший материал.
16. Как читатель, я хочу видеть новые версии, медиа и результаты обработки по действующим правилам открытого материала, чтобы экономия чтений не скрывала изменения.
17. Как пользователь обработки, я хочу пересчитывать актуальность только затронутых публикаций, чтобы завершение одной операции не запускало полный обход.
18. Как пользователь настроек, я хочу применять изменения фида, папки и общих правил ко всем затронутым материалам, чтобы локальное согласование не пропускало зависимости.
19. Как пользователь обработчика, я хочу сохранять актуальные готовые результаты при смене параметров будущего выполнения, чтобы оптимизация не нарушала принятое разделение актуальности и происхождения.
20. Как пользователь Telegram, я хочу синхронизировать несколько фидов без повторного чтения всех подписок для каждого, чтобы стоимость росла соразмерно числу фидов.
21. Как пользователь Telegram, я хочу сохранить безопасную границу прочитанного и правила автопрочитывания, чтобы оптимизация не расширяла внешнюю отметку.
22. Как пользователь, я хочу, чтобы накопление просмотренных публикаций и завершённых заданий не заставляло каждое локальное действие сканировать всю историю.
23. Как пользователь, я хочу получать актуальные проблемы и исходы команд без повторных одинаковых записей, чтобы статус оставался полезным и недорогим.
24. Как пользователь, я хочу восстанавливать корректное состояние после перезапуска или пропущенного обновления, чтобы временная недоступность не оставляла устаревший кэш.
25. Как пользователь, я хочу, чтобы выключение Око останавливало сбор и обработку при сохранении чтения, чтобы оптимизация не меняла управление работой.
26. Как сопровождающий, я хочу видеть воспроизводимые бюджеты и планы запросов, чтобы отличать реальное сокращение работы от переноса нагрузки в файлы или Python.

## Implementation Decisions

1. Сохранить текущие границы владения: Runtime управляет действиями, допуском, отменой и ожиданиями; Store — транзакциями, файлами и восстановлением; состав чтения — едиными правилами списка, счётчиков и завершения.
2. Разделить реализацию на два направления с отдельными измерениями: стоимость серверных сценариев и выборочное обновление браузера. Не считать одно направление выполнением другого.
3. Получать общие настройки фида, папки и Око один раз на чтение соответствующего набора. Не строить полное описание подписки и агрегаты истории при каждом запросе настройки публикации. Пакетно получать версии, состояния заданий, восстановления фильтра и сохранённых результатов.
4. В пределах одного чтения материала вычислять фильтр, принятые тезисы, их происхождение и список предыдущих версий без повторной загрузки одних данных. Не сохранять безусловный глобальный кэш, способный пережить изменение входов или настроек.
5. Развести компактную проекцию карточки и полный открытый материал. Если превью требует текста, читать необходимое содержимое один раз; не переносить скрытую полную сборку материала в новый помощник.
6. Ограничивать выборку фидом или папкой до построения представлений. Подтверждение завершения получает точный состав и число доступных карточек без полной загрузки чужих материалов. Состав завершения включает скрытые, незагруженные и нечитаемые публикации.
7. Согласовывать фильтрацию и тезисы по затронутым публикациям и областям настроек. Полный проход допустим при восстановлении и действительно глобальных изменениях; неизменившийся обычный цикл не должен его повторять. Смена модели Codex, усилия рассуждения и Fast для будущей работы сама по себе не инвалидирует готовые результаты.
8. Сохранить проверку поколения задания и актуальности входов при принятии результата. Оптимизация предварительных чтений не разрешает позднюю фиксацию после просмотра, удаления, изменения настроек или остановки.
9. Для Telegram использовать уже полученную конфигурацию фида, пакетные профили и привязки. Разделить восстановление из просмотренных записей и обычное продвижение состояния; сохранить все основания безопасной границы прочитанного.
10. Статус не должен повторно разбирать одинаковые наборы проблем внутри прохода. Записывать изменившиеся состояния проблем; сохранять идентичность происшествия, историю исходов и действующие сроки очистки.
11. Проверить и внедрить индексы по подтверждённым планам: поиск истории по материалу; задания по материалу; последняя команда по предметной идентичности и последовательности; непросмотренные публикации с нужным порядком; ожидающие задания по времени допуска. Учитывать существующие составные и уникальные индексы, цену записи и распределение данных. Не создавать все кандидаты механически.
12. Миграции индексов должны безопасно работать на существующей базе, повторно запускаться и сохранять содержимое, настройки, версии и служебные отметки. Не менять журналирование, secure_delete или гарантии фиксации ради результата бенчмарка.
13. Каждое действие браузера читает данные нужной области. Неизменившаяся область не пересобирается сервером и не передаётся целиком. Способ обнаружения изменений и доставки остаётся выбором реализации с обоснованием: текущий аудит не выбирал между коротким опросом признаков изменений и уведомлениями сервера.
14. При выборе протокола определить области инвалидации для состава чтения, списка, открытого материала и статуса, а также восстановление после пропуска изменений и смены экземпляра сервера. Не обещать атомарный снимок для нескольких независимых HTTP-запросов.
15. Любые изменения публичного HTTP-контракта проводить через канонический OpenAPI и генерацию DTO/SDK с действующими проверками совместимости. Не добавлять внутренние тестовые endpoints, ручные изменения generated-кода или вторую транспортную библиотеку.
16. Сохранить существующих владельцев браузерной сессии, списка, открытого материала и форм. Изменения не должны дублировать heartbeat, опрос, BroadcastChannel или управление поздними ответами.
17. Порядок работы: воспроизводимая исходная стоимость → пакетные чтения и ограничение области → индексы → локальное согласование → выборочное обновление браузера → интеграционные проверки. Проверять эффект каждого этапа отдельно; реализация может уточнять порядок при доказанной зависимости.

## Testing Decisions

Границы проверки подтверждены пользователем вместе с разбиением на пять задач: HTTP с временной SQLite, Playwright и измерение SQL.

- Основная граница — существующий HTTP interface читателя с временными SQLite и файлами, синтетическими источниками, обработчиком и управляемым временем. Через него проверять навигацию, карточки, открытие материала, статус, завершение фида/папки, просмотр, настройки и последствия фоновой обработки.
- Браузерная часть — существующий настоящий браузер через Playwright и управляемый HTTP adapter. Проверять видимый результат и фактические запросы, допуск поздних ответов, текущую область, фокус, прокрутку и обновление после действий; просмотреть снятые скриншоты затронутых состояний.
- Использовать существующий механизм подсчёта SQL через trace callback на временном соединении. Отделять запрос конкретного HTTP-сценария от фона. Для фоновой работы учитывать один завершённый проход отдельно. Это измерительная инструментация, не новый продуктовый interface.
- Предшествующие примеры: ограничение стоимости чтения фида, HTTP-контракты, состав чтения и завершение папки/фида, версии и поздние ответы, жизненный цикл обработки, Telegram read sync, восстановление и browser refresh.
- Проверять результат и зависимость стоимости от данных, не имена внутренних методов, расположение модулей или точный текст каждого SQL. Не требовать одинаковой строки EXPLAIN между версиями SQLite.
- Перед изменением воспроизвести исходные сценарии ниже; после изменения измерить их на тех же данных. Для каждого изменённого сценария зафиксировать меньший численный бюджет на основании измерений и добавить регрессионную проверку. Исторические пороги в тысячи запросов не переносить без обоснования.
- Масштабирование проверять независимо по размеру выбранной области, числу посторонних материалов, числу фидов и объёму завершённой истории. Время фиксировать как вспомогательную метрику вместе с числом SQL, планом/работой SQLite и повторными чтениями содержимого.

Критерии приёмки:

- [ ] Четыре фида по 26 и по 100 материалов: сохранены результаты навигации, списка, открытия материала, статуса, завершения и просмотра; измеренные SQL-бюджеты ниже исходных для затронутых сценариев.
- [ ] При неизменном наборе выбранного фида добавление материалов в другие фиды не увеличивает число SQL/чтений содержимого для построения выбранных карточек пропорционально чужим материалам.
- [ ] Открытие одного материала не загружает описания всех фидов; увеличение числа посторонних фидов не даёт линейного роста SQL этого сценария.
- [ ] Подготовка завершения одной папки не строит карточки других папок; сохраняются скрытые/незагруженные публикации и конфликт при изменении состава после подтверждения.
- [ ] Просмотр одной публикации и принятие результата обработки не запускают обычное полное согласование всех непросмотренных материалов. Результаты остальных публикаций сохраняются.
- [ ] Несколько фоновых циклов без изменений не выполняют повторное согласование всех материалов, а браузер не получает повторно полные неизменившиеся представления.
- [ ] Новая публикация, версия, результат фильтрации или тезисы, восстановление скрытого материала, перенос фида и изменение настроек обновляют все затронутые представления; изменения не теряются при нескольких событиях между обновлениями.
- [ ] Успешное действие текущей вкладки отражается без ожидания фонового обновления; фоновое изменение видно за 1–2 секунды в управляемом сценарии без сетевых задержек и перегруженного сервера.
- [ ] Смена области, сортировки и показа скрытых материалов, несколько вкладок, поздние ответы, пропущенные уведомления, разрыв связи и перезапуск не оставляют устаревший список или открытый материал.
- [ ] На 5, 20 и 50 синтетических Telegram-фидах отсутствует повторная загрузка всех фидов для каждого фида; число SQL растёт линейно, а безопасная граница прочитанного и автопрочитывание сохраняются.
- [ ] На 20 000 служебных записях планы точечного обновления истории и отмены заданий используют поиск по материалу вместо полного сканирования соответствующей таблицы.
- [ ] На 3 000 синтетических ошибочных командах поиск последнего исхода не выполняет полный поиск по журналу для каждой команды.
- [ ] При большой доле просмотренных публикаций и завершённых заданий чтение текущей области и выбор ожидающего задания не обходят весь накопленный архив без необходимости; измерены цена добавленных индексов при записи и поведение после миграции.
- [ ] Перезапуск восстанавливает незавершённые изменения и актуальность результатов. Остановка, удаление и просмотр закрывают приём позднего результата; выключенное Око сохраняет чтение.
- [ ] Пройдены затронутые HTTP, lifecycle и Playwright-наборы, проверки API при изменении контракта и обязательные проверки проекта. Неудачные прогоны, повторные проверки и ограничения отражены отдельно от требований.

## Out of Scope

- Пагинация списков, новый способ сортировки, редизайн интерфейса и изменение состава карточек.
- Замена SQLite другой СУБД, внедрение ORM, общего кэш-сервиса или универсального scheduler.
- Изменение правил актуальности обработки, безопасного прочитанного Telegram, удаления собранного содержимого или завершения папки.
- Сокращение задержки за счёт ослабления фиксации, отключения защиты данных либо удаления нужных проверок поколений.
- Запуск личных подписок, настоящий Telegram-аккаунт, реальный обработчик, изменение личной базы, перезапуск или развёртывание пользовательского экземпляра.
- Автоматическое начало реализации, назначение исполнителя или метка запуска Ready после публикации этой спецификации.

## Further Notes

Исходные измерения аудита 2026-10-20:

| Сценарий | 104 материала | 400 материалов |
|---|---:|---:|
| HTTP: навигация | 1 288 | 4 840 |
| HTTP: карточки одного фида | 1 703 | 6 439 |
| HTTP: все карточки | 6 695 | 25 639 |
| HTTP: один материал | 92 | 92 |
| HTTP: статус | 354 | 946 |
| HTTP: подготовка завершения одной папки | 6 381 | 24 437 |
| Store: один проход согласования обработки | 4 578 | 17 602 |
| Store: просмотр одной публикации | 4 575 | 17 599 |

Четыре фида распределены равномерно; содержимое синтетическое, YouTube без субтитров. Фоновая работа отключена для изолированных HTTP-замеров; прямые вызовы Store измерены отдельно. Дополнительный стенд на 20 фидах по 5 материалов подтвердил рост стоимости открытия одного материала до 172 SQL против 92 на четырёх фидах.

Отдельный проход синхронизации Telegram без материалов: 196 / 2 281 / 13 201 SQL при 5 / 20 / 50 фидах. Настоящие аккаунты не использовались.

Индексные эксперименты выполнялись только на временной базе. На 20 000 материалах со 100 непросмотренными работа запроса общего списка сократилась приблизительно с 61 100 до 400 инструкций SQLite. На 3 000 ошибочных командах работа поиска последних исходов сократилась с 18,1 млн до 102 тыс. инструкций. Кандидат индекса ожидающих заданий проверялся после ANALYZE; сортировка по приоритету остаётся отдельной частью плана. Эти результаты не гарантируют аналогичный выигрыш всей системы.

Существующая проверка стоимости чтения прошла, но её пределы — менее 2 000 SQL на навигацию 104 публикаций и менее 3 000 на 26 карточек — не исключают обнаруженную повторную работу. Все измеренные HTTP-сценарии вернули 200. Личная база и производительность реального браузера не измерялись; эти результаты не являются приёмкой будущей реализации.

При подготовке учтён текущий проект обновления данных читателя: он задаёт выборочное чтение, отсутствие пересборки неизменившейся области, задержку фонового показа 1–2 секунды и немедленное отражение успешного действия. Способ доставки изменений и публичный контракт в нём ещё не выбраны; эта спецификация не объявляет конкретный транспорт ранее согласованным.

SQLite допускает много небольших локальных запросов; основание оптимизации здесь — измеренное повторение работы и плохое масштабирование сценариев, а не число запросов само по себе. Справочные материалы: [many small queries](https://www3.sqlite.org/matrix/np1queryprob.html), [partial indexes](https://www.sqlite.org/partialindex.html), [EXPLAIN QUERY PLAN](https://sqlite.org/eqp.html).

Публикация описания с меткой ready-for-agent означает готовность требований. Реализация требует отдельного задания пользователя.
