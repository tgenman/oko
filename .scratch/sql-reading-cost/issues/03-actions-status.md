# 03: Просмотр, завершение папок и состояние приложения

Status: ready-for-agent
GitHub: https://github.com/tgenman/oko/issues/55
Blocked by: 01, 02

## What to build

Просмотр одной публикации и завершение фида/папки выполняют только необходимую работу, а состояние приложения и исходы команд остаются корректными без повторного сканирования и одинаковых записей.

## Acceptance criteria

- [ ] Просмотр одной публикации не запускает глобальное согласование обработки или Telegram; действие отражается через HTTP и UI, остальные материалы сохраняются. Исходные 4 575/17 599 SQL на 104/400 материалах заменены измеренным меньшим бюджетом.
- [ ] Подготовка завершения фида/папки не строит карточки чужих областей. Охват включает скрытые, незагруженные и нечитаемые публикации; число доступных карточек сохраняет свой смысл.
- [ ] Токен подтверждения фиксирует точные публикации. Новое поступление вызывает существующий конфликт и не удаляется по старому токену; поздние ответы и межвкладочные действия не очищают новые материалы.
- [ ] На 20 000 служебных записях обновление истории и отмена заданий по материалу используют поиск вместо полного сканирования; индексы и миграции проверены вместе с действиями.
- [ ] Статус не перечитывает одинаковые настройки/наборы проблем внутри прохода, не повторяет ненужное чтение содержимого и не записывает неизменившиеся проблемы. Сохраняются идентичность проблемы, исходы команд и сроки очистки.
- [ ] На 3 000 ошибочных командах последняя команда по предметной идентичности определяется без полного поиска по журналу для каждой записи; сохранены failed/unknown/pending и восстановление после перезапуска.
- [ ] Воспроизведены исходные HTTP-бюджеты подготовки завершения папки 6 381/24 437 и статуса 354/946 на 104/400 материалах. Зафиксированы новые бюджеты и поведенческие HTTP/Playwright-проверки.

## Проверка и ограничения

Проверять через существующий HTTP interface с временными SQLite/файлами, синтетическими источниками и обработчиком. Браузер — Playwright с проверкой запросов, видимого результата и просмотром скриншотов затронутых состояний. SQL trace конкретного запроса отделять от фоновой работы; планы и работу SQLite измерять отдельно от времени всего сценария. Фиксировать исходные и итоговые бюджеты, рост с размером выбранной области и посторонних данных. Проверять внешнее поведение, не расположение методов и не точную строку EXPLAIN.

Сохранить Runtime как владельца действий/отмены, Store как владельца транзакций/файлов/восстановления, единые правила состава чтения. Сохранить поколения заданий, актуальность результатов, версии, безопасную границу прочитанного Telegram и точный состав подтверждений. Смена параметров будущего выполнения Codex не инвалидирует готовые результаты. Индексы вводить по измерениям, с проверкой цены записи и повторного запуска миграции. Не ослаблять фиксацию, secure_delete или проверки поздних результатов.

Любое изменение HTTP-контракта проходит канонический OpenAPI, генерацию DTO/SDK и действующие проверки совместимости. Не добавлять тестовые endpoints, ORM, универсальный scheduler, глобальный кэш без инвалидации, пагинацию или редизайн. Личные источники, аккаунты, настоящий обработчик и пользовательский экземпляр не затрагивать. Каждая задача проходит свои необходимые проверки и остаётся работоспособной до итоговой приёмки. Результаты, неудачные прогоны и ограничения записать отдельно от требований. Метка ready-for-agent не запускает реализацию.
