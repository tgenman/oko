# 04: Выборочное обновление браузера

Status: done
GitHub: https://github.com/tgenman/oko/issues/56
Blocked by: 01, 03

## What to build

От обнаружения серверного изменения до отображения в браузере обновляются только нужные области: список, навигация, открытый материал и статус. Неизменившиеся представления не пересобираются и не передаются целиком.

## Acceptance criteria

- [x] Обоснован способ доставки изменений (короткий опрос признаков либо уведомления), определены области инвалидации и восстановление после пропуска/перезапуска. Аудит не считается предварительным выбором конкретного транспорта.
- [x] Каждое действие читателя запрашивает необходимые данные: открытие карточки — материал, выбор области — её список. Последовательные неизменившиеся обновления не пересобирают и не передают полные представления.
- [x] Новые публикации, версии, фильтрация, тезисы, восстановление скрытого материала, перенос фида и настройки инвалидируют все затронутые области; несколько событий между обновлениями не теряются.
- [x] Успешное действие текущей вкладки отражается после ответа без ожидания фонового цикла. Фоновое изменение видно за 1–2 секунды в управляемом окружении с доступным сервером.
- [x] Выбор области, сортировка, скрытые материалы, фокус, прокрутка, выбранная карточка, версии и медиа сохраняют действующее поведение. Поздний ответ старой области не изменяет текущий показ.
- [x] Проверены несколько вкладок, пропущенные изменения, разрыв связи, перезапуск, выключенное Око и остановка. Устаревшие серверные признаки изменений не считаются актуальными после восстановления.
- [x] Существующие владельцы списка, открытого материала, форм и браузерной сессии сохраняются; heartbeat, BroadcastChannel и управление ресурсами не дублируются. Несколько HTTP-чтений не объявляются атомарным снимком.
- [x] Контракт и SDK проходят генерацию/совместимость; Playwright проверяет фактические запросы и видимый результат. Измерено сокращение полного цикла относительно исходных 31 425 SQL на 400 материалах, отдельно от эффекта серверных оптимизаций.

## Проверка и ограничения

Проверять через существующий HTTP interface с временными SQLite/файлами, синтетическими источниками и обработчиком. Браузер — Playwright с проверкой запросов, видимого результата и просмотром скриншотов затронутых состояний. SQL trace конкретного запроса отделять от фоновой работы; планы и работу SQLite измерять отдельно от времени всего сценария. Фиксировать исходные и итоговые бюджеты, рост с размером выбранной области и посторонних данных. Проверять внешнее поведение, не расположение методов и не точную строку EXPLAIN.

Сохранить Runtime как владельца действий/отмены, Store как владельца транзакций/файлов/восстановления, единые правила состава чтения. Сохранить поколения заданий, актуальность результатов, версии, безопасную границу прочитанного Telegram и точный состав подтверждений. Смена параметров будущего выполнения Codex не инвалидирует готовые результаты. Индексы вводить по измерениям, с проверкой цены записи и повторного запуска миграции. Не ослаблять фиксацию, secure_delete или проверки поздних результатов.

Любое изменение HTTP-контракта проходит канонический OpenAPI, генерацию DTO/SDK и действующие проверки совместимости. Не добавлять тестовые endpoints, ORM, универсальный scheduler, глобальный кэш без инвалидации, пагинацию или редизайн. Личные источники, аккаунты, настоящий обработчик и пользовательский экземпляр не затрагивать. Каждая задача проходит свои необходимые проверки и остаётся работоспособной до итоговой приёмки. Результаты, неудачные прогоны и ограничения записать отдельно от требований. Метка ready-for-agent не запускает реализацию.
