# Выбор начальной истории при подключении источника

Status: done
Design: решения 1–17 согласованы пользователем
Testing: HTTP API, браузерные сценарии и узкие проверки сборщиков согласованы вместе с разбиением
Execution: реализация завершена на codex/initial-history; проверки и ревью прошли

## Problem Statement

При подключении источника пользователь не может сразу выбрать, сколько ранее опубликованных материалов получить. Настройка глубины в днях находится уже в настройках фида, хотя первый сбор фиксирует границу истории и последующее изменение настройки не расширяет её. Пользователю нужны последние N публикаций либо история начиная с выбранной даты, предсказуемый прогресс и восстановление загрузки после перезапуска.

## Solution

В формах подключения RSS/Atom, YouTube и Telegram пользователь выбирает один из режимов начальной загрузки истории:

- «Последние N публикаций», по умолчанию 20. N — целое число от 1 без произвольного верхнего лимита.
- «Начиная с даты», включительно с 00:00 выбранного дня в часовом поясе пользователя. Будущие даты не допускаются.

Граница сохраняется вместе с подключением до начала сбора. Набор последних N фиксируется при первом успешном обращении к источнику; новые поступления собираются дополнительно и не расходуют N. История загружается порциями, а сохранённые материалы сразу доступны для чтения.

В настройках фида показаны режим, граница, прогресс, состояние, ошибки и кнопка «Приостановить историю»/«Продолжить историю». Пауза не останавливает сбор новых публикаций. После перезапуска сохраняются набор, прогресс и состояние паузы.

RSS/YouTube собирают доступное окно фида без отдельного обращения к архиву. Если запрошено 100 публикаций, а доступны 15, это явно показано. В режиме даты выводится предупреждение, если полнота истории за период не подтверждена. Telegram-альбом считается одной публикацией и загружается целиком.

Повторное подключение открывает существующий фид без изменения его настроек или истории. OPML сохраняет прежнее поведение. У существующих фидов редактируемая глубина в днях заменяется информацией о начальной загрузке.

## User Stories

1. Как пользователь Око, я хочу выбрать глубину истории при подключении RSS/Atom, чтобы сразу получить нужные ранее опубликованные материалы.
2. Как пользователь Око, я хочу тот же выбор для YouTube, чтобы управлять начальным объёмом видео в чтении.
3. Как пользователь Око, я хочу тот же выбор для Telegram, чтобы не менять настройки после начала сбора.
4. Как пользователь Око, я хочу получить последние N публикаций, чтобы ограничить начальный объём чтения.
5. Как пользователь Око, я хочу получить историю начиная с даты включительно, чтобы охватить интересующий период.
6. Как пользователь Око, я хочу видеть последние 20 выбранными по умолчанию, чтобы подключить источник без дополнительной настройки.
7. Как пользователь Око, я хочу выбрать большое положительное количество, чтобы получить нужную глубину без произвольного лимита.
8. Как пользователь Око, я хочу видеть ошибки количества и даты рядом с полями, чтобы исправить ввод до подключения.
9. Как пользователь Око, я хочу, чтобы выбранный день учитывал мой часовой пояс, чтобы начало периода соответствовало моему ожиданию.
10. Как пользователь Око, я хочу, чтобы выбранная граница не сдвигалась при смене часового пояса, чтобы история оставалась предсказуемой.
11. Как пользователь Око, я хочу, чтобы последние N фиксировались при первом успешном обращении, чтобы последующая порционная загрузка не меняла набор.
12. Как пользователь Око, я хочу получать все новые публикации после подключения, чтобы начальное ограничение не ограничивало дальнейший сбор.
13. Как пользователь Око, я хочу читать уже сохранённые материалы во время загрузки истории, чтобы не ждать её завершения.
14. Как пользователь Око, я хочу видеть количество загруженных исторических публикаций, чтобы понимать прогресс.
15. Как пользователь Око, я хочу видеть прогресс загрузки с даты без выдуманного общего количества, чтобы оценивать фактический результат.
16. Как пользователь Око, я хочу приостановить историю и продолжить позже, чтобы управлять большой загрузкой.
17. Как пользователь Око, я хочу получать новые публикации во время паузы истории, чтобы оставаться в курсе источника.
18. Как пользователь Око, я хочу продолжить прежнюю историю после перезапуска, чтобы не терять прогресс и не получать дубли.
19. Как пользователь Око, я хочу видеть недостаточную глубину RSS/YouTube, чтобы не принимать доступное окно за полный архив.
20. Как пользователь Око, я хочу получать Telegram-альбом целиком как одну публикацию, чтобы количество не разрывало материал.
21. Как пользователь Око, я хочу видеть публикации без даты с явной пометкой, чтобы неизвестная дата не выглядела достоверной.
22. Как пользователь Око, я хочу видеть предупреждение о неоднозначном порядке фида, чтобы понимать точность выбора последних N.
23. Как пользователь Око, я хочу отличать сохранённые, неполные и недоступные материалы, чтобы видеть реальную полноту загрузки.
24. Как пользователь Око, я хочу, чтобы ошибка одного материала не блокировала остальные, чтобы получать доступную историю.
25. Как пользователь Око, я хочу видеть ожидание повторной попытки при временной ошибке, чтобы понимать, почему загрузка не завершена.
26. Как пользователь Око, я хочу видеть окончательно недоступные публикации без подмены другими, чтобы выбранный набор оставался точным.
27. Как пользователь Око, я хочу завершать загрузку независимо от готовности тезисов, чтобы ожидание AI не мешало чтению.
28. Как пользователь Око, я хочу открыть существующий фид при повторном подключении, чтобы не создать дубль и не потерять настройки.
29. Как пользователь Око, я хочу сохранить прежнее поведение OPML, чтобы изменение формы не меняло пакетный импорт.
30. Как пользователь Око, я хочу видеть фактическую начальную границу существующего фида вместо неработающего изменения глубины, чтобы настройки не обещали расширение истории.

## Implementation Decisions

- Используется существующее разделение ответственности: Runtime координирует сбор и внешние ожидания, Store отвечает за сохранение и транзакции, адаптеры — за взаимодействие с источниками.
- Контракты подключения нового фида принимают взаимоисключающий режим количества или даты. Параметры проходят серверную валидацию и сохраняются до запуска первого сбора; интерфейс показывает ошибки рядом с полями.
- Для даты сохраняется однозначная временная граница, рассчитанная с учётом часового пояса пользователя. Текущее значение даты проверяется в том же часовом поясе.
- Для количества сохраняется фиксированный исторический набор либо эквивалентное восстанавливаемое описание набора и границы. Порции, перезапуск и новые поступления не меняют его состав.
- Обнаружение новой истории и сбор новых поступлений согласуются без дублей. Пауза относится к начальной истории, а не ко всему фиду.
- Состояние начальной истории включает выбранный режим, границу, прогресс, паузу и исходы материалов. Повторная доставка уже сохранённой публикации не увеличивает счётчик.
- Число «Загружено» отражает сохранённые материалы по существующим правилам источника. Неполнота содержимого отображается отдельно; обнаруженная ссылка сама по себе не означает успешную загрузку. Готовность тезисов не участвует в завершении истории.
- История завершается, когда выбранные материалы сохранены либо отмечены окончательно недоступными. Временные ошибки сохраняют ожидание повторной попытки с задержкой и не блокируют остальные материалы.
- Окончательная недоступность не приводит к бесконечным повторам или замене публикации следующей за границей N. Конкретная классификация использует семантику ошибок источника; один временный сбой не является доказательством окончательной недоступности.
- RSS/YouTube сохраняют существующую границу возможностей: только доступный XML-фид. Для количества показывается запрошенный и доступный объём; для даты — предупреждение о неподтверждённой полноте периода.
- Отсутствие даты представлено как неизвестная дата, а не достоверное время публикации. Такие записи включаются в режим даты. Для количества используется порядок фида с новыми записями первыми; неоднозначность сопровождается предупреждением.
- Telegram считает целый альбом одной исходной публикацией, в том числе на границах порций и количества.
- Настройки фида показывают состояние и управление начальной историей; подробности исключений поступают в существующую диагностику.
- Повторное подключение сохраняет настройки, границу и прогресс существующего фида. Изменение интерфейса для старых фидов не запускает повторный импорт.
- OPML сохраняет существующие правила. Расширение истории существующего фида не добавляется.
- Точная схема хранения, названия полей API и размеры порций остаются решениями реализации при соблюдении этих контрактов.

## Testing Decisions

Границы проверок подтверждены пользователем вместе с разбиением; они не требуют новых публичных интерфейсов.

- Основная граница — существующий HTTP API читателя с управляемыми ответами источников: подключение, валидация, состояния фида, материалы, пауза/продолжение и восстановление после перезапуска. Тест проверяет наблюдаемое поведение, не внутренний порядок вызовов или структуру таблиц.
- Для поведения интерфейса используется существующая браузерная проверка действий пользователя: переключение режима, ошибки полей, состояние формы, прогресс и управление историей. Одна API-проверка не подтверждает видимость и доступность этих элементов.
- При необходимости узкие проверки адаптеров покрывают особенности, которые нельзя достоверно выразить одним HTTP-сценарием: Telegram-альбомы на границе порции, отсутствующие даты, неоднозначный порядок и ограниченное окно фида. Новые тестовые интерфейсы не вводятся без необходимости.
- Существующие проверки добавления RSS по URL, подключения Telegram, настроек фидов и сборщиков служат образцами. Реальные личные подписки и материалы для тестов не изменяются.
- Обязательные сценарии: последние 20 по умолчанию; допустимые и ошибочные значения; выбранный день и часовой пояс; сохранение границы до первого сбора; новые публикации во время истории; загрузка 7 из 20 с перезапуском; пауза с перезапуском; повторная доставка без дублей; ограниченная история; альбом; публикация без даты; временная ошибка; окончательная недоступность; неполный материал; незавершённая AI-обработка; повторное подключение; неизменность OPML и существующих фидов.

## Out of Scope

- Отдельная загрузка полного архива YouTube вне текущего RSS-окна.
- Расширение истории уже подключённого фида отдельным действием.
- Новые правила начальной загрузки пакетного OPML-импорта.
- Изменение правил отметок чтения, тезисов, обработки содержимого и загрузки медиа.
- Внешняя публикация приложения.

## Further Notes

- Telegram API не предоставляет атомарный снимок истории на один момент времени. Для количества первое успешное получение выбранного набора означает завершение порционного подбора его ID; затем список сохраняется и используется без подмены при загрузке содержимого. Верхняя граница новых сообщений закрепляется отдельно. Публикации, исчезнувшие до получения их ID во время самого подбора, API восстановить не может; эта неопределённость должна быть явно показана.
- Все продуктовые решения 1–17 согласованы в диалоге. Подробные критерии приёмки сохранены в сопровождающем описании проектирования.
- Пример прогресса количества: «Загружено 7 из 20»; пример временной ошибки: «Загружено 19 из 20 · 1 ожидает повторной попытки».
- Пример прогресса даты: «Загружено 37 публикаций с 1 октября»; неизвестное общее количество не отображается.
- Текущая начальная граница фиксируется первым сбором; редактирование прежней глубины в днях после этого не расширяет историю. Новая форма устраняет этот конфликт ожиданий.
- Проект использует локальный Markdown-трекер. Все шесть задач завершены по разрешению пользователя через implement-spec. Итоговая проверка: [отчёт](../../docs/verification/initial-history.md).
