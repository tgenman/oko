# Полный переход на Poetry

Status: done

## Согласовано

2026-10-15. Итоговый план после интервью `grill-with-docs`. Пользователь выбрал полный переход: Poetry вместо uv для зависимостей и окружения, poetry-core вместо setuptools для сборки, один `poetry.lock` вместо `uv.lock`. 2026-10-15 пользователь вызвал implement-spec и разрешил реализацию.

Следующим ответом пользователь подтвердил:

- Python `>=3.11` и текущие версии библиотек сохраняются. Обновление Python — отдельная задача.
- Окружение `.venv` остаётся внутри проекта; установка через `poetry sync`, запуск через `poetry run python -m oko`.
- Установка по lock обязательна для разработки и CI. Пользовательская поставка остаётся обычным wheel; `pip install` не получает гарантию установки транзитивных зависимостей по `poetry.lock`.
- Полный CI остаётся на Ubuntu / Python 3.11. На macOS проверяются установка, сборка и запуск. Расширение матрицы Python и поддержка Windows — отдельные задачи.
- Инструменты тестирования, генерации API и сборки переходят из extra `dev` в группу разработки Poetry, устанавливаемую стандартной командой `poetry sync`. Прежняя команда `pip install -e '.[dev]'` заменяется в действующих инструкциях, совместимость этого extra не сохраняется.

Дополнение от 2026-10-15 при реализации: пользователь разрешил уточнить диапазон до `>=3.11,<3.15`, сохранив версии библиотек. Причина — опубликованное ограничение `youtube-transcript-api==1.2.4` (`>=3.8,<3.15`), из-за которого Poetry не разрешает первоначально заявленный диапазон. Это дополнение уточняет прежнее решение о Python во всех разделах ниже.

## Результат и границы

Разработчик и CI получают зависимости из одного `poetry.lock`; пакет читателя собирается через poetry-core с прежними проверками и составом поставки. В итоговой конфигурации uv и setuptools больше не управляют проектом. Setuptools может остаться транзитивной зависимостью стороннего инструмента, если это требуется его metadata.

Поведение читателя, OpenAPI-контракт, версии прямых runtime-зависимостей, сборка React/Vite и пользовательский запуск установленного wheel сохраняются. План не включает обновление Python, публикацию пакета, перезапуск личного экземпляра или изменение личного хранилища.

## Исходное состояние

- `pyproject.toml`: metadata PEP 621, Python `>=3.11`, точные версии прямых зависимостей, extra `dev`, backend `setuptools.build_meta`.
- `README.md`: разработка через `uv sync --extra dev` / `uv run`; в репозитории есть `uv.lock`.
- `.github/workflows/check.yml`: Ubuntu, Python 3.11, установка через `pip install -e '.[dev]'`, без использования lock-файла.
- `scripts/build-package.py`: проверяет генерацию API и готовую сборку фронтенда, создаёт временное дерево, упаковывает только текущую законченную generation, вызывает setuptools напрямую.
- В wheel входят frontend assets, Swagger и generated API DTO/JSON/YAML. Установленный читатель работает без Node и исходников checkout.
- `scripts/check`, `scripts/generate-api.mjs`, `scripts/launch.applescript` используют локальную `.venv`; первые два поддерживают `OKO_PYTHON`.
- `scripts/check-api-staged.py` учитывает `uv.lock` и читает версии генераторов из extra `dev`.
- Проверки установленного wheel выполняются вне checkout с пустым PATH, но используют доступные зависимости текущего Python-окружения. Они не доказывают чистую установку зависимостей из lock.
- Существующая инфраструктура проверок рассчитана на POSIX; Windows не входит в доказанную совместимость.

## План реализации

### 1. Зафиксировать исходные зависимости и состав поставки

Сохранить для сравнения прямые pins, варианты транзитивных зависимостей из `uv.lock` и состав wheel. Различать изменение версий зависимостей и добавление самого инструментария Poetry. Сохранить metadata PEP 621 и формат пользовательского запуска `python -m oko`.

### 2. Перевести конфигурацию и окружение

Закрепить совместимые стабильные версии Poetry и poetry-core, одинаковые локально и в CI. Точные номера выбираются и фиксируются при реализации после проверки совместимости с Python 3.11; плавающая установка latest в инструкциях и CI исключается. Сам CLI Poetry устанавливается отдельно от окружения приложения. Poetry-core закрепляется в build-system и доступен в dev-окружении для упаковщика.

Использовать проектную настройку `virtualenvs.in-project = true` в `poetry.toml`. Заменить backend на poetry-core, явно описать Python-пакет и включение generated DTO/контрактов, Swagger и frontend assets в wheel. Перенести extra `dev` в не optional группу разработки Poetry; удалить прямые dev-зависимости setuptools/wheel, если они больше не нужны инструментам. Пакеты runtime остаются в `[project.dependencies]`, dev-группа не попадает в Requires-Dist приложения.

Создать и проверить `poetry.lock`, сохраняя точные прямые версии. Сопоставить транзитивные версии с `uv.lock` по Python/platform markers: любое необходимое расхождение показать отдельно с причиной, а не маскировать под смену инструмента. Удалять `uv.lock` только после успешной проверки нового lock. В CI использовать установку из принятого lock, без его пересоздания.

Если разрешение зависимостей потребует изменения прямого pin или сужения диапазона Python, зафиксировать конкретный конфликт как отклонение от согласованного плана и согласовать его отдельно.

Первую проверку установки выполнять в новой временной копии и свежей `.venv`, не синхронизировать действующее окружение пользователя автоматически. Для перехода существующего checkout описать создание нового окружения и возврат к прежнему.

### 3. Сохранить проверяемую процедуру упаковки

Сохранить `scripts/build-package.py` как единую процедуру подготовки поставки. Проверки генерации API, свежести и целостности assets выполняются перед упаковкой. Сохраняются временное дерево и включение только текущей законченной frontend generation. Сменить вызов setuptools на poetry-core из окружения с закреплённым инструментарием; учитывать все файлы, на которые ссылаются metadata.

Целевые команды после установки закреплённого Poetry и выбора Python:

```sh
poetry sync
poetry run python -m oko
npm ci
npm run build
poetry run python scripts/build-package.py --output /tmp/oko-wheels
poetry run ./scripts/check all
```

В документации командой выпуска остаётся процедура с проверками и временным деревом. Прямой `poetry build` не объявляется эквивалентной командой выпуска без тех же гарантий.

### 4. Перевести CI и инструменты разработки

В CI заменить установку через pip на закреплённый Poetry и установку по lock в `.venv`. При кэшировании учитывать Python, платформу и `poetry.lock`. Сохранить независимую установку npm-зависимостей и Playwright.

Перед установкой проверять наличие и согласованность lock через команду проверки закреплённой версии Poetry. Зафиксировать Python 3.11 в Ubuntu job, явно использовать Python из созданной `.venv` при выполнении runner и генерации API. CI завершается ошибкой при отсутствующем или рассогласованном lock; solver в CI не обновляет зависимости.

В `scripts/check-api-staged.py` заменить вход `uv.lock` на `poetry.lock`, адаптировать извлечение закреплённых версий генераторов под выбранную организацию dev-зависимостей. Сохранить проверку именно staged-содержимого и существующие возможности `OKO_PYTHON`.

Проверить совместимость runner, API generation и macOS launcher с `.venv`. Обновить README, инструкции окружения и упаковки; исторические отчёты сохраняют прежние команды как свидетельства своих версий.

### 5. Приёмка

- Проверка согласованности pyproject/lock закреплённым Poetry; чистая установка dev-окружения по lock без изменения файлов проекта.
- Сравнение зависимостей: прежние прямые pins сохранены, каждое расхождение транзитивных версий объяснено.
- Проверка staged API generation с новым lock и организацией dev-зависимостей.
- Сборка настоящего wheel: внутри только Python-пакет и требуемые assets/контракты, текущая frontend generation; dev-инструментарий не становится runtime dependency.
- Устаревшая/неполная frontend-сборка и рассинхрон generated API по-прежнему останавливают упаковку.
- Существующие HTTP/browser-проверки установленного wheel вне checkout, без Node и с пустым PATH; разрешение runtime-зависимостей обычным pip остаётся вне гарантии lock.
- Полный `./scripts/check all` в чистом подготовленном checkout; проверка macOS launcher по согласованной платформенной границе.

На macOS выполнить чистую установку по lock, сборку wheel и запуск установленного приложения с синтетическими источниками и временным хранилищем. Проверить совместимость launcher с путём `.venv`, не запускать через него личное хранилище; если полноценный запуск launcher нельзя направить на временные данные, отдельно записать это ограничение. В отчёте указать фактическую версию Python и архитектуру Mac. Проверка Ubuntu/Python 3.11 и macOS не объявляется доказательством совместимости со всеми версиями, допускаемыми `>=3.11`.

При изменении упаковщика и staged-проверок добавить регрессии в существующие наборы `tests/api/test_installed_package.py` и `tests/development/test_api_generation.py` либо соседние тесты соответствующей поддержки. После целевых проверок выполнить полный набор, пройти независимое ревью соответствия этому плану и правил проекта.

Проверки используют временные хранилища и синтетические источники. Результаты, ограничения и фактические команды фиксируются отдельным отчётом при реализации.

### 6. Переход и откат

Завершить переход согласованным набором конфигурации, lock, упаковки, CI и документации, чтобы не оставлять две действующие инструкции установки. До этого работающий checkout и его `.venv` остаются пригодны для запуска. При неуспешной приёмке сохранить прежний вариант; после принятия откат включает возврат конфигурации/lock/инструментов и пересоздание окружения по прежней инструкции.

Критерий завершения реализации: один действующий Python lock, установка по нему в разработке и CI, подтверждённая поставка wheel, обновлённые команды и отдельный фактический отчёт. Наличие этого плана со статусом `ready-for-agent` означает готовность описания, а не начало реализации.
