# Явное разделение фронтенда и бэкенда

Status: done

2026-10-13. Пользователь согласовал спецификацию и шесть тикетов: один репозиторий, один запуск Око, явное разделение фронтенда и бэкенда. Изначально разрешалось только проектирование; затем пользователь отдельно поручил полную реализацию через implement-spec. Реализация завершена, фактические проверки и ревью: [отчёт](../../docs/verification/frontend-backend-separation.md).

## Результат

Браузерный код находится в самостоятельном каталоге `frontend/`, серверный — в Python-пакете `oko/`. Они взаимодействуют через существующий HTTP interface читателя с явными контрактами данных. Один запуск `python -m oko` обслуживает и читатель, и его данные на одном origin; существующие параметры и способы запуска сохраняются.

Добавление браузерного module не требует регистрации его имени в Python. Общие правила запросов сосредоточены в одном module транспорта. Изменение формы основных ответов проверяется автоматически на настоящих ответах сервера и на снимках, используемых браузерными сценариями.

## Исходное состояние

Изученная база: `6783dc9`. Перед реализацией сверить её с текущим checkout.

- `oko/web/` содержит HTML, CSS и браузерные ES modules. `oko/reader/app.py` отдельно регистрирует выдачу каждого JS-файла.
- `oko/web/app.js` одновременно собирает UI и реализует JSON-запросы с авторизацией и обработкой ошибок. Медиа, закрытие вкладки и `debug.js` имеют отдельные вызовы `fetch`.
- Основные ответы читателя, включая карточки, навигацию, открытый материал и статус, описаны на HTTP-уровне как словари с `Any`. Структуру знают серверная implementation, браузер и тестовые снимки.
- Сервер проверяет локальный host, совпадение origin и Bearer-токен для `/api/`; выдаёт защитные заголовки. Эти правила относятся и к новой организации файлов.
- Браузерные сценарии уже работают через настоящий сервер; часть управляет снимками HTTP-ответов и задержками. Сквозной сценарий использует настоящие данные читателя с синтетическими внешними adapters.
- `scripts/check` и `scripts/lint-js.cjs` содержат пути `oko/web`; перенос требует обновления обнаружения файлов проверками.

## Владение

| Фронтенд | Бэкенд |
| --- | --- |
| DOM, фокус, навигация, меню, черновики, локальные предпочтения | Сбор, обработка, хранение, состав чтения и эффективные настройки |
| Отправка действий, показ данных и прогресса | Исполнение действий, отмена, внешние ожидания и восстановление |
| Допуск позднего ответа к текущему экрану | Допуск результата работы к сохранению |
| Время жизни показа, воспроизведения и blob URL | Доступ к локальным файлам и версиям материала |

Runtime сохраняет владение выполнением; Store — фиксацией и восстановлением. Фронтенд не воспроизводит серверные правила membership, группировки, актуальности обработки или завершения папки. Бэкенд не хранит состояние фокуса, открытого меню или несохранённого черновика.

Сохраняются решения [управления работой](../../docs/architecture/reader-work.md), [открытого материала](../../docs/architecture/opened-material.md), [UI-состояния](../../docs/architecture/ui-settings.md), [состава чтения](../../docs/architecture/reading-composition.md) и [согласования обработки](../../docs/architecture/processing-coordination.md). Термины продукта заданы в [GLOSSARY.md](../../GLOSSARY.md).

## Организация кода и запуска

```text
frontend/
  index.html
  app.js
  transport.js
  style.css
  ... существующие браузерные modules
oko/
  __main__.py
  reader/
    app.py
    contracts.py
    runtime.py
  ... существующие серверные пакеты
tests/
  browser/
  reader/
  ... существующие сценарные наборы
```

- Перенести браузерные файлы из `oko/web` без копий и реэкспортов. Существующие URL страницы, скриптов, CSS и `/api/` сохраняются. Путь к `frontend` разрешается относительно установки/checkout, а не текущего рабочего каталога процесса.
- Сервер выдаёт статические файлы из одного выделенного каталога. Новые JS-файлы и вложенные ES imports доступны без изменения Python. Выдача статики не перехватывает `/api/`, не превращает неизвестный HTTP-маршрут в HTML и не открывает файлы за пределами каталога, в том числе через обход пути или symlink.
- Размещение файлов в одном репозитории и доставка вместе с бэкендом сохраняются. Отдельный frontend server, порт, процесс, обязательный сборщик или Node при пользовательском запуске не появляются. Node остаётся инструментом разработки и проверок.
- Корневые `package.json`, lock-файл и команды проверок сохраняются; их пути обновляются. Проверки должны находить и вложенные JS modules.
- Существующие тестовые каталоги сохраняются. Новая организация production-кода не требует переноса сценариев ради симметрии папок.

## Module транспорта

`frontend/transport.js` скрывает правила авторизации, JSON-кодирования/декодирования, загрузки медиа, преобразования HTTP-ошибок и получения диагностических заголовков. Он принимает зависимости при создании; реальный fetch adapter и управляемый транспорт браузерных тестов используют один interface.

Interface выражает необходимые операции JSON-запроса, получения медиа и отправки при закрытии вкладки. Точные имена выбираются при реализации. Не создавать отдельную обёртку для каждого серверного маршрута или второй набор продуктовых действий поверх HTTP.

Обязательные свойства:

- Общая авторизация для данных, медиа, диагностики и закрытия вкладки. Токен не передаётся на посторонний origin; существующие URL медиа и версий сохраняются.
- Сохраняются методы, тела запросов, `AbortSignal`, `keepalive` закрытия вкладки и требуемое поведение кэширования.
- HTTP-ошибки сохраняют detail, диагностический идентификатор и существующее различение ожидаемых ошибок. Ошибка сети или не-JSON ответ дают обрабатываемую ошибку, а не успешный результат.
- Транспорт не владеет DOM, выбором карточки, поколениями UI или отменой серверной работы. Отмена браузерного ожидания не означает откат успешной записи.
- Поздние ответы по-прежнему проходят допуск у владельца UI-состояния. Транспорт не добавляет автоматических повторов мутаций, скрытого polling или общего отменяемого контекста для всех экранов.
- Доставка диагностической ошибки сама не порождает рекурсивную доставку той же ошибки. Очередь, повторная доставка и дедупликация диагностики сохраняют существующее владение; транспорт предоставляет только правила передачи.

Depth этого module определяется тем, что callers больше не повторяют правила передачи и ошибок. Deletion test: его удаление снова распределит эти правила между чтением, настройками, медиа и диагностикой. Перенос папки отдельно улучшает locality, но не увеличивает depth.

## Явный HTTP interface

Первый объём контрактов ограничен ответами:

1. `GET /api/navigation` — папки, фиды и счётчики.
2. `GET /api/cards` — все существующие виды карточек и состояния их данных.
3. `GET /api/materials/{item}` и `GET /api/materials/{item}/versions/{number}` — открытый материал, исходники, версии и ссылки на медиа.
4. `GET /api/status` — состояние работы, источников, диагностики и доступные действия восстановления.

Схемы этих ответов принадлежат `oko/reader/contracts.py`. Это описание передаваемых данных; внутреннее устройство Store и Runtime не становится частью interface. Использовать текущие средства описания моделей проекта; новый framework не нужен.

Из одного серверного описания получать машинно проверяемую схему для проверки браузерных снимков. Не поддерживать независимо написанные Python- и JavaScript-схемы одинаковых данных. Экспорт схемы выполняется локально для проверок и не требует открытия публичного OpenAPI-маршрута или запуска личных источников.

Контракт фиксирует существующие поля, типы, варианты, обязательность, различие отсутствующего поля и `null`, значения состояний и форму ссылок. Новая сериализация не удаляет существующие поля и не добавляет defaults, меняющие смысл ответа. Сначала инвентаризировать фактические варианты по implementation и сценариям; нельзя описать только успешный ответ одиночной публикации.

Общие правила interface также включают авторизацию, HTTP-коды, диагностические заголовки, ограничения отмены и временной порядок: успешная запись остаётся состоявшейся после закрытия формы, а несколько читающих запросов не обещают один транзакционный снимок. Не добавлять несуществующих гарантий согласованности.

Остальные маршруты настроек и действий сохраняют текущие контракты. Полная типизация всех HTTP-ответов и миграция фронтенда на TypeScript не входят в этот объём.

## Сохраняемое поведение и ограничения

- Один репозиторий, существующая команда запуска и один origin. Локальная сессия, host/origin-проверки, CSP и прочие защитные заголовки сохраняются.
- UI, действия пользователя, форматы SQLite/Markdown, фоновые процессы, heartbeat и завершение работы по вкладкам сохраняются.
- Не менять алгоритмы обработки, права доступа к AI, пользовательские подключения и подписки.
- Не вводить отдельный deploy фронтенда, CORS, новый frontend framework, универсальный клиент с методом на каждый маршрут или дополнительные modules только для проксирования вызовов.
- Действующие документы обновить после реализации; исторические отчёты остаются результатами своих версий. План уточняет перенос `web` относительно прежнего решения [о структуре пакетов](../../docs/architecture/package-layout.md), остальные решения этого документа сохраняются.

## Критерии приёмки

1. Один существующий запуск открывает рабочий читатель без отдельного frontend-процесса или сборки. Запуск из другого рабочего каталога сохраняет выдачу файлов.
2. Весь браузерный production-код находится в `frontend/`; добавление вложенного JS module не требует регистрации маршрута в Python. Настоящий сервер выдаёт весь импортируемый граф с корректными MIME-типами.
3. `/api/` сохраняет авторизацию и ошибки; неизвестные маршруты возвращают прежний класс ответа. Статика не раскрывает файлы вне `frontend`, включая проверяемые попытки обхода пути и symlink.
4. Callers используют единый транспорт; авторизация, ошибки, диагностические заголовки, медиа и закрытие вкладки проходят соответствующие сценарии. Сбой диагностики не создаёт бесконечного потока запросов.
5. Настоящие HTTP-ответы и снимки браузерных тестов соответствуют одним схемам основных контрактов. Заведомо неверный тип или пропущенное обязательное поле обнаруживаются проверкой. Проверены все существующие варианты карточек и неполных/ошибочных состояний.
6. В настоящем браузере сохраняются чтение, настройки и черновики, переходы между карточками и областями, медиа и версии. Поздний ответ не меняет новый экран; успешная запись после закрытия формы не теряется; остановка и просмотр сохраняют очистку.
7. Сквозной сценарий без подмены browser fetch подтверждает совместную работу фронтенда и бэкенда. Серверные сценарии сохраняют правила состава чтения, выполнения и восстановления.
8. `./scripts/check all` включает обновлённое обнаружение файлов и проверку контрактов и проходит с временными хранилищами и синтетическими источниками/моделями. Проверки не используют личные подписки, Telegram-аккаунт или настоящий обработчик.
