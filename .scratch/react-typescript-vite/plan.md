# План перехода на React + TypeScript + Vite

Status: claimed
Date: 2026-10-14

Основание: [спецификация](spec.md) и [API-first](api-contract.md). Разрешена подготовка документов; начало реализации требует отдельного задания пользователя. Все строки ниже — будущая работа. После добавления OpenAPI прежние этапы 01–08 перенумерованы в 03–10; первыми идут контракт и generated-библиотеки.

## Порядок

Один исполнитель ведёт последовательный перенос в одном checkout. Этап завершается работающим браузерным приложением, удалением заменённого кода и отчётом затронутых проверок. Проверки и независимое ревью выбираются по [порядку разработки](../../docs/agents/development.md); этапы не означают автоматические коммиты или публикации.

Последовательность выбрана по зависимости: OpenAPI регламентирует generated-модели и клиент; до React-переноса обе стороны используют этот контракт. Первый React-контейнер показывает работу с живыми снимками, одно поле — работу с черновиками; медиа переносится после стабилизации этих механизмов. Это не оценка длительности: её можно уточнить после первых этапов. Полноту схем не откладывать до переноса соответствующего экрана.

## Условия перед началом

1. Перечитать текущий AGENTS.md, спецификацию, затронутую архитектуру и текущий checkout; проверить связанные изменения оформления и тестов. Прежние dirty-изменения не относятся автоматически к этой задаче.
2. Сохранить baseline по `scripts/task_changes.py`. Зафиксировать текущие результаты релевантных проверок, известные ошибки и визуальные состояния на синтетических данных.
3. Обозначить в отчёте этапа владельцев DOM и состояния, которые переносятся. До удаления старого владельца проверить, кто ещё вызывает его interface.
4. Описать новые build/typecheck команды как действующие только после их реализации. Во время тестов не менять source checkout параллельно: guard рассматривает это как загрязнение.

## Общая граница проверки

- OpenAPI lint, codegen обеих библиотек, route/HTTP drift и проверка совместимости контракта предшествуют приёмке потребителей. Схема Swagger совпадает с источником SDK/DTO.
- Все UI-сценарии проверяются по настоящей production-сборке, выдаваемой Python. UI snapshots могут подменять ответы транспорта по существующим правилам; интегрированный reader HTTP остаётся отдельным набором без подмены browser fetch.
- Для поздних ответов использовать управляемый транспорт, который может игнорировать abort. Проход только happy path не подтверждает сохранение жизненного цикла.
- Для локального этапа запускать затронутые наборы; для общего UI и финального перехода — подходящий расширенный набор. Не повторять полный прогон без новых изменений/нерешённых сомнений.
- Новая проверка типов охватывает весь TS-проект, даже если выбран один browser-файл. Отказ типов/сборки должен завершаться явной ошибкой до тяжёлых проверок.
- Build outputs и временные exports пишутся в игнорируемые/временные каталоги. Генерация проверок не обновляет сохранённые исходники или lock-файл.

## Контроль объёма

Приёмка каждой строки не может быть заменена «страница открылась». Сценарии в тикетах — обязательные свойства, уже покрытые проверки не дублируются. При обнаружении нового продуктового решения его отделяют от переноса и явно описывают; изменение требований не маскируют исправлением типов.

Удаление старого кода входит в каждый этап. После этапа 10 не остаются параллельные JS/TS реализации, ручные дубликаты wire-схем, adapters для удалённых владельцев, старые entry points и тесты исходной структуры файлов. Исследовательские прототипы и исторические отчёты сохраняются вне product build.

## Структура проекта

Целевая структура — ориентир по владельцам; имена небольших внутренних файлов выбираются при реализации:

```text
api/
  openapi.yaml            # редактируемый источник всего HTTP-контракта
  codegen/                # закреплённая конфигурация генераторов
frontend/
  index.html
  vite.config.ts
  tsconfig.json
  src/
    main.tsx
    app/                  # сборка UI, выбор области, согласование чтения
    api/
      generated/          # SDK и типы из OpenAPI
      transport.ts        # настройка клиента, авторизация и ошибки
    reading/              # дерево, список, открытый материал, действия папки
    settings/             # редактор, черновики и навигация
    connections/          # RSS, Telegram, OPML, модели, YouTube, история
    status/               # панель, локальные исходы команд, диагностика
    shared/               # реально общие элементы и UI operations
    styles/               # существующее оформление
  legacy/                 # временно, до завершения переноса
  dist/                   # результат сборки, не исходник
package.json              # единые npm scripts и зависимости разработки
package-lock.json         # один lock-файл
oko/reader/
  generated/              # Python wire-модели из OpenAPI
  ...                     # handlers, Runtime, выдача сборки/документации
tests/browser/            # прежние сценарии и их поддержка
tests/reader/             # прежний HTTP interface
```

Сохраняется один репозиторий и корневой npm-проект. Отдельный workspace, второй lock-файл и перенос тестов ради симметрии production-папок не нужны. Генераторы закрепляются в этапе 02; React, React DOM, TypeScript, Vite, React plugin и ESLint — совместимым набором в этапе 03. Node engines проверяется по выбранным версиям, а не берётся автоматически из старого package.json.

TypeScript работает в strict-режиме. Новые production-файлы пишутся на `.ts`/`.tsx`; временный JavaScript разрешён только для ещё не перенесённого legacy-кода. При завершении этот допуск удаляется. При ручном декодировании внешний JSON имеет тип `unknown` до проверки; generated TS-типы не выдают за runtime-валидацию. Систематические `any`, двойные приведения и `@ts-ignore` не являются способом завершить перенос.

UI использует React state/reducers/context по месту владения. Transport, ошибки и правила актуальности операций не требуют React. Не создавать собственный универсальный store ради независимости от фреймворка. Router, query cache, библиотека форм, UI-kit и React Compiler не входят в стартовый набор: существующие сценарии не требуют их добавления.

## Сборка, запуск и разработка

1. Исходники собираются из `frontend/` в `frontend/dist/`. Корневые scripts предоставляют `frontend:typecheck`, `frontend:build` и `frontend:watch`; точные команды фиксируются в этапе 03. Проверка типов выполняется отдельно от Vite build. Обе сборки используют библиотеки из OpenAPI по [правилам API-first](api-contract.md).
2. `dist` исключён из Git; сборка воспроизводится из исходников и lock-файла. В выдаваемую сборку входят только production entry и его ресурсы. Прототипы, данные, `.scratch`, конфигурация и исходные карты не публикуются как часть читателя по умолчанию.
3. `python -m oko` сохраняет текущие параметры и отдаёт готовые файлы без запуска npm, установки зависимостей или обращения к сети. В source checkout перед запуском нужен явный build. Если сборка отсутствует или устарела, запуск сообщает причину и команду подготовки до старта Runtime; незаметного возврата к старому JS нет.
4. Сборка содержит отпечаток влияющих входов: production-исходников/ресурсов, конфигурации сборки, OpenAPI/генерируемых библиотек и lock-файлов. В source checkout проверка свежести использует эти входы и не зависит только от времени файлов. Автосохранение редактора само по себе не является новой версией сборки.
5. При подготовке Python-дистрибутива те же готовые assets включаются как package resources, например под `oko/reader/web/`. Это результат упаковки, а не вторая поддерживаемая копия frontend. Установленный пакет работает без исходного checkout и Node; источник assets выбирается явно для установки или checkout, независимо от cwd. Подготовка пакета отклоняет отсутствующую/устаревшую сборку.
6. Для первого режима разработки использовать Vite build в watch-режиме и существующий Python origin; после успешной пересборки страницу обновляют. React state сохранять между перезагрузками не обещается. Неполная/неуспешная сборка не объявляется готовой; связанные assets публикуются согласованно. Оптимизация через HMR не является критерием завершения этой миграции.
7. Существующие host/origin-проверки, bearer session, CSP и защитные заголовки сохраняются. Статика отдаёт только каталог сборки с корректными MIME и защитой от выхода через пути/symlink. Неизвестные `/api/` и assets не превращаются в HTML. Хэшированные имена JS/CSS могут заменить прежние внутренние URL; маршруты API, медиа и пользовательские ссылки сохраняются.

Выбор watch build позволяет проверять тот же тип файлов и тот же origin, что у обычного запуска. Подключение dev-server на другом origin потребовало бы отдельного решения для авторизации, CSP и proxy; обход этих проверок не входит в план. Основание возможностей сборки: [Vite build](https://vite.dev/guide/build), [backend integration](https://vite.dev/guide/backend-integration).
