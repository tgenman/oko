Status: ready-for-agent

Основание: [спецификация](spec.md). Разрешена подготовка документов; начало реализации требует отдельного задания пользователя. Все строки ниже — будущая работа, а не выполненные изменения.

## Порядок

Один исполнитель ведёт последовательный перенос в одном checkout. Этап завершается работающим браузерным приложением, удалением заменённого кода и отчётом затронутых проверок. Проверки и независимое ревью выбираются по [порядку разработки](../../docs/agents/development.md); этапы не означают автоматические коммиты или публикации.

Это не оценка длительности: её можно уточнить после этапов 01–04.

## Условия перед началом

1. Перечитать текущий AGENTS.md, спецификацию, затронутую архитектуру и текущий checkout; проверить связанные изменения оформления и тестов. Прежние dirty-изменения не относятся автоматически к этой задаче.
2. Сохранить baseline по `scripts/task_changes.py`. Зафиксировать текущие результаты релевантных проверок, известные ошибки и визуальные состояния на синтетических данных.
3. Обозначить в отчёте этапа владельцев DOM и состояния, которые переносятся. До удаления старого владельца проверить, кто ещё вызывает его interface.
4. Описать новые build/typecheck команды как действующие только после их реализации. Во время тестов не менять source checkout параллельно: guard рассматривает это как загрязнение.

## Общая граница проверки

- Все UI-сценарии проверяются по настоящей production-сборке, выдаваемой Python. UI snapshots могут подменять ответы транспорта по существующим правилам; интегрированный reader HTTP остаётся отдельным набором без подмены browser fetch.
- Для поздних ответов использовать управляемый транспорт, который может игнорировать abort. Проход только happy path не подтверждает сохранение жизненного цикла.
- Для локального этапа запускать затронутые наборы; для общего UI и финального перехода — подходящий расширенный набор. Не повторять полный прогон без новых изменений/нерешённых сомнений.
- Новая проверка типов охватывает весь TS-проект, даже если выбран один browser-файл. Отказ типов/сборки должен завершаться явной ошибкой до тяжёлых проверок.
- Build outputs и временные exports пишутся в игнорируемые/временные каталоги. Генерация проверок не обновляет сохранённые исходники или lock-файл.

## Контроль объёма

Приёмка каждой строки не может быть заменена «страница открылась». Сценарии в тикетах — обязательные свойства, уже покрытые проверки не дублируются. При обнаружении нового продуктового решения его отделяют от переноса и явно описывают; изменение требований не маскируют исправлением типов.

Удаление старого кода входит в каждый этап. После этапа 08 не остаются параллельные JS/TS реализации, adapters для удалённых владельцев, старые entry points и тесты исходной структуры файлов. Исследовательские прототипы и исторические отчёты сохраняются вне product build.
