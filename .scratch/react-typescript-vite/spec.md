# Переход браузерного фронтенда на React + TypeScript + Vite

Status: ready-for-agent
Date: 2026-10-14

Пользователь выбрал React + TypeScript + Vite и поручил подготовить план без реализации. Настоящая спецификация описывает только браузерное приложение с Python-бэкендом. Готовность описания не разрешает начинать реализацию.

## Результат

Весь production-интерфейс читателя описан React-компонентами на TypeScript. Vite собирает HTML, JavaScript, CSS и локальные ресурсы; Python отдаёт готовую сборку и существующий HTTP API на одном origin. Поведение, содержание, оформление и обычная команда запуска Око сохраняются. Ручной код согласования DOM удалён по мере замены, а правила черновиков, поздних ответов и медиаресурсов остаются явно выраженными.

Исследование вариантов: [frontend-framework.md](../../docs/research/frontend-framework.md). Его сравнительная рекомендация — исторический материал; выбранный стек определён этой спецификацией. Последовательность и зависимости: [план](plan.md). Фактически выполненная проверка документов: [verification.md](verification.md).

## Структура проекта

Целевая структура — ориентир по владельцам; имена небольших внутренних файлов выбираются при реализации:

```text
frontend/
  index.html
  vite.config.ts
  tsconfig.json
  src/
    main.tsx
    app/                  # сборка UI, выбор области, согласование чтения
    api/                  # transport, типы wire interface и ошибок
    reading/              # дерево, список, открытый материал, действия папки
    settings/             # редактор, черновики и навигация
    connections/          # RSS, Telegram, OPML, модели, YouTube, история
    status/               # панель, локальные исходы команд, диагностика
    shared/               # реально общие элементы и UI operations
    styles/               # существующее оформление
  legacy/                 # временно, до завершения переноса
  dist/                   # результат сборки, не исходник
package.json              # единые npm scripts и зависимости разработки
package-lock.json         # один lock-файл
oko/reader/               # HTTP, Runtime и доставка сборки
tests/browser/            # прежние сценарии и их поддержка
tests/reader/             # прежний HTTP interface
```

Сохраняется один репозиторий и корневой npm-проект. Отдельный workspace, второй lock-файл и перенос тестов ради симметрии production-папок не нужны. Версии React, React DOM, TypeScript, Vite, React plugin и инструментов ESLint закрепляются совместимым набором в первом этапе; Node engines проверяется по выбранным версиям, а не берётся автоматически из старого package.json.

TypeScript работает в strict-режиме. Новые production-файлы пишутся на `.ts`/`.tsx`; временный JavaScript разрешён только для ещё не перенесённого legacy-кода. При завершении этот допуск удаляется. JSON на входе имеет тип `unknown` до проверки; систематические `any`, двойные приведения и `@ts-ignore` не являются способом завершить перенос.

UI использует React state/reducers/context по месту владения. Transport, ошибки и правила актуальности операций не требуют React. Не создавать собственный универсальный store ради независимости от фреймворка. Router, query cache, библиотека форм, UI-kit и React Compiler не входят в стартовый набор: существующие сценарии не требуют их добавления.

## Сборка, запуск и разработка

1. Исходники собираются из `frontend/` в `frontend/dist/`. Корневые scripts предоставляют `frontend:typecheck`, `frontend:build` и `frontend:watch`; точные команды фиксируются в этапе 01. Проверка типов выполняется отдельно от Vite build.
2. `dist` исключён из Git; сборка воспроизводится из исходников и lock-файла. В выдаваемую сборку входят только production entry и его ресурсы. Прототипы, данные, `.scratch`, конфигурация и исходные карты не публикуются как часть читателя по умолчанию.
3. `python -m oko` сохраняет текущие параметры и отдаёт готовые файлы без запуска npm, установки зависимостей или обращения к сети. В source checkout перед запуском нужен явный build. Если сборка отсутствует или устарела, запуск сообщает причину и команду подготовки до старта Runtime; незаметного возврата к старому JS нет.
4. Сборка содержит отпечаток влияющих входов: production-исходников/ресурсов, конфигурации сборки, схем/генерируемых типов и lock-файла. В source checkout проверка свежести использует эти входы и не зависит только от времени файлов. Автосохранение редактора само по себе не является новой версией сборки.
5. При подготовке Python-дистрибутива те же готовые assets включаются как package resources, например под `oko/reader/web/`. Это результат упаковки, а не вторая поддерживаемая копия frontend. Установленный пакет работает без исходного checkout и Node; источник assets выбирается явно для установки или checkout, независимо от cwd. Подготовка пакета отклоняет отсутствующую/устаревшую сборку.
6. Для первого режима разработки использовать Vite build в watch-режиме и существующий Python origin; после успешной пересборки страницу обновляют. React state сохранять между перезагрузками не обещается. Неполная/неуспешная сборка не объявляется готовой; связанные assets публикуются согласованно. Оптимизация через HMR не является критерием завершения этой миграции.
7. Существующие host/origin-проверки, bearer session, CSP и защитные заголовки сохраняются. Статика отдаёт только каталог сборки с корректными MIME и защитой от выхода через пути/symlink. Неизвестные `/api/` и assets не превращаются в HTML. Хэшированные имена JS/CSS могут заменить прежние внутренние URL; маршруты API, медиа и пользовательские ссылки сохраняются.

Выбор watch build позволяет проверять тот же тип файлов и тот же origin, что у обычного запуска. Подключение dev-server на другом origin потребовало бы отдельного решения для авторизации, CSP и proxy; обход этих проверок не входит в план. Основание возможностей сборки: [Vite build](https://vite.dev/guide/build), [backend integration](https://vite.dev/guide/backend-integration).

## HTTP interface и типы

Сервер уже экспортирует JSON Schema из `oko/reader/contracts.py` для navigation, cards, material, version и status. Из этого же источника получать TypeScript-типы воспроизводимым генератором. Проверка drift сравнивает сгенерированный результат с сохранённым контрактом, не переписывая отслеживаемые файлы во время тестов. Формы и команды текущим экспортом покрыты не полностью: их контракты описываются в соответствующем этапе до перевода потребителя на TS.

Описания запросов переиспользуют существующие серверные модели; ответы дополняются wire types без изменения значений, optional/null и полей. Не экспортировать внутренние типы Store/Runtime. Для каждого перенесённого сценария должны быть известны запрос, успешный ответ, ожидаемая ошибка и диагностические заголовки. Преобразование ответа к TS-типу само по себе не проверяет JSON: сохраняются настоящая серверная проверка wire responses и проверка браузерных snapshots; для ещё не проверяемой сервером формы нужна явная проверка на границе.

Transport принимает fetch adapter, token и origin. Сохраняются Authorization только для своего origin, методы/тела, signal, no-store, медиавыдача и keepalive при закрытии. Ошибки сохраняют detail, ожидаемость, подтверждённость, action ID и diagnostic ID. Transport не делает автоматических повторов команд и не владеет актуальностью экрана.

## Владельцы состояния в React

| Состояние | Владелец | Срок жизни |
| --- | --- | --- |
| Текущая область, сортировка, фильтр скрытых, согласование ответа | Сборка читателя и владелец списка | Сессия вкладки; локальные предпочтения сохраняются как сейчас |
| Открытый материал, версии, медиа | Владелец открытого материала | Конкретный показ; смена карточки его завершает |
| Активное меню, стек страниц, opener, контекст показа | Владелец меню/навигации | Открытие меню и переходы страниц |
| Черновики полей и подключений | Соответствующий редактор, выше размонтируемого поля | Переживают существующие переходы и закрытие меню |
| Выполняющаяся запись, отправленные значения и сверка исхода | Владелец действия/редактора | До обработки исхода, даже после ухода с экрана |
| Раскрытие и положение карточек проблем | Панель состояния | По текущим правилам открытия и чтения деталей |
| Диагностическая очередь, дедупликация и повтор доставки | Диагностика | Сессия вкладки; отделена от видимости панели |
| Heartbeat, опрос, BroadcastChannel, pagehide | Один владелец сессии читателя | Сессия вкладки; имеет явное прекращение работы |

Сохранение запускается обработчиком пользовательского действия. Производные значения вычисляются из состояния. Effects используются для подписок, таймеров, наблюдателей и синхронизации с DOM; cleanup освобождает принадлежащие ресурсы. StrictMode в разработке не должен удваивать команды, heartbeat/polling или оставлять подписки; проверочное размонтирование не отправляет бизнес-команду остановки/закрытия вкладки. [React effects](https://react.dev/learn/you-might-not-need-an-effect), [StrictMode](https://react.dev/reference/react/StrictMode).

`createOperations` переносится с прежней семантикой либо заменяется эквивалентом с теми же проверками. Отдельные назначения запросов независимы. Abort не заменяет guard актуальности. Смена контекста закрывает право менять показ, но не отменяет согласование успешной серверной записи.

## Сохраняемое поведение

- Черновики разделены по владельцу и полю. Сохранённое A не стирает введённое во время запроса B. Reset наследования, отмена черновика и сохранение поля остаются разными действиями. Закрытие и навигация ничего не сохраняют автоматически.
- Поздние успешные ответы и ошибки не меняют другой объект, повторно открытое меню или текущую карточку. Завершённая запись обновляет относящиеся к ней данные даже после ухода с формы.
- React не получает в state DOM-дерево как источник истины. Например, раскрытие `<details>` и удержание завершённой карточки в прежней группе выражаются явным состоянием; стабильный key сам по себе не сохраняет компонент при переносе к другому родителю.
- Список сохраняет строки и превью при неизменном polling, фокус, scroll anchor, сортировку и размеры. Просмотр удаляет карточку и переводит фокус по прежним правилам, без автоматического открытия следующей.
- Открытый материал немедленно очищается при переключении; поздние версии и медиа не возвращаются. При прекращении показа playback останавливается, blob URL освобождаются. Контекст медиаресурса учитывает идентичность/версию, а не произвольный render.
- Все виды содержимого, происхождение обработки, предыдущие версии, скрытые материалы, скачивание вложений, копирование ссылок и переход к оригиналу сохраняются. Текст внешних источников остаётся текстом; перенос не вводит `dangerouslySetInnerHTML` для него.
- Сохраняются вкладки RSS/Telegram/OPML, выбор/создание папки, темы форума, планы импорта, начальная и дополнительная история, настройки моделей и их сообщения/ошибки.
- Команды папки сохраняют preview/token, обработку конфликта и согласование из других вкладок. Кнопка остановки, heartbeat, pagehide/keepalive и протокол исчезновения последней вкладки не меняются.
- Диагностика сохраняет маскирование чувствительных значений, очередь, повтор доставки, дедупликацию и очистку. Ошибка отправки диагностики не сообщает саму себя. Ошибки React render и ошибки async-действий должны попадать в соответствующий существующий канал; error boundary не заменяет обработку ошибок запросов.
- Сохраняются CSS, responsive-компоновка, aria, клавиатура, возврат фокуса и сообщения. Миграция не включает редизайн и переименование продуктовых понятий.

## Постепенный перенос

После подключения сборки существующий UI продолжает работать. Legacy-код перемещается, а не копируется; Vite собирает его вместе с новыми участками. React получает выделенные контейнеры. Старый код может управлять оболочкой контейнера, но не менять его дочернее дерево; React не перерисовывает соседний legacy DOM. Временные адаптеры сохраняют интерфейсы между ещё не перенесёнными владельцами и удаляются при переходе на общий root.

Первый участок — список проблем внутри панели, затем вся панель и диагностика. Далее одно поле настроек с асинхронными сценариями, остальной редактор и подключения, список/дерево чтения и открытый материал. Итог — один React root, прежний browser HTTP interface, отсутствие production legacy-механики. Детали разбиты на самостоятельные [задачи](plan.md).

После каждого этапа приложение остаётся запускаемым, затронутые проверки проходят, заменённая реализация удалена. Следующий этап не начинается с известной необъяснённой регрессией. Возврат к предыдущему этапу выполняется откатом конкретных изменений кода и пересборкой; второй постоянный UI, runtime feature flag и миграции пользовательских данных не создаются.

## Проверка и приёмка

Проверка идёт через существующий HTTP interface и настоящее приложение в Playwright, с временными SQLite/файлами и синтетическими adapters. Computer Use, личные подписки, Telegram-аккаунт и реальный обработчик не нужны. Текущие поведенческие сценарии сохраняются; locators адаптируются только при сохранении проверяемого поведения. Новые проверки добавляются для отсутствующих значимых сценариев.

Runner сохраняет существующие команды. Typecheck фронтенда — отдельный набор, например `frontend-types`, чтобы `types` продолжал означать Python/mypy. UI/browser/HTTP-проверки assets получают свежую production-сборку; build выполняется один раз на прогон до запуска серверов. Python-наборы, которым assets не нужны, не получают зависимость от Node. Подготовка окружения остаётся явной: runner не устанавливает зависимости.

Проверка загрузки assets больше не разбирает исходные `import` регулярным выражением: она проверяет фактические HTML/manifest/файлы сборки, а настоящий браузер — загрузку entry, chunks и CSS. Сохраняются проверки unknown API, MIME, traversal/symlink и запуска из другого cwd. Нужен smoke установленного Python-пакета с включённой сборкой и отсутствующим source checkout.

После переноса каждого UI-участка снимаются и просматриваются скриншоты desktop/mobile на одинаковых синтетических данных. Сравниваются оформление, геометрия, содержимое, фокус и состояния загрузки/ошибки; визуальные изменения не прячутся под видом смены фреймворка.

Финальная приёмка включает `./scripts/check all` на подготовленном дереве задачи по [порядку разработки](../../docs/agents/development.md), browser lifecycle, HTTP/security, проверку установки и просмотра снимков. Нужен независимый reviewer по требованиям и изменённым границам. Фактические команды, результаты, ошибки/повторы, screenshots и ограничения фиксируются в отдельном отчёте после реализации. Исторические отчёты не переписываются.

## Критерии завершения

- Production UI полностью на React + strict TypeScript; legacy-код и временные адаптеры удалены.
- Сборка воспроизводима, выдаётся Python-сервером, свежесть исходников проверяется; обычный запуск не требует Node-процесса.
- Все используемые HTTP-контракты типизированы из серверного источника или явно проверены на границе без скрытых приведений.
- Сохраняются перечисленные продуктовые, асинхронные, медиа- и визуальные сценарии.
- Runner, staged-проверки и CI учитывают TS/TSX, hooks, типы, сборку и browser interface; guards чистоты checkout продолжают работать.
- Текущие архитектурные документы описывают выполненное устройство, а новый отчёт содержит фактическую проверку и ревью.

## За пределами задачи

Новые продуктовые функции, редизайн, SSR, новый серверный runtime, пересмотр хранения и обработки, перенос HTTP на иной транспорт, изменение жизненного цикла Око и поддержка дополнительных ОС. Подготовка этого плана не включает установку зависимостей, изменение кода, запуск приложения, коммит, публикацию или реализацию этапов.
