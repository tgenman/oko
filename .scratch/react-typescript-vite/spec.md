# Око: React + TypeScript + Vite и API-first

Status: done
Label: ready-for-agent
Date: 2026-10-14

## Problem Statement

Интерфейс Око развивается, и сопровождение ручной отрисовки начинает мешать изменениям. Состояние форм, обновление карточек, фокус, навигация и асинхронные запросы приходится согласовывать вручную. Пользователь хочет снизить этот технический долг, сохранив уже работающий читатель и его поведение.

Контракт между фронтендом и бэкендом описан частично и выводится из Python-моделей. Пользователь хочет явную OpenAPI-спецификацию в репозитории, которая регламентирует обе стороны. Сборки должны генерировать из неё библиотеки, реально используемые приложениями, и выявлять расхождения до выпуска. Сам контракт должен быть доступен для чтения в Swagger UI.

## Solution

Перевести браузерный интерфейс на выбранные пользователем React, strict TypeScript и Vite. Сохранить Python-бэкенд, существующий HTTP-интерфейс, обычный запуск, оформление и пользовательские сценарии. Переносить интерфейс последовательно, удаляя заменённый код после проверки каждого участка.

Сделать хранимую в Git OpenAPI-спецификацию единственным редактируемым источником HTTP-контракта. Генерировать из неё TypeScript SDK для фронтенда и Python/Pydantic-модели для бэкенда; проверять, что обе стороны используют эти библиотеки и соответствуют контракту. Добавить Swagger UI у работающего приложения и самостоятельный локальный просмотр спеки без запуска сбора или обработки материалов.

Сейчас подготовлена спецификация. Начало реализации определяется отдельным заданием пользователя; метка готовности описания не означает разрешение менять приложение.

## Implementation Decisions

1. Выбраны React, TypeScript в strict-режиме и Vite. Сохраняются один репозиторий, один корневой npm-проект и один npm lock-файл. Совместимые версии и требования к Node закрепляются при реализации; старые ограничения не принимаются автоматически.
2. Фронтенд владеет представлением, фокусом, навигацией, черновиками и допуском ответа к текущему показу. Runtime владеет выполнением, отменой, внешними ожиданиями и остановкой; Store — сохранением и восстановлением. Состав чтения, эффективные настройки и актуальность обработки определяются сервером.
3. Выделяются владельцы сборки читателя и сессии вкладки, списка/дерева, открытого материала, меню/навигации, редактора, подключений, панели состояния и диагностики. Общие элементы вводятся по реальному повторному использованию. Transport, ошибки и правила актуальности не зависят от React.
4. Единственный редактируемый источник полного HTTP-контракта — хранимый в Git OpenAPI YAML версии 3.1 с закреплённым dialect. Для всех операций описываются стабильные уникальные operation IDs, параметры, тела, content types, security, успешные ответы, ошибки, headers и синтетические примеры. Включены бинарные медиа, формы, команды, диагностика и протокол вкладок.
5. Существующие wire descriptions и поведение служат основанием первоначального переноса контракта. Затем изменения начинаются с OpenAPI. Автоматическая генерация спеки из FastAPI не становится источником истины; ручные дубликаты wire-схем удаляются после подключения их generated-замены.
6. Сборки генерируют локальные библиотеки для обеих сторон. Базовый выбор для фронтенда — Hey API с TypeScript, SDK и Fetch client; для бэкенда — datamodel-code-generator с моделями Pydantic v2. Версии и конфигурация закрепляются. Перед массовым подключением проверяется точное сохранение optional/null, PATCH, unions, aliases, дополнительных полей и ошибок; несовместимая конфигурация не меняет контракт ради удобства генератора.
7. Фронтенд вызывает generated-функции операций; бэкенд импортирует generated-модели для HTTP-входов и выходов. Handlers и domain logic остаются рукописными. Преобразование DTO в доменные значения явно сохраняет бизнес-правила и прежние HTTP-коды; генерация не подменяет реализацию операции.
8. Отсутствующее PATCH-поле, null и значение различаются. Сериализация не дописывает отсутствовавшие поля и не маскирует неверный ответ defaults или удалением лишних данных. Обязательные nullable-поля остаются обязательными. Политика coercion и дополнительных свойств фиксируется для соответствующего входа/выхода.
9. Generated output хранится в Git как производный результат с запретом ручного редактирования. Явная команда обновляет его; проверки и сборки повторяют генерацию во временное место и отказывают при расхождении, не исправляя source checkout. Генерация детерминирована, использует локальные входы и не требует работающего Око. Общая CI проверяет обе языковые ветви; Python-ветка может проверяться без Node.
10. Frontend SDK, backend DTO, сборка интерфейса и документация привязаны к одной ревизии bundled-контракта. Несовпадение ревизий и устаревший generated output блокируют поставку. Проверка потенциально несовместимого изменения дополняется явным решением о версии и порядке обновления потребителей.
11. Transport настраивает отдельный клиент сессии через fetch adapter, token и origin. Сохраняются авторизация только своего origin, диагностические/action headers, signal, cache semantics, keepalive и доступ к raw Response для медиа. HTTP-ошибка, ошибка сети и ошибка декодирования различаются; автоматические повторы мутаций не добавляются. Общий media fetch по полученным ссылкам не становится второй схемой routes.
12. Swagger показывает тот же bundled-контракт. Предусмотрены отдельный локальный режим чтения без Runtime/Store и страница у работающего Око. Standalone-режим не выполняет API-вызовы; встроенное ручное выполнение требует явной авторизации. Token хранится только в памяти страницы, не внедряется автоматически из читателя и не включается в документ или постоянное хранилище.
13. Документация поставляется с локальными JS/CSS и initializer, без CDN и внешней проверки спецификации. Сохраняется CSP. Просмотр документации не создаёт вкладку читателя, не посылает heartbeat и не меняет lease/grace; длительное чтение при остановленном Око обеспечивается standalone-режимом.
14. Vite собирает только production entry и его ресурсы. Python отдаёт готовую сборку на том же origin, что и API; при обычном запуске не запускаются npm, генераторы или установка зависимостей. В пользовательскую поставку включаются готовые assets, generated-библиотеки и документация, работающие без исходного checkout и Node.
15. Source checkout требует явной подготовки сборки. Отсутствующая/устаревшая сборка обнаруживается до старта Runtime и сообщает команду подготовки. Свежесть определяется содержимым влияющих исходников, ресурсов, контрактов, конфигурации и lock-файлов; неполная сборка не публикуется как готовая. Результат сборки не хранится как поддерживаемый исходник.
16. Начальный режим разработки — watch build и обновление страницы на существующем Python origin. Сохранение React state при перезагрузке не обещается. HMR и отдельный dev origin не входят в обязательный результат. Существующие host/origin, bearer, CSP, MIME, защитные заголовки и правила недоступности чужих файлов сохраняются; неизвестный API или asset не превращается в HTML.
17. Локальный UI state размещается у соответствующих владельцев с помощью state/reducers/context. Универсальный собственный store, router, query cache, библиотека форм, UI-kit и React Compiler не входят в стартовый набор. При ручном декодировании внешний JSON проверяется до использования; generated TS-типы не объявляются runtime-валидацией.
18. Меню владеет активным диалогом, стеком страниц, opener и контекстом показа. Редакторы держат черновики по объектам/полям выше размонтируемого поля. Незавершённая запись и её отправленные значения живут до обработки исхода. Успех согласуется после ухода с формы; видимые сообщения и переходы допускаются только в актуальном контексте.
19. Сохранение, reset наследования и discard черновика остаются разными явными действиями. Закрытие меню и переход назад ничего не сохраняют автоматически. Ответ на A не стирает более новый B; загрузка сохранённых значений накладывает черновик только соответствующего объекта. Независимые операции не отменяют друг друга.
20. Guard актуальности остаётся обязательным, даже если запрос был abort-нут. Повторное открытие того же меню создаёт новый контекст. Поздние успех и ошибка не меняют другой объект или экран. Ошибки направляются в диагностику независимо от права показывать их в ушедшем контексте.
21. Один владелец сессии отвечает за tab identity, heartbeat, polling, BroadcastChannel и события закрытия/восстановления страницы. React effects применяются к подпискам и ресурсам; пользовательские команды запускаются обработчиками действий. StrictMode не удваивает циклы/команды, а проверочный cleanup не означает закрытие вкладки или остановку работы.
22. Список сохраняет выбор, раскрытие, сортировку, локальные размеры, scroll anchor и неизменные строки/превью. Идентичность ресурсов привязана к материалу/версии. Просмотр переводит фокус по прежним правилам и не открывает следующую карточку автоматически. Команды папки сохраняют preview/token, конфликт состава и согласование из других вкладок.
23. Владелец открытого материала управляет загрузкой, исходниками сводок, версиями и медиа. Выбор другой карточки сразу завершает старый показ без отметки просмотренным; остановка, потеря связи и просмотр не позволяют поздним ответам вернуть содержимое. Cleanup останавливает playback и освобождает blob URL. Все состояния полноты, происхождения, фильтрации, тезисов и действия со ссылками сохраняются; внешний текст остаётся текстом.
24. Сохраняются существующие формы RSS/Telegram/OPML, выбор новой/существующей папки, темы форума, настройки обработчиков, YouTube и история. Старый preview/ответ каталога не меняет новый файл или экран. Настоящий формат обмена сохраняется: файловый input в интерфейсе сам по себе не меняет формат API.
25. Панель хранит раскрытие, порядок и положение карточек как состояние представления. Раскрытая завершившаяся проблема удерживается по прежним правилам; стабильный key сам по себе не заменяет это решение. Диагностика владеет очередью, повторной доставкой, маскированием и дедупликацией независимо от видимости панели. Ошибка доставки не создаёт рекурсивную доставку; ошибки render и async-действий обрабатываются соответствующими каналами.
26. Во время миграции старый и React-код получают непересекающиеся DOM-контейнеры. Старые файлы перемещаются без поддерживаемых копий; временный адаптер сохраняет interface ещё не перенесённого владельца и удаляется вместе с ним. Итог — один React root, без второй production-реализации или постоянного migration flag.
27. Последовательность: полный OpenAPI; обе библиотеки и backend integration; сборка/Swagger; SDK и общая сессия; панель/диагностика; редактор/меню; подключения/история; дерево/список/команды; открытый материал; общий root и приёмка. Первый React-контейнер и первое поле проверяются до переноса всей связанной области. Каждый этап оставляет работающее приложение и удаляет заменённый код.
28. Тестовые каталоги и единый runner сохраняются. Проверка типов фронтенда отделена от Python/mypy и от успешной Vite-сборки. Свежий build готовится один раз до UI/asset-наборов; Python-проверки без assets не получают лишнюю зависимость от Node. Guards чистоты checkout, staged-проверки и CI учитывают новые расширения и codegen.

## Testing Decisions

1. Подтверждённая пользователем граница приёмки — существующий HTTP-интерфейс читателя, который использует настоящий браузерный UI. Playwright открывает приложение, выдаваемое тем же Python-сервером, и проверяет пользовательские действия. Для контрактных артефактов используются команды сборки; доступность и содержимое Swagger проверяются таким же браузерным автотестом. Пользователь подтвердил этот набор и публикацию спецификации 14 октября 2026 года.
2. Хороший тест подтверждает внешний результат и правила жизненного цикла, а не имя функции, устройство hooks или точный JSX. Основное доказательство UI-переноса — действия через браузер, для серверной границы — реальные HTTP-запросы/ответы. Внутренние проверки компонентов не подменяют эти сценарии.
3. Используются временные SQLite/файлы, синтетические источники/модели и существующие test factories. Управляемые snapshots могут задерживать ответы и игнорировать abort; отдельный интегрированный reader-сценарий использует настоящий HTTP без подмены browser fetch. Личные источники не нужны.
4. Prior art — существующие сценарии transport, reader HTTP, меню и навигации, UI-lifecycle, дерева/списка, открытого материала, панели/диагностики, подключений и истории. Сохранить их утверждения и организацию; locators менять только при сохранении проверяемого поведения. Новые тесты добавлять для отсутствующего значимого случая, а не копировать старые.
5. Контракт проверяется на полноту method/path/operation ID, параметры, security, статусы, content types и headers. Позитивные и негативные настоящие HTTP-примеры проверяют required/null/enum/type и дополнительные поля по объявленной политике, ошибки авторизации, конфликт завершения папки и бинарные responses. Генерация или публикация YAML сами по себе не доказывают соответствия реализации.
6. Генерация обеих библиотек проверяется на детерминизм, общую ревизию и использование потребителями. Изменение спеки с устаревшим output должно давать FAIL. Потенциально breaking changes сравниваются с проверенным baseline и проходят семантическое ревью. Проверки ничего не переписывают в source checkout.
7. Схемы browser snapshots происходят из того же OpenAPI и используют совместимый JSON Schema dialect. Проверяется также доставленный устаревший ответ, даже если UI его отверг. Прежний draft-07 validator не становится совместимым с OpenAPI 3.1 простой заменой метки dialect.
8. Для настроек обязательны сохранение A с последующим вводом B, закрытие/Back и поздний результат, повторное открытие, смена владельца, независимость полей, reset/discard и возврат фокуса. Для подключений — старые catalogs/previews, успешная запись после ухода, история и повтор загрузки прерванного каталога.
9. Для чтения обязательны неизменный polling, scroll/focus/preview, просмотр без автоматического открытия следующего, выбор B при незавершённом A, late text/version/media, очистка playback/blob URL, остановка/потеря связи и просмотр из другой вкладки. Незатронутый материал сохраняется.
10. Для панели и диагностики обязательны раскрытая завершившаяся карточка, порядок, mobile dialog/inert/focus, сверка неизвестных исходов с receipts, маскирование, повтор доставки и отсутствие рекурсии. StrictMode не должен добавлять второй цикл сессии или повторять бизнес-действия.
11. Swagger-автотест сам запускает тестовый браузер, переходит на страницу документации и проверяет видимые операции, параметры и успешную загрузку нужной ревизии спеки. Проверяется standalone-режим при неработающем Око, локальные assets/CSP без внешней сети и ручной авторизованный Try на синтетическом backend. Открытие docs не создаёт reader lease и не выполняет команды.
12. Проверяются свежесть build, ранний отказ типов/сборки, выдача реальных entry/chunks/CSS, MIME, неизвестные пути, traversal/symlink и запуск из другого рабочего каталога. Нужен smoke установленного Python-пакета без checkout и Node; тест regex по исходным imports заменяется проверкой фактической поставки.
13. До и после переноса участка снимаются и просматриваются desktop/mobile screenshots на одинаковых синтетических данных. Проверяются содержание, геометрия, оформление, фокус, загрузка и ошибки. Playwright используется и для управления браузером, и для получения снимков; Computer Use не входит в процесс.
14. Каждый этап запускает затронутые наборы; расширение требуется для общих изменений или нерешённых сомнений. Финальная приёмка включает полный runner на подготовленном дереве задачи, сборку/установку, просмотр снимков и независимое ревью по требованиям и границам. Фактические команды, падения/повторы и ограничения фиксируются отдельно от плана; исторические отчёты сохраняются.

## Out of Scope

- Реализация в ходе подготовки этой спецификации, установка зависимостей, запуск личного экземпляра, коммит и публикация приложения.
- Настольная оболочка, мобильное приложение и добавление поддержки других ОС.
- Редизайн, изменение компоновки и содержания, новые функции читателя помимо согласованного просмотра API-контракта.
- Изменение хранения, работы источников/обработчиков, правил состава чтения или семантики «Просмотрено».
- Изменение жизненного цикла Око, фонового режима и протокола вкладок.
- SSR, новый серверный runtime, замена HTTP другим транспортом и отдельный репозиторий фронтенда.
- Обязательное внедрение router, глобального state framework, query cache, UI-kit, React Compiler или HMR.
- Вызовы личных Telegram/RSS/YouTube-источников и настоящих моделей ради миграционных тестов; Computer Use.
