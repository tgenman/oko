# Ответы Telegram: исправление парсинга и карточка контекста A

Status: done — реализовано и проверено 21 октября 2026
GitHub: https://github.com/tgenman/oko/issues/70
Дата: 21 октября 2026

## Цель и согласованные решения

Собственный текст Telegram-публикации отделён от предпросмотра сообщения, на которое она отвечает. Заголовок формируется из собственного текста, а ответ представлен компактной карточкой варианта A.

Пользователь выбрал A: карточка над текстом, автор, две строки доступного фрагмента, раскрытие фрагмента и переход к цитируемому посту. По последнему решению пользователя **ИИ обрабатывает весь доступный текст: собственный текст публикации и сохранённый фрагмент сообщения, на которое она отвечает**. Это относится и к фильтрации, и к тезисам. Разделение этих частей в хранении и интерфейсе сохраняется.

Исходный этап ограничивался спецификацией. 21 октября 2026 пользователь поручил реализацию через implement-spec; разрешены код, контракты, проверки, локальные коммиты и ведение задачи #70. Слияние и обновление рабочего экземпляра требуют последующего задания.

## Объём

Первый этап охватывает публичный веб-доступ Telegram, где воспроизведена проблема, и отображение сохранённого предпросмотра в читателе. Режимы личного аккаунта и аккаунта для сбора сохраняют существующее поведение; получение контекста ответов через Telegram API в эту задачу не входит. Общий контракт допускает отсутствие предпросмотра у любого материала.

Работа затрагивает разбор источника, сохранение и чтение версий, HTTP-проекции и область чтения. Состав подписок, отметки просмотра, пересылки, обычные link previews и загрузка вложений не переопределяются. Ссылки и обычный Markdown собственного текста продолжают работать по действующим правилам.

## Данные и контракт

Добавить явное представление `reply_preview` — предпросмотр ответа, доступный в полученной копии публикации:

| Поле | Значение |
| --- | --- |
| `author` | Отображаемое имя из предпросмотра, строка либо `null` |
| `text` | Доступный фрагмент цитируемого сообщения, обычный текст, может быть пустым |
| `source_url` | Полученный от Telegram безопасный HTTP(S)-адрес цитируемого сообщения либо `null` |

`reply_preview=null` означает отсутствие извлечённого предпросмотра. Пустые отдельные поля не требуют придумывать автора, содержание или адрес. Наличие объекта не обещает полного текста цитируемой публикации.

1. У материала есть собственные `title`/`text` и отдельный `reply_preview`. Не хранить весь предпросмотр одной Markdown-ссылкой внутри собственного текста или в `description`.
2. Сохранять предпросмотр вместе с конкретной версией публикации. Текущая версия и предыдущие версии имеют собственные значения; перезапуск не теряет контекст.
3. Добавить nullable-поле в `AvailablePublicationContent` и `PublicationVersion` канонического OpenAPI. Сервер всегда возвращает объект либо `null`; старые файлы без поля читаются как `null`. Pending-состояние не содержит выдуманный предпросмотр.
4. Внутренние контракты сбора, сериализация, snapshot-валидация, HTTP-проекции и generated Python/TypeScript-модели обновляются согласованно. Править исходный OpenAPI, затем генерировать библиотеки; добавить валидные примеры схем и ответов.
5. Для списка чтения достаточно правильного `title`; полный предпросмотр передаётся при открытии материала. Новые операции API и настройка включения карточки ответа не требуются.

## Разбор публичного HTML

1. Разбирать `.tgme_widget_message_reply` отдельно, до общей сериализации содержимого. Сохранить автора, адрес и текст фрагмента из их собственных элементов.
2. Собственный текст извлекать из `.tgme_widget_message_text`, исключая элементы внутри предпросмотра ответа. Не допускать повторного включения цитируемого фрагмента через вложенный селектор.
3. Заголовок материала и карточки чтения формировать из первой содержательной строки собственного текста по действующим правилам заголовков. Контекст ответа не становится заголовком.
4. Для публикации без собственного текста, но с предпросмотром ответа, использовать нейтральный заголовок «Ответ на сообщение». Наличие одного предпросмотра не создаёт фиктивное неподдерживаемое вложение. Без ответа продолжают действовать существующие fallback-правила для медиа.
5. В имени и фрагменте нормализовать технические пробелы/переносы HTML до одиночных пробелов; сохранить видимые символы и подписи emoji. Не переносить HTML, CSS и служебные элементы в данные. Весь фрагмент не превращается в ссылочную Markdown-конструкцию; вложенные ссылки не исполняются как HTML.
6. Адрес извлекать из `href` самой ссылки предпросмотра, при необходимости разрешая относительный URL от страницы Telegram. Небезопасная схема даёт `source_url=null`; ссылка не угадывается по имени автора или тексту фрагмента.
7. Не считать `.tgme_widget_message_forwarded_from` предпросмотром ответа. Настоящий `<blockquote>` внутри собственного текста остаётся частью собственного текста и рендерится обычным Markdown как цитата.
8. Не переходить к цитируемому посту во время сбора. Не догружать его полный текст, медиа, аватар, историю переписки и другие публикации ради карточки. Не считать усечённый Telegram фрагмент ошибкой загрузки основного материала.

Для примера 75124 ожидаются:

- `title`: «Встреча Путина и Уиткоффа в Петербурге завершилась, сообщил Песков.»
- `text`: собственные два абзаца поста; ни `Varlamov News`, ни фрагмент ответа в них не добавлены.
- `reply_preview.author`: `Varlamov News`.
- `reply_preview.source_url`: `https://t.me/varlamov_news/75122`.
- `reply_preview.text`: только предоставленный Telegram фрагмент, включая имеющееся у источника многоточие.

## Представление — вариант A

1. После заголовка/даты и перед основным текстом показывается компактная карточка ответа. Собственный текст остаётся обычным открытым содержимым, как в действующем читателе.
2. Карточка имеет спокойный фон и левую акцентную линию. Сверху — имя автора, под ним — максимум две визуальные строки фрагмента с усечением по ширине. Нет встроенных принудительных пустых абзацев.
3. Нажатие на автора/область ссылки открывает `source_url` цитируемого поста во внешней вкладке с `noopener noreferrer`. Заголовок материала и ссылка «Оригинал публикации» продолжают вести на текущую публикацию, а не на цитируемую.
4. Отдельная кнопка «Весь фрагмент» раскрывает весь **сохранённый фрагмент**, «Свернуть» возвращает компактный вид. Она не запускает сеть, не открывает ссылку и не обещает полный исходный пост. При заведомо помещающемся фрагменте раскрытие можно не показывать; потеря доступа к сохранённому тексту из-за обрезки недопустима.
5. Раскрытие живёт только в памяти текущего показа материала. Другой материал и явное переключение на новую ревизию начинают с компактного состояния; фоновое обновление тезисов той же ревизии не сворачивает раскрытую карточку.
6. При `author=null` подпись — «Ответ на сообщение». При пустом фрагменте карточка показывает доступную подпись и ссылку. При `source_url=null` карточка остаётся читаемой без перехода; отсутствие адреса само по себе не означает удаление источником.
7. `reply_preview=null` не оставляет пустого блока или отступа. Не показывать придуманные даты и статус доступности цитируемого сообщения.
8. Кнопка раскрытия доступна клавиатурой, передаёт `aria-expanded` и имеет видимый фокус. На узком экране текст переносится, карточка не расширяет страницу.
9. Полный исходник при фильтрации и его медиа сохраняют действующее поведение. Одна карточка ответа текущей ревизии не дублируется внутри раскрытого полного исходника.
10. Предыдущая версия при раскрытии показывает собственный предпросмотр, если он сохранён, перед собственным текстом этой версии.

## Фильтрация, тезисы и актуальность

1. Вход фильтрации и тезисов включает собственный текст и заголовок публикации, а также весь сохранённый `reply_preview.text` с доступными автором и безопасным адресом источника. Ограничение карточки двумя визуальными строками не ограничивает вход ИИ.
2. Передавать предпросмотр как отдельный явно обозначенный контекст сообщения, на которое отвечает публикация; не приписывать его слова автору текущего поста. Настоящая цитата внутри собственного текста также участвует в обработке.
3. Фильтрация оценивает материал с учётом обеих частей и может принять решение о скрытии на основании цитируемого фрагмента. Преобразованный основной текст остаётся результатом фильтрации собственного текста; исходная карточка ответа сохраняет сохранённый фрагмент и не подменяется модельным пересказом. Тезисы могут опираться на обе части, сохраняя различие между цитируемым сообщением и собственным текстом публикации.
4. Изменение предпросмотра, влияющее на фактический вход ИИ, делает готовые результаты неактуальными по тем же правилам, что изменение собственного текста. Переработка выполняется в рамках существующих условий запуска, настроек и допуска Runtime; отдельный безусловный вызов модели при каждом получении не добавляется.
5. Предпросмотр участвует в подписи входа обработки и в согласовании снимка/HTTP `revision_id`. При изменении входа старый ответ модели не принимается к новой версии. При идентичном входе и настройках сохраняются результаты и их происхождение.
6. Для публикации без собственного текста доступный непустой фрагмент ответа является достаточным текстовым входом для фильтрации и тезисов по действующим условиям запуска. При отсутствии содержательного текста в обеих частях не вызывать модель только ради имени автора или адреса.
7. Обрабатывается только сохранённый фрагмент. Включение ответа в ИИ-вход не разрешает догружать полный цитируемый пост, историю переписки или другие материалы.

## Уже сохранённые материалы и история

1. Старые файлы и предыдущие версии без явного поля читаются совместимо как `reply_preview=null`. Не разбирать произвольный сохранённый Markdown эвристикой «первая цитата — это ответ»: так можно ошибочно удалить настоящую авторскую цитату.
2. Само обновление приложения не запускает массовое переполучение, перезапись истории или пересоздание производных результатов. До нового получения старый материал остаётся в своём сохранённом представлении.
3. При следующем обычном получении публикации новым парсером, в том числе через существующий Reload, принять корректно разделённые текст и предпросмотр через действующий Runtime/Store. Дополнительная команда миграции или новый HTTP endpoint не нужны.
4. Первое такое получение может создать новую локальную версию: прежняя копия содержала предпросмотр в тексте. Старую версию сохранить; исправление парсинга само по себе не доказывает авторскую правку. Не устанавливать флаг upstream `edited` ради этого перехода.
5. После первого разделения действуют обычные проверки фактического входа обработки. Если его состав или представление изменились, результаты старого объединённого входа не выдаются за актуальные для нового. Изменения предпросмотра учитываются при актуальности, как определено выше.
6. Старую сохранённую веб-копию можно обрабатывать в существующем объединённом представлении до штатного переполучения: обе её текстовые части теперь входят в разрешённый вход ИИ. Обязательная предварительная загрузка из Telegram ради запуска ИИ не требуется; недоступность источника сама по себе не блокирует обработку сохранённого текста.
7. Повторное получение идентичных новых данных не создаёт дубликатов карточки, видимой версии или дополнительных модельных запросов. Условия полноты загрузки и сохранение уже загруженных медиа не ухудшаются.

## Владение состоянием и ограничения

Предпросмотр передаётся вместе с тем же снимком материала и той же ревизией, что его текст. При выборе другой карточки старый контекст сразу убирается; поздние ответы не возвращают его. Уведомление о новой версии удерживает старые текст, контекст, тезисы и медиа до явного переключения. При просмотре в другой вкладке сохраняется уже загруженный контекст в памяти текущего показа; новой сетевой работы для него не возникает.

Не меняются правила «Просмотрено», состав чтения, принадлежность папкам и фидам. Переход к цитируемому посту не отмечает просмотренными текущую публикацию, другую локальную карточку или Telegram-диалог.

Глобальная нормализация повреждённых Markdown-ссылок не заменяет разбор структуры Telegram и не удаляется этой задачей. Прототип, A/B/C-переключатель и подготовленная JSON-фикстура не входят в рабочую поставку. Авторизация на реализацию, публикацию и деплой берётся из последующего задания пользователя.

## Критерии приёмки

1. На структуре HTML поста 75124 сервер отдаёт правильный заголовок, только собственный текст и отдельный предпросмотр со ссылкой на 75122. В DOM нет сломанного `> [Varlamov News` и большой Markdown-ссылки из автора с цитатой.
2. Предпросмотр не дублируется в тексте; заголовок списка и открытого материала одинаково основан на собственном тексте.
3. Вариант A показывает две строки фрагмента, раскрытие/сворачивание и правильные разные ссылки на текущий и цитируемый посты. Раскрытие не создаёт запросов.
4. Отсутствующий ответ, пустые автор/фрагмент/URL, ответ без собственного текста и небезопасный адрес обрабатываются по правилам выше. Не возникают выдуманные автор, URL, ошибка медиа или обещание полного цитируемого текста.
5. Обычная цитата внутри поста, ссылки собственного текста, пересылка, link preview и вложения сохраняют свои назначения.
6. Реально отправленные синтетическому обработчику запросы фильтрации и тезисов содержат уникальные маркеры собственного текста и всего сохранённого предпросмотра, включая часть за пределами двух строк карточки. Принадлежность цитируемого фрагмента обозначена отдельно. Проверены влияние контекста на фильтрацию и тезисы, а также обработка ответа без собственного текста.
7. Изменение только предпросмотра, меняющее вход ИИ, корректно инвалидирует результаты и допускает переработку по обычным условиям запуска, как изменение собственного текста. Идентичный вход сохраняет результаты/происхождение. Смена контекста не позволяет принять старый ответ модели к другому входу.
8. Контекст сохраняется после перезапуска, принадлежит своей версии и не смешивается при переключении карточек, ревизий или storage. Фоновое обновление той же ревизии сохраняет раскрытие и положение чтения.
9. Старый материал открывается без миграции; повторная загрузка исправляет его, сохраняя старую версию. До переполучения сохранённый объединённый текст доступен ИИ без обязательной загрузки источника; проверен запуск при недоступном источнике. Последующий идентичный reload не создаёт лишнюю версию. Во время исправления уже открытая копия удерживается до переключения новой версии.
10. OpenAPI, generated-библиотеки, примеры, текущие и исторические ответы согласованы. Desktop и узкий экран подтверждены просмотренными Playwright-снимками; управление работает клавиатурой.

## План реализации и проверки

Связный объём выполняет один исполнитель; сначала зафиксировать базу и изолировать изменения от параллельных правок. Порядок: контракт/сохранение предпросмотра → парсер и разделение входов → UI A → совместимость и регрессии. Реализация ведётся одной задачей [#70](https://github.com/tgenman/oko/issues/70) без зависимостей.

Тестировать через существующий HTTP interface читателя с временными SQLite/файлами и синтетическими source/AI adapters, затем настоящий браузер Playwright. Публичный HTML использовать как основание синтетической фикстуры; автоматические тесты не зависят от живого t.me. Не запускать личные подписки и аккаунты ради проверок.

- Сначала падающие сценарии разделения данных, заголовка и модельного входа; затем проверки варианта A, старого хранения, версий и поздних ответов.
- Расширить существующие Telegram HTTP/reader-сценарии и браузерный набор открытого материала. Проверки должны читать HTTP-ответы/DOM и запросы синтетического обработчика, а не закреплять внутренние имена функций.
- Выполнить `npm run api:generate`, `npm run api:check`, целевые проверки и итоговый `./scripts/check all --compact`: задача затрагивает API, хранение, версии и актуальность обработки.
- Просмотреть снимки, провести независимое ревью относительно этой спецификации; фактические команды, исходы и ограничения сохранить отдельно от плана.
- После реализации обновить архитектурное описание и указатель на архив прототипа, не переписывая исторические результаты его проверки.
