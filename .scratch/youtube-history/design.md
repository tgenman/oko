# История YouTube через yt-dlp

Статус: запись этапа проектирования. Последующее разрешение и критерии реализации зафиксированы в [spec.md](spec.md).
Дата: 2026-10-13.

## Уже согласовано пользователем

- Начальная история YouTube в режиме последних N видео перечисляется через yt-dlp.
- Последующие обновления собираются через официальный RSS/Atom.
- Список не запрашивается повторно для каждого ролика: результат перечисления передаётся в дальнейшую обработку и сохраняется для восстановления.
- Видео и аудио не скачиваются. Собственный YouTube Data API key для перечисления не нужен.
- Ранее согласованное правило субтитров сохраняется: успешно полученный текст повторно не запрашивается.
- На этапе этого обсуждения работа была ограничена проектированием и документами.
- Shorts исключены из истории и последующих RSS-обновлений. Опубликованные записи трансляций включаются вместе с обычными видео.
- В настройках существующего фида доступна явная догрузка последних N видео. N — размер последних публикаций источника, а не число дополнительных карточек. Известные ID учитываются и не дублируются, просмотренные не возвращаются.
- Принимаются неполные метаданные: описания и точные даты берутся из RSS, когда доступны; ради отсутствующих полей страницы отдельных видео автоматически не запрашиваются. Превью сохраняются отдельно, неизвестная дата показана явно.
- Текущий сборщик субтитров сохраняется; переход на yt-dlp для субтитров не входит в эту задачу.
- При ошибке подбора найденное сохраняется; пользователь видит ошибку и может явно продолжить. RSS-обновления работают независимо. Ошибка не выдаётся за конец списка.
- При подтверждённом конце источника раньше N отображается фактическое количество и причина недобора; автоматических попыток добрать отсутствующее нет.
- Уже сохранённые Shorts остаются до обычной отметки «Просмотрено». Исключение действует на новые поступления и догрузку.
- Режим «начиная с даты» сохраняется в пределах доступного RSS с явным предупреждением о глубине. Через yt-dlp расширяется только режим последних N.
- Длинный подбор ограничен порциями сетевой работы. Исчерпание бюджета порции сохраняет прогресс и требует явного продолжения; это не конец источника и не молчаливое уменьшение N.

## Факты и действующая модель

- [Эксперимент с yt-dlp](../../docs/research/ytdlp-history.md): версия 2026.08.19, 60 различных ID за один запрос плейлиста загрузок; первые 15 совпали с RSS. В ответе есть названия, URL, длительности и ссылки на превью, но нет описаний, точных дат и live_status. Один запрос не гарантирован для любых источников.
- [Термины Око](../../GLOSSARY.md): начальная загрузка истории выбирает прошлые публикации; собранный материал может быть неполным. Найденная ссылка не равна полностью сохранённому материалу. Новые поступления не меняют выбранную начальную историю.
- По действующим [правилам выполнения](../../docs/architecture/reader-work.md) Runtime отвечает за выполнение и отмену, Store — за сохранение и восстановление. Сетевые ожидания не должны удерживать блокировку действий.
- `YouTubeSource.fetch()` сейчас повторно вызывает `read_entries()`. Подмена этого метода запуском yt-dlp размножила бы запросы; такая реализация исключена.
- Существующий сборщик субтитров — youtube-transcript-api. Сам факт добавления yt-dlp для истории не означает замены этого сборщика.
- Старые согласованные ограничения RSS/YouTube на доступное окно описаны в [спецификации истории](../initial-history/spec.md). Новая работа расширяет только согласованный сценарий последних N видео YouTube; финальная спецификация должна явно описать поведение остальных режимов.

## Дерево решений

1. Состав последних N: единый список загрузок или только обычные видео.
   - Далее: будущие эфиры, недоступные публикации, недобор N, порядок без точной даты.
2. Расширение истории уже подключённого фида: действие, смысл N и граница нового подбора.
   - Далее: существующие/просмотренные публикации, неизменность набора при новых поступлениях, повторное действие.
3. Содержание старых материалов вне RSS: минимальные данные или отдельное получение подробностей.
   - Далее: прогресс, полнота, представление неизвестной даты, локальные превью, стоимость запросов.
4. Субтитры: сохранить текущий сборщик или отдельно оценить замену на yt-dlp.
   - Далее, если замена выбрана: языки, выбор одной дорожки, последовательность и ограничения запросов, ошибки и повторные попытки.
5. После определения состава и обработки: пауза, остановка, восстановление, ошибки перечисления, лимиты, диагностика, критерии приёмки.

## Раунд 1 — ответы пользователя

1. **Состав:** пользователь уточнил «без shorts». Ранее предложенный единый список всех загрузок нельзя считать принятым без этого исключения. Записи трансляций и RSS-обновления требуют уточнения.
2. **Существующий фид:** принято явное действие «Загрузить последние N видео» в настройках фида. N — размер последних публикаций источника, а не число дополнительных новых карточек; уже известные ID учитываются и не дублируются, просмотренные не возвращаются.
3. **Подробности:** принят экономный режим: сохранить доступные названия/ссылки, отдельно загрузить превью; описания и точные даты взять из RSS там, где они доступны. Вне RSS не запрашивать автоматически страницу каждого видео ради заполнения полей. Неизвестную дату показывать явно.
4. **Субтитры:** принято оставить текущий сборщик в этой задаче; замену на yt-dlp оценивать отдельным сравнением на нескольких роликах. Самостоятельное переключение или последовательное обращение к двум сборщикам не согласованы.

В GLOSSARY добавлена «Догрузка истории»: согласованный сценарий для уже подключённого источника, отдельный от начальной загрузки при подключении. ADR пока не требуется.

## Факты после исключения Shorts

- По [коду yt-dlp](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/extractor/youtube/_tab.py), `/videos` и `/streams` — отдельные вкладки. Выбор `/videos` исключает отдельные вкладки Shorts и трансляций. У исходного списка Uploads нельзя гарантированно распознать все Shorts по отсутствию маркера, длительность не является надёжным признаком.
- В [yt-feed-cli](https://github.com/NataliaBondarenko/yt-feed-cli) и [raycast-youtube-to-rss](https://github.com/cashwu/raycast-youtube-to-rss) используются RSS-плейлисты с префиксом UULF для обычных видео. Это кандидат для RSS без Shorts; контракт Google и фактическая работа такого URL в этой задаче пока не подтверждены.
- Ранее измеренный один запрос относится к общему Uploads, а не к новому варианту без Shorts. Бюджет запросов последнего ещё не измерен.
- Runtime сейчас выполняет одну задачу сбора одновременно. Субтитры 60 новых материалов могут последовательно запрашиваться по существующим настройкам тезисов/важности. Сохранённые субтитры повторно не запрашиваются.

## Раунд 2 — ответы пользователя

5. **Записи трансляций:** пользователь ответил «нужны». История должна включать обычные видео и опубликованные записи трансляций, исключая Shorts. Ограничение одной вкладкой `/videos` отклонено.
6. **Новые Shorts:** принято исключение также из RSS-обновлений. Технический способ фильтрации RSS требует проверки. Одного обычного channel_id-фида для достоверной классификации недостаточно.
7. **Ошибка подбора:** принято сохранять уже найденное, показывать незавершённый подбор и кнопку продолжения. Повторный подбор — по явному действию, с распознаванием известных ID; RSS-обновления продолжаются независимо. Конец списка и сетевая ошибка различаются.
8. **История короче N:** принято: если источник успешно обойдён и подходящих публикаций меньше N, показать фактическое количество и причину недобора. Это завершённый обход источника, а не ошибка и не основание для бесконечных повторов.

## Техническая проверка состава после раунда 2

[Инвентаризация YouTube-Play-All](https://github.com/RobertWesner/YouTube-Play-All/blob/main/documentation/available-lists.md) и [исходник Invidious](https://github.com/iv-org/invidious/blob/master/src/invidious/routes/api/v1/channels.cr) разделяют `UU` (все загрузки), `UULF` (обычные видео), `UULV` (трансляции) и `UUSH` (Shorts). Единого готового списка «видео + записи трансляций, без Shorts» в изученных источниках не найдено. Это наблюдаемые возможности YouTube, а не обещанный Google контракт.

Проверяемый вариант для истории: получить кандидатов из списков видео и трансляций, а их общий порядок взять из Uploads по ID. Даты для такого объединения не нужны; запросов на каждый ролик тоже нет. Однако согласованность списков, полноту кандидатов и обработку текущих/будущих трансляций ещё нужно проверить фактически. При большом количестве Shorts обход Uploads может потребовать много страниц. Вариант для обновлений — два RSS этих типов внутри одного фида Око; их фактическая доступность и состав ещё не проверены. Техническая схема пока не считается выбранной.

## Раунд 3 — ответы пользователя

9. **Уже сохранённые Shorts:** принято оставить существующие материалы до обычной отметки «Просмотрено», а исключение применять к новым поступлениям и догрузке. Автоматическое удаление накопленного не входит в согласованный объём.
10. **Выбор по дате:** принято сохранить существующий режим в пределах RSS с явным предупреждением об ограниченной глубине. Расширенная история через yt-dlp в этой задаче поддерживает только последние N; точная дата для старых видео неизвестна.
11. **Длинный обход:** приняты ограниченные порции сетевой работы. При достижении бюджета обращений сохранять прогресс и показывать «Подбор не завершён — Продолжить», а не ошибку или конец источника. N не уменьшается молча. Это особенно важно для каналов с большим числом Shorts между обычными видео.

## Раунд 4 — ответы пользователя

12. **Пауза и перезапуск:** принято сохранять выбранные ID, доступные метаданные, прогресс и причину остановки. После перезапуска активная загрузка может продолжиться при открытой вкладке; пауза, ошибка или ожидание следующей порции не снимаются автоматически. Сохранённые материалы не требуют повторного перечисления истории.
13. **Новая догрузка во время текущей:** принята одна операция истории на фид. Изменить N можно после завершения либо явной остановки текущей операции; остановка не удаляет сохранённые материалы. Новый подбор получает новую границу последних N; «Продолжить» относится к прежнему подбору.
14. **Материалы без даты:** принято сохранить существующую группу «Дата неизвестна» после датированных материалов. Внутри одного фида неизвестные даты упорядочивать по сохранённому порядку источника (обратно для сортировки «старые сверху»); не подставлять дату загрузки вместо публикации. Между фидами при отсутствии дат нужна стабильная техническая последовательность, не обещание общей хронологии.
15. **Неизвестный статус трансляции:** RSS не содержит гарантированного признака завершения эфира. Принято отбрасывать распознанные будущие/текущие эфиры по уже полученным данным и сохранять прежнее удаление распознанного анонса при запросе субтитров. Отдельный запрос каждого ролика только для проверки статуса не делать. Принято ограничение: до распознавания анонс может оказаться в списке.

Пункты 12–15 подтверждены ответом пользователя «ок».

Сохраняется ранее согласованное правило начальной истории: недоступность после фиксации набора не приводит к автоматической замене более старой публикацией. Окончательно недоступный материал учитывается отдельным исходом; распознанный анонс обрабатывается по действующему правилу пропуска.

## Восстановление перечисления — выявленное ограничение

В установленном yt-dlp 2026.08.19 продолжение YouTube хранится внутри генератора `_entries` (`yt_dlp/extractor/youtube/_tab.py`), а не в публичном сохраняемом курсоре. Выбор `--playlist-start` использует LazyList и после нового запуска не избавляет от сетевого чтения предыдущих страниц. Поэтому стандартный CLI сам по себе не обеспечивает продолжение с сохранённой сетевой позиции.

Два варианта:

- Простой: между порциями живой worker сохраняет позицию; после его завершения при перезапуске или ошибке допускается один повторный обход уже пройденных страниц для восстановления позиции. Найденные ID/метаданные сохранены, не дублируются. После завершения подбора перечитывания для обработки материалов нет. Повторы восстановления должны быть ограничены; если повторные страницы исчерпали бюджет, нельзя бесконечно показывать обычное «Продолжить» без возможности продвижения — требуется явно выделенный ограниченный бюджет восстановления и его расход в диагностике.
- Более сложный: сохранять ответы страниц в локальном кеше одной операции и воспроизводить их для нового worker без сети. Это потребует ограничений размера/срока, привязки версии и конфигурации yt-dlp, очистки и обработки протухших continuation. Добавлять такую инфраструктуру без выбора компромисса не следует.

## Раунд 5 — открытое решение

16. **Перечитывание после перезапуска незавершённого подбора:** рекомендован простой вариант — разрешить один ограниченный повторный обход прежних страниц после завершения worker, сохраняя список и результаты. Для законченного подбора и обработки отдельных роликов перечитываний нет. Если нужен строгий запрет повторных сетевых страниц и для незавершённого подбора, потребуется кеш ответов операции.

Решение 16 пока не принято. Оно уточняет техническую возможность выполнить согласованные пункты 11–12, не меняя сохранность материалов и ручной характер продолжения после ошибки/исчерпания порции.

## Критерии приёмки — собранный черновик

- На смешанном синтетическом канале выбираются последние N обычных видео и записей трансляций в порядке источника; Shorts не занимают места в N. Порядок не вычисляется из выдуманных или приблизительных дат.
- N не превращается в N дополнительных карточек. Уже сохранённые публикации учитываются один раз, просмотренные не возвращаются; уменьшение N не удаляет прежние материалы.
- Одновременное повторное действие из двух вкладок не создаёт две операции истории. Смена N требует завершения/остановки прежней; поздний ответ прежней операции не меняет новую.
- Состояния подбора, загрузки выбранных материалов, паузы, ожидания ручного продолжения, ошибки, отмены и завершения различимы. До подтверждённого конца не показывается окончательное «доступно только X».
- Найденные ID, их метаданные, порядок и прогресс переживают перезапуск. Ручная пауза и ожидание продолжения сохраняются. Активная операция выполняется только при наличии открытой вкладки.
- Во время обработки 60 выбранных материалов счётчики обращений к спискам yt-dlp и RSS не растут из-за каждого материала. Плановое RSS-обновление проверяется отдельно. Успешно сохранённые субтитры не запрашиваются повторно.
- Ошибка одной RSS-ленты не требует отбросить успешный ответ другой; автоматической замены на смешанный RSS, возвращающей Shorts, нет. Нераспознанный или неподдерживаемый ответ показывается как ошибка, а не пустой конец источника.
- Неполные данные представлены честно: неизвестная дата отдельной группой, порядок внутри фида сохранён; отсутствующее описание не порождает запрос страницы ролика. Превью загружаются отдельно и не считаются частью стоимости перечисления.
- Распознанные анонсы/идущие эфиры пропускаются; отдельно проверен согласованный сценарий неизвестного статуса и последующего распознавания анонса текущим сборщиком.
- Достигнутый конец с X меньше N, временная ошибка, цикл continuation и исчерпание порции не смешиваются. Восстановление позиции не застревает в бесконечном перечитывании одной порции; подробный критерий зависит от ответа 16.
- Старые фиды не начинают массовую догрузку сами после обновления Око. Режим даты остаётся ограниченным RSS, уже сохранённые Shorts остаются до просмотра.
- Поведение проверяется через HTTP interface читателя с временным Store и синтетическим внешним транспортом; формы, прогресс, пауза и повторное действие — настоящим браузером. Реальные подписки для автоматических проверок не используются.

## Фактическая проверка двух типов, 2026-10-13

Проверен публичный официальный канал YouTube `UCBR8-60-B28hp2BmDPdntcQ`. yt-dlp 2026.08.19; три GET плейлистов (UULF/UULV/UU) и два GET соответствующих RSS UULF/UULV, всего пять, все HTTP 200. Запросы роликов, субтитров и медиа запрещены исследовательским скриптом; повторы отключены. Пользовательские подписки не изменялись.

- UULF: выбраны первые 20 обычных видео. RSS вернул первые 15 с точно совпавшими ID и порядком.
- UULV: семь записей, у всех flat-метаданные `live_status=was_live`. RSS вернул те же семь ID в том же порядке.
- UU: первые 20 элементов общего списка содержали только два ID из проверенного списка обычных видео, на позициях 6 и 18, и ни одного из семи ID трансляций. Это подтверждает необходимость порционного обхода общего порядка.
- Точных дат flat-списки не содержат; в RSS даты есть. Общий порядок всей истории по датам двух flat-списков не восстанавливается.
- В RSS трансляций нет явного признака завершения. Успех на завершённых записях не доказывает автоматическое исключение текущих и будущих эфиров для любых каналов.

Результат подтверждает доступность двух RSS и плейлистов на одном канале. Достоверность полного объединения последних N, восстановление порций и поведение при изменении списка ещё не проверены. Исследовательские результаты: `/tmp/oko-ytdlp-mixed-results.json`, `/tmp/oko-ytdlp-mixed-raw.json`; код Око не менялся.

## Ответ на вопрос о возможностях yt-dlp

По [документации yt-dlp](https://github.com/yt-dlp/yt-dlp#subtitle-options), `--write-subs` и `--write-auto-subs` поддерживают обычные и автоматические субтитры, `--sub-langs` позволяет ограничивать языки. `--skip-download` позволяет сохранять субтитры без видеофайла; режим flat для перечисления истории сам субтитры не получает. Для них требуются отдельные обращения по конкретным видео.

Получение субтитров не гарантировано: [официальная инструкция проекта](https://github.com/yt-dlp/yt-dlp/wiki/PO-Token-Guide) описывает дополнительные токены для субтитров некоторых клиентов YouTube. Нет измерений, подтверждающих меньший расход запросов или меньше блокировок по сравнению с нынешним сборщиком. В рамках проектирования реальные субтитры не запрашивались.
