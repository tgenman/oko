# Проверки разработки

Единая команда (macOS/Linux, Python 3.11+ для runner):

```sh
./scripts/check ui
./scripts/check all
./scripts/check python types
./scripts/check http
./scripts/check browser
./scripts/check lint
./scripts/check browser --files tests/browser/test_material_list.cjs tests/browser/test_reader_http.cjs
./scripts/check python --files tests/development/test_hooks.py
```

[Runner](../../scripts/check) — источник состава режимов. Он обнаруживает актуальные JavaScript-модули и браузерные сценарии, печатает результаты и время, возвращает ненулевой код при падении, отсутствующей зависимости или прерывании. При прерывании завершает принадлежащие ему дочерние процессы. Проверка diff охватывает staged и unstaged изменения; успешная проверка не означает чистое рабочее дерево.

`ui` включает синтаксис, ESLint `no-undef`, HTTP-проверку выдачи всего графа JavaScript настоящим сервером, браузер и diff. `all` добавляет весь Python-набор, типизацию и CLI. Отдельно доступны `syntax`, `lint`, `http`, `browser`, `python`, `types`, `diff`, `entrypoint`, `staged`; можно указать несколько, повторы выполняются один раз. `python`, `types` и `http` не требуют Node/Playwright. `syntax` и `lint` не требуют браузера. После локального исправления повторяйте затронутый набор; полный прогон нужен перед push и в CI.

`--files` идёт после выбранных наборов и задаёт существующие файлы внутри checkout. Для Python поддерживается также `файл.py::имя_теста`. Каждый файл должен соответствовать хотя бы одному выбранному набору; несуществующий путь, путь вне checkout и неподходящий тип завершаются ошибкой до запуска. Повторные пути выполняются один раз. Наборы без подходящих указанных файлов сохраняют полный объём; например, `python types --files tests/development/test_hooks.py` ограничивает pytest, но выполняет всю типизацию. `ui --files tests/browser/test_material_list.cjs` проверяет выбранный JS-файл и браузерный сценарий, HTTP и diff остаются полными. Hooks и CI запускают обязательные команды без `--files`.

## Обязательные проверки

Для нового checkout выполните `./scripts/install-hooks`. Скрипт включает локальный `core.hooksPath=.githooks` и сохраняет чужую настройку hooks, завершаясь с ошибкой при конфликте.

- `pre-commit` вызывает `check staged`: проверяет whitespace, синтаксис Python/JavaScript и `no-undef` именно из индекса, в том числе при частичном staging. Зависимости приложения и браузер для этой проверки не нужны; для staged JavaScript нужны Node и установленные через `npm ci` зависимости линтера.
- `pre-push` вызывает `check all`; ошибка блокирует push.
- GitHub Actions запускает `check all` на push и pull request с Python 3.11, Node 22 и Chromium. Установку зависимостей выполняют отдельные шаги CI; runner их не устанавливает. После подключения remote настройте `Full checks` как required check в правилах защищённой ветки, если нужна серверная блокировка merge.

## Подготовка окружения

Один раз установите Python-зависимости по [README](../../README.md), включая extra `dev`. Поддерживаемые версии Node заданы в `engines` корневого package.json. Браузерные зависимости и ESLint закреплены в package.json и lock-файле:

```sh
npm ci
```

Используйте установленный Chrome/Chromium либо отдельно установите браузер Playwright:

```sh
npx playwright install chromium
```

Эти команды выполняет разработчик при настройке. Сам runner ничего не устанавливает и не скачивает.

| Переменная | Назначение | По умолчанию |
| --- | --- | --- |
| `OKO_NODE` | Исполняемый файл Node | `node` из PATH |
| `OKO_PYTHON` | Python с зависимостями проекта, для полного режима | `.venv/bin/python` checkout, иначе `python3` из PATH |
| `NODE_PATH` | Каталог внешних Node-пакетов, если нет локального node_modules | Стандартный поиск Node |
| `OKO_BROWSER_EXECUTABLE` | Исполняемый файл Chrome/Chromium | Установленный браузер Playwright, затем стандартные пути Chrome/Chromium macOS/Linux |

Для worktree без своего virtualenv задайте `OKO_PYTHON` путём к существующему окружению. В Codex runtime и пакеты можно найти через `load_workspace_dependencies`; персональные пути в репозиторий не копируются. Для sandbox нужны разрешения на loopback, запуск браузера и чтение дерева процессов через POSIX `ps` (для завершения потомков, в том числе отдельных групп браузера).

## Граница браузерных тестов

Сценарии открывают настоящий HTML/JavaScript Око в headless Chrome, проверяют DOM, воспроизведение и освобождение URL медиа. Подменяется только внешний транспорт. Задержанный транспорт намеренно игнорирует AbortSignal: поздний ответ должен быть безопасен независимо от отмены.

Каждый сценарий использует временный loopback HTTP-сервер и отдельный профиль браузера; личные источники и AI не вызываются. Canvas WebM проверяет воспроизведение без внешнего файла. Настоящие RSS, Telegram, YouTube и подключения моделей этими тестами не проверяются.

`test_reader_http.cjs` отдельно запускает production-приложение через uvicorn и временное хранилище. Браузер получает настоящие `/api/cards`, `/api/navigation`, локальные картинки и ответы действий. Подменены только внешние RSS и обработчик модели на сервере; browser fetch не заменяется. Сценарий проверяет папку, оба участвующих фида и пустой фид, объединение события с сохранением всех источников, счётчики и удаление просмотренного. Runner передаёт выбранный Python через `OKO_PYTHON`; при прямом запуске файла используется `OKO_PYTHON`, существующий `.venv/bin/python` или `python3`. Сервер, браузер и временное хранилище очищаются при завершении и отмене.

Отдельный файл можно запустить через `node --test tests/browser/test_opened_material.cjs` с тем же окружением. Для прямого запуска без runner явно задайте `OKO_BROWSER_EXECUTABLE`, если Chrome находится не в стандартном macOS-пути.
