# Проверки разработки

Все сценарии с хранилищем используют PostgreSQL. Перед запуском задайте
`OKO_TEST_POSTGRES_URL` для отдельной синтетической базы; без неё storage-проверки
завершаются ошибкой. Каждый сценарий получает собственную схему, включая браузер.
Подготовка: [PostgreSQL](../../docs/development/postgresql.md).


Единая команда (macOS/Linux, Python 3.11+ для runner):

```sh
./scripts/check ui
./scripts/check all --compact
./scripts/check python types
./scripts/check http
./scripts/check browser
./scripts/check node
./scripts/check lint
./scripts/check browser --files tests/browser/test_material_list.ts tests/browser/test_reader_http.ts
./scripts/check tools --files tests/development/test_hooks.py
```

Полный локальный `all` использует снимок, новые исходники сначала добавляются в
индекс. Флаг `--compact` сокращает только консоль, полный лог сохраняется.
Обновление checkout и чтение сводки report.json:
[процесс проверок](../../docs/development/check-workflow.md).


[Runner](../../scripts/check) — источник состава режимов. Он обнаруживает актуальные JavaScript-модули и браузерные сценарии, печатает результаты и время, возвращает ненулевой код при падении, отсутствующей зависимости или прерывании. При прерывании завершает принадлежащие ему дочерние процессы. Проверка diff охватывает staged и unstaged изменения; успешная проверка не означает чистое рабочее дерево.

`ui` включает синтаксис, ESLint `no-undef`, HTTP-проверку выдачи всего графа JavaScript настоящим сервером, браузер и diff. `all` добавляет Python-тесты приложения, типизацию и CLI; тесты инструментов добавляются автоматически при изменении их входов. Отдельно доступны `syntax`, `lint`, `http`, `browser`, `python`, `tools`, `types`, `diff`, `entrypoint`, `staged`; можно указать несколько, повторы выполняются один раз. `python`, `types` и `http` не требуют Node/Playwright. `syntax` и `lint` не требуют браузера. После локального исправления повторяйте затронутый файл или сценарий. `ui` и `all` — широкая приёмка, не обязательный шаг каждой локальной итерации; CI выполняет свои группы проверок.

`--files` идёт после выбранных наборов и задаёт существующие файлы внутри checkout. Для Python поддерживается также `файл.py::имя_теста`. Каждый файл должен соответствовать хотя бы одному выбранному набору; несуществующий путь, путь вне checkout и неподходящий тип завершаются ошибкой до запуска. Повторные пути выполняются один раз. Наборы без подходящих указанных файлов сохраняют полный объём; например, `python types --files tests/development/test_hooks.py` ограничивает pytest, но выполняет всю типизацию. `ui --files tests/browser/test_material_list.ts` проверяет выбранный TS-файл и браузерный сценарий, HTTP и diff остаются полными. Ручная проверка `staged` и CI используют свои обязательные наборы; commit и push проверки не запускают.

## Проверка переходов и поздних ответов

При изменении меню, формы или редактора запускайте короткий набор:

```sh
./scripts/check lifecycle
./scripts/check lifecycle --match 'a completed field write'
./scripts/check browser --match 'late.*draft' --files tests/browser/test_ui_lifecycle.ts
```

`lifecycle` выполняет синтаксис, lint, пять браузерных регрессий и diff. Эти же сценарии входят в обычные `browser`, `ui` и CI через `all`; дублировать их в других файлах не требуется. Набор использует существующий HTTP-интерфейс читателя с временным хранилищем и синтетическими подключениями.

| Порядок событий | Наблюдаемый результат |
| --- | --- |
| Сохранить → новый ввод → назад → ответ | Записанное значение обновилось, новый черновик остался, фокус сохранён |
| Сохранить → ответ → назад | Фокус вернулся на актуальную ссылку поля/раздела |
| Загрузить подключение → назад → ответ | Форма прежней страницы не появилась на текущей |
| Загрузить каталог → уйти → вернуться | Прерванная загрузка возобновилась, старый ответ не заменил новый |
| Сохранить подключение → новый ввод → закрыть → ответ → открыть | Новый ввод сохранён, закрытый диалог не открылся поздним ответом |

Новая форма дополняет свой браузерный набор применимыми порядками из таблицы. Проверяйте состояние через видимые значения, черновик, фокус и навигацию; не через внутренние счётчики операций.

`--match` — регулярное выражение по имени браузерного сценария; оно требует браузерного набора и сохраняется в JSON-отчёте. Если ни один сценарий не прошёл из-за отсутствия совпадений, команда завершается ошибкой, а не объявляет успех. Обычные действия общих browser contexts имеют таймаут 5 секунд, навигация — 10 секунд. Долгая обработка задаёт явное ожидание в конкретном сценарии. Если выбранные syntax/lint падают, браузер не запускается; остальные независимые результаты сохраняются.

## Артефакты и контроль checkout

Runner перед каждым браузерным и Python-тестовым набором создаёт каталог `artifacts/<набор>` внутри отчёта и передаёт его через `OKO_TEST_ARTIFACT_DIR`. Для снимков браузера используйте `artifactPath('имя.png')` из общего `artifacts.ts`: файл попадёт в подкаталог текущего процесса, чтобы параллельные файлы не перезаписывали друг друга. При прямом запуске `node --require tsx/cjs --require ./scripts/register-browser-typescript.cts --test` без runner helper создаёт каталог в системном temporary directory. Старые сохранённые иллюстрации не являются выходным каталогом тестов.

Перед и после тестового набора runner сравнивает Git inventory, содержимое и режим файлов checkout, включая неигнорируемые новые файлы и символические ссылки без чтения их целей. Исходные staged/unstaged/untracked правки разрешены: сравнение выполняется с состоянием перед набором, а не с HEAD. Игнорируемые runtime-кэши и собственный каталог отчёта не считаются загрязнением. Изменения других файлов дают FAIL со списком путей и `checkout_changes` в JSON. Guard ничего не удаляет и не восстанавливает. Не редактируйте checkout параллельно с проверкой: такие изменения также попадут в сравнение.

## Отчёты запусков

Каждый запуск runner создаёт отдельный каталог в `.scratch/check-runs/` и печатает путь к `report.json`. `output.log` содержит полный вывод команд; JSON сохраняет выбранные файлы, результаты наборов, команды с кодами завершения и список падений, распознанных из pytest и TAP. Для ошибки зависимости, прерывания или команды без списка тестов смотрите статус набора и лог. Каталог исключён из Git. Через `--report-dir <каталог>` можно выбрать другое место хранения.

Повторный запуск создаёт новый отчёт и сохраняет предыдущий. Сравнивайте выбранные файлы и результаты: успешный ограниченный повтор не означает, что весь `all` прошёл. CI сохраняет отчёты как artifact `check-reports`, включая неуспешные запуски.

## Подготовка синтетических сценариев

Для приложения в Python-тестах и дочерних тестовых серверах используйте `tests.support.app.create_app`. Фабрика вызывает production assembly с синтетическими Codex, субтитрами и историей YouTube; транспорт по умолчанию запрещает все сетевые обращения, включая localhost. Внешние URL требуют явно переданного `MockTransport`; принадлежащий тесту сервер подключается через `OwnedServerTransport(origin)` с точным адресом. Переданные adapters сохраняются: тест границы CLI/worker явно создаёт `LocalCodex`/`LocalCaptions` и подменяет внешний CLI/SDK. Это не меняет продуктовые defaults и не разрешает использование пользовательских источников в тестах.

`check contracts` проверяет наследуемые сигнатуры тестовых Codex-клиентов, включая родителей из других файлов и import aliases относительно текущего `CodexClient` и применение тестовой фабрики. Он выполняется первым в `python` и `all`; `check staged` проверяет те же контракты по байтам индекса. Общий `tests/support/codex.py` и фабрика входят в строгую типизацию. Следовательно, CI запускает раннюю проверку, а ручной `check staged` проверяет staged версию без импорта тестовых сценариев.

До heartbeat явно задавайте включённую обработку, которую проверяет сценарий. `setup_reader(client, theses=...)` требует явного выбора тезисов. Помощники событий, фильтров и обзоров задают свои режимы, включая отключение несвязанных этапов. Производственные defaults проверяются отдельными HTTP-тестами без подмены defaults. Синтетические модели тезисов, фильтров, событий и обзоров отклоняют неподдерживаемую операцию с её именем, вместо ответа по чужой схеме. Смешанный сценарий явно передаёт `theses=True` модели фильтров или обзоров.

Библиотеки для бюджетов чтения строятся настоящим Store один раз на форму данных в процессе тестов. `tests.support.library_templates` хранит шаблон схемы PostgreSQL и файлов во временном каталоге и копирует их каждому сценарию; Store, файлы, metadata и клиенты сценариев независимы. Эти образы не переживают завершение процесса и не кэшируют результаты проверок. Performance-сценарии получают копию через существующий Python host; 104/400 материалов, idle/active, 320 кликов и порог p95 <200 мс сохраняются.

## Обязательные проверки

Подпроцессные проверки через `tests/support/processes.py` сохраняют объединённые stdout/stderr каждого запуска в отдельный файл `<временное хранилище>/process-logs/server-*.log`, включая повторные запуски после сбоя. Ошибка старта или ожидания готовности содержит путь, PID, exit code и последние 8 KiB вывода. Полный лог остаётся в хранилище теста на срок хранения временных каталогов pytest.

Автоматические pre-commit и pre-push hooks удалены. Commit и push не запускают локальные проверки. Оставшийся `core.hooksPath=.githooks` не запускает удалённый hook.

- Ручной `./scripts/check staged` проверяет whitespace, синтаксис Python/JavaScript и `no-undef` именно из индекса, включая частичный staging; проверки типов и generated-контракта сохраняют прежнюю строгость.
- GitHub Actions на pull request и push в `main` выполняет общую сборку, затем Python- и браузерную группы параллельно, с Python 3.11, Node 26.12.0 (из `.node-version`) и Chromium. Push в рабочую ветку без PR не запускает CI; обновление открытого PR запускает один полный набор. Установку зависимостей выполняют отдельные шаги CI; runner их не устанавливает. После подключения remote настройте `Full checks` как required check в правилах защищённой ветки, если нужна серверная блокировка merge.

## Управляемое время читателя

`tests.support.reader.Clock.options()` возвращает пару `clock` / `wall_clock`:
`create_app(..., **clock.options())`. Используйте её, когда время сессии должно
меняться только действием теста. Увеличение `clock.now` двигает оба времени;
сценарии проверки различий часов по-прежнему передают их независимо.

## Подготовка окружения

Для нового worktree с установленными в основном checkout зависимостями используйте
[prepare-worktree](../../docs/development/check-workflow.md#подготовка-нового-worktree).

Исходные HTML, CSS и браузерные modules находятся в корневом `frontend/`; настоящим сервером читателя выдаётся готовая сборка Vite. Отдельный frontend server для запуска не нужен. `check syntax` и линтер рекурсивно находят JavaScript в этом каталоге; staged-проверки проверяют выбранные файлы по байтам индекса независимо от вложенности.

Проверки маршрута субтитров используют настоящий SDK и локальный HTTP/CONNECT-прокси. Для временного тестового TLS-сертификата нужен `openssl` в PATH. Сертификаты и ключи создаются во временном каталоге; внешние сетевые соединения запрещены тестовым окружением worker. Настоящий YouTube и платный прокси не вызываются.

Один раз установите Python-зависимости по [README](../../README.md), через `uv sync --locked` (группа разработки устанавливается по умолчанию). Для разработки используется Node.js 26.12.0 из `.node-version`; совместимые обновления ветки 26 заданы в `engines` корневого package.json. Браузерные зависимости и ESLint закреплены в package.json и lock-файле:

```sh
npm ci
```

Используйте установленный Chrome/Chromium либо отдельно установите браузер Playwright:

```sh
npx playwright install chromium
```

Эти команды выполняет разработчик при настройке. Сам runner ничего не устанавливает и не скачивает.

| Переменная | Назначение | По умолчанию |
| --- | --- | --- |
| `OKO_NODE` | Исполняемый файл Node | `node` из PATH |
| `OKO_PYTHON` | Python с зависимостями проекта, для полного режима | `.venv/bin/python` checkout, иначе `python3` из PATH |
| `NODE_PATH` | Каталог внешних Node-пакетов, если нет локального node_modules | Стандартный поиск Node |
| `OKO_BROWSER_EXECUTABLE` | Исполняемый файл Chrome/Chromium | Установленный браузер Playwright, затем стандартные пути Chrome/Chromium macOS/Linux |

Для worktree без своего virtualenv задайте `OKO_PYTHON` путём к существующему окружению. В Codex runtime и пакеты можно найти через `load_workspace_dependencies`; персональные пути в репозиторий не копируются. Для sandbox нужны разрешения на loopback, запуск браузера и чтение дерева процессов через POSIX `ps` (для завершения потомков, в том числе отдельных групп браузера).

## Граница браузерных тестов

Сценарии открывают HTML/JavaScript production-приложения в headless Chrome, проверяют DOM, воспроизведение и освобождение URL медиа. `reader()` использует тот же HTTP-сервер и очистку, что и `productionReader()`: свою временную схему PostgreSQL и файлы и синтетические внешние adapters для каждого сценария. Файлы UI и журнал диагностики обслуживает настоящий сервер.

В UI-сценариях `readerTransport.replies` задаёт статические снимки ответов: точный `METHOD /path?query`, URL либо общий pathname. Ответ с `next: [[route, reply]]` явно задаёт следующий снимок после конкретного запроса. Helper не вычисляет навигацию из подписок, membership карточек, удаление просмотренного или группы ошибок. Сценарий задаёт ожидаемые ответы для выбранных областей сам; стартовый снимок содержит одну папку `f` и один фид `feed` и не выводит их из материалов. Нет подмены ответа — запрос получает настоящий сервер. Задержанный транспорт намеренно игнорирует AbortSignal: поздний ответ должен быть безопасен независимо от отмены.

Это UI-проверки со снимками ответов, а не сквозная проверка всех правил сервера. Правила membership, группировки и viewed проверяет `test_reader_http.ts` без подмены browser fetch; журнал проверяется через настоящий `/api/v3/diagnostics`, включая повтор доставки и очистку.

Runner запускает не более двух тестовых файлов одновременно. В каждом файловом процессе Chromium переиспользуется до завершения файла; каждый сценарий получает новый изолированный browser context (cookies, storage, страницы) и временный loopback HTTP-сервер.

Python-процесс также переиспользуется в пределах файла: повторные сценарии не импортируют зависимости заново. Каждый HTTP-сценарий получает новое приложение, Runtime, adapters, схему PostgreSQL и каталог файлов, порт и токен; uvicorn работает в отдельном потоке со своим asyncio loop, чтобы обработчик фоновых ошибок не попадал в чужой журнал. Ответ о готовности отправляется после startup/lifespan uvicorn. Закрытие сценария закрывает context, завершает lifespan сервера и удаляет каталог; отмена не останавливает соседний сценарий. EOF или SIGTERM управляющего процесса закрывает оставшиеся серверы, ошибка запуска завершает host с ошибкой. Chromium и Python-процесс закрываются в завершающих hooks файла.

Личные источники и AI не вызываются. Canvas WebM проверяет воспроизведение без внешнего файла. Настоящие RSS, Telegram, YouTube и подключения моделей этими тестами не проверяются.

`test_reader_http.ts` использует ту же изолированную сборку production-приложения через uvicorn и временное хранилище. Браузер получает настоящие `/api/v3/cards`, `/api/v3/reading-composition`, локальные картинки и ответы действий. Подменены только внешние RSS и обработчик модели на сервере; browser fetch не заменяется. Сценарий проверяет папку, оба участвующих фида и пустой фид, сохранённые публикации и тезисы, счётчики и удаление просмотренного. Runner передаёт выбранный Python через `OKO_PYTHON`; при прямом запуске файла используется `OKO_PYTHON`, существующий `.venv/bin/python` или `python3`. Сервер, браузер и временное хранилище очищаются при завершении и отмене.

Отдельный файл можно запустить через `node --require tsx/cjs --require ./scripts/register-browser-typescript.cts --test tests/browser/test_opened_material.ts` с тем же окружением. Для прямого запуска без runner явно задайте `OKO_BROWSER_EXECUTABLE`, если Chrome находится не в стандартном macOS-пути.

Матрицы `test_settings_owner.ts` проверяют публичные операции MenusOwner через настоящий generated SDK и управляемый Fetch adapter в Node. Они не создают DOM, browser context или HTTP-сервер. Save/reset, новые и ABA-черновики, соседние поля и объекты проверяются здесь; реальные открытия редактора, focus/navigation, HTTP save/reset и очистка ошибки остаются в Playwright-сценариях.

## Контракты ответов читателя

Настоящий сервер проверяет основные ответы через строгие wire types. Поддержка браузерных сценариев читает JSON Schema из generated OpenAPI и проверяет успешные снимки карточек, навигации, открытого материала, версий и статуса через закреплённый Ajv. Задержанный ответ проверяется при доставке; нарушение схемы проваливает сценарий даже если UI отбросил ответ как устаревший. Фикстуры задают валидные данные явно и не получают исправляющих defaults из валидатора. Неверный тип и пропущенное обязательное поле проверяются отдельным отрицательным сценарием.

Локальный экспорт без запуска читателя: `python -m oko.reader.contracts`. Режим `check http` включает проверки контрактов, выдачи графа modules, статики и запуска из другого рабочего каталога. В `all` входят также проверка снимков в браузере, Python-набор и строгая типизация.

## Снимок панели для показа результата

`test_status_panel.ts` сохраняет готовую панель на широком и мобильном экране через общий `artifactPath`. Выполнить десктопный сценарий:

```sh
node --require tsx/cjs --require ./scripts/register-browser-typescript.cts --test --test-name-pattern='missing model opens' tests/browser/test_status_panel.ts
```

Путь `status-panel-desktop.png` печатается в выводе. При прямом запуске используется временный каталог либо `OKO_TEST_ARTIFACT_DIR/<pid>/`, если переменная задана. При запуске через runner снимки сохраняются в `artifacts/browser/<pid>/` соответствующего отчёта. Для показа результата используйте эти снимки из уже выполненной проверки; отдельный dev-server или Computer Use не требуется.

Если выбран набор `types` вместе с браузерными или Python-тестами, типизация запускается до них. Её отказ оставляет тяжёлые наборы `NOT RUN`; остальные выбранные результаты сохраняются. В `all` типизация включена по умолчанию.

## Сборка интерфейса

Перед запуском из checkout выполните `npm ci` и `npm run build`. `npm run typecheck` отдельно проверяет TypeScript в strict-режиме; Браузерные тесты и их поддержка также проверяются в strict-режиме через `tsconfig.browser-tests.json`. `npm run dev` следит за исходниками и публикует новые production assets; читатель продолжает работать на Python origin, без отдельного Vite server и ослабления CSP.

`check ui`, `check lifecycle` и `check all` включают набор `build`: typecheck, сборку и проверку актуальности. Сборка пишет только в игнорируемый `oko/frontend_build/`. HTML и JS/CSS получают согласованные адреса с хешами; watch атомарно меняет указатель поколения и сохраняет старые assets для уже открытых вкладок. Неудачная сборка не публикуется. Обычный `python -m oko` не запускает npm или генераторы: отсутствующая, устаревшая или повреждённая сборка останавливает запуск до создания Runtime и хранилища.

## React / API-first

Полный контракт: api/openapi.yaml. Команды api:lint, api:generate, api:check и standalone api:docs описаны в [API README](../../api/README.md). Generated libs проверяются без записи в checkout. Swagger browser-проверки и проверки wheel удалены; источники и модели в оставшихся сценариях только синтетические. Историческое описание TypedDict wire export выше относится к версии до React-переноса.

## TypeScript в браузерных тестах

Все сценарии и общая поддержка находятся в `tests/browser/*.ts`. Runner автоматически выполняет `browser-types` перед запуском выбранных сценариев; ошибка типов оставляет браузерный набор `NOT RUN`. `npm run typecheck` проверяет фронтенд, тесты и инструменты; `npm run typecheck:browser` — только тесты. CI получает эти проверки через `check all`. Pre-commit проверяет синтаксис и типы точного индекса, включая импортируемые помощники, независимо от незакоммиченных исправлений.

Прямой запуск: `node --require tsx/cjs --require ./scripts/register-browser-typescript.cts --enable-source-maps --test --test-reporter=tap tests/browser/test_opened_material.ts`. Preload использует закреплённый TypeScript и сохраняет динамические `import()` внутри функций, которые Playwright отправляет браузеру. Перед прямым запуском выполните `npm run typecheck:browser`; runner делает это автоматически. Runner явно выбирает TAP, чтобы разбор падений и числа прошедших сценариев не зависел от формата отчёта Node по умолчанию.

Фикстуры используют DTO сгенерированного OpenAPI. Подмена транспорта принимает `unknown`, чтобы отрицательные тесты могли отправлять неверные данные; успешные снимки дополнительно проверяются JSON Schema при доставке. Non-null assertions в сценариях сохраняют прежнее требование наличия элемента/запроса после ожидания Playwright и не отключают проверку типов полей.

## TypeScript в инструментах

Конфигурации Vite/ESLint и Node-инструменты также написаны на TypeScript. `.mts` сохраняет ES modules сборки и генерации с top-level await; `.cts` сохраняет CommonJS-интерфейс preload и проверок. Корневой тип модулей приложения остаётся прежним.

Команды npm и runner загружают инструменты через закреплённый `tsx`; ESLint читает `eslint.config.ts` через закреплённый `jiti`. Для Playwright сначала загружается `tsx/cjs`, затем `register-browser-typescript.cts`: последний компилирует тестовые функции штатным TypeScript, сохраняя браузерный `import()`.

`npm run typecheck:tooling` проверяет `tsconfig.tooling.json` в strict-режиме. Runner включает `tooling-types` перед сборкой, синтаксисом, линтером и браузером; ошибка останавливает зависимые тяжёлые проверки. Pre-commit проверяет `.ts`, `.tsx`, `.cts`, `.mts` и обе конфигурации тестов/инструментов по точным байтам индекса. Линтер применяет прежний `no-undef` к исполняемому представлению после стирания типов; исходные типы отдельно проверяет TypeScript. Производные JS-файлы для инструментов в checkout не создаются.

## Быстрый повторный цикл

Начинайте с затронутого файла: `./scripts/check browser --files tests/browser/test_material_list.ts`
или `./scripts/check python --files tests/reader/test_http_contracts.py`. После изменения фронтенда
сначала выполните `npm run build`; `npm run dev` публикует готовые поколения при редактировании.
`ui` и `all` по-прежнему включают сборку, но не входят в каждую локальную итерацию.
Завершение ограниченной задачи подтверждают затронутые сценарии и проверки её границ.
Полный набор выбирайте отдельно для широкого изменения; не повторяйте его ради формальности.

Синтаксис TypeScript проверяется одним процессом для всех выбранных файлов. Pre-commit также
передаёт все выбранные TypeScript-файлы из Git index одним пакетом; исправления рабочей копии
не скрывают ошибку в индексе. TypeScript сохраняет incremental state в `.scratch/check-cache/types/`.
В `all` четыре HTTP-модуля выполняются в наборе `http`, а из последующего полного pytest
исключаются только эти модули. Самостоятельный `python` и явный `--files` сохраняют свой выбор.

Успешные проверки API и сборки сохраняют локальные записи в игнорируемом `.scratch/check-cache/`.
Повторное использование требует тех же байтов входов, состава generated-файлов, версий инструментов
и влияющего окружения (служебные npm/runner/shell поля исключены). Проверяются добавления и удаления, не только даты изменения. Ключ API включает baseline,
генераторы и шаблоны.
Сбой не сохраняется. Отсутствующий или повреждённый кэш вызывает обычную проверку.

Сборка связывает manifest с ключом проверенных входов и проверяет целостность текущего поколения,
включая полный список assets. Изменение окружения или инструментов не позволяет принять assets
от другой сборки. При пересборке сохраняются атомарная публикация и старые поколения для открытых
вкладок. Кэш не участвует в обычном запуске читателя.

`npm run api:check -- --fresh` принудительно повторяет генерацию и сравнение обеих библиотек,
когда присутствует переходная библиотека. Проверки индекса выполняются в новом временном каталоге
и не используют результаты рабочей копии. CI начинает с `--fresh`, затем проверяет типы, синтаксис,
линтер и сборку; Python (включая HTTP) и браузер выполняются параллельно над одной сборкой assets.
Перед использованием скачанных assets проверяются их хеши и соответствие исходникам.
CI кэширует загруженные пакеты uv по версии инструмента и lock-файлам; `uv sync --locked` выполняется
при каждом запуске. Результаты тестов не кэшируются; итоговый `Full checks` требует успеха всех групп.


### Цена и назначение тестов

- `tests/reader/test_frontend_build.py` проверяет отказ запуска с отсутствующими, устаревшими
  и повреждёнными assets без запуска сборщика. Сборка/watch проверяются отдельно в
  `tests/development/test_frontend_builder.py` на маленьком приложении.
- Валидация API, generated drift и Git index используют маленький контракт в
  `tests/support/build_tools.py`; полный контракт продукта проверяется на настоящих HTTP-ответах.
- Повреждения manifest, смена ключа сборки и матрица cache inputs проверяются одним Node-процессом;
  эти варианты не требуют многократной production-сборки.
- Упаковка wheel и Swagger UI не входят в регрессионный набор.
- Историческая галерея поверхностей не входит в `browser`, `ui` и `all`.
  Для сознательной визуальной проверки запустите
  `node --require tsx/cjs --require ./scripts/register-browser-typescript.cts --test tests/browser/visual_reader_surfaces.ts`
  и просмотрите её скриншоты. Это инструмент визуальной проверки, а не ежедневная регрессия.
- Тесты реальной остановки процесса, удаления, восстановления после сбоя и поздних ответов
  сохраняются: их стоимость оправдана предотвращением потери данных. Выбирайте их при изменении
  соответствующего поведения, а не после каждой правки CSS.

## Выбор тестов инструментов и параллельный запуск

`./scripts/check python` проверяет приложение. `./scripts/check tools` явно запускает
инструментальные тесты; `tools --files ...` выбирает конкретный файл. `all` автоматически
добавляет `tool-tests`, когда затронуты scripts, hooks, CI, контракты/генерация, зависимости,
конфигурации компиляции или соответствующие тесты и их поддержка. Явный `--files` сохраняет
свой выбор. Точный список файлов и входов находится в `TOOL_TESTS`/`TOOL_INPUTS` runner.
Проверки installed runtime, синтетического окружения и ограничений adapters остаются
в обычном Python-наборе, хотя исторически лежат в `tests/development`.

По умолчанию база — merge-base HEAD с origin/main. Учитываются коммиты ветки, индекс,
рабочие файлы, удаления, переносы и новые неигнорируемые файлы. `--base <revision>` задаёт
базу явно; неизвестная база включает tools, а не скрывает проверки. JSON содержит
`tool_selection` с причиной выбора. В CI отдельная matrix-группа выполняет
`tools --if-changed --base <PR base SHA или push before SHA>`; она обязательна для итогового
результата и явно сообщает, если инструментальных изменений нет.

Генерация API, typecheck и сборка завершаются до тестов. После этого `browser`, `node-tests`,
`python-tests` и выбранный `tool-tests` исполняются параллельно в отдельных процессах.
Время групп пересекается и не суммируется во время полного прогона. Каждая группа владеет
своим логом `parallel/<группа>/<запуск>/output.log` и artifacts; итоговый report объединяет
все исходы. Падение одной группы не скрывает результаты остальных. Прерывание останавливает
workers и их дочерние процессы. Общий guard проверяет checkout до и после параллельной
фазы; обнаруженные изменения делают её группы неуспешными без отката файлов.


### Повторные проверки и ограниченная параллельность

Отдельный Python-набор разделяется максимум на четыре непустых набора файлов.
Python сохраняет четыре workers и при одновременном запуске browser или tools; tools — два.
Каждый выбранный файл выполняется один раз. В полном прогоне вместе с browser это
не более восьми владельцев тестовых групп (включая короткую Node-группу). Отчёты и artifacts каждого Python worker находятся
в `parallel/python-tests-1` … `parallel/python-tests-4` и соответствующих каталогах tools.
Общий результат требует успеха всех workers; SIGINT завершает их дочерние процессы.
По умолчанию выполняются восемь браузерных файлов на машинах с 12 и более
логическими CPU, четыре — на остальных (в том числе когда число CPU неизвестно).
`--browser-workers 2` или `4` снижает параллельность на ограниченной машине;
`--browser-workers 8` явно выбирает верхнюю границу.
Каждый сценарий по-прежнему получает собственный browser context, HTTP-приложение и хранилище.
Запуск HTTP-приложения и browser context выполняется параллельно; cleanup дожидается
обоих ресурсов, в том числе при ошибке запуска или отмене.

Ручной `./scripts/check staged` проверяет точные bytes Git index, включая частичный staging. Проверка
контрактов Python запускается при изменении Python-тестов, Codex-контракта или checker.
TypeScript выбирает затронутые проекты по импортам staged исходников; изменения
JSON/config и удалений проверяются консервативно. Успешная staged-проверка сохраняет receipt
в `.scratch/check-cache/staged`: ключ включает весь индекс, HEAD, фактические
проверяющие скрипты, окружение и установленные версии инструментов. Ошибки не кэшируются.
Рабочая копия не подменяет staged исходники. `git diff --cached --check` выполняется
даже при попадании в кэш. Документационный коммит не запускает языковые проверки.

Runner и frontend builder разделяют receipt успешной типизации по bytes исходников,
конфигов (включая extends) и инструментов. API cache не учитывает служебные маркеры
`PYTEST_CURRENT_TEST`/`PYTEST_VERSION`; версии Python-пакетов по-прежнему входят в ключ.
В CI необходимость tools определяется до установки зависимостей. Ошибка определения
не превращается в пропуск; browser types проверяются в browser job, а не дважды.

### Быстрые браузерные проверки

Валидатор синтетических ответов читает generated OpenAPI JSON напрямую и компилирует
только используемые схемы. Импорт Python для каждого браузерного файла не требуется;
проверки ссылок, обязательных полей и форматов остаются в Ajv 2020-12.
В polling-сценариях дерева, previews и журнала используется Playwright clock.
После перевода времени тест ждёт наблюдаемое изменение ответа в DOM, затем проверяет
сохранение фокуса или отсутствие повторной загрузки картинки. Сам факт запуска запроса
не считается доказательством завершившегося обновления.

Проверка `test_reading_performance_http.ts` обязательна в полном `browser`, `ui`
и `all`. Локальный runner запускает её отдельной командой после остальных
браузерных файлов. В CI ей выделена отдельная VM (`latency checks`), поэтому
она может идти параллельно функциональным шардам. Бюджет p95 <200 мс относится к свободному стенду, а не к конкуренции
нескольких браузерных наборов за CPU. Порог не меняется. Явный `--files`
по-прежнему ограничивает выбранные сценарии.


## Готовность и скорость synthetic-сценариев

`productionReader().openReader()` открывает страницу и ждёт подтверждённой
регистрации браузерной сессии (либо explicit lifetime). Используйте его перед
прямыми HTTP-командами, требующими открытого читателя: завершение `page.goto`
само по себе presence не подтверждает.

Обычные функциональные Telegram web-сценарии явно вызывают
`tests.support.telegram.configure_fast_web(client)` только для временного
тестового хранилища. Helper задаёт существующую настройку `telegram_http_rps=10`
через HTTP. Проверки бюджета, backoff/FloodWait, отмены и настроек лимита задают
свои параметры; production default и рабочее хранилище этот helper не меняет.


### Уровень проверки и стоимость сценария

Матрицы форматов и большие границы проверяются у владельца правила. Например,
RSSSource с MockTransport проходит все 1000 страниц, включая redirect в другую
ветку, и выбирает 200 публикаций. Короткий HTTP-сценарий проверяет сохранение
статуса и возобновление настоящего курсора с диска на 999-й странице; другой
загружает шесть статей через redirect, пустую страницу и архив. Лимиты продукта
и сохранность данных не заменяются test-only параметрами.

Браузер нужен для действий, DOM, фокуса, поздних ответов и измерения видимой
задержки. Benchmark по-прежнему открывает 40 разных материалов дважды для каждой
из четырёх библиотек, но ждёт сигнал DOM observer через animation frame вместо
100ms polling между измерениями. Порог p95 <200ms и реальный click сохраняются.

Чистые контракты SDK/fetch (`tests/node/test_transport_contract.ts`), матрица
настроек и валидация fixtures расположены в `tests/node` и запускаются `check node` без
браузера и reader: binary bytes/headers, авторизация, JSON, keepalive и все шесть
ошибочных ответов. Они входят в `ui`/`all` и отдельную Node job CI. `check browser` запускает только Playwright.
`test_transport.ts` сохраняет браузерные pagehide/pageshow и отображение ошибки
с повтором diagnostics для той же occurrence.


### Общий Chromium, независимые сценарии

Runner запускает каждую браузерную команду через `scripts/run-browser-tests.cts`.
Этот процесс владеет одним Chromium; каждый тестовый файл подключается независимо,
каждый сценарий создаёт новый browser context, HTTP-приложение и хранилище.
Закрытие Browser у подключённого файла закрывает его соединение и contexts,
не Chromium соседних файлов. Успех, ошибка или прерывание команды завершают
Chromium владельца; сигнал при запуске учитывается до запуска тестовых файлов.

Внутренний `OKO_TEST_BROWSER_WS` передаётся только дочерним файлам. Прямой запуск
через node --test без runner сохраняет прежний собственный Chromium на файл.
Performance идёт отдельной командой с отдельным Chromium после обычных файлов.
`test_browser_suite.ts` проверяет изоляцию соединений, exit codes и отсутствие
оставшихся процессов после success/failure/SIGINT.

Большая записанная Telegram-страница проверяется parser без загрузки посторонних
медиа; короткий HTTP-сценарий сохраняет исходный альбом из девяти видео.
При подготовке API используется CSafeLoader при наличии libyaml, иначе SafeLoader;
проверки контракта, примеров и generated drift сохраняются.
Подробности измерений и ограничений: [отчёт](../../docs/verification/test-fixture-cost-20261021.md).

## Повторная подготовка в одном прогоне

Runner создаёт отдельный временный каталог `OKO_TEST_LIBRARY_DIR` для одного
запуска и удаляет его после завершения дочерних наборов. Закрытая синтетическая
библиотека публикуется под файловой блокировкой только после успешного builder;
каждый сценарий получает обычную независимую копию файлов и metadata. Открытые
Store, соединения, Runtime и результаты проверок не переиспользуются. Между
прогонами шаблоны не сохраняются; прямой запуск без runner использует временные
шаблоны своего процесса.

Браузерный wrapper распределяет файлы между прежним числом worker-процессов
по размеру исходников. В worker файлы регистрируют сценарии последовательно;
переиспользуются модули, подключение к suite browser и Python import host.
Сценарий по-прежнему владеет отдельными context, токеном, HTTP origin, Store,
Runtime и очисткой. Hooks общих владельцев выполняются в конце группы.
`--files`, имена сценариев, `--match` и ненулевой статус при падении сохраняются.
Performance-файл запускается отдельной командой после функциональных сценариев.

## Отчёт по четырём группам

`report.json.test_groups` и `scripts/check-report` разделяют Python (включая HTTP),
tools (все `tests/development` и проверки API-генератора), Node и Playwright.
Каждая группа содержит counts (passed/failed/skipped/total) и duration_seconds.
Группы выполняются параллельно; их времена не складываются в wall-clock всего
прогона. Python включает предварительный HTTP-набор, когда он выбран отдельно.
Сборка, типизация и остальные служебные проверки видны отдельно в suites и входят
в Total. Старые отчёты читаются без переписывания. Node-набор не запускает Python-тесты, Chrome
или reader-сервер; сам runner по-прежнему требует Python 3.11+. `--files` и `--match` доступны для Node и Playwright.
