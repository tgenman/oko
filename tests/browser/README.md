# Проверки разработки

Единая команда (macOS/Linux, Python 3.11+ для runner):

```sh
./scripts/check ui
./scripts/check all
./scripts/check python types
./scripts/check http
./scripts/check browser
./scripts/check lint
./scripts/check browser --files tests/browser/test_material_list.cjs tests/browser/test_reader_http.cjs
./scripts/check python --files tests/development/test_hooks.py
```

[Runner](../../scripts/check) — источник состава режимов. Он обнаруживает актуальные JavaScript-модули и браузерные сценарии, печатает результаты и время, возвращает ненулевой код при падении, отсутствующей зависимости или прерывании. При прерывании завершает принадлежащие ему дочерние процессы. Проверка diff охватывает staged и unstaged изменения; успешная проверка не означает чистое рабочее дерево.

`ui` включает синтаксис, ESLint `no-undef`, HTTP-проверку выдачи всего графа JavaScript настоящим сервером, браузер и diff. `all` добавляет весь Python-набор, типизацию и CLI. Отдельно доступны `syntax`, `lint`, `http`, `browser`, `python`, `types`, `diff`, `entrypoint`, `staged`; можно указать несколько, повторы выполняются один раз. `python`, `types` и `http` не требуют Node/Playwright. `syntax` и `lint` не требуют браузера. После локального исправления повторяйте затронутый набор; полный прогон обязателен в CI; локальный `all` остаётся доступен для общей проверки по риску изменения.

`--files` идёт после выбранных наборов и задаёт существующие файлы внутри checkout. Для Python поддерживается также `файл.py::имя_теста`. Каждый файл должен соответствовать хотя бы одному выбранному набору; несуществующий путь, путь вне checkout и неподходящий тип завершаются ошибкой до запуска. Повторные пути выполняются один раз. Наборы без подходящих указанных файлов сохраняют полный объём; например, `python types --files tests/development/test_hooks.py` ограничивает pytest, но выполняет всю типизацию. `ui --files tests/browser/test_material_list.cjs` проверяет выбранный JS-файл и браузерный сценарий, HTTP и diff остаются полными. Pre-commit и CI запускают свои обязательные команды без `--files`.

## Подготовка синтетических сценариев

До heartbeat явно задавайте включённую обработку, которую проверяет сценарий. `setup_reader(client, theses=...)` требует явного выбора тезисов. Помощники событий, фильтров и обзоров задают свои режимы, включая отключение несвязанных этапов. Производственные defaults проверяются отдельными HTTP-тестами без подмены defaults. Синтетические модели тезисов, фильтров, событий и обзоров отклоняют неподдерживаемую операцию с её именем, вместо ответа по чужой схеме. Смешанный сценарий явно передаёт `theses=True` модели фильтров или обзоров.

## Обязательные проверки

Для нового checkout выполните `./scripts/install-hooks`. Скрипт включает локальный `core.hooksPath=.githooks` и сохраняет чужую настройку hooks, завершаясь с ошибкой при конфликте.

- `pre-commit` вызывает `check staged`: проверяет whitespace, синтаксис Python/JavaScript и `no-undef` именно из индекса, в том числе при частичном staging. Зависимости приложения и браузер для этой проверки не нужны; для staged JavaScript нужны Node и установленные через `npm ci` зависимости линтера.
- `pre-push` отсутствует: push не повторяет полный локальный прогон. В checkout с установленным `core.hooksPath=.githooks` удаление hook действует сразу, повторная установка не нужна.
- GitHub Actions запускает `check all` на pull request и push в `main` с Python 3.11, Node 22 и Chromium. Push в рабочую ветку без PR не запускает CI; обновление открытого PR запускает один полный набор. Установку зависимостей выполняют отдельные шаги CI; runner их не устанавливает. После подключения remote настройте `Full checks` как required check в правилах защищённой ветки, если нужна серверная блокировка merge.

## Подготовка окружения

Проверки маршрута субтитров используют настоящий SDK и локальный HTTP/CONNECT-прокси. Для временного тестового TLS-сертификата нужен `openssl` в PATH. Сертификаты и ключи создаются во временном каталоге; внешние сетевые соединения запрещены тестовым окружением worker. Настоящий YouTube и платный прокси не вызываются.

Один раз установите Python-зависимости по [README](../../README.md), включая extra `dev`. Поддерживаемые версии Node заданы в `engines` корневого package.json. Браузерные зависимости и ESLint закреплены в package.json и lock-файле:

```sh
npm ci
```

Используйте установленный Chrome/Chromium либо отдельно установите браузер Playwright:

```sh
npx playwright install chromium
```

Эти команды выполняет разработчик при настройке. Сам runner ничего не устанавливает и не скачивает.

| Переменная | Назначение | По умолчанию |
| --- | --- | --- |
| `OKO_NODE` | Исполняемый файл Node | `node` из PATH |
| `OKO_PYTHON` | Python с зависимостями проекта, для полного режима | `.venv/bin/python` checkout, иначе `python3` из PATH |
| `NODE_PATH` | Каталог внешних Node-пакетов, если нет локального node_modules | Стандартный поиск Node |
| `OKO_BROWSER_EXECUTABLE` | Исполняемый файл Chrome/Chromium | Установленный браузер Playwright, затем стандартные пути Chrome/Chromium macOS/Linux |

Для worktree без своего virtualenv задайте `OKO_PYTHON` путём к существующему окружению. В Codex runtime и пакеты можно найти через `load_workspace_dependencies`; персональные пути в репозиторий не копируются. Для sandbox нужны разрешения на loopback, запуск браузера и чтение дерева процессов через POSIX `ps` (для завершения потомков, в том числе отдельных групп браузера).

## Граница браузерных тестов

Сценарии открывают HTML/JavaScript production-приложения в headless Chrome, проверяют DOM, воспроизведение и освобождение URL медиа. `reader()` использует тот же HTTP-сервер и очистку, что и `productionReader()`: свои временные SQLite/файлы и синтетические внешние adapters для каждого сценария. Файлы UI и журнал диагностики обслуживает настоящий сервер.

В UI-сценариях `readerTransport.replies` задаёт статические снимки ответов: точный `METHOD /path?query`, URL либо общий pathname. Ответ с `next: [[route, reply]]` явно задаёт следующий снимок после конкретного запроса. Helper не вычисляет навигацию из подписок, membership карточек, удаление просмотренного или группы ошибок. Сценарий задаёт ожидаемые ответы для выбранных областей сам; стартовый снимок содержит одну папку `f` и один фид `feed` и не выводит их из материалов. Нет подмены ответа — запрос получает настоящий сервер. Задержанный транспорт намеренно игнорирует AbortSignal: поздний ответ должен быть безопасен независимо от отмены.

Это UI-проверки со снимками ответов, а не сквозная проверка всех правил сервера. Правила membership, группировки и viewed проверяет `test_reader_http.cjs` без подмены browser fetch; журнал проверяется через настоящий `/api/debug`, включая повтор доставки и очистку.

Runner запускает не более двух тестовых файлов одновременно. В каждом файловом процессе Chromium переиспользуется до завершения файла; каждый сценарий получает новый изолированный browser context (cookies, storage, страницы) и временный loopback HTTP-сервер.

Python-процесс также переиспользуется в пределах файла: повторные сценарии не импортируют зависимости заново. Каждый HTTP-сценарий получает новое приложение, Runtime, adapters, каталог SQLite/файлов, порт и токен; uvicorn работает в отдельном потоке со своим asyncio loop, чтобы обработчик фоновых ошибок не попадал в чужой журнал. Ответ о готовности отправляется после startup/lifespan uvicorn. Закрытие сценария закрывает context, завершает lifespan сервера и удаляет каталог; отмена не останавливает соседний сценарий. EOF или SIGTERM управляющего процесса закрывает оставшиеся серверы, ошибка запуска завершает host с ошибкой. Chromium и Python-процесс закрываются в завершающих hooks файла.

Личные источники и AI не вызываются. Canvas WebM проверяет воспроизведение без внешнего файла. Настоящие RSS, Telegram, YouTube и подключения моделей этими тестами не проверяются.

`test_reader_http.cjs` использует ту же изолированную сборку production-приложения через uvicorn и временное хранилище. Браузер получает настоящие `/api/cards`, `/api/navigation`, локальные картинки и ответы действий. Подменены только внешние RSS и обработчик модели на сервере; browser fetch не заменяется. Сценарий проверяет папку, оба участвующих фида и пустой фид, объединение события с сохранением всех источников, счётчики и удаление просмотренного. Runner передаёт выбранный Python через `OKO_PYTHON`; при прямом запуске файла используется `OKO_PYTHON`, существующий `.venv/bin/python` или `python3`. Сервер, браузер и временное хранилище очищаются при завершении и отмене.

Отдельный файл можно запустить через `node --test tests/browser/test_opened_material.cjs` с тем же окружением. Для прямого запуска без runner явно задайте `OKO_BROWSER_EXECUTABLE`, если Chrome находится не в стандартном macOS-пути.
